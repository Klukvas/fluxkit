## Goal
A shopper whose cart holds physical goods chooses a delivery method at checkout (for example "Nova Poshta branch or parcel locker", "courier", "pickup at the shop"), picks a Nova Poshta branch from a searchable list served by our API, sees the shipping cost the server computed, and places an order whose total includes that cost, recalculated on the server and never taken from the client. The order stores an immutable snapshot of the chosen method, price and destination. An admin configures methods and rates, creates a carrier waybill for a paid order from the order page, sees its tracking status, and cancels it while the carrier still allows it. Carriers are plugins behind a core port; Nova Poshta is the first one; EU and US carriers follow as further plugins without core changes.

## Scope (proposed v1; the owner fixes it with questions 1 to 4)
**In v1:**
- Core shipping methods with admin-managed rates: flat price, free over a subtotal threshold, price tiers by cart subtotal; a country allow-list per method; method kinds `address` (courier or post to an address), `pickup_point` (a carrier branch or parcel locker), `store_pickup` (self-collection, question 4).
- The shipping adjustment in the order total (the first writer of `order_adjustment`), the order shipping snapshot, a quote/options endpoint for the storefront.
- A `ShippingProviderPort` in core and a provider registry in the API; a fake provider package for tests and e2e.
- The Nova Poshta plugin (`packages/providers/nova-poshta`): city and branch/parcel-locker lookup (through our API, cached), an informational price estimate (question 2), waybill (TTN, "express invoice") creation and cancellation from the admin, tracking by polling (question 10), the printable label proxied through our API.
- Shipment records with a status journal and events; admin shipment panel; admin shipping settings screens.

**Later (each its own plan or a later step, not v1):** cash on delivery and Nova Poshta "payment control" (needs the payment plan's status split, question 3); charging a live carrier quote (question 2); weight- or volume-based rates and catalog weight/dimensions (question 5); several shipments or parcels per order (question 9); returns and return waybills (question 11); insurance beyond the declared value; international shipping and customs data; EU and US carrier plugins; address book and saved branches for customers; courier pickup scheduling (NP "call a courier"); maps or geolocation in the picker; webhooks (NP offers none as far as we know, see section 8); multi-location stock allocation (ADR 0015 consequence); discounts that change the free-shipping threshold (the pricing pipeline plan).

**Non-goals:** any change to the order status machine in v1 (question 3 keeps `fulfilled` an admin or system action from `paid`); any provider key, provider URL or provider call in the browser; storing provider secrets in the database in clear text.

## Existing functionality found (verified 2026-10-24 on `origin/main` at `f6ffc43`)

### Cart and checkout
- **`requiresShipping`** (cart shape, `docs/api/cart.md`): core `shippingAddressRequired` (`packages/core/src/orders/contact.ts`) over the AVAILABLE lines, using `product_type.requires_shipping` (`apps/api/src/database/schema/catalog.ts` line 177, `boolean NOT NULL DEFAULT true`), read live on every request. The checkout enforces the same rule: `400 shipping_address_required` (`apps/api/src/orders/checkout.service.ts` line 212).
- **Cart `total`** equals `subtotal` today ("until shipping, discount and tax adjustments exist", `docs/api/cart.md`). Nothing about shipping is stored on `cart` or `cart_item` (`apps/api/src/database/schema/carts.ts`).
- **Checkout** (`checkout.service.ts`, ADR 0015, 0024): one transaction with the lock order customer -> cart `FOR UPDATE` -> guest-email advisory lock -> products `FOR SHARE` -> variants `FOR SHARE` -> inventory levels `FOR UPDATE` -> inserts. Totals: `computeOrderTotals(lines, [])` (line 203): the adjustment list is ALWAYS empty today. `expectedTotal` is compared with `compareMoney` and a mismatch is `409 cart_changed` with the fresh cart; nothing is reserved. Deadlocks are retried once.
- **The storefront sends `expectedTotal = cart.total`** (`apps/storefront/src/lib/checkout-store.ts` line 165). Once shipping is added to the order total, that value is wrong for every shipped order: the storefront must take the expected total from the server's shipping options (section 5).
- **Idempotency** (`checkout-fingerprint.ts`): SHA-256 of canonical JSON `{v: 1, cartId, email, phone, firstName, lastName, shippingAddress, billingAddress, locale, expectedTotal}`. `FINGERPRINT_VERSION = 1` is documented as "bump when the fields change".
- **Address shape** (core `validateAddress`): `{countryCode (pattern only), region?, city, postalCode?, line1, line2?, recipientFirstName?, recipientLastName?, recipientPhone?}`; strict (unknown fields refused); comment: "until the shipping plan adds provider details it also carries things like a carrier branch". No country list, no carrier rule in core.
- **Storefront checkout** (`apps/storefront/src/config/checkout.ts`): `allowedShippingCountries: ["UA"]`, `defaultCountry: "UA"`, configurable address fields; the address block shows only when `requiresShipping`; the `recipient*` fields are never sent. The storefront CSP has `connect-src 'self'` (`apps/storefront/next.config.ts` line 99): the browser cannot call a carrier API directly, which matches this plan.

### Orders and totals
- **Totals** (core `computeOrderTotals`, `packages/core/src/orders/totals.ts`): `total = subtotal + adjustments not included in the price`; kind `shipping` must be `>= 0`; `shippingTotal` sums every shipping adjustment; currency mismatch, `adjustments_out_of_range`, `total_out_of_range`, `negative_total` are typed refusals. Already tested in core; nothing calls it with an adjustment yet.
- **`sales_order`** has `shipping_total` (`CHECK 0..MAX_AMOUNT`), `shipping_address` JSONB, `total_amount`; **`order_adjustment`** (`kind`, `code`, `label` JSONB, signed `amount`, `included_in_price`, `source`; append-only trigger, ADR 0019) exists and is read by both order views, but NO code inserts into it (searched `apps/api/src`).
- **`order_item.requires_shipping`** is in the immutable snapshot.
- **Status machine** (core `ORDER_TRANSITIONS`): `paid -> fulfilled` by `admin` or `system`, stock effect `commit` (backordered lines: `awaiting_stock` until on hand). `fulfilled` is terminal. `POST /admin/orders/{id}/mark-fulfilled` takes no body. There is no fulfilment entity; ADR 0017 keeps one explicit status "until the payment plan" and notes that cash on delivery needs `fulfilled` before `paid`, which a single status cannot express.
- **Unpaid orders expire** after `ORDER_PAYMENT_TTL_MINUTES` (default 30) and release their stock. Without an online payment provider, a shop must mark orders paid by hand within that window. Relevant for cash on delivery (question 3).
- **Ports** (`packages/core/src/orders/events.ts`, `read-port.ts`): `OrderPaymentsPort.markPaid` (token `fluxkit:order-payments-port`, implemented by `OrdersService`), `OrderReadPort.getOrder` (the admin view, with addresses and contact). `OrdersService.markFulfilled(orderId, actor)` exists but is NOT exposed through a port. `MediaStoragePort` (ADR 0028) is the other direction of the pattern: a port in core that a driver implements and the API calls.
- **Events** (`docs/contracts/events.md`): `order.placed|paid|cancelled|expired|fulfilled`, payload ids and number only, at-least-once, handlers discovered by metadata `fluxkit:domain-event-handler`, 30 s handler timeout, no transaction open during a handler (ADR 0025). Type pattern `^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*)+$` (a CHECK of `domain_event.type`), so new names need no migration.
- **Jobs** (`docs/api/jobs.md`): seven bounded jobs under one advisory lock, 30 s budget per job, per-transaction statement and lock timeouts (ADR 0025).

### Admin, auth, limits, config, catalog
- **Admin order detail** (`apps/admin/src/areas/orders/order-detail-view.tsx`): shows the shipping address section and the mark-paid, mark-fulfilled and cancel actions per status; no shipment UI.
- **Permissions** (core `PERMISSIONS`, fixed in code, ADR 0009): `catalog.*`, `users.manage`, `orders.read|write`, `customers.read|write`. No shipping permission. Admin routes are default-deny (`AdminPathGuard`).
- **Rate limits** (`apps/api/src/rate-limit/rate-limiter.ts`): named in-memory windows (`checkout` 10 per 10 min per address, `cartWrite`, `orderLookup`, ... `mediaUpload` per admin user); single process.
- **Config** (`packages/config/src/env.ts`): `loadEnv` parses every API variable; `ORDER_TOKEN_SECRET` is the precedent for a secret (no default, length check, never logged, refused in production when missing). `SHOP_CURRENCY` is the one selling currency; `PRICES_INCLUDE_TAX` is a flag only ("no tax is calculated").
- **Plugins**: `packages/providers/` holds a README only; `pnpm-workspace.yaml` already includes `packages/providers/*`. The feature loader (`apps/api/src/features/feature-loader.ts`) discovers ONLY `packages/features` manifests (`"fluxkit": {"feature": ...}`, `FEATURES_ENABLED`); there is no provider loader. `.dependency-cruiser.cjs` forbids core importing features and infrastructure and packages importing apps; it has NO rule that forbids core importing `packages/providers` (gap: add one in step 2).
- **Catalog weight**: no weight or dimension column exists on `product` or `variant`. The seeds have a descriptive attribute `weight` (`inputType: number`, `unit: "g"`, assigned to the `hand_tool` preset at product level, `seeds/src/dictionaries.ts`, `presets.ts`); `attribute.unit` is free text, so it is not a reliable machine unit. `variant.attributes` JSONB exists for variant-level attributes.
- **Money helpers** in core: `createMoney`, `addMoney`, `compareMoney`, `parseDecimalString`, `toDecimalString`; integer minor units, `MAX_AMOUNT` 10^12.
- **`docs/contracts/README.md`**: price adjusters (the pricing pipeline hook) are "not written yet". ADR 0004 "Still open": pipeline steps, adjuster contract, rounding per currency.

### What is missing
Shipping methods and rates, a carrier abstraction, any provider package or loader, a shipping selection in checkout, any adjustment writer, an order shipping snapshot, shipment and tracking entities, carrier lookups, a fulfilment port, shipment events, admin screens for all of it, and a provider test harness.

## Proposal

### 1. Architecture and boundaries
| Piece | Where | Why there |
|---|---|---|
| Rate rules (`decideShippingPrice`: flat, free over threshold, subtotal tiers; country allow-list; method availability for a cart), shipping selection validation, the shipping adjustment builder, normalized shipment statuses and allowed transitions, method code and limit constants | `packages/core/src/shipping/` (pure, no I/O, TDD) | Money logic belongs to core (ADR 0004 "rounding rules in one module with TDD"); reused by checkout, the options endpoint and the admin preview |
| `ShippingProviderPort` (types and constants only), provider metadata key `fluxkit:shipping-provider`, typed provider errors | `packages/core/src/shipping/provider-port.ts` | Same pattern as `MediaStoragePort` and the event handler contract: a plugin implements a core interface without importing `apps/api` |
| `OrderFulfilmentPort` (token `fluxkit:order-fulfilment-port`), implemented by `OrdersService` | `packages/core/src/orders/` + `apps/api/src/orders/` | ADR 0018 promised it; needed only if question 10 answer lets the system fulfil |
| Shipping module: methods and settings repositories, options service, checkout integration, provider registry, lookup proxy with cache, shipment service, tracking job | `apps/api/src/shipping/` (core module, no flag; question 12) | I/O, network and database live in the API |
| Carrier plugins | `packages/providers/<code>` (first `nova-poshta`); a test-only fake in `packages/providers/_fake` or `apps/api/src/test/` (decided in step 6) | AGENTS.md section 5 |
| Provider configuration and secrets | each plugin parses its own variables with a small parser exported for `loadEnv`-style validation; the variable names are listed in `docs/contracts/config.md` | question 6 |
| Store and admin client methods | `packages/api-client` | one transport (ADR 0026, 0027) |
| Delivery step, settings screens, shipment panel | `apps/storefront`, `apps/admin` | existing areas |

**Provider registration (question 13).** Recommended: a provider loader mirroring the feature loader: a package declares `"fluxkit": {"provider": "nova-poshta", "kind": "shipping"}`, exports `providerModule` (a Nest module); the API imports only the providers named in `SHIPPING_PROVIDERS_ENABLED` (comma-separated; unset = none); an enabled but missing or broken provider fails startup; a disabled or deleted one has no effect. Inside the module, a provider class carries the metadata `fluxkit:shipping-provider` and implements `ShippingProviderPort`; the API finds it with the `DiscoveryService` technique of ADR 0021 (a marked provider without the methods, or with a duplicate code, stops startup). CI gets a provider matrix like the feature matrix (on, off, deleted). Core and `apps/api` never import a provider statically.

**`ShippingProviderPort` (proposed, internal until the first external plugin; then listed in `docs/contracts/`):**
```ts
interface ShippingProviderPort {
  readonly code: string;                       // "nova_poshta"; matches CODE_PATTERN
  readonly capabilities: ShippingCapabilities; // {pickupPoints, estimate, waybills, cancelWaybill, tracking, labels}
  searchCities(input: {query: string; locale: string; limit: number}, signal: AbortSignal): Promise<CityResult[]>;
  listPickupPoints(input: {cityRef: string; kinds: PickupPointKind[]}, signal: AbortSignal): Promise<PickupPoint[]>;
  estimate(input: EstimateRequest, signal: AbortSignal): Promise<ProviderResult<Money>>;
  createWaybill(input: WaybillRequest, signal: AbortSignal): Promise<ProviderResult<WaybillCreated>>;
  cancelWaybill(input: {providerRef: string}, signal: AbortSignal): Promise<ProviderResult<void>>;
  track(input: {trackingNumbers: string[]; phones: string[]}, signal: AbortSignal): Promise<ProviderResult<TrackingUpdate[]>>;
  fetchLabel(input: {providerRef: string; format: "pdf"}, signal: AbortSignal): Promise<ProviderResult<{bytes: Uint8Array; contentType: "application/pdf"}>>;
  checkConnection(signal: AbortSignal): Promise<ProviderResult<void>>;
}
// ProviderResult = {ok: true, value} | {ok: false, reason: "unavailable" | "rejected" | "invalid_credentials" | "not_supported", providerCodes: string[]}
```
Money crosses the port in minor units with a currency (the plugin converts carrier decimals with core `parseDecimalString`; a value with more decimals than the currency allows is `rejected`, never rounded). Errors carry provider CODES, never the carrier's message text (it can echo names, phones or the key). The API, not the plugin, decides timeouts (it passes the `AbortSignal`), logging and caching.

**Events (proposed names; question 14 lists the alternative):** `shipment.created`, `shipment.status_changed`, `shipment.cancelled`, aggregate = the shipment id, payload `{shipmentId, orderId, orderNumber, status}` (ids and normalized status only, never a tracking number, phone or name). Written in the same transaction as the change (ADR 0018). An email plugin later sends "your parcel is on the way".

**How fulfilment ties to shipments.** v1 keeps the single order status (ADR 0017). A shipment can be created only for a `paid` order with no line awaiting stock (the same check `mark-fulfilled` makes, read without committing anything). Creating a waybill does not change the order status. Question 10 decides whether the tracking job may move `paid -> fulfilled` (actor `system`, through `OrderFulfilmentPort`) when the carrier first reports the parcel accepted. Cancelling a shipment never touches the order or the stock. The fulfilment entity of ADR 0004 decision 4 (status derived from payment and fulfilment) stays for the payment plan, which must also decide cash on delivery.

### 2. Data model (red zone: one migration `0006_shipping` with a hand-written `0006_shipping.down.sql` that also deletes its `drizzle.__drizzle_migrations` row; up, down, up, down tested)
Names and columns are proposals for ADR 0029; ADR 0004 rules apply: money in integer minor units with a currency, snapshots on the order, explicit state machines, no niche fields.

**`shipping_method`** (admin-managed)
| Column | Rule |
|---|---|
| `id` uuid PK; `code` text UNIQUE | `CODE_PATTERN`; never renamed (like product type codes, ADR 0006 section 10) |
| `title`, `description` | i18n JSONB maps (default locale required on write, like catalog texts) |
| `kind` | `address`, `pickup_point`, `store_pickup` (CHECK) |
| `provider_code` | NULL for a method without a carrier plugin (manual courier, store pickup); else a provider code |
| `provider_service` | NULL or a provider-specific service code (`warehouse`, `postomat`, `doors` for Nova Poshta), validated by the plugin |
| `pricing` | JSONB validated by core: `{type: "flat", amount}`, `{type: "free_over", amount, freeFrom}`, `{type: "tiers", tiers: [{fromSubtotal, amount}]}`, or `{type: "carrier_on_delivery"}` (question 2: shop charges 0, recipient pays the carrier) |
| `currency` | the currency of every amount in `pricing`; a method whose currency is not `SHOP_CURRENCY` is not offered (as product prices) |
| `country_codes` | text[] of ISO alpha-2, non-empty (CHECK pattern per element) |
| `is_active`, `position`, `created_at`, `updated_at` | |

Zones as a separate table are not proposed for v1 (question 15): the country list per method covers "Ukraine only" and "EU countries" without another join.

**`shipping_provider_setting`** (non-secret provider settings edited in the admin, one row per provider code): `provider_code` PK, `settings` JSONB validated by the plugin (Nova Poshta: sender counterparty ref, contact person ref, sender phone, sender city ref, sender branch ref, default parcel weight and size, default cargo description), `updated_at`, `updated_by` (admin, SET NULL). Secrets never go here (question 6).

**`order_shipping`** (the immutable shipping snapshot, 1:1 with the order; trigger in the ADR 0019 style: no UPDATE, DELETE only by the cascade from `sales_order`)
| Column | Rule |
|---|---|
| `order_id` PK -> `sales_order` CASCADE | |
| `method_id` | link, `ON DELETE SET NULL` (the snapshot stays; same exception technique as `order_item.variant_id`) |
| `method_code`, `kind`, `provider_code`, `provider_service` | copied |
| `title` | i18n map copied whole (every locale, ADR 0025 snapshot rule) |
| `amount`, `currency` | what the shop charged (equals the shipping adjustment) |
| `payer` | `shop_charge` or `recipient_on_delivery` (question 2) |
| `estimated_carrier_amount` | NULL or the informational carrier estimate shown at checkout (minor units, same currency) |
| `destination` | JSONB: for `pickup_point` `{providerRef, number, kind, cityRef, cityName, description}` (public carrier data, no personal data); for `address` NULL (the address stays in `sales_order.shipping_address`); for `store_pickup` NULL |

`sales_order.shipping_address` stays the recipient's address of record. For a `pickup_point` order the API also writes a readable address there (`countryCode`, `city` = city name, `line1` = the branch description), so every existing view, the admin page and `OrderReadPort` keep showing where it goes without change.

**`order_adjustment`** gets its first rows: one `{kind: "shipping", code: <method code>, label: <title map>, amount, includedInPrice: false, source: <provider code or null>}` per order with a shipping selection. A free or `carrier_on_delivery` method writes the row with amount 0, so the adjustment list always names the chosen method (`computeOrderTotals` allows 0; listed under Assumptions).

**`shipment`**
| Column | Rule |
|---|---|
| `id` uuid PK; `order_id` -> `sales_order` RESTRICT | a shipped order is never deleted under its shipment |
| `provider_code`, `provider_service` | |
| `status` | normalized: `pending` (row written, carrier not answered yet), `unknown` (carrier call timed out: result not known), `created`, `in_transit`, `arrived` (at the branch or locker), `delivered`, `returning`, `returned`, `cancelled`, `failed` (carrier refused the creation); allowed transitions are data in core |
| `carrier_status_code`, `carrier_status_at` | the raw carrier code (text, short pattern) and its time; never the carrier's text |
| `tracking_number` | the waybill number (Nova Poshta: 14 digits starting with 20 or 59, to be verified); unique per provider |
| `provider_ref` | the carrier's internal id (Nova Poshta `Ref`, a uuid) |
| `client_reference` | our order number sent to the carrier (to find a waybill after a lost answer, section 8) |
| `declared_value_amount`, `currency`; `carrier_cost_amount` | minor units; the carrier's own price for this waybill, informational |
| `payer` | `sender` or `recipient` |
| `weight_grams`, `length_mm`, `width_mm`, `height_mm`, `seats` | entered at creation (question 5); `seats = 1` in v1 |
| `created_by`, `created_at`, `cancelled_at`, `delivered_at`, `next_track_at`, `tracking_attempts` | `next_track_at` drives the polling job (index on `next_track_at` where the status is not terminal) |

Partial unique index: at most one shipment per order whose status is not `cancelled` or `failed` (question 9). **`shipment_status_change`**: append-only journal (from, to, carrier code, actor `admin|system`, admin id SET NULL, `clock_timestamp()`), trigger as `order_status_change`.

**Weight and dimensions (question 5).** Recommended for v1: NOT in the catalog. The admin enters the parcel weight and size when creating the waybill (prefilled from the provider settings' defaults). Reason: v1 rates do not depend on weight, and the catalog rule (AGENTS.md 2.3) forbids ad-hoc product fields. When weight-based rates come, nullable integer variant columns (`shipping_weight_grams`, dimensions in mm) are the proposed home: logistics data every shipped variant has, used by money logic, needing exact units and indexes; descriptive attributes such as the seed's `weight` stay attributes for the storefront. That is a catalog schema change with its own approval.

**Not stored:** API keys; carrier response bodies; recipient names or phones in shipment rows (they live on the order); lookup results (cache only, section 4).

### 3. Checkout and totals (red zone: order-total calculation, checkout contract)
**Request.** `POST /store/checkout` gains an optional member `shipping: {methodCode, pickupPointRef?}` (strict). Rules:
- Cart `requiresShipping = false`: `shipping` must be absent (or is refused as `400 shipping_not_applicable`; proposal: refuse, so a stale client is told). No adjustment, no snapshot (today's behaviour).
- Cart `requiresShipping = true` and at least one active method exists for the shop: `shipping` is required (`400 shipping_method_required`); a shop with NO active method keeps today's behaviour (address only, shipping 0). This keeps a fresh installation working; it is still a tightened validation once a method exists (breaking by `docs/contracts/api.md`, pre-1.0, recorded in `CHANGELOG.md`, like "publish needs a price").
- `methodCode` must name an active method whose country list contains `shippingAddress.countryCode` (for `address`) or the carrier country (for `pickup_point`, the carrier's country, `UA` for Nova Poshta) and whose currency is `SHOP_CURRENCY`: else `409 shipping_changed` (below).
- `pickup_point`: `pickupPointRef` required; the server resolves it through the provider registry and its cache (section 4). The checkout transaction never calls the network: the point must already be in the cache filled by the shopper's lookups (or is fetched BEFORE the transaction opens, outside every lock, with a 5 s timeout). Unknown point: `400 validation_failed` `shipping.pickupPointRef` `unknown_pickup_point`; provider unreachable and not cached: `503 shipping_provider_unavailable` with `Retry-After` (question 7).
- `store_pickup`: no address needed (proposal: `shippingAddress` optional for it; the contact is the recipient).

**Price.** Inside the transaction, after the cart is priced: core `decideShippingPrice(method.pricing, {subtotal, currency})` -> `Money` (exact integers, no rounding: amounts are entered in minor units; `free_over` compares the cart subtotal with `freeFrom` by `compareMoney`; tiers pick the highest `fromSubtotal <= subtotal`). The adjustment goes into `computeOrderTotals(lines, [shippingAdjustment])`; its refusals (`adjustments_out_of_range`, `total_out_of_range`) answer `409 rule_violation` with that rule. Free-shipping threshold basis = the subtotal of all available lines (digital lines included) in v1; question 16 decides; discounts do not exist yet, so the pricing pipeline plan must revisit it.

**Consent.** `expectedTotal` must equal subtotal + shipping. Order of answers: `cart_changed` (the cart's own lines changed, as today) first, then `shipping_changed` (new, additive `409` code with a member `shipping`: the method's fresh option as the options endpoint returns it, or `available: false`), when only the shipping price or the method's availability changed. Nothing is reserved in either case. The storefront shows the new price and asks again.

**Snapshot and write.** In the same transaction: insert the order, the `order_shipping` row, the shipping `order_adjustment` row, the lines, reservations, journal and `order.placed` as today. `sales_order.shipping_total` = core `shippingTotal`.

**Idempotency.** The normalized `shipping` member joins the fingerprint and `FINGERPRINT_VERSION` becomes 2. Consequence: a replay sent across the deploy for an order placed under version 1 answers `idempotency_key_reused` (a lost answer in the deploy minute; recorded). A replay never recomputes the price and never calls a provider (the replay check stays the first thing the transaction does; a pre-transaction pickup-point fetch is skipped when the key already exists, read without a lock first).

**Guest token, open-order limit, expiry, lock order**: unchanged (ADR 0023, 0024, 0015). The shipping tables are written after the existing inserts, so no lock is added before the inventory locks.

**Tax (question 17).** No tax is computed. A shipping amount means what a product price means under `PRICES_INCLUDE_TAX` (tax included or not); `includedInPrice` of the shipping adjustment is `false` (it is added to the total). The tax plan later gives methods a tax class.

**Payment interplay.** The total `markPaid` checks now includes shipping; nothing else changes. Cash on delivery is question 3.

**Options endpoint (new, store).** `GET /store/shipping/options?country=UA&locale=uk` for the caller's cart (cookie or session, like the cart routes): `{options: [{methodCode, kind, title, description, providerCode, price: Money | null, payer, estimate: Money | null, total: Money, available, reason?}]}`; `total` = cart subtotal + price, computed by the server (the storefront sends it back as `expectedTotal`, so the browser never adds money). `estimate` is the informational carrier price (question 2), filled only for a pickup point or city the request names (`cityRef`, `pickupPointRef`), from the cache or a provider call with a 5 s timeout; on any provider failure it is `null`, never an error of the whole answer. `no-store`, rate limited (`shippingOptions` per address), no cart is created. Empty cart: `options: []`.

**What is cached:** carrier directories (section 4) and estimates for 10 minutes per (method, city, point, subtotal band); never a price used in a total.

### 4. Lookups through our API (storefront picker)
- `GET /store/shipping/providers/{code}/cities?q=&locale=` (q: 2 to 50 characters) and `GET /store/shipping/providers/{code}/pickup-points?cityRef=&q=&kinds=branch,locker`: public, `GET` (no CSRF), rate limited (`shippingLookup`, proposal 60 per minute per address), `Cache-Control: public, max-age=300` (not personal data), responses capped (50 cities, 200 points per page, `limit`/`offset`).
- **Cache (question 8, part of provider-down behaviour):** recommended: an in-process cache per API instance: city searches by normalized query (TTL 24 h), the full point list of a city fetched once and filtered locally (TTL 12 h), bounded by entry count (LRU, numbers fixed in step 6 after measuring list sizes). On a provider failure an expired entry is served for up to 72 h (stale-if-error), marked `stale: true`. No Redis requirement (`REDIS_URL` stays optional). A per-provider concurrency cap (proposal 4 calls in flight per process) and one in-flight fetch per cache key (request coalescing) stop a burst from hitting the carrier with our key.
- **Abuse:** the proxy turns anonymous requests into calls under the shop's carrier key; the limits above, minimum query length, coalescing and the cache bound it. The carrier may throttle the key shop-wide (Nova Poshta limits not verified): the stale cache keeps the picker working.

### 5. Storefront (delivery step)
- The checkout page gets a "Delivery" section before the address: a radio group of methods from `GET /store/shipping/options` (title, price or "free" or "paid to the carrier on delivery, about X", from i18n messages; nothing hardcoded), then per kind: `address` shows today's address fields; `pickup_point` shows a city combobox and a branch/locker combobox (WAI-ARIA combobox pattern with a listbox, debounced 300 ms, minimum 2 characters, keyboard operable, results announced in a polite live region, each option with number and address text); `store_pickup` shows the configured pickup text.
- The order summary shows subtotal, shipping and total from the options answer for the selected method; `expectedTotal` = that `total`. A `409 shipping_changed` re-reads the options, shows the new price and asks for consent; `409 cart_changed` keeps today's handling.
- States: loading, no method available for the country ("we do not deliver to ...", with the methods endpoint telling), provider lookup failed (retry, and a hint to choose another method), stale lookup data (a note), no results, digital-only cart (no delivery section, as today).
- No provider key, URL or call in the browser (CSP `connect-src 'self'` already enforces it). The storefront's hardcoded `allowedShippingCountries` is replaced by the countries of the active methods (served by the options endpoint), keeping the config file for field layout only.
- Order pages (guest and account) show the method title, price, pickup point and, when a shipment exists, the tracking number and normalized status (additive fields of the store order shape).
- i18n: uk and en messages for every new string; carrier texts (branch names) are shown as the carrier sends them (Nova Poshta returns Ukrainian and Russian descriptions as far as we know, no English: the en storefront shows the Ukrainian text; verify).

### 6. Admin
- **Settings (new area "Shipping")**: methods list and editor (code, i18n title and description, kind, provider and service, pricing type with amounts typed as decimals and converted to minor units with the existing core-copied parser, countries, active, order), provider panel per enabled provider (configured or not: "API key present" from the server, never the key; the sender profile form; "Test connection" calls `checkConnection` and shows ok or a translated reason).
- **Order detail, shipment panel** (`orders.read` to see, `orders.write` to act): create waybill (form: weight, size, declared value (default the order subtotal), payer (default from the method), description; refused while the order is not `paid` or a line awaits stock), the result (tracking number, carrier cost, status), "Print label" (opens `GET /admin/orders/{id}/shipments/{shipmentId}/label`, a PDF streamed by our API), "Refresh tracking", "Cancel waybill" (confirmed), the shipment journal. A lost answer of "create" shows "result unknown" and offers "Check with the carrier" (section 8) instead of a blind retry (ADR 0027: writes are never retried).
- **Permissions (question 18):** recommended a new `shipping.manage` (owner and manager) for the settings routes; shipments reuse `orders.read` / `orders.write`. A new permission is an auth and public contract change (red zone).
- **Audit:** the shipment journal records the acting admin; settings changes record `updated_by` only (no audit log exists, HANDOFF "Auth follow-ups").

### 8. Nova Poshta plugin (`packages/providers/nova-poshta`)
**What I know from memory, NOT verified (no network access in this session; every item must be checked against the official API documentation and a real business account before step 7 starts):**
- One endpoint `https://api.novaposhta.ua/v2.0/json/` (an `/xml/` variant exists), `POST` with JSON `{apiKey, modelName, calledMethod, methodProperties}` (JSON-RPC style). The answer is HTTP 200 even for errors, with `{success, data[], errors[], warnings[], info, messageCodes, errorCodes, warningCodes, infoCodes}`; errors come as text (Ukrainian/Russian) plus codes. The API key travels in the BODY, so any request-body logging leaks it.
- Directories: `Address.searchSettlements` and `Address.getCities` (city search, `FindByString`, paging `Page`/`Limit`), `Address.getWarehouses` / `AddressGeneral.getWarehouses` (by `CityRef`, `FindByString`, `TypeOfWarehouseRef`, paging; fields such as `Ref`, `Number`, `Description`, `DescriptionRu`, `ShortAddress`, `CategoryOfWarehouse` (`Branch`, `Postomat`), `PlaceMaxWeightAllowed`, `TotalMaxWeightAllowed`, dimension limits, `WarehouseStatus`), `Address.getWarehouseTypes`.
- Price: `InternetDocument.getDocumentPrice` (`CitySender`, `CityRecipient`, `Weight` in kg, `ServiceType` `WarehouseWarehouse`/`WarehouseDoors`/`DoorsWarehouse`/`DoorsDoors` (and a postomat service type), `Cost` declared value, `CargoType` `Parcel`/`Cargo`/`Documents`, `SeatsAmount`, optional redelivery fields) returning `Cost` and `AssessedCost` in hryvnias as numbers or decimal strings. `InternetDocument.getDocumentDeliveryDate` gives an estimated date.
- Waybill: `InternetDocument.save` (sender counterparty, contact and address refs, sender phone, recipient data (either refs created by `Counterparty.save`/`ContactPerson.save` or the newer inline recipient fields: to verify), `PayerType` `Sender`/`Recipient`, `PaymentMethod` `Cash`/`NonCash`, weight, `OptionsSeat` for dimensions, `Description`, `Cost`, optionally `InfoRegClientBarcodes` (our reference) and `BackwardDeliveryData` or `AfterpaymentOnGoodsCost` for cash on delivery / payment control). Answers `Ref`, `IntDocNumber` (the TTN), `CostOnSite`, `EstimatedDeliveryDate`. `InternetDocument.delete` (`DocumentRefs`) cancels while the parcel is not handed over. `InternetDocument.getDocumentList` lists the sender's documents for a date range (usable to find a waybill after a lost answer by our reference).
- Tracking: `TrackingDocument.getStatusDocuments` with `Documents: [{DocumentNumber, Phone}]`, up to 100 numbers per call (to verify); without the recipient's or sender's phone the answer is reduced. Status codes are numbers (for example 1 created, 2 deleted, 3 not found, 4 to 8 in transit, 7/8 arrived at branch or locker, 9 received, 10/11 received with payment, 102/103/108 refused or returning; the full table must be copied from the docs and frozen in a fixture).
- Labels: printable markings are URLs on `my.novaposhta.ua` that, as far as I remember, embed the API key in the path; such a URL must never reach a browser: our API fetches the PDF and streams it (or the feature is cut).
- Limits: a request rate limit exists but its numbers are not public to my knowledge; there is NO sandbox: tests against the real API use a real key and create real documents (delete them right after). Keys are created in the business cabinet and can have an expiry date set there. Nova Poshta does not offer webhooks for tracking in the public API as far as I know: tracking is polling. Recipient names may have to be Cyrillic for domestic waybills (to verify). Postomat waybills have weight and size limits and maybe a declared-value cap (to verify).
- No idempotency key exists for `save` as far as I know: hence the `pending`/`unknown` statuses and `reconcile` (find the waybill by `InfoRegClientBarcodes` = our order number through `getDocumentList`).

**Implementation rules:** `fetch` from Node 22 (no HTTP library; no new dependency), the base URL a constant in the package (never configurable from the admin or a request: no SSRF), `redirect: "error"`, `AbortSignal` from the API (5 s lookups and estimates, 15 s waybill calls), a response size cap before JSON parsing, every answer validated by a schema in the plugin (zod 4.6.7, the version core and config already pin: a new dependency edge of a new package, same version, owner confirms), money converted with core `parseDecimalString` in UAH only, no request or response body logged (codes, durations and the method name only). Recorded fixtures are hand-written by us from the documented shapes with invented refs and placeholder city names (no copied carrier data). A verification spike (step 7a, owner's key, a human runs it) confirms every item above and writes the answers into the plan before step 7b codes against them.

### 9. Tracking job (question 10)
Job 8 `track-shipments` (bounded like ADR 0025): selects non-terminal shipments with `next_track_at <= now` (pages of 100, 5 pages per run), calls `track` OUTSIDE any transaction (one provider call per page, its own timeout), then one short transaction per shipment: status, journal row, `shipment.status_changed`, `next_track_at` by a backoff (created: 2 h; in transit: 4 h; arrived: 6 h; after 30 days without a terminal status: stop and log). A failed call leaves the rows due for the next tick. With question 10 option 1 the job also fulfils (`paid -> fulfilled` through `OrderFulfilmentPort`, actor `system`) on the first "accepted by the carrier" status; `awaiting_stock` or a non-`paid` order leaves the order as it is and logs a code.

### 10. Security and privacy
- **Keys:** environment only (question 6), parsed at start, length and character checks, never logged, never in an answer (the admin sees "configured"), never in the database, never in the browser; tests inject a fake. Error messages name the variable, never the value.
- **Personal data:** recipient name and phone go to the carrier (required to deliver; the privacy plan lists the carrier as a processor). Shipment rows and events carry no names or phones; logs carry codes only; carrier error texts are never logged or stored (they may echo personal data). `order_shipping.destination` holds public branch data only.
- **SSRF:** provider URLs are constants; refs from the client are validated by pattern (uuid for Nova Poshta refs) before they enter a carrier request; the label route streams only from the plugin's fixed host.
- **Rate limits:** `shippingLookup`, `shippingOptions` per address (in-memory, single process, as the others); admin shipment writes are not limited beyond the session (as other admin writes).
- **Abuse of the lookup proxy:** section 4. **Directory caching:** public carrier data, cached in memory only; whether Nova Poshta's terms allow longer storage is unknown.
- **Integrity:** prices only from core rules and admin data; the client never sends a shipping price; the order total check stays in core.

## Risks
- **Totals regression:** the first adjustment writer touches the most sensitive code path; mitigated by TDD, the consent check, concurrency specs and the review. A storefront not updated together with step 6 sends `expectedTotal = cart.total` and every shipped checkout answers `shipping_changed`: release steps 6, 9 and 10 together.
- **Nova Poshta unknowns** (section 8): field names, limits, label URLs, recipient rules; the spike (7a) must happen before 7b; any finding may change the port.
- **No carrier idempotency:** a lost `save` answer can create a waybill we do not know about; `unknown` plus `reconcile` reduce it; the admin can still see it in the carrier's cabinet.
- **Network in the scheduler:** the tracking job adds outbound calls to the tick; bounded by the job budget and timeouts (ADR 0025); a slow carrier delays nothing that runs earlier in the tick (the job runs after the time-critical ones).
- **In-memory cache and limits** are per process (same known limit as the rate limiter); several instances multiply carrier calls by the instance count.
- **Fingerprint v2:** replays across the deploy fail as `idempotency_key_reused` (rare).
- **Free-shipping threshold vs future discounts:** the threshold uses the pre-discount subtotal until the pricing pipeline decides.
- **Cash on delivery is common in Ukraine;** shipping v1 without it may not satisfy the first clients; the payment plan must schedule it.
- **Unpaid orders expire in 30 minutes** while a shop without online payment marks them paid by hand; shipping does not change this but makes the gap more visible (an order must be paid before a waybill).

   - One waybill with several parcels (seats). Fits bulky orders; per-seat dimensions in the form.
10. **Tracking and fulfilment?**
    - **(Recommended) Polling job (job 8) updates the shipment; the order is still fulfilled by an admin by hand.** No automatic terminal transition while the rules are new.
    - Polling job, and the system marks the order fulfilled when the carrier first reports the parcel accepted (`OrderFulfilmentPort`). Less admin work; a carrier mistake fulfils an order (terminal).
    - No polling; "Refresh tracking" button only. No outbound traffic from the scheduler; stale statuses.
11. **Returns and waybill cancellation in v1?**
    - **(Recommended) Cancel a waybill while the carrier allows it; returns later (their own plan with refunds).** Covers mistakes, not returns.
    - Also create return waybills (no refund logic). Useful in Ukraine; carrier return flows to verify.
    - Neither (cancel in the carrier's cabinet). Least code; the shipment row would lie.
12. **Shipping as core or as an optional feature?**
    - **(Recommended) Core for methods, rates, snapshot and shipments; carriers as plugins enabled by configuration; no methods configured = today's behaviour.** Matches AGENTS.md section 1 and ADR 0015.
    - An optional feature `features/shipping` with a flag. Removable; checkout needs a price-adjuster extension point first (the pricing pipeline, not built).
    - Core plus a global `SHIPPING_ENABLED` flag. Explicit off switch; one more variable that duplicates "no methods".
13. **How are provider plugins enabled?**
    - **(Recommended) A provider loader like the feature loader: manifest `"fluxkit": {"provider": ..., "kind": "shipping"}`, `SHIPPING_PROVIDERS_ENABLED`, CI provider matrix.** Same mental model as features; explicit.
    - Providers are features (`packages/features/nova-poshta`, `FEATURES_ENABLED`). No new loader; contradicts AGENTS.md section 5 (`packages/providers`).
    - Every installed provider package is active when its key is set. No flag; presence of a secret switches behaviour, which is hard to see.
14. **Event names?**
    - **(Recommended) `shipment.created`, `shipment.status_changed`, `shipment.cancelled` (aggregate = shipment).** One aggregate per name prefix, like `order.*`.
    - `order.shipment_created`, `order.shipment_status_changed`, `order.shipment_cancelled` (aggregate = order). Handlers of order events find them next to the others.
    - Only `order.fulfilled` (no shipment events). Least surface; email plugins cannot say "on the way".
15. **Zones?**
    - **(Recommended) A country list per method, no zone table.** Enough for one country and simple EU lists.
    - A zone table (countries, later regions or postal codes) referenced by methods. Reuse across methods; another table and screen.
    - One shop-wide list of shipping countries. Simplest; every method ships everywhere the shop does.
16. **Free-shipping rule basis?**
    - **(Recommended) Cart subtotal of all available lines (before any future discount), compared exactly in minor units.** Easy to explain; revisit with the pricing pipeline.
    - Subtotal of shippable lines only (digital lines excluded). Fairer for mixed carts; one more rule to explain.
    - No free-shipping rule in v1 (tiers can express it). Fewer types; less obvious for admins.
17. **Tax on shipping?**
    - **(Recommended) Shipping amounts follow `PRICES_INCLUDE_TAX` like product prices; no tax computed until the tax plan.** Consistent and honest about "no tax yet".
    - Shipping is always tax-exempt. Wrong for most VAT systems.
    - A tax class on methods now. Prepares the tax plan; no calculation would use it yet.
18. **Admin permission for shipping settings?**
    - **(Recommended) New `shipping.manage` for owner and manager; shipments use `orders.read`/`orders.write`.** Clear separation; an auth and contract change.
    - Reuse `catalog.write` for settings. No new permission; mixes catalog and logistics rights.
    - Owner only (`users.manage`-like). Strict; managers cannot fix a rate.
19. **Waybill creation for an order with a line awaiting stock?**
    - **(Recommended) Refused (same rule as `mark-fulfilled`).** No parcel without the goods.
    - Allowed with a warning. Flexible; risk of shipping incomplete orders.
    - Allowed only for the lines on hand (needs partial shipments, question 9 option 2).
