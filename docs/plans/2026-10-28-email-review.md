# Email review (independent reviewer, 2026-10-28)

Scope: the transactional email work merged on `main` up to `009bd80` (email plan steps 1 to 11: ADR 0031, `packages/core/src/email`, migration `0007_email`, config and loader, outbox, sender, jobs 9 and 10, template registry, `packages/providers/resend`, customer reset and verification API, order and shipment mails, admin email API, storefront reset and verify pages, admin Email area). Reviewer did not write any of it. Fresh clone, scratch database `fluxkit_rvemail_test`, no real provider called, no key used.

## Verdict

No BLOCKER, no MAJOR. The account-takeover surface (token derivation, storage, single use, binding, session revocation, link construction) is sound and well tested: every auth mutation I made was killed. Findings are latent risks, a timing gap under row-lock contention, a missing resend limit, a denylist-based redaction and a stale `HANDOFF.md`.

### ADR 0031 vs implementation (deviations)

Each item is recorded in the plan's step rows, but ADR 0031 itself was neither amended nor superseded. NIT; AGENTS.md says to supersede rather than edit, so a short "0031 as built" note or a superseding ADR would keep the ADR honest.

- Preview is `GET /admin/email/templates/{key}/preview?locale` (the ADR has `POST` with a body).
- The message list pages by `limit` and `offset` (the ADR has a cursor), filters by a `recipient` substring (the ADR has an exact `email`), and adds `createdFrom` and `createdTo`.
- The admin outbox shows the full address. The ADR and plan section 9 specify masking as `a***@domain` with a "show" action; it was not built.
- No resend limit (F2). The ADR does not require one, but the plan lists it as not built.
- The claim is per row (`lockClaimable` with `SKIP LOCKED` per id after an unlocked `listDue` page). The ADR describes one `UPDATE ... FOR UPDATE SKIP LOCKED LIMIT n RETURNING`. The behaviour is equivalent.
- Status adds `since`, `queueDepth` and `errorCodes`; resend refuses every `customer.*` key, wider than the ADR's "auth templates" (documented in `docs/api/email.md`).

## What I checked and found clean (with evidence)

- **Tokens.** Derivation `HMAC(ORDER_TOKEN_SECRET, "fluxkit:customer-auth-token:v1\n"+purpose+"\n"+uuid)`. The guest order token uses the label `fluxkit:order-access-token:v1` and refuses `\n` in its fields, so no message of one kind can equal a message of the other: no cross-purpose confusion. The token has 256 bits. Only the SHA-256 hash is stored, the outbox holds only `tokenId`, lookup goes through the unique hash index, then a constant-time re-check. Single use is one guarded `UPDATE` (M2 killed). Purpose is bound (`wrong_purpose`). The address is bound (M1 killed). An inactive customer is refused. The expiry boundary is exclusive (spec). Older tokens are invalidated on a newer token, a password change (`account.service.ts:283`) and a deactivation (`admin-customers.service.ts:69-71`), and deleted by cascade with the customer.
- **Reset confirmation.** The token is re-evaluated under the customer row lock, the password and `password_changed_at` are set, the lockout is cleared, every session is revoked (M3 killed), the other reset tokens are invalidated, and the notice is enqueued. No sign-in follows.
- **Enumeration.** Body and headers are byte-identical for existing, unknown, inactive and locked addresses (spec). The 429 per email is counted before any lookup, for every address alike. The floor holds (M4 killed). Logs carry reason codes only. Only F1 remains.
- **Links.** Links use `STOREFRONT_PUBLIC_URL` only (a spec forges `Host` and `X-Forwarded-Host`). The token is in the fragment, removed with `replaceState`, and the pages send `Referrer-Policy: no-referrer` plus the meta tag. The pages are dynamic (`ƒ` in the build output), and the token is sent in the POST body only. CSRF header is required on all four store routes.
- **Guest order links in mail.** The link is derived from the stored `order_id` and `idempotency_key` and checked against the stored hash (M9 killed). The recipient is the order's own contact address, and a resend keeps the original recipient. An admin cannot redirect a guest link to another address.
- **Outbox.** Claim, lease and record are guarded by `status = 'sending' AND attempts = claimed` (M5 killed). An expired lease past its deadline becomes `unknown` (M6 killed). The idempotency key is the row id, the deadline (12 h) is inside Resend's 24 h window, and the dedupe key `<eventId>:<template>` uses `ON CONFLICT DO NOTHING`. A template version change fails queued mail instead of re-rendering it. A provider-wide reason stops job 9. Pacing is shared with the immediate attempts, and the 120 s lease is far above the pacing wait plus the 10 s timeout. The purge deletes final statuses only (but see F11).
- **Provider boundary (Resend).** The endpoint is constant, redirects are refused (M11 killed), the answer is capped at 64 KiB, and only documented error names are kept. `invalid_idempotent_request` maps to `idempotency_conflict` and every other 409 to `unavailable` (M12 killed). The key appears only in the `Authorization` header, and the matrix guard checks that no request goes out at startup. The JSON body has no `headers`, `cc` or `bcc`. Mailboxes and subjects are validated in core: no CR, LF, NUL, bidi controls or `" < > \` in display names. The no-network guard wraps `fetch` (the plugin's only route out; a static spec bans socket modules). R3 (`reply_to`) and R9 remain UNKNOWN until S1, as documented.
- **HTML.** Escaping goes through the `html` tag, `unsafeRawHtml` is unused in the templates, and hostile-value specs exist for every template, including the subject. The text part is body only, so newlines there cannot inject headers.
- **Admin preview and CSP.** The preview iframe has an empty `sandbox` and uses `srcdoc`. `style-src-attr 'unsafe-inline'` only allows `style` attributes in parsed markup. `<style>` elements stay blocked, `script-src 'self'` is unchanged, and React applies styles through CSSOM, which CSP does not govern, so there is no script gain. The residual risk is restyling markup that is already injected, but the admin uses no `dangerouslySetInnerHTML` anywhere. Images in the preview obey `img-src`.
- **Admin API.** All 8 routes require `email.manage` (owner and manager; viewer 403) through the controller default pair. The test send goes only to the caller's address, with no `to` member. Resend refuses `customer.*` (M8 killed). Cancel and claim race under the row lock (spec). `recipient` LIKE wildcards are escaped. Detail and list never return a rendered body.
- **Docs and contracts.** `openapi.json` has the 4 store and 8 admin routes; `docs/api/email.md`, `customers.md` and `jobs.md`, `CHANGELOG.md` and `.env.example` match the code. No client data, and texts come from the uk and en catalogs. Exceptions: F5 and the ADR deviations above.
- **Test quality.** The specs are not vacuous: they run against real Postgres, and the in-repo test provider models R4 replay and conflict. The test provider skips `validateOutgoingEmail`, but the sender runs it before every call, so no over-acceptance reaches production code.
