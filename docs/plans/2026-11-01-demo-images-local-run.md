# Demo images and a one-command local run (2026-11-01)

Status: asked by the owner through the orchestrator (2026-11-01). Branch `feature/demo-images-and-local-run`. No PR is opened by the implementing agent.
Goal: the owner clicks through the shop on their own computer: a demo catalog with real-looking product images and one documented command that starts everything.

## What exists (checked before building)
- `seeds/src/products.ts`: 11 media entries, all `https://example.com/placeholder/<name>.jpg` (never load); 4 of them tied to a colour (`SeedMedia.optionValue`). `SeedBrand` has no logo field, so there is no brand logo to draw.
- `apps/api/src/seed/catalog-seeder.ts`: writes media through `ProductsService.putMedia` (the rules of `PUT /admin/products/{id}/media`, attach marking included). `seed-command.ts` boots `AppModule` WITHOUT a media config, so `MediaModule` gets `DISABLED_MEDIA_CONFIG` (driver `none`).
- `apps/api/src/media/media-upload.service.ts`: the real upload pipeline (gate, decode, re-encode, random key, atomic store, `media_upload` row). Only entry: `upload(request, admin, connection)` for the HTTP route; `created_by` is nullable.
- `sharp` 0.35.5 is a direct dependency of `apps/api` (ADR 0028); Playwright is installed for the e2e suites. No new dependency is needed.
- `README.md` quick start (manual steps), Admin sign-in (`ADMIN_PASSWORD` from the environment), Checkout walkthrough; `packages/providers/_fake-payment/README.md` "Driving it from another process" (signed webhook, `FAKE_PAYMENT_ADOPT_WEBHOOKS`); `apps/storefront/e2e/support/fake-provider.ts` (the signing scheme).
- No `demo:*` script exists in the root `package.json`.

## Decisions
1. **Images are drawn by a script, committed as seed data.** `scripts/generate-demo-images.mjs` draws one flat, neutral SVG illustration per media entry (no text, no brands, no people; one shared palette and layout) and encodes it with the API's own `sharp` (resolved from `apps/api`, no new dependency) to 800 x 800 WebP. Output: `seeds/assets/<name>.webp`. The files are committed: they are seed DATA (like the JSON-like product data), small (target well under 2 MB in total), and rendering SVG depends on the local librsvg, so committing keeps every machine seeding the same bytes and `pnpm seed` needs no extra step. The script stays in the repo to regenerate them (`node scripts/generate-demo-images.mjs`).
2. **Seed data names a file, not a URL.** `SeedMedia.url` becomes `SeedMedia.file` (`<name>.webp` inside `seeds/assets/`). The seeds package stays pure data (no I/O); the runner resolves the directory.
3. **The runner uploads through the real media service.** `MediaUploadService` gets a second entry `storeSystemImage(bytes)` for system callers (no admin, `created_by` null, no rate limit or HTTP checks; same pipeline, key, row and log line, `admin=system`). The seed command passes the media config of `loadEnv` (as the API, `jobs:run-once` and `search:reindex` do, including `prepareDefaultMediaDirectory`). For each product it CREATES, the runner reads the image files first (a missing file stops the run before anything is written), creates the product (invalid product data fails before any upload), uploads the images, then saves the media list through `ProductsService.putMedia` with the returned URLs, which marks the uploads attached. (Changed while implementing: uploading before the product would have left upload rows behind for invalid product data, which the existing "creates nothing" test forbids; a failed upload now leaves a half-built product, the runner's documented crash limit, and an unattached upload that job 7 deletes after 24 h.) Existing products are never touched, so a second run uploads nothing.
4. **`MEDIA_STORAGE_DRIVER=none`:** products are created without images and the summary says `images not uploaded: MEDIA_STORAGE_DRIVER is none` (like the search line). A later run with `local` does not add them (products are never updated): delete the demo products and seed again (documented).
5. **`pnpm demo:up` / `pnpm demo:down`** (`scripts/demo-up.mjs`, `scripts/demo-down.mjs`, Node only, no dependency): generate `.env` from `.env.example` when missing (random secrets from `node:crypto`, file mode 0600, never committed: `.env` is git-ignored), with `DATABASE_URL` on `fluxkit_dev`, `SEARCH_ENABLED=true`, `MEDIA_STORAGE_DRIVER=local`, plain-HTTP cookies, `SHIPPING_PROVIDERS_ENABLED=fake`, `PAYMENT_PROVIDERS_ENABLED=fake`, `FAKE_PAYMENT_ADOPT_WEBHOOKS=true` (all test-only and refused under `NODE_ENV=production` by `loadEnv`); start the Compose services with `--wait`; create the scoped Meilisearch key with the master key when `MEILI_API_KEY` is still the placeholder and write it into `.env`; stop with a hint when `node_modules` is missing; then `pnpm build`, migrate, seed, reindex, create `owner@example.com` with a random password passed through `ADMIN_PASSWORD` in the child's environment only and printed once (skipped when that admin exists); print the URLs and the dev-server commands. `demo:down` stops the services and keeps the data (wiping is a documented manual `docker compose ... down -v`).
6. **Fake payment in the browser:** the fake has no payment page (`https://pay.fake.invalid` resolves nowhere). `pnpm demo:pay` (`scripts/demo-pay.mjs`) plays the provider like the e2e suites: it finds the newest pending `fake` payment in the `_dev`/`_demo`/`_local`/`_test` database, posts the signed webhook to the local API and prints the storefront return page URL. Refuses `NODE_ENV=production`, any other database name and any provider but `fake`. It changes no payment code.
7. **Shipping methods** stay inactive after the seed (unchanged runner rule); there is no API-free documented way to activate them, so the README tells the owner to activate them in the admin (Shipping). The checkout works without them.

## Open question for the owner (not built here)
- **The storefront cannot show uploaded images on a developer machine.** By design (owner answer 7, ADR 0028 decision 6, README "Uploaded images") it accepts only absolute `https` URLs of `STOREFRONT_IMAGE_HOSTS`, and the Next optimizer refuses loopback addresses, so locally every product shows the token-styled placeholder; the admin shows the images. Changing that is a storefront security and config-contract change (red zone). Options: (a, recommended) a development-only rule: in `next dev`, rewrite `/media/*` to the API like `/store/*` and accept relative `/media/<key>` URLs when the API's `MEDIA_PUBLIC_BASE_URL` is the storefront origin plus `/media`; (b) a local HTTPS proxy with a public-resolving host name (fragile, needs a certificate); (c) leave as is and document. This change takes (c) and asks.

## Risks
- Docker cannot run in the agent sandbox: `demo:up`/`demo:down` are verified here only for the parts that do not need Docker (the `.env` generation and the steps after the services, against natively started services). Stated in the report.
- The seed now needs a writable `MEDIA_DIR` by default (outside production `<repo>/var/media`, created if missing).
