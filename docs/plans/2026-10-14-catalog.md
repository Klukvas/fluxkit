# Plan: catalog domain (ProductType, attributes, products, variants, categories)

Status: complete. Steps 1 to 7 merged (step 7 in PR #25); step 8 (independent review, 2026-10-16) done: its findings are recorded in PR #26 and fixed in PRs #27 to #29; the items still open are in `docs/plans/2026-10-16-catalog-review-findings.md`. Decisions are in "Decisions"; the result is in "Outcome".
Roles: Architect (step 1), Developers (steps 2 to 7), independent Reviewer (step 8), Docs agent (step 7).
Follows: `docs/plans/2026-10-14-monorepo-scaffold.md` (completed). Design basis: ADR 0004 (data model), ADR 0005 (search notes), AGENTS.md section 2.3.

## Goal
First real core domain: a niche-agnostic catalog that stores products with data-driven attributes and variants, can be managed through an admin API and read through a public storefront API,
plus ProductType presets and demo data. After this plan a client can describe a T-shirt shop or a hand-tool shop purely with data, without code changes.

### Out of scope (each gets its own plan)
Pricing and taxes (`price` table, pipeline), inventory, cart/checkout/orders, search indexing and facets (blocked by the open ADR 0005 decisions), media upload and storage (only URL + alt are stored),
admin UI, authentication and roles, CSV import/export, category filter overrides, reviews and other features.

## Existing functionality found
- No catalog code exists. The only matches for "product/variant/category" are placeholder UI strings in `apps/storefront`, `apps/admin` and `packages/ui`.
- `packages/core` is an empty scaffold (`src/index.ts` exports nothing); `apps/api/src/database/schema.ts` has only the throwaway `health_check` table; `seeds/` has only a README.
- Reusable: Drizzle + migration convention with `.down.sql` (AGENTS.md section 3), feature loader and `packages/config`, Vitest + real Postgres test harness (`apps/api/src/test`), OpenAPI export and its freshness test, dependency-cruiser rules, CI matrix, `packages/ui` i18n (`uk`, `en`).
- Nothing for auth or guards exists. Admin endpoints must be default-deny (AGENTS.md section 11), so this plan ships an `AdminGuard` that rejects everything until the auth plan provides a real one (see decision 1).

## Scope: core, no feature flag (catalog is core). Owned paths are listed per step.

### Step 1. Architect: catalog schema ADR (Fable, high effort; docs only)
Write `docs/adr/0006-catalog-schema.md` that finalizes what ADR 0004 left as a draft. It must decide, with reasons:
- Tables, columns, constraints and indexes for: `attribute`, `attribute_option`, `option`, `option_value`, `product_type`, `product_type_attribute` (level product or variant, required, sort),
  `product_type_option`, `category` (tree), `brand`, `product`, `product_option`, `product_option_value`, `variant`, `variant_option_value`, `media`, `product_category`.
- Options vs attributes (AGENTS.md 2.3): proposal is global `option` definitions (code, labels, values) that a ProductType allows; a product chooses a subset of values; every variant holds exactly one value per
  product option, and the combination is unique per product. Attributes are descriptive typed fields (JSONB on product or variant, codes not labels).
- Attribute input types for v1 (proposal: text, number with unit, boolean, select, multiselect, date) and the validation rules per type (required, min/max, allowed option codes).
- Rules for changing a ProductType after products exist (type of an attribute never changes; removing or retyping blocked when values exist; renaming option codes blocked or migrated explicitly).
- Product lifecycle (`draft`, `active`, `archived`), the default-variant rule for simple products, SKU uniqueness and format, slug rules, soft delete versus hard delete, ordering columns.
- i18n storage for names and descriptions (decision 2), locale fallback, and what `is_internal` hides from the public API.
- Limits: max options per product (3), max variants generated at once, max category depth, page sizes.
Output is reviewed by the orchestrator before steps 2 and 3 start.

### Step 2. Core domain logic, pure TypeScript (Developer, Sonnet, high effort; tests first)
Path: `packages/core/src/catalog/**` (no Nest, no Drizzle, no I/O).
- Types for the entities above; `validateAttributeValues(productType, values)` returning typed errors per attribute; `generateVariants(options, existing, limits)` (cartesian product, skips existing
  combinations, enforces limits); invariants: exactly one default variant, option coverage per variant, unique option combination, category tree without cycles and within depth.
- TDD: write failing tests first for each rule (valid and invalid values per input type, unit handling, required, unknown option codes, limit exceeded, empty option lists, duplicate combinations,
  simple product with no options, cycles, depth), then implement. The report must show failing-then-passing evidence.
- New dependency: `zod` in `packages/core` (already approved and used in `packages/config`); no other additions.
- Add a dependency-cruiser rule: `packages/core` must not import `@nestjs/*`, `drizzle-orm`, `pg`, `ioredis`, `bullmq` or `meilisearch` (negative test with a deliberate violation).

### Step 3. Database schema and migrations (Developer, Sonnet, high effort; RED ZONE: migration needs approval at plan approval)
Path: `apps/api/src/database/schema/**` (split by domain), `apps/api/drizzle/**`.
- Implement the ADR 0006 tables with all constraints (unique SKU, unique slug, foreign keys, check constraints for status and level), indexes for the public queries.
- One generated migration plus a hand-written `.down.sql` that also removes its row in `drizzle.__drizzle_migrations` (convention from the scaffold).
- Tests on real Postgres: up, down, up, down; each constraint rejects bad data (duplicate SKU, duplicate slug, variant without product, duplicate option combination at the DB level where expressible).
- Runs in parallel with step 2 (disjoint paths).

### Step 4. Admin write API (Developer, Sonnet, medium; needs steps 2 and 3)
Path: `apps/api/src/catalog/admin/**`, `apps/api/src/auth/admin.guard.ts`.
- Nest modules and services using the core domain functions inside DB transactions. Validation through a Zod pipe (no new dependency). Errors as consistent problem responses (400 validation with per-field details, 404, 409 for conflicts).
- Endpoints (all under `/admin`, all behind `AdminGuard`, default deny, tests override the guard):
  `attributes` (+ options), `options` (+ values), `product-types` (assign attributes and options), `categories` (CRUD and move), `brands`, `products` (CRUD, publish, archive),
  `products/:id/variants` (CRUD and `generate`).
- Rules enforced in the service layer, not only in the DB: the ProductType change rules, the lifecycle rules (cannot publish without a default variant and required attributes), the generation limits.

### Step 5. Public storefront read API (Developer, Sonnet, medium)
Path: `apps/api/src/catalog/store/**`.
- `GET /store/categories` (tree), `GET /store/products` (paginated list of ACTIVE products; filters by category and brand only; max page size 100; no facets and no text search yet),
  `GET /store/products/:slug` (product, options, variants, visible attributes, media). Locale via `?locale=uk|en` with fallback to the default locale.
- Hard rules with tests: draft and archived products never appear; attributes flagged `is_internal` never leave the API; unknown locale gives 400; pagination bounds enforced.

### Step 6. ProductType presets and demo data (Developer, Sonnet, medium)
Path: `seeds/**`, root script `pnpm seed`.
- Presets as data: Clothing (options color and size), Hand tool (attributes only), Digital product (no shipping flag). Demo products and categories in `uk` and `en`; placeholders only, no client data.
- Idempotent seed script (runs twice without errors or duplicates), built output executed by Node (no new runtime dependency).
- Test: seed on an empty database, then the store API returns the demo products; run again, counts unchanged.

### Step 7. OpenAPI and documentation (Docs agent, Haiku, low; orchestrator checks)
- Regenerate `docs/api/openapi.json` (core routes include catalog), add `docs/api/catalog.md` (one line per endpoint), update `docs/contracts/api.md`,
  `docs/files/api.md` and `docs/files/core.md`, ADR index, `CHANGELOG.md`, README status. `pnpm check:docs` must pass.

### Step 8. Independent review (Reviewer, Opus, high; a different agent than the authors)
Review the full diff against AGENTS.md (core purity, no leaks of internal attributes, default-deny, migration reversibility, tests that cannot pass while the code is broken). Findings are fixed before merge.

## Order and parallelism
1 -> (2 and 3 in parallel) -> 4 -> 5 -> 6 -> 7 -> 8. Each step is its own branch and PR into `main` (small PRs), CI green before merge.

## Data and API changes
- New migration (up and down) creating the catalog tables. No change to existing tables.
- New public API surface (admin and store endpoints above). These become public contracts under SemVer (`docs/contracts/api.md`): approving this plan approves the first version of that surface.

## Risks
- Getting the schema wrong is expensive. Mitigations: step 1 ADR reviewed before code; the schema is pre-release (no client data yet), so a correction costs a new migration, not a data migration; keep tables minimal.
- JSONB attribute values reference option codes: renaming or deleting options and retyping attributes can corrupt data. Mitigation: blocked by rules in the service layer and tested.
- Combinatorial explosion in variant generation: limits enforced in the domain function and tested.
- Admin endpoints are unusable in production until the auth plan lands (default-deny guard). Intentional; do not add an interim backdoor.
- `packages/core` purity can erode under deadline pressure: enforced by the new dependency-cruiser rule in CI.
- Search facets for variant-level attributes remain unsolved (ADR 0005); this plan deliberately does not build filters beyond category and brand.

## Decisions (owner, 2026-10-14)
1. **Admin auth**: this plan ships a default-deny `AdminGuard`; a separate small "auth and roles" plan follows right after. No temporary API key.
2. **Translations**: JSONB map per text field (`{"uk": "...", "en": "..."}`), `uk` required, fallback to `uk`.
3. **Slugs**: one latin slug per product, category and brand (transliterated from the `uk` title, editable, unique per entity type).
4. **Media**: only `url`, `alt` and position in this plan; upload and storage in a later plan.

5. **Default locale** is configuration (`DEFAULT_LOCALE`, `LOCALES`), not a DB rule (ADR 0006, decision 1). `packages/config` gains these two variables in step 4.
6. **Slug redirects** are deferred to the storefront SEO plan; **options are frozen after publish**; **`requires_shipping` lives on `product_type`**; **barcode is free text** (ADR 0006).

## Still open (does not block this plan)
7. Variant-level facets and Ukrainian search morphology (ADR 0005). They block the search plan that follows the catalog; decide before it.

Deviations from the plan:

- Step 4 was delivered as 4a, 4b, 4c, 4d-1 and 4d-2 (one PR each), not as one step.
- The seed data lives in `seeds/` as planned, but the runner that writes it is in `apps/api/src/seed/` (it creates rows through the admin services).
- A store API design document was added before step 5 (`docs/plans/2026-10-16-catalog-store-api-design.md`).
- The admin list page size is 50 (default) and 100 (max), as in the admin design document. ADR 0006 section 9 says the default is 24; the store API uses 24.
- `GET /admin/products` `?categoryId` matches products assigned to that category directly. ADR 0006 section 8 says listings include descendants; only the store API does that.
- `GET /admin/categories` accepts `?parentId`, but `docs/api/openapi.json` does not list it (the route decorator documents only pagination).

Follow-ups (not in this plan):

- Auth and roles plan. Until it lands, every `/admin` route answers 401 by design.
- Rate limiting for auth, search and checkout endpoints (needs a dependency: red zone, approval first).
- A `db:migrate` script (there is none; tests migrate through `apps/api/src/test/migrate.ts`, seeding needs a migrated database).
- Search plan: blocked by the open decisions in ADR 0005 (Ukrainian morphology, variant-level facet counts).
- Slug redirects belong to the storefront SEO plan and must land before the first client launch (ADR 0006, owner decision 2).
