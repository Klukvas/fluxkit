## 1. Goal and scope

- Step 1: add `packages/providers/brevo`, selectable alone with `EMAIL_PROVIDER=brevo`, using Node `fetch`, without a Brevo SDK or a new third-party npm dependency. Reuse the email port, discovery, templates, outbox and admin area.
- Step 1b: authenticate provider feedback into a shared local suppression list and check it before every send; mandatory before step 2 (section 4.5).
- Step 2: keep `EMAIL_PROVIDER` as the primary and add an ordered fallback list. On a **proven non-acceptance**, try the next eligible provider before a daily wait consumes the message's deadline.
- Motivation: Resend's 100/day free cap is the owner's context. The current retry rule sends a daily-quota failure to the next 00:05 UTC, or fails it immediately when that instant is outside its deadline. Order mail has 12 hours; token mail has at most one hour. A second service can help only before any service may have accepted the message.
- Email remains core, with removable provider packages; no feature flag. No changes to prices, stock, payments, account authorization, token generation/lifetimes or mail contents beyond necessary provider-neutral admin-test wording.
- Excluded: marketing, bulk send, attachments, provider-managed templates, tracking, new admin recovery flows, production deployment, account creation, DNS edits, keys in files and unrelated documentation cleanup. This revision implements no code or migrations; webhook/suppression implementation belongs to future step 1b.
- **Discovery changes the size of step 1:** Brevo's message IDs do not fit the existing validator, and its documented idempotency window is shorter than Fluxkit's retries. The compatibility prerequisites in section 3 are approved (section 11); a plugin-only copy of Resend is not safe to enable.

### 3.2 Result mapping

Mapping is a proposed adapter policy under ADR 0031, not a claim that every combination was observed. Strictly allowlist documented codes; discard free-form `message`, unknown codes, addresses and raw bodies. Check transport/5xx/invalid envelopes before trusting a body that claims a safe error.

| Observed condition | ADR 0031 result | Step 2 switch eligibility |
|---|---|---|
| Local validation or abort before `fetch` | `not_sent` | Yes if unpinned and another provider could help; invalid common payload fails before routing. |
| Validated `401`/`403` authentication/permission refusal; verified account/domain configuration refusal | `misconfigured` | Yes if unpinned. Missing key at startup still fails startup; fallback does not conceal invalid configuration. |
| Proven refusal with `not_enough_credits` (`400`/`402` pairing to verify) | `quota_exceeded` | Yes only after non-acceptance is confirmed. Omit `quotaPeriod` unless the service identifies it. Bare `402` is not proof of a daily quota. |
| Recognizable Brevo `429` throttle response | `rate_limited` | Yes if unpinned. Convert a verified seconds-based reset to bounded whole `retryAfterSeconds`; honor a valid longer `Retry-After` if present. Missing/unusable delay uses core backoff. |
| Recognizable `400` field refusal (`invalid_parameter`, `missing_parameter`, `out_of_range`); verified recipient refusal | `rejected` | **No.** Permanent payload/recipient problems are not availability problems; preserve terminal failure, including suppression refusals. |
| Idempotency duplicate (`duplicate_parameter` in the verified idempotency context) | `idempotency_conflict` → `unknown` unless authoritative reconciliation proves acceptance | **No.** Reusing this existing conservative reason requires documenting that Brevo's duplicate need not mean a changed body. Do not manufacture a success ID. Generic duplicate errors remain ambiguous until classified. |
| Timeout, transport failure, 408, any 5xx, unreadable/oversize/malformed response, unexpected status, thrown error | `unavailable` | **Never.** The provider may have accepted; retry only the same provider/key within its safe window. 5xx wire shapes are UNKNOWN, handled conservatively regardless. |
| Valid `201` and validated message ID, even if delivery is queued | success | **No.** A queue/delivery problem is not a pre-send failure. |

- B3/B4 provide the HTTP/code evidence; `not_sent`, conservative 5xx handling and failover eligibility follow local `provider-port.ts:17` and `email-provider-call.ts:103`.
- Unknown quota response semantics block classifying that Brevo response as switch-safe. Do not infer quota from message text or set `quotaPeriod=daily` just because the account is Free; Resend's 00:05 UTC rule is not a verified Brevo reset rule.

### 3.3 Implementation sequence after approval

1. **Compatibility prerequisite: provider message ID.** Brevo returns an RFC-style identifier containing `<`, `@`, `>` (B1); core, provider contract, API boundary and DB currently require `^[A-Za-z0-9_.:-]{1,64}$` (`provider-contract.ts:131`, `email-provider-call.ts:70`, `schema/email.ts:206`). Introduce a separate bounded provider-message-ID validator accepting the existing codes and a single bracketed ID; proposed maximum 255 characters. Preserve the exact ID for investigation; never truncate, hash it in place, or broaden `EMAIL_CODE_PATTERN` used for errors. Length beyond this bound is UNKNOWN and must fail conservatively. Update parity/hostile-input tests and the DB check via the small reversible migration in section 5. This is a newly discovered step-1 red zone.
2. **Compatibility prerequisite: bounded retries.** Add an optional `idempotencyWindowSeconds` capability with explicit documentation and validation: absent retains existing provider behavior; false `idempotencyKeys` means no automatic replay after ambiguity. Brevo declares false until B2's exact request is verified; after verification, true with 1,800 seconds. The sender must actually consume this capability; setting a boolean alone does nothing today. No hardcoded provider name in core.
3. **Compatibility prerequisite: durable pin (moved into step 1 after QA review).** Today the sender uses whatever provider is configured now (`email-sender.ts:104`) and the claim overwrites `provider_code` (`email-message-changes.ts:159`), so changing `EMAIL_PROVIDER` between attempts could replay an already accepted mail through another service. Add nullable `email_message.pinned_provider_code` and `pinned_at` (section 5, step-1 migration). Set them, inside the existing fenced record transaction, when an attempt ends `unavailable` (timeout, transport, 5xx, malformed, thrown), and in the claim transaction when a `sending` row with an expired lease is reclaimed (the crashed attempt may have sent); `pinned_at` = that attempt's claim time (`lease_until - EMAIL_LEASE_SECONDS`). Never cleared. A pinned row is only ever sent through its pinned provider with the same key; if that provider is no longer configured the row is held (admin-visible code) and becomes `unknown` at its deadline.
4. **Retry window only for possible acceptance.** For a provider with a declared `idempotencyWindowSeconds` (Brevo: 1,800), a **pinned** message is retried only until `min(deadline_at, pinned_at + window - 5 minutes)`; then it becomes `unknown`, no further automatic send. An **unpinned** message (every earlier attempt proven unsent: `not_sent`, `quota_exceeded`, `rate_limited`, `misconfigured`) keeps the normal ADR 0031 schedule and deadline. Resend (24 h window, longer than the 12 h deadline) behaves exactly as today.
5. **Precedence rule (QA review).** If a message is pinned, any later terminal outcome (`rejected`, `template_unavailable`/`variables_invalid` at render, deadline, provider no longer configured) ends in `unknown`, not `failed`: a later refusal does not prove the earlier attempt was not accepted. Only an authoritative success gives `sent`. This needs a new `pending -> unknown` transition in core `EMAIL_MESSAGE_TRANSITIONS` (`packages/core/src/email/status.ts:51`, which today has none) and changes to `nextEmailAttempt` / `email-outcome.ts:116`. Regression tests: pinned then `rejected`, pinned then render failure, pinned pending past deadline.
6. Build `packages/providers/brevo` in the Resend layout: manifest, Nest `providerModule`, own `config.ts`, `http.ts`, `request.ts`, `answer-map.ts`, provider class, local stub, contract/no-network/hostile/secrets tests, README and TypeScript/Vitest setup. Reuse already pinned workspace/Nest/zod tooling; no new library/SDK. Include the package in production-image runtime dependency checks and workspace lockfile metadata when implementation occurs.
7. Parse `BREVO_API_KEY` only in the enabled package. Require a nonempty bounded header-safe value; the vendor's exact key grammar is UNKNOWN, so do not copy the `re_` regex or invent a mandatory prefix. Missing/malformed errors name the variable only. Fixed HTTPS endpoint, no redirects/URL env override, 64 KiB response cap, caller-owned abort/timeout, one POST at most per `send`, no startup network call.
8. Map the rendered message to B1, pass the UUID in B2's JSON headers, and optionally add `X-Mailin-custom` containing only the outbox UUID for operator correlation. No arbitrary headers from stored variables. No contact import, tracking, attachments or provider templates. Correlation headers/tags do **not** deduplicate.
9. Extend `EMAIL_PROVIDER_CHOICES`, config/schema parity, loader tests and matrix with `providers-email-brevo`: missing key fails; invented key boots with no external call or secret output; `emailDelivery=true`; none/deleted remain safe. Update `.github/workflows/ci.yml` to actually run the new mode and add Brevo to the deleted-provider assertions.
10. Update the step-1 docs in section 7: the Brevo README and client-facing `docs/contracts/config.md` / `docs/deployment.md` provider notes disclose Free-plan branding and that removing it requires a paid Brevo plan (owner decision 2). Mark every unverified provider behaviour `TODO(fluxkit): not live-verified` in code and README, and list it in `docs/HANDOFF.md` during implementation (decision 6); report local evidence separately from live findings. Keep the plugin disabled in a real shop until the relevant B2/B6 checks and owner approvals are complete.

## 4. Step 2 — primary plus ordered fallback

### 4.1 Configuration and contracts

- Add **`EMAIL_FALLBACK_PROVIDERS`**, comma-separated ordered codes, default empty. Keep `EMAIL_PROVIDER` as primary: `EMAIL_PROVIDER=resend`, `EMAIL_FALLBACK_PROVIDERS=brevo`. The name expresses an additive fallback list; `EMAIL_PROVIDERS` would introduce competing definitions of the primary.
- Unset/blank list means today's one-provider selection and off behavior. Primary remains required for a nonempty list; `EMAIL_PROVIDER=none` plus a nonempty list fails startup. Do not auto-enable mail from a fallback value alone.
- Trim/lowercase like the existing choice. Reject unknown codes, empty interior entries, duplicates after normalization, primary repeated in the list, and `none` anywhere in the list. Validate before the shared loader, whose `Set` at `provider-package-loader.ts:123` would otherwise silently remove duplicates.
- All selected packages and their own keys must be valid at startup; `RESEND_API_KEY` and `BREVO_API_KEY` are independently required when selected anywhere. An invalid remote key discovered on send can trigger safe failover; an absent local key is a startup error.
- With a **nonempty normalized** `EMAIL_FALLBACK_PROVIDERS`, refuse startup unless step 1b is locally ready: its migration is recorded, required suppression/receipt schema is queryable, the shared sender guard is wired, and every configured provider (primary included) registers a webhook verifier/route with a valid webhook secret. Check before enabling job 9 or immediate sends; no bypass flag. Missing secret/verifier/schema fails with codes/variable names only. Empty/unset retains single-provider selection; suppression still applies once step 1b is installed. Section 4.5 defines remote setup checks that startup cannot prove.
- Preserve the legacy non-production `EMAIL_PROVIDER=fake` harness for compatibility. New multi-provider fake codes/chains are test fixtures only, accepted through explicit test setup (`NODE_ENV=test`); production refuses every test-only code at any position. No fake can become a real shop's fallback.
- No change to the shared sender/from/reply-to/link origin. Both real services must verify the same sender. `emailDelivery` means configured, not “every provider is healthy”.
- [ADR 0056](../adr/0056-email-brevo-suppression-and-fallback.md) records the approved decisions before step 1. It distinguishes steps 1, 1b and 2 and supersedes ADR 0031 in part: decision 4 (one provider), decision 5 (provider-message-ID pattern), decision 7 (12-hour retry-window assumption), and the affected portions of 1/3/6/12/15/17. Do not edit ADR 0031. Update config/API contracts and SemVer notes during implementation; keep existing response members and off behavior.

### 4.2 Routing invariants

| Condition | Decision |
|---|---|
| New unpinned mail | Start with primary; skip a provider under a proven shared cooldown, then consider the list in order. |
| `quota_exceeded`, `rate_limited`, `misconfigured`, `not_sent`, no ambiguous history | May advance to the next provider. The adapter must prove non-acceptance; a local invalid common payload is rejected before any chain is attempted. |
| `rejected` | Terminal; do not try another provider. It can mean bad recipient/content or suppression. Successful delivery through a second service would not make bypassing that refusal correct. |
| `unavailable`, timeout, 5xx, malformed, thrown, interrupted dispatch/expired lease | Persist ambiguity and **pin this message to that provider**. All subsequent permitted retries use that provider and the same UUID. |
| Pinned A later returns quota/rate/misconfigured/not_sent | **Still pinned to A. Never switch later.** The later safe failure does not disprove the earlier acceptance. |
| `idempotency_conflict` | Terminal `unknown`, existing semantics; never automatic fallback. |
| Any accepted result | Store actual accepting provider and ID; stop. No fallback on later bounce, deferral, remote queueing or missing delivery confirmation. |
| Deadline or safe dedupe window exhausted | No more network calls. `unknown` if any acceptance remains possible; `failed` only if all dispatches are proven unsent. |

- Use `email_message.id` unchanged at A and B. Independent services have independent key namespaces; use `(message id, provider code)` for local history and window calculations. Never change the key per retry. Manual resend remains a new row/key, with the existing prohibition for `customer.*` mail and an explicit possible-duplicate warning for an unknown original.
- When all providers are safely unavailable, schedule the earliest eligible retry before the message deadline, using provider-specific delays and the existing message-level attempt count (minimal design, decision 7). Do not apply A's quota deadline failure before trying eligible B. No tight loops: each provider at most once per routing pass; subsequent passes use backoff/cooldowns. A recovered primary is preferred on a later pass only if **all** previous attempts were safe.
- Bound every immediate fallback by the remaining job/lease/deadline budget and pacing capacity. If insufficient, durably record safe next-provider selection and defer for another claim; a delay of one tick is preferable to an unfenced send. Keep the immediate auth path on the same state machine as job 9.
- Reordering/removing a provider cannot unpin existing mail. A pinned provider unavailable under the current configuration is held with an admin-visible code, then becomes `unknown` at expiry; never silently route it elsewhere. Do not log any key/account secret.

### 4.3 Durable state, cooldowns and multiple instances

- **Postgres is authoritative.** **Approved minimal design (owner decision 7):** reuse step 1's `pinned_provider_code`/`pinned_at` as the sticky-ambiguity record, add `email_message.route_provider_code` (the provider the next attempt must use; NULL = start at the primary) and one small `email_provider_state` table for shared cooldowns (section 5). Existing `provider_code` stays the provider of the current/last attempt and, on `sent`, the provider that accepted it (it is already required for `sent` rows); do not present a pending row's value as evidence of delivery. Existing `attempts` remains a message-level counter; backoff stays message-level.
- **Deferred fallback (QA review):** when A refuses safely and the remaining job/lease budget cannot cover B, the record transaction sets `route_provider_code = B`; the next claim calls B before going back to the primary. A routing pass ends when the last provider in the chain refused safely; `route_provider_code` is then reset to NULL and the message waits for the earliest provider cooldown or the backoff. Regression: "A refuses safely, budget too small for B, restart, the next claim calls B, not A".
- **Deferred alternative, not selected (owner decision 7):** a per-dispatch `email_provider_attempt` ledger (started/finished/outcome per provider) with a paginated attempt history in the admin API. It gives an operational audit trail and exact per-provider dispatch times, at the cost of one more table, retention/erasure rules, an API pagination contract and UI. Safety does not need it: the pin is set by the fenced record step and by lease-expiry reclaim, which already covers a crash between the claim and the record. No ledger or admin attempt history in these steps.
- Preserve the existing no-DB-between-final-slot-and-call rule; a worker that proves pacing never invoked the provider returns the claim with the existing `defer` (no attempt spent, no pin).
- Record result, sticky pin, next route/time and provider cooldown in **one short transaction** fenced by message status, claim attempt/lease and provider. A late worker cannot overwrite a newer claim or unpin. On a lost record/DB connection, stop that worker's chain; lease recovery pins the unresolved provider before considering another. No DB transaction spans a fetch.
- Store cooldown by provider code per shop database: `unavailable_until`, safe reason and recovery-probe lease. Code identifies the single configured account for that service. Use DB time for shared expiry/probe admission; no key hashes or raw keys in the table. Duplicate use of one service/account under aliases is unsupported.
- On safe quota/rate/config refusal atomically extend the cooldown (`max(existing, observed)`); other instances skip it. Resend daily reset remains next 00:05 UTC; monthly/unknown quota and misconfiguration use an hourly probe; rate limit uses validated server delay/backoff. Never infer a Brevo UTC reset. `not_sent` and `rejected` are message-specific and do not globally disable a provider.
- Once a cooldown expires, a conditional row update grants one bounded recovery probe across instances; others use fallback or wait. A matching successful probe clears the block; stale completion cannot clear a newer block. Calls already admitted before a refusal may finish; this is not an exact account-credit reservation system.
- Why Postgres: durable restart behavior, works with both `RATE_LIMIT_STORE=memory|redis`, and can commit cooldown with message routing. In-process state multiplies across instances; Redis is suitable for disposable pacing but its eviction/outage fallback must not erase ambiguity or quota decisions. A DB failure prevents sends because durable ownership cannot be proven; never replace routing state with process memory.
- Keep the existing global 8/s pacer initially, including Redis sharing when selected. It is conservative for either service and avoids redesigning the pacer in this change. It does not coordinate usage from other shops/apps sharing the same provider account; use separate shop credentials/accounts and handle actual provider responses. Account rotation preserves cooldown until its bounded expiry/probe; no automatic reset from restarting a process.
- Job 9 continues past a blocked provider when other messages have an eligible provider. A pinned blocked message does not stop all mail. Preserve page/time budgets, due ordering and existing retention job; update the meaning of `paused` and `docs/api/jobs.md` without inventing a new job.

### 4.5 Step 1b — shared local suppression list (mandatory before fallback, owner decision 5)

- **Boundary and routes:** `POST /webhooks/email/resend` and `POST /webhooks/email/brevo`, public (no customer/admin session), provider-authenticated, HTTPS, rate limited through the existing window-store abstraction, bounded to 64 KiB. Each enabled plugin verifies headers/RAW bytes before parsing and returns validated facts; core owns suppression and persistence. Reuse the route-scoped raw-body approach in `apps/api/src/payments/webhook/webhook-raw-body.ts` without changing payment behaviour; never verify re-serialized JSON (AGENTS.md section 11). Disabled/deleted providers have no route; absent credentials never allow unauthenticated ingestion.
- **Events:** hard bounce and spam complaint for both providers; transactional unsubscribe/blocked when reported. Resend: `email.bounced`, `email.complained`, `email.suppressed` and `suppression.added` (a block created in Resend, manual or automatic, maps to `blocked`; `suppression.removed` is ignored: no automatic unsuppression; regression: a block added in Resend while Resend is on cooldown stops a Brevo fallback send); Brevo subscriptions: `hardBounce`, `spam`, `unsubscribed`, `blocked` (map actual payload spellings separately). Ignore soft bounces, delivery delay, opens/clicks and marketing events; allowlist reasons, never store vendor text. Sources: [Resend event reference](https://github.com/resend/resend-openapi/blob/main/resend.yaml), [Resend suppression](https://resend.com/changelog/email-suppression-visibility), [Brevo event subscriptions](https://developers.brevo.com/reference/create-webhook).
- **Resend verification:** `svix-id`, `svix-timestamp`, `svix-signature`; HMAC-SHA256 of `id.timestamp.rawBody` with the base64-decoded portion after `whsec_`, accept a matching supported `v1` signature using constant-time comparison. Require the signed delivery timestamp within ±5 minutes of the server clock (Svix's default); an old event can arrive with a fresh delivery signature. Use Node crypto and official test vectors, no new SDK dependency. [Resend verification](https://resend.com/docs/webhooks/verify-webhooks-requests), [Svix signing specification](https://docs.svix.com/receiving/verifying-payloads/how-manual), [Svix tolerance and stable IDs](https://www.svix.com/resources/webhook-university/reliability/idempotency-and-deduplication/).
- **Brevo authentication:** no transactional body HMAC/signature is documented. Available options are URL username/password, configured `auth.type=bearer` / `auth.token`, custom headers and source-IP allowlisting. Choose a dedicated high-entropy bearer token over HTTPS, compared in constant time using fixed-length digests of bounded values; no URL credentials or API-key reuse. Optional edge allowlisting uses current official webhook CIDRs and trusted-proxy rules. **Residual risk:** a leaked token or compromised TLS terminator can forge body/timestamp values; this is not signed-body verification. [Brevo security options and IP-range link](https://developers.brevo.com/docs/secured-webhooks).
- **Idempotency and replay:** atomically insert a receipt and upsert suppression, then acknowledge `204`; duplicates do nothing, including after admin removal. Key receipts by provider + stable event ID (Resend `svix-id`). Brevo documents `id` as the webhook ID, not a unique event ID: until a stable event ID is verified, derive a versioned SHA-256 key from the validated tuple (webhook ID, message ID, normalized recipient, event type, `ts_event`), never just `id`. Tuple stability is `TODO(fluxkit): not live-verified`. Local event-age policy: at most 7 days old / 5 minutes future for both providers, separate from Resend's signed-delivery window; keep receipts 8 days after receipt, purge through job 10. Older events require operator reconciliation, not a silent success. Brevo's timestamp is unsigned, so this bounds honest replays, not forgery. On transient DB failure return `429` with bounded retry delay; never acknowledge before commit. Brevo documents discarding on 5xx and on 4xx other than 429. [Brevo payloads](https://developers.brevo.com/docs/transactional-webhooks), [retry policy](https://developers.brevo.com/docs/retry-mechanism).
- **Storage/privacy:** choose `email_suppression` with opaque UUID, unique normalized address (existing trim/lowercase validator; no provider-specific dot/plus rewriting), allowlisted reason, source provider and first/last event times. A normalized address supports admin inspection and exact erasure without a new long-lived hash key; a keyed hash would remain personal data and complicate key rotation, not settle retention legality. Store no payload, subject, message body, links or provider text. Receipts keep only provider, dedupe key, normalized address and event/receipt times. Classify addresses as personal D16, entry IDs/event keys as pseudonymous D16 (excluded from export), reason/source/times as subject-linked D16 metadata; export suppression reason/source/times in verified address scope, exclude internal keys and repeated address. Register every column in the privacy inventory.
- **Erasure decision pending legal review (non-blocking for implementation):** default to deleting suppression and linked-by-address receipts when a verified address subject is erased; an unverified account deletion cannot clear a global address block (ADR 0035). No customer FK cascade that bypasses this scope. Keep active suppression until authorized removal or scoped erasure; receipt retention is independent of outbox retention. Whether a minimal keyed-hash block should instead survive customer erasure for legitimate interests, and for how long, is an explicit owner/legal open item, not an assumed exemption. Deletion can permit future mail and a later valid event can recreate suppression; document this tradeoff in the privacy guide.
- **Sender gate:** query shared Postgres before each provider attempt, including every fallback, job 9, immediate auth, admin test and resend; check before pacing admission and again on a deferred/new attempt. A lookup failure defers without sending. Suppressed unpinned mail becomes terminal `failed` / `suppressed`; pinned mail becomes `unknown` / `suppressed` under section 3.3's precedence rule. No auth exemption: a hard bounce or complaint remains unsafe for reset/verification/password-change mail; keep public auth responses and token rules unchanged to avoid enumeration. No automatic resend on removal. Preserve ADR 0055's no-DB-between-final-slot-and-call invariant: feedback arriving after admission cannot recall that already admitted/in-flight send; test and disclose this race.
- **Admin/audit:** `GET /admin/email/suppressions` (bounded limit/offset list) and `DELETE /admin/email/suppressions/{id}` (opaque UUID, CSRF, confirmation), both `email.manage`; masked address with existing authorized reveal pattern, reason/source/times, uk/en states. Removal and its `email_suppression.removed` audit entry commit together (actor/entry IDs, action/time only). Keep receipts after manual removal to prevent a duplicate from recreating it; a genuinely new event can suppress again. No address in query/path, logs, errors or audit payloads; remote blocklists remain untouched (ADR 0033/0035).
- **Configuration and readiness:** plugin-owned `RESEND_WEBHOOK_SECRET` (valid `whsec_` signing secret) and `BREVO_WEBHOOK_SECRET` (dedicated bearer token, at least 32 random bytes encoded header-safely), blank examples only. Single-provider operation can omit webhook credentials with its route disabled; the local sender check remains active. With a nonempty fallback list, **every** selected provider needs valid webhook credentials and a registered verifier/route; test fixtures supply equivalent fake verifiers/secrets. “List in place” means step-1b schema/journal + guard + handlers + secrets pass the local bootstrap checks in 4.1, not that the table has rows. Bootstrap resolves the mandatory suppression service and provider handlers, checks the step-1b journal version, reads required columns with a zero-row query and checks the app role's required SELECT/INSERT/UPDATE/DELETE privileges without writing. Startup never migrates or calls a provider. It cannot prove remote subscription, matching token, reachability or historical completeness: before production fallback the operator configures/tests both subscriptions and reconciles existing remote suppressions; record that evidence separately.
- **Routing separation:** webhook ingestion only adds/updates suppression; it never marks mail delivered, unpins, changes a route/cooldown or extends Brevo's 30-minute idempotency window. Lack of feedback is not non-acceptance. A suppression blocks all providers even while pinned; it does not authorize a switch. Docs, fake matrix coverage and implementation files are listed in sections 6–7.

## 8. Risks

- Free quotas and provider terms can change; Brevo can queue accepted mail beyond Fluxkit's deadline. Two free tiers do not provide an inbox-delivery SLA.
- Brevo's short dedupe window and duplicate-error semantics reduce safe retry opportunities. Safety stops can leave mail `unknown`; retrying later anyway can duplicate. Neither a custom header nor logs prove exactly-once delivery.
- Hidden earlier acceptance is the primary failover hazard: crash-safe intent, sticky pin, conservative legacy backfill and fenced atomic completion are mandatory, even when they reduce availability.
- Provider ID widening is a step-1 schema change discovered from actual API format. Rollback may be refused by retained IDs; no lossy conversion is allowed.
- Shared cooldowns prevent repeated known failures, not already admitted calls or consumption by another application. Recovery-probe correctness and job fairness need multi-instance tests.
- Step 1b is mandatory: missing/delayed webhook events or unreconciled historical remote blocks can still leave gaps; startup only proves local readiness. Suppression arriving after send admission cannot recall it. Auth suppression can prevent recovery email; removal needs authorized review, not fallback. Brevo bearer auth has no body-signature guarantee; protect the token and optionally restrict source IPs. Receipt/event-age windows trade replay protection against late-event reconciliation.
- Suppression addresses/receipts are personal data. Erasure defaults to deleting in verified address scope; retention after deletion on legitimate-interest grounds remains an owner/legal open item, non-blocking for implementation. Free-plan branding and queue limitations are accepted (decision 2); client setup docs must disclose the paid-plan requirement for removing branding.
- More processors receive sensitive rendered mail, including bearer links. EU database hosting alone does not settle DPA/transfer/retention questions; provider logs may retain content beyond local deletion.
- Old and new senders must not overlap during routing-state cutover. No automatic rollback may discard active pins or attempt evidence.
