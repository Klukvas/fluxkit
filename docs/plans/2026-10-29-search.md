## Goal
A shopper types a query in the storefront (Ukrainian or English, with typos, inflected word forms, Latin or Cyrillic brand names) and gets relevant products, each once, with facets to narrow the result by brand, category, price, availability, option values (size, colour) and filterable attributes, and sort by relevance, newest or price. Filters on variant data apply to the SAME variant (ADR 0005). The index is derived from Postgres, never the source of truth: it is fed reliably from the database (no lost updates after a crash), can be rebuilt with zero downtime, and never contains internal or non-public data. With search off or Meilisearch down, the shop still works (catalog browsing through today's SQL listing) and says clearly that search is unavailable.

## Scope (proposed v1; the owner fixes it with questions 1 to 5)
**In v1:**
- Spike S1 (before the ADR): measure the Ukrainian stemmer and the facet strategy on Meilisearch v1.55.0 with an extended corpus; record the evidence that closes the two ADR 0005 decisions.
- Core pure rules `packages/core/src/search/`: search document builder (variant documents per locale, public data only), index settings derivation and its hash, safe filter expression builder from typed facet selections, query normalization (and stemming, question 1), facet result rules, sort mapping.
- Indexing: a dedicated coalescing queue table written in the same transaction as every catalog, price and stock change that can alter a search document; incremental sync job; full rebuild job with index swap (zero downtime); `pnpm search:reindex`.
- Store API: `GET /store/search` (query, facets, filters, sort, pages) and `GET /store/search/suggest` (autocomplete, products only); `search` flag in `GET /store/config`.
- Admin API and UI: search status (index, queue lag, last rebuild, last error), "Rebuild index" action, synonym groups (question 4).
- Storefront: search box with suggestions in the header, results page `/{locale}/search`, facet panel and sort on the results page and (question 3) on the catalog and category pages, with a fallback to the SQL listing.
- Configuration `SEARCH_ENABLED`, `MEILI_URL`, `MEILI_API_KEY`, `MEILI_INDEX_PREFIX`; CI matrix modes `search-on` / `search-off`.

**Later (each its own plan or step):** semantic or hybrid search (Meilisearch `embedders`), exact counts for variant-level facets computed in Postgres (question 2 option 2), admin product list title search through the index (question 13), sorting by `is_sortable` attributes, search analytics (popular and zero-result queries: privacy plan first), "did you mean", per-category facet order overrides (`category_filter` of ADR 0004, deferred by ADR 0006), customer-group prices in the index (no such table exists yet), merchandising (pinned products, boosts).

**Non-goals:** Meilisearch reachable from browsers (no search key in the storefront bundle), an SQL `ILIKE` fallback search (ADR 0004: search runs through an index), indexing orders, customers or anything not public, Meilisearch Enterprise Edition features (BUSL, `infra/docker-compose.yml` comment, `docs/dependencies.md`), a second search engine.

Moving it to a feature later would need an extension point on the catalog writers (question 5 lists it).

### 2. Index design
**One index per locale** (question 9): `<MEILI_INDEX_PREFIX>catalog_<locale>` is the LIVE uid, held in `search_index_state`; a rebuild writes `<prefix>catalog_<locale>_<yyyymmddhhmmss>` and swaps (M7). Per-locale indexes keep ranking, typo settings, stop words, synonyms and stemming per language; texts are resolved with the catalog's fallback (requested locale, then `DEFAULT_LOCALE`, then the first) when the document is built, so an `en` document of a product without English text carries the Ukrainian text (and its Ukrainian stems).

**One document per sellable variant** (ADR 0005, AGENTS.md 2.3), primary key `id` = variant id. A product with no sellable variant (not `active`, or no active variant priced in `SHOP_CURRENCY`) has no documents. Fields (all PUBLIC data; built only through `isPublicAttribute` and the flags):
| Field | Content | Settings |
|---|---|---|
| `id`, `productId` | variant id, product id | `productId` filterable (needed by `distinct`, M1) and used for deletes |
| `title`, `brandName`, `sku`, `optionLabels[]`, `categoryNames[]`, `attributeText[]`, `description` | product title, brand name, variant SKU (public in the store detail), localized labels of the variant's option values, names of the product's visible categories, text of public attributes with `is_searchable` (select labels, multiselect labels, text values, numbers with unit), description cut to 2 000 characters | searchable in this order (title first, description last) |
| `stems[]` | stemmed tokens of the searchable text (question 1; absent when stemming is off) | searchable, after `attributeText`; excluded from typo tolerance (`disableOnAttributes`) to avoid fuzzy matches on stems |
| `brand` | brand slug or absent | filterable, product-level facet |
| `categories[]` | ids of the product's categories AND their ancestors | filterable, product-level facet; the API shows only visible categories |
| `opt_<optionCode>` | the variant's option value code | filterable, variant-level facet |
| `attr_<attributeCode>` | public `is_filterable` attribute value of its level: select code, multiselect codes, boolean, number | filterable; facet level = the attribute's level in the product type |
| `price` | variant price in `SHOP_CURRENCY`, minor units | filterable (range) and sortable |
| `inStock` | `availabilityOf(...) !== "out_of_stock"` at build time | filterable, variant-level facet |
| `publishedAt` | product `published_at` as epoch seconds | sortable ("newest") |
| `productSlug` | for suggestions only (the title is the searchable `title`; step 3 dropped the duplicate `productTitle`) | displayed |
`displayedAttributes`: `id`, `productId`, `productSlug`, `title` (nothing else is ever returned by Meilisearch, defence in depth). Codes are safe as field names (`^[a-z][a-z0-9_]{0,63}$`). Labels are not stored for facets: facet values are codes, the API resolves labels from the definitions per request (a label change needs no reindex).

**Not in the index:** internal or hidden attributes, barcodes, quantities (`on_hand`, `reserved`), cost data, draft or archived products, inactive or unpriced variants, prices in other currencies, compare-at prices (shown from Postgres), media.

**Settings** are DERIVED from the definitions (core `deriveIndexSettings`): `filterableAttributes` = fixed fields + `opt_*` of every option used by a product type + `attr_*` of every public `is_filterable` attribute; `sortableAttributes` = `price`, `publishedAt`; `searchableAttributes` as above; `rankingRules` default with `sort` kept; `typoTolerance` default plus `disableOnAttributes: ["sku", "stems"]` and `disableOnNumbers: true` (SKUs and sizes must match exactly); `faceting.maxValuesPerFacet` 100; `pagination.maxTotalHits` 10 000 (= `CATALOG_LIMITS.maxOffset`); `synonyms` from the synonym groups of the locale (question 4); `stopWords` none in v1 (a Ukrainian list exists in Snowball; S1 decides); `localizedAttributes` `[{attributePatterns: ["*"], locales: ["ukr"]}]` on the `uk` index (`eng` on `en`) because it is harmless and correct, not because it helps (M5); no `distinctAttribute` setting (M2). The hash of the derived settings plus `SEARCH_DOCUMENT_VERSION`, `SHOP_CURRENCY` and the locale is stored in `search_index_state`: a different hash of the filterable, sortable or synonym part updates the live index's settings in place (Meilisearch re-indexes in the background, search keeps working); a different document version or currency triggers a full rebuild.

### 3. Indexing pipeline (red zones: schema, new jobs)
**Decision (question 7): a dedicated coalescing queue `search_sync_queue`, one row per product id, written in the SAME transaction as the change.** Not `domain_event`: a catalog edit or a reservation would add one event row per write (volume), a retry calls every handler of the event (ADR 0021), and ordering is not needed because the indexer always builds documents from the CURRENT database state (a row only says "product X may be stale"). Not watermark polling of `updated_at`: Drizzle's `$onUpdate` is not set by every SQL path, a long transaction can commit an `updated_at` older than the watermark (missed change), and hard deletes leave no row.

- **Enqueue** `enqueueSearchSync(tx, productIds, reason)`: `INSERT ... ON CONFLICT (product_id) DO UPDATE SET change_seq = nextval('search_sync_seq'), next_attempt_at = least(...)`; a no-op with `SEARCH_ENABLED=false`. Called by: product create, update, status change, delete; variant create, update, activate, delete; option and option value changes of a product; product categories; media list (no: media is not indexed); prices of a product (only `SHOP_CURRENCY` rows matter, the call is unconditional for simplicity); stock movements and reservations (question 8). Fan-out writers enqueue every product they affect, in batches, inside their transaction: brand rename (products of the brand), category rename or move (products in the subtree), option or attribute option label change (products using it), attribute flag change (no enqueue: settings update or full rebuild, see above). Fan-out above 5 000 products enqueues nothing and marks the state `rebuild_requested` instead (one bounded write).
- **Sync** (job 12, after job 3 and before job 8 in the tick; pages of 100 product ids, at most 20 pages, 30 s budget): claim with `FOR UPDATE SKIP LOCKED` and a lease (as job 9), remember each row's `change_seq`; outside any transaction read the products' current state in batched queries (no N+1), build documents per locale with core; per locale send ONE `addDocuments` (full replacement of each document) and ONE `deleteDocuments` by filter `productId IN [...] AND id NOT IN [current variant ids]` (stale variants) or `productId IN [...]` for products that are gone or not sellable; wait for both tasks (M8) up to 20 s; then delete the queue row `WHERE product_id = $1 AND change_seq = <claimed>` (a change that arrived meanwhile keeps the row for the next run). A failed or timed-out task keeps the row with backoff (1, 2, 5, 10, 30 minutes, then hourly) and `last_error_code` (codes only, never the engine's message). Order of tasks per index is FIFO (M8), so the add-then-delete pair cannot leave a window with no document for a still-sellable product.
- **Idempotency:** documents are full and derived from current state; repeating a sync is harmless. Two instances never sync one product at the same time (claim lease). Lost answers: the row stays and is synced again.
- **Rebuild** (job 13, only when `search_index_state.rebuild_requested` or the live index is missing; resumable across ticks): create `<prefix>catalog_<locale>_<stamp>`, apply settings, page through ALL sellable products by id cursor (cursor stored in the state row), add documents in batches of 1 000 documents, wait; when complete: one `swap-indexes` request for all locales (atomic, M7), update the state row's live uid, delete the old index. **Job 12 is paused while a rebuild runs** (it leaves the queue untouched); after the swap it syncs every row that accumulated, so a change made during the build is never lost (a product read by the build before its change still has its queue row). Interrupted builds resume from the cursor; a build older than 24 h is dropped and restarted. `pnpm search:reindex` requests a rebuild and runs the jobs in the foreground (for seeds and operators).
- **First start:** with search enabled and no live index, job 13 builds one; until it swaps, `GET /store/search` answers `503 search_unavailable` (the storefront falls back, section 9).
- **Seeds:** `pnpm seed` writes through the repositories, so it enqueues; `seeds/README.md` documents `pnpm search:reindex` after seeding; demo synonym groups (question 4) are seeded (generic Ukrainian examples such as `викрутка`/`відвертка`, `футболка`/`футболки`; no client data).

### 5. Ukrainian morphology (ADR 0005 decision 1; question 1)
**Recommended:** stem on both sides with the Snowball Ukrainian stemmer (BSD-3-Clause, M13), behind a measured spike:
- Core `normalizeSearchQuery`: NFC, lower case, apostrophe variants (`'`, `ʼ`, `’`, `` ` ``) to one form (Snowball leaves them, M13; the spike showed Meilisearch already treats them alike in documents), collapse whitespace, max 200 characters, at most 10 words kept (M12).
- **Index side:** `stems[]` = Snowball stems of the searchable words of the document's locale (Ukrainian stemmer on `uk`, English Snowball on `en`); **query side:** the API sends `q` = original words, AND for the `uk` index a second query `q` = stemmed words restricted with `attributesToSearchOn: ["stems"]`; both in ONE multi-search request with `federation` and `distinct: "productId"` (M9), so an exact or typo match on the original text and a stem match both count, ranked together. If S1 shows federation cannot carry what the results need (facets, `totalHits` with distinct), the fallback is a single query whose words are the stems, searching `stems` plus `title`, `sku`, `brandName` (prefix matching keeps `футб` working). S1 picks one and records why.
- **Code:** the Snowball-generated JavaScript for Ukrainian and English vendored under `packages/core/src/search/stemmers/` with its BSD-3 notice (a red-zone dependency decision: third-party code, AGENTS.md section 14; pure functions, no I/O). If no generated JavaScript of the Ukrainian algorithm is published, S1 records it and the fallback is question 1 option 2.
- **Synonyms** (question 4) cover what stemming cannot: different words (`викрутка`/`відвертка`) and Russian queries (`рубашка` -> `сорочка`). No Russian stemming in v1.
- **Measured acceptance (S1):** every query of the ADR 0005 failing list (`сорочці`, `книзі`, `ноги`/`нозі`, `рукавиці`, `зимовий`, `класичний чоловічий`) finds its product; every query the spike already finds still finds it (no regression: typos, prefixes, apostrophes, Latin brands); on a corpus of at least 300 product titles across five niches (`seeds/` presets plus invented generic titles, no client data) and 100 queries with expected products, recall improves and precision at 10 drops by at most 5 percentage points against typo tolerance alone. Numbers recorded in the ADR. If the bar is not met: option 2.

### 6. Facets and variant-level counts (ADR 0005 decision 2; question 2)
**Recommended: exact product counts for product-level facets; variant-level facets show their values WITHOUT counts.**
- **Hits query:** `q`, all filters, `distinct: "productId"`, the chosen sort, `page`/`hitsPerPage` (exhaustive totals, M3). Filters on variant fields apply to the same variant document (ADR 0005), so `opt_size = m AND price < 300000` never matches a product whose M variant is dearer. With sort `price:asc` the representative is the cheapest matching variant.
- **Product-level facets** (`brand`, `categories`, `attr_*` of product level): `facets` on a query WITH distinct; every variant of a product carries the same value, so the count is the number of products (spike: brand counts exact). Disjunctive behaviour (other values of a facet stay visible while one is selected): one extra query per selected group without that group's filter, with `page: 1, hitsPerPage: 0` (S1: with distinct the counts are exact only on the exhaustive `page`/`hitsPerPage` path; `limit: 0` counts variants).
- **Variant-level facets** (`opt_*`, `attr_*` of variant level, `inStock`): values from a query WITHOUT distinct (`limit: 0` is right here, it is the cheap path, about 3 ms), so every value some matching variant has is listed (the distinct query loses them, M2); counts there are per variant, not per product, so the API returns `count: null` and the storefront shows no number. Disjunctive per selected group as above.
- **Price:** `facetStats` of `price` for the range control (min, max of matching variants).
- All queries go in ONE `POST /multi-search` (M9): at most 2 + number of selected groups queries (changed by ADR 0036: one request per pass only when the text is one query; with several text queries one federation per planned query, see "Review fixes" F3); the API caps selected groups at 8 (`400` above). The facets asked for are all filterable fields of the settings; the engine returns only values with matches, so a facet with no value in the result is dropped by the API; at most 20 facets are returned, in the order of the definitions' positions (per-category order is a later plan).
- Only values the shopper can reach are listed: a value whose only variants are not sellable has no document (consistent with ADR 0007).
- Option 2 (exact variant counts) is a later plan: count products per value in Postgres over the matching product ids, bounded by `maxTotalHits`.

### 8. API surface (red zone: public contract; exact shapes in ADR 0034 and `docs/api/search.md` at build time)
| Route | Auth | Purpose |
|---|---|---|
| `GET /store/search?q&locale&f=<facet>:<value>&price=<min>..<max>&sort&page&limit` | public; rate limited per address for browser calls (window `search`, 120 per minute; 60 since ADR 0036) | products for a query (empty `q` = browse with facets), facets, totals |
| `GET /store/search/suggest?q&locale` | public, window `searchSuggest` 120 per minute | at most 6 `{slug, title}` from the index (titles are public); `q` at least 2 characters |
| `GET /store/config`, `GET /admin/config` | as today | + `search` (additive) |
| `GET /admin/search/status` | `catalog.read` (question 12) | per locale: live uid, documents, built at, settings fresh; queue depth, oldest due, top error codes; rebuild progress; engine reachable (one `GET /health` with a 2 s limit) |
| `POST /admin/search/rebuild` | `catalog.write` | request a rebuild (`202`); idempotent while one runs |
| `GET/POST /admin/search/synonyms`, `PATCH/DELETE /admin/search/synonyms/{id}` | `catalog.read` / `catalog.write` | synonym groups (question 4) |
- **Query validation (strict):** `q` NFC, at most 200 characters, no control characters; `f` repeated, each `<facetKey>:<valueCode>` where `facetKey` is `brand`, `category`, `inStock`, `opt.<code>` or `attr.<code>` and the value matches the slug, uuid, boolean or option code pattern of its kind, at most 50 `f` values and 8 groups; `price` two integers `0..MAX_AMOUNT`; `sort` in `relevance` (default with `q`), `newest` (default without `q`), `price_asc`, `price_desc`; `page` 1 to 417 and `limit` 1 to 48 (default 24) so `page * limit <= 10 000`. Unknown facet keys answer `400` (no silent ignore). The Meilisearch filter string is built ONLY by core `buildSearchFilter` from these typed values, every value quoted and escaped (no filter injection), never from client text.
- **Response:** `{items: StoreProductListItem[], total, page, pageCount, facets: [{key, kind, level, label, counted, values: [{code, label, count | null, selected}]}], price: {min, max} | null, query: {normalized}}`. **Items are hydrated from Postgres** (question 10): the API takes the product ids in hit order and builds each item with the existing list item code (`StoreService` path: sellable rule, `pickSellablePrice`, `availabilityOf`, media), dropping ids that are no longer sellable (a stale index never shows a stale price, a draft or a deleted product; a dropped id is enqueued for sync). The page may then hold fewer items than `limit`; `total` is the engine's (documented as approximate by at most the number of stale products).
- **Errors:** `503 search_unavailable` (engine unreachable, timeout of 2 s, no live index yet) with `Retry-After: 30`, logged with a code; `400` validation as today; `404` when off. New problem code `search_unavailable` (minor contract change).
- **Caching:** `Cache-Control: no-store` for suggest; `public, max-age=30` for search without personal data (decided in ADR 0034 together with the storefront's data cache).

### 11. Security and privacy
- **Public data only, decided in one place:** core `buildSearchDocuments` uses `isPublicAttribute` plus `is_searchable` / `is_filterable`; the database CHECK already forbids internal attributes with those flags. Tests: a document built from a product with an internal attribute whose value is a unique marker string; the marker must appear in no document, in no settings, in no search, suggest or facet response (string scan of the JSON), checked for both levels and both locales; a mutation that drops `isPublicAttribute` must fail.
- **Engine never public:** Compose binds `127.0.0.1` (exists); deployment notes: a private network only, `MEILI_ENV=production` (master key of at least 16 bytes, M10), no port on the edge proxy. The browser never receives a Meilisearch key or URL; all search goes through `/store/search*`.
- **Keys (question 6):** the API holds `MEILI_API_KEY`, a key with actions `search`, `documents.add`, `documents.delete`, `indexes.create`, `indexes.delete`, `indexes.swap`, `settings.update`, `settings.get`, `tasks.get`, `stats.get` on `<prefix>*` (M10, index pattern LIKELY), created once by the operator with the master key (`README.md` gives the `curl` command); the master key stays in the engine's environment and the tests. A leaked API key can rewrite the index but not other indexes or keys.
- **Filter injection:** filters only from typed values through core (section 8); a spec feeds hostile values (`"`, ``, ` OR `, `)`, NUL) and asserts `400` or a quoted literal.
- **Abuse:** rate limits on the browser-called routes; `q` and facet caps; the engine's `searchCutoffMs` 1 500 ms default and our 2 s client timeout; server-rendered search pages share the HANDOFF launch blocker (reads from the Next server are not limited per shopper).
- **Logs:** query text is personal-ish data: not logged (only length, facet keys, duration, hit count, error codes).

### 12. Failure handling
| Situation | Behaviour |
|---|---|
| Engine down or slow at search time | `503 search_unavailable` after at most 2 s; results page shows the message; catalog and category pages fall back to the SQL listing |
| Engine down during sync | queue rows stay with backoff; admin status shows the lag and the code; one error log per process and code |
| Engine data lost (volume wiped) | live index missing -> job 13 rebuilds; meanwhile `503` and the fallback |
| Task failed (document refused) | row kept with `last_error_code`; after 10 attempts it waits hourly; error log with the product id |
| Crash between claim and result | lease expires (2 minutes), another run syncs again (idempotent) |
| Change during a rebuild | job 12 paused; the queue row survives; synced after the swap |
| Stale document (index behind) | hydration drops non-sellable ids and shows current price and availability; matching may be up to one sync behind |
| Settings drift (attribute flags changed) | in-place settings update; facets of a new filterable attribute appear once the engine re-indexed |

## Risks
- **Stemming quality:** a stemmer built on Wikipedia may over-stem short product words (sizes, models) and lower precision; mitigated by the S1 bar, `stems` without typo tolerance, the original-text query ranked alongside, and the synonyms fallback.
- **Facet UX without counts** for size and colour may look unfinished to some shops; exact counts are a later plan (question 2).
- **Hot path writes:** enqueuing on reservations adds an upsert to the checkout transaction and a row lock per product; concurrent checkouts of different variants of one product serialize briefly on the queue row (measured in step 6; question 8 offers the alternative).
- **Index lag:** up to two ticks; a sold-out product may still match "in stock" until the sync; hydration shows the truth.
- **Engine operations:** memory and disk for large catalogs are not measured; a wiped volume means minutes of `503` until the rebuild (fallback keeps browsing alive).
- **Contract growth:** many new public shapes (search response, facet keys `opt.<code>` / `attr.<code>`, problem code, config flag); renaming an attribute or option code changes facet keys in URLs (shared links break).
- **Vendored third-party code** in core (stemmer): license notice, updates by hand; the dependency policy needs the owner's approval.
- **Meilisearch UNKNOWNs** (M2 switch-off, M3 totals with distinct, M7 `rename`, M8 task retention, M10 index patterns, M13 stemmer availability) may change details; S1 closes what it can.

## Open questions (owner quiz; recommended option first; ordered by importance)

1. **[OWNER] Ukrainian morphology (ADR 0005 decision 1)?**
   - **(Recommended) Snowball Ukrainian stemmer on both sides (vendored, BSD-3), accepted only if spike S1 meets the section 5 bar; plus synonym groups for different words and Russian queries; typo tolerance stays.** Fixes the measured failures (`сорочці`, `зимовий`, `класичний чоловічий`) with no new service; a fallback is defined if S1 fails.
   - Synonyms and word-form lists only (admin-managed), typo tolerance otherwise. No third-party code; coverage depends on manual lists, inflected adjectives keep failing.
   - A different engine with a Ukrainian analyzer (OpenSearch, Apache-2.0). Real morphology; replaces the decided stack (ADR 0002), heavier operations, a new ADR and CI service.
2. **[OWNER] Variant-level facet counts (ADR 0005 decision 2)?**
   - **(Recommended) Exact product counts for product-level facets (brand, category, product attributes); variant-level facets (size, colour, variant attributes, in stock) list their values without counts.** Correct filtering and complete value lists; no misleading numbers; cheap.
   - Exact counts for every facet computed in Postgres per request over the matching products. Best UX; a heavy query per facet request, bounded by `maxTotalHits`, its own plan.
   - Approximate counts: a second product-level index with value arrays for counting (ADR 0005 option a). Numbers everywhere; double indexing, counts that can disagree with the result.
3. **[OWNER] Where do facets appear in v1?**
   - **(Recommended) Search results page AND catalog/category pages (through `GET /store/search` with the category filter), falling back to today's SQL listing when search is unavailable or off.** Shops expect filters on category pages; the fallback keeps browsing alive.
   - Search results page only; category pages unchanged. Smaller; category pages stay without filters.
   - Replace `GET /store/products` with the index everywhere. One path; browsing dies with the engine.
4. **[OWNER] Synonyms in v1?**
   - **(Recommended) Admin-editable synonym groups per locale (one table, three routes, an editor), demo groups in seeds.** Covers `викрутка`/`відвертка` and Russian queries without a deploy.
   - A JSON file in the repository per shop fork. No table or UI; every change is a deploy.
   - None in v1. Smallest; Russian queries find nothing.
5. **`SEARCH_ENABLED` default?**
   - **(Recommended) `false` in code, `true` in `.env.example` and the e2e environment.** Existing deployments behave as today until the operator creates the scoped key; a fresh template has search on.
   - `true` by default (search is part of the stack). Every deployment needs the engine and a key at once.
   - A feature package with `FEATURES_ENABLED=search` and a catalog extension point. Matches section 2.1 literally; needs a new extension point on the core writers.
6. **Meilisearch keys?**
   - **(Recommended) One `MEILI_API_KEY` scoped to `<prefix>*` with the actions the API needs, created by the operator with the master key; the master key never in the API.** Least privilege for a single server-side client.
   - Two keys (a search-only key for store routes, an indexing key for jobs). Narrower blast radius per path; one more secret.
   - The master key in the API. Simplest; a leak gives full control of the engine and its keys.
7. **Indexing feed?**
   - **(Recommended) Dedicated coalescing queue table written in the same transaction (section 3).** Reliable, deduplicated per product, no unrelated retries.
   - Domain events `catalog.product_changed` through `domain_event`. Reuses the outbox; a row per write, retries call all handlers, high volume from reservations.
   - Watermark polling of `updated_at`. No writes in hot paths; misses long transactions and hard deletes, needs a nightly full reconcile.
8. **Stock in the index?**
   - **(Recommended) `inStock` per variant, refreshed by enqueuing on stock movements and reservations.** "In stock only" filter works within one sync.
   - `inStock` refreshed only by an hourly availability sweep (no enqueue in checkout). No hot-path write; up to an hour stale.
   - No stock in the index (no "in stock" filter). Simplest; a common filter missing.
9. **Index layout?**
   - **(Recommended) One index per locale with per-locale text and stems.** Language settings per index; simple queries.
   - One index with fields per locale (`title_uk`, `title_en`) and `attributesToSearchOn`. Half the documents; shared synonyms and typo settings across languages.
   - Index the default locale only. Least work; English shoppers search Ukrainian text.
10. **Where do result items come from?**
    - **(Recommended) Hydrated from Postgres by product id (existing list item code).** Prices, availability and visibility are never stale; one batched read per page.
    - Rendered from the index documents. Faster; stale prices possible until the sync.
    - Hydrate only price and availability. Middle ground; two shapes to keep in step.
11. **Autocomplete?**
    - **(Recommended) Product suggestions (title, link), up to 6, from the index.** Common and cheap.
    - Products and categories and popular queries. Richer; needs query logging (privacy plan first).
    - None in v1. The box just submits.
12. **Admin permissions?**

    - New `search.manage` for owner and manager. Separate right; one more permission in the role table.
    - Owner only (`users.manage`). Strict; managers cannot rebuild.
13. **Admin product list title search through the index?**

    - In v1 through the public index. Finds only live products; confusing for editors.
    - Never; a Postgres trigram index instead. Needs `pg_trgm` and a migration.
14. **Sort options in v1?**
