## Goal
An admin with `catalog.write` uploads image files from the Media tab of the product editor and from the brand form. The API checks each file by its content, re-encodes it (recommended, open question 1), stores it through a storage abstraction (local disk first) under a random name, and answers with a URL that the existing `PUT /admin/products/{id}/media` and brand `logoUrl` accept unchanged. Uploaded files are served with headers that can never run script. URL-based media keeps working exactly as today; the public store API's `media[].url` and `image.url` keep their shape.

## Scope
**In v1 (proposed):** upload of product images and brand logos (one file per request, several files one after the other from the UI); content sniffing with an allow-list; size, dimension and pixel limits; metadata stripping (by re-encoding, open question 1); a storage port with a local-disk driver; a public read route for the files; an additive `media_upload` table for metadata and orphan cleanup (open question 6); a scheduler job that deletes abandoned uploads; admin UI controls (file picker, drop zone, per-file status, alt text through the existing media rows); config variables; docs; tests.

**Non-goals (each a later plan if wanted):** a media library screen (browse, search, reuse uploads); video, PDF or any non-image file; editing, cropping, focal points; responsive variants generated by us (the storefront's Next optimizer resizes on request already); CDN integration and signed URLs; the S3-compatible driver (designed for, not built); background processing through a queue (uploads are processed in the request; the files are small and bounded); virus scanning (images are re-encoded and never executed; a scanner is out of scope and listed under Risks); server-side fetching of a URL ("import from URL" would be SSRF surface: not in v1); deleting files that were ever attached to a product or brand (see Deletion); per-user storage quotas; a seed with real image files (template cleanliness: AGENTS.md section 15).

## Existing functionality found (verified 2026-10-23 on `origin/main` at `54cd837`)

### Data model and API
- **`media` table** (ADR 0006 section 2, `apps/api/src/database/schema/catalog.ts` line 490): `product_id` (CASCADE), `option_id`/`option_value_id` (both or none, FK RESTRICT to `product_option_value`), `url text NOT NULL` (max 2048), `alt` i18n map NULL (max 255 per locale), `position`. **Per-image alt text already exists** for product media; brands have no logo alt (the brand name serves).
- **`brand.logo_url`** text NULL (max 2048).
- **`order_item.image_url`** (`apps/api/src/database/schema/orders.ts` line 210): the checkout copies the product image URL into the order snapshot (`docs/api/orders.md`). A file referenced there must survive product edits and deletes, or order history shows broken images.
- **`PUT /admin/products/{id}/media`** (`docs/api/catalog.md`): replaces the list, items `{url, alt?, position?, optionId?, optionValueId?}`, max 100 (`MAX_MEDIA_PER_PRODUCT`). `url` is `z.url({protocol: /^https?$/})`, max `TEXT_LIMITS.url`, database-safe text (`products.schemas.ts` line 36). Brand `logoUrl` is validated the same way (`brands.schemas.ts` line 26).
- **Store API**: `GET /store/products` returns `image: {url, alt} | null`; `GET /store/products/{slug}` returns `media[] {url, alt, optionValueId}` filtered by ADR 0007. `docs/contracts/api.md` makes the shapes contract; the URL is a plain string today (always absolute http(s) because the admin validation demands it).
- **Admin config**: `GET /admin/config` (`apps/api/src/admin-config/`) returns `{defaultLocale, locales, shopCurrency, currencyExponent, supportedCurrencies, pricesIncludeTax, lowStockThreshold}` "and nothing else"; adding fields is additive (minor).
- **Permissions**: catalog routes need `catalog.write` for every non-GET method (`docs/contracts/api.md`, route to permission); manager and owner hold it, viewer does not.

### Request handling, CSRF, limits
- **Body parsing**: Nest's Express adapter registers only `express.json` and `express.urlencoded` with the default 100 KB limit (`@nestjs/platform-express` 12.1.3 `registerParserMiddleware`, read in `node_modules`). A body of any other content type is not consumed by a parser: a handler can stream it. The 100 KB JSON limit (`413` before any guard, `apps/api/src/common/request-body.spec.ts`) is unaffected by a binary route.
- **CSRF** (`apps/api/src/auth/csrf.ts`, ADR 0009, `docs/contracts/api.md` "CSRF header"): every non-GET/HEAD/OPTIONS request under `/admin` needs `X-Fluxkit-CSRF: 1` **and, with a body, `Content-Type: application/json`, else `403`**. Today **no binary or multipart body can reach any admin route**. An upload route therefore needs a deliberate, route-scoped change of this rule: an auth change and a public contract change (red zone).
- **Order of checks**: the global `AdminPathGuard` (CSRF, `401`, `403`) runs before route guards and before the handler, so an unauthenticated or unauthorized upload is refused before a byte of its body is read by us.
- **Rate limits** (`apps/api/src/rate-limit/`): named in-memory windows per client address (`RATE_LIMITS`: login, registration, checkout, orderLookup, guestCancel, cartWrite), `@RateLimit(name)`, `429` with `Retry-After`, single process. No limit is keyed by admin user yet.
- **Problem model** (`apps/api/src/common/problem.filter.ts`): `application/problem+json`; `413` keeps its status with `code: validation_failed`.

### Plugins, ports, jobs, features
- **Ports pattern** (ADR 0018, `docs/contracts/events.md`): interfaces and string tokens live in `@fluxkit/core` (types and constants only, still pure); implementations live in `apps/api` and are injected by token; plugins never import `apps/api`. `packages/providers/` exists with a README only (no provider yet).
- **Boundaries** (`.dependency-cruiser.cjs`): `core-must-not-import-infrastructure` (no Nest, Drizzle, pg, ioredis, bullmq, meilisearch in core), `packages-must-not-import-apps`, `apps-must-not-import-each-other`, `no-deep-imports-into-packages`. Node built-ins such as `node:fs` are not on the core list, but core is "pure TypeScript: no I/O" by convention (`docs/HANDOFF.md`).
- **Feature loader** (`docs/contracts/config.md`): `FEATURES_ENABLED`, a feature exports `featureModule`; a feature's admin routes are default-denied until it declares a permission. Core = catalog, cart, checkout, orders, customers, admin basics.
- **Scheduler** (`docs/api/jobs.md`, ADR 0021, 0025): one in-process timer under a Postgres advisory lock (one instance works per tick), six bounded jobs, `pnpm jobs:run-once`. A new bounded delete job fits the pattern of `delete-expired-carts.job.ts`.

### Config, storefront, admin, proxies
- **`packages/config`**: `loadEnv` (API), `loadStorefrontEnv`; no media variables. `STOREFRONT_IMAGE_HOSTS` (host names only) feeds the storefront CSP `img-src` and `images.remotePatterns` (`https` only).
- **Storefront images**: `apps/storefront/src/lib/image-source.ts` `allowedImageUrl` passes only **absolute `https` URLs on an allowed host** (no port, no credentials) to `next/image`; anything else renders the placeholder. The optimizer serves `/_next/image?url=...`.

- **Storefront CSP** (`apps/storefront/next.config.ts`): `img-src 'self' data: https://<STOREFRONT_IMAGE_HOSTS>`. Storefront routes all live under `/[locale]/...`; there is no `/media` route.

Media tab: `src/areas/products/tabs/media-tab.tsx` with the pure list model `media-list.ts` (`MAX_MEDIA = 100`, `ALT_MAX_LENGTH = 255`, `safeHttpUrl` previews). Brand logo: `src/areas/catalog-dictionaries/brand-form-view.tsx`, `dictionary-forms.ts`. Writes are single-flight (`createFormWriter`, step 13 L1), never retried, a lost answer is "result unknown".
- **`@fluxkit/api-client`** (`packages/api-client/src/request.ts`): `buildRequest` always serializes `body` as JSON and sets `Content-Type: application/json`; there is no binary body. `fetch` gives no upload progress in browsers.
- **Proxies**: `apps/admin/e2e/proxy.ts` routes `^/(store|admin)(/|\?|$)` to the API, `/admin-ui` to the SPA, anything else `404`; `apps/storefront/e2e/proxy.ts` routes `/store`, `/admin` to the API and the rest to Next. README "Example edge proxy" (Caddy, nginx; untested here). **nginx's default `client_max_body_size` is 1 MB** (nginx documentation; the README example does not set it), so uploads through that example would fail with `413` from nginx.
- **Compose** (`infra/docker-compose.yml`): Postgres, Redis, Meilisearch only; no API image, no app volume.

## Proposal

### 1. Architecture and boundaries
| Piece | Where | Why there |
|---|---|---|

`MediaStoragePort` (proposed, internal until listed in `docs/contracts/`; becomes contract when the first external driver exists):
```ts
interface MediaStoragePort {
  /** Moves a finished, validated local temp file to its final place under `key`; atomic; never overwrites. */
  put(key: MediaKey, sourcePath: string, contentType: AllowedImageType): Promise<void>;
  /** Readable stream and size, or undefined when absent. Only the read route uses it (local driver). */
  open(key: MediaKey): Promise<{ stream: Readable; byteSize: number } | undefined>;
  /** Idempotent: an absent key is success. */
  delete(key: MediaKey): Promise<void>;
}
```
`open` uses Node stream types, so the interface lives in core as a type only (`import type`), like the event handler types. The S3 driver later serves files from the bucket or CDN URL (then `MEDIA_PUBLIC_BASE_URL` points there and the API read route is unused).

Driver selection: `MEDIA_STORAGE_DRIVER` with `local` (and `none`, open question 9). An unknown value (for example `s3` before that plugin exists) fails startup loudly instead of silently writing to the local disk.

### 2. Storage: local-disk driver
- **Key**: `<32 lowercase hex>.<ext>` = 128 random bits from `node:crypto` `randomBytes(16)` plus the extension of the OUTPUT type (`jpg`, `png`, `webp`). No user input reaches the key or the path: the original file name is never read, stored or echoed (no stored XSS or traversal through names).
- **Layout**: `MEDIA_DIR/<first 2 hex>/<next 2 hex>/<key>` (65 536 directories at most; keeps directory sizes small). The path is built only from a key that passed `isMediaKey` (`^[0-9a-f]{32}\.(jpg|png|webp)$`), then checked to stay inside `MEDIA_DIR` after `path.resolve` (defence in depth, tested with `..`, `/`, `%2f`, NUL, upper case).
- **Atomic write**: the request body streams into `MEDIA_DIR/.tmp/<random>` (`open` with `wx`, mode `0640`), the byte counter aborts at the limit; the re-encoded output goes to a second temp file; `fsync`, then `rename` into the final path (same file system, so atomic; `link`+`unlink` or an existence check first so a key is never overwritten), then the database row is inserted. If the insert fails the file is unlinked. Temp files are unlinked in `finally`; on start the driver deletes `.tmp` entries older than one hour.
- **Crash window**: a crash between `rename` and the row insert leaves a file without a row. It is invisible (nobody knows its key) and harmless; a later `pnpm media:verify` (not in v1) could list such files. Recorded as a known limit.
- **Directory permissions**: `MEDIA_DIR` owned by the API's user, `0750`; files `0640`; never executable; the API refuses to start when `MEDIA_DIR` is not an absolute path, does not exist or is not writable (checked once at start with a probe file).
- **Several API instances**: the local driver needs ONE instance or a shared volume (all instances see the same `MEDIA_DIR`), because the read route and the cleanup job (which runs on whichever instance holds the scheduler lock) must see every file. Documented in README and the ADR; the S3 driver is the multi-instance answer.
- **Disk full**: `ENOSPC`/`EDQUOT` while writing answers `503` with a new problem code `storage_unavailable`, logged as an error (code only), temp files removed. Same for an unwritable directory at runtime.
- **Backups**: `MEDIA_DIR` must be backed up together with Postgres (rows and files belong together; a restore of only one side leaves broken images or invisible files). README note.

### 3. Upload endpoint (proposed contract)
`POST /admin/media/uploads` (new controller `@AdminController("media")`; permission `catalog.write` by the default pair; in `x-fluxkit-permission`).

| Item | Proposal |
|---|---|
| Body | The raw file bytes, `Content-Type: application/octet-stream` (open question 11). No file name, no form fields, no JSON. One file per request |
| CSRF | `X-Fluxkit-CSRF: 1` stays required. `assertCsrfSafe` gains ONE exception: a route that declares `@AcceptsBinaryUpload()` (route metadata read by `AdminPathGuard`) accepts exactly `application/octet-stream`; every other admin route keeps the JSON rule. `application/octet-stream` is not a CORS-safelisted content type, so it forces a preflight just like `application/json` does (the API never answers preflights with permission). Tests: the upload route refuses a missing header, `multipart/form-data`, `text/plain`, `application/x-www-form-urlencoded`, `image/jpeg`; every other admin route still refuses `application/octet-stream` (route walk) |
| Length | `Content-Length` required (`411`, `validation_failed`, reason `length_required`); `Transfer-Encoding: chunked` refused the same way. `Content-Length` above `MEDIA_MAX_BYTES` answers `413` (reason `file_too_large`) before the body is read; the stream counter enforces the limit again (a lying client is cut off at the limit + 1 byte); `0` answers `400 empty_file` |
| Sniffing | First 32 bytes against magic numbers: JPEG `FF D8 FF`; PNG `89 50 4E 47 0D 0A 1A 0A`; WebP `RIFF....WEBP`. The declared `Content-Type` and any extension are ignored. Anything else, SVG/HTML/XML/PDF/TIFF/GIF/AVIF/HEIC included, answers `400 validation_failed` reason `unsupported_type` (open questions 3, 4) |
| Decoding limits | sharp with `limitInputPixels` = `MEDIA_MAX_PIXELS`, `failOn: "warning"` (truncated or corrupt data is refused, reason `corrupt_image`), `sequentialRead`, `pages: 1`; an animated WebP (`pages > 1` in metadata) is refused (`animated_not_supported`); the format libvips reports must equal the sniffed one (else `unsupported_type`); width and height read from the header before decoding, refused above `MEDIA_MAX_DIMENSION` per side (`dimensions_too_large`) or above the pixel limit (`too_many_pixels`) |
| Re-encode (open questions 1, 2) | `.rotate()` (apply the EXIF orientation), convert to sRGB, `resize` to fit `MEDIA_OUTPUT_MAX_SIDE` without enlargement (open question 5), encode in the SAME format (JPEG quality 85 progressive, PNG lossless compression level 6, WebP quality 85; alpha kept for PNG and WebP). sharp writes no metadata unless asked (`withMetadata` is never called), so EXIF (GPS, camera serial), XMP, IPTC, comments and ICC profiles are dropped, and trailing bytes after the image (polyglots, appended archives or HTML) do not survive |
| Memory and CPU | `sharp.cache(false)`, `sharp.concurrency(1)`; at most `2` uploads processed at once per process (an in-process semaphore); a third waits up to 10 s, then `429 too_many_requests` with `Retry-After: 5`. Peak memory per upload is bounded by the pixel limit (50 MP x 4 bytes = 200 MB worst case for a non-shrinkable PNG; JPEG shrink-on-load is far less): the README states the API needs about 512 MB headroom (to be measured in step 4) |
| Rate limit | A named limit `mediaUpload`: 60 uploads per 10 minutes, keyed by the ADMIN USER id (the route is authenticated; admins in one office share an address). Needs a small internal extension of `RateLimitGuard` (a key function). Counted after the auth guard, before the body is read |
| Timeouts | Node's default `requestTimeout` (300 s) bounds a slow upload. Processing gets a 30 s budget; when it runs out the upload is refused with `400 validation_failed` reason `processing_timeout` (an input we will not process, not a server fault) and the temp files are removed. The exact budget is set in step 4 from measurements and recorded in ADR 0028 |
| Idempotency | None (owner answer 12 of the admin plan: no idempotency keys on admin writes). A lost answer leaves at most one unattached upload, which the cleanup job deletes after 24 h. The client never retries automatically |
| Response | `201` `{id, url, contentType, byteSize, width, height, createdAt}`; `url` = `MEDIA_PUBLIC_BASE_URL + "/" + key`; `contentType` and dimensions are the OUTPUT's. No `Location` header (no read route for the metadata in v1). `Cache-Control: no-store` (all `/admin`) |
| Errors | `400 validation_failed` with one `errors[] {path: "body", code}` of `empty_file`, `unsupported_type`, `corrupt_image`, `animated_not_supported`, `dimensions_too_large`, `too_many_pixels`, `processing_timeout`; `411` `length_required`; `413` `file_too_large`; `401`, `403` (CSRF, permission); `429`; `503 storage_unavailable` (new code: additive) and `503 uploads_disabled` (only with `MEDIA_STORAGE_DRIVER=none`, open question 9) |
| Logging | One info line per upload: admin id, upload id, byte size in and out, type, dimensions, duration. Never the bytes, never a client-supplied header value |

**`GET /admin/config`** gains an additive block `media: {uploadsEnabled, maxBytes, contentTypes}` so the static SPA can mirror the server's limits and hide the controls when uploads are off (public contract, additive).

**`PUT /admin/products/{id}/media` and brand `POST`/`PATCH`** (behaviour change, open question 6, option 1): in the same transaction, every URL that starts with `MEDIA_PUBLIC_BASE_URL + "/"` must name an existing `media_upload` row (`400 validation_failed`, `media.N.url` or `logoUrl`, reason `upload_not_found`), and those rows get `first_attached_at = now()` if it is null. URLs on other hosts are untouched (URL-based media keeps working). This is a tightened validation on an existing route, which `docs/contracts/api.md` calls breaking; it only affects URLs under our own media prefix that point at nothing, and the contract has had no release yet (pre-1.0), so it is recorded in `CHANGELOG.md` without a migration guide (same handling as the "publish needs a price" change).

### 4. Data model (open question 6; recommendation: option 1)
New table `media_upload` (migration `0005_media_upload.sql` plus hand-written `0005_media_upload.down.sql` that also deletes its `drizzle.__drizzle_migrations` row; up, down, up, down tested):

| Column | Type | Rule |
|---|---|---|
| `id` | uuid PK | |
| `storage_key` | text NOT NULL UNIQUE | `CHECK (storage_key ~ '^[0-9a-f]{32}\.(jpg|png|webp)$')` |
| `content_type` | text NOT NULL | `CHECK IN ('image/jpeg','image/png','image/webp')` |
| `byte_size` | integer NOT NULL | `CHECK > 0` |
| `width`, `height` | integer NOT NULL | `CHECK > 0` |
| `sha256` | text NOT NULL | hex of the stored bytes (integrity check, later dedupe; not unique: two uploads of one picture stay two rows) |
| `created_by` | uuid NULL -> `admin_user(id)` ON DELETE SET NULL | admins are never deleted today; SET NULL keeps a future delete possible |
| `created_at` | timestamptz NOT NULL default now() | |
| `first_attached_at` | timestamptz NULL | set when a product media list or a brand first references the upload |

Index: `(created_at) WHERE first_attached_at IS NULL` for the cleanup job.

Why not the alternatives (details in open question 6): keeping no table loses the creator, sizes and dimensions and makes orphan detection a scan of the whole disk against three tables (`media.url`, `brand.logo_url`, `order_item.image_url`, none indexed for it); a foreign key from `media`/`brand` to the upload row changes two catalog tables, needs "exactly one of url or upload" CHECKs and builds the public URL at read time, for no v1 benefit. `media.url` stays the single reference, so ADR 0006 and 0007 are untouched and the store API returns the same field.

**Deletion semantics (open question 12):**
- An upload never attached within 24 hours of its creation is abandoned: job 7 `delete-abandoned-uploads` (bounded like ADR 0025: pages of 100, at most 50 pages per run) runs `DELETE FROM media_upload WHERE id = ANY($page) AND first_attached_at IS NULL RETURNING storage_key`, commits, then calls `storage.delete(key)` for each (an absent file is success; other errors are logged with their code and the file is left; the row is gone, so the file is invisible). Result counts `deleted`, `truncated`, `fileErrors`.
- Race with an attaching save: the save runs `UPDATE media_upload SET first_attached_at = now() WHERE storage_key = ANY($keys) AND ... RETURNING` under the row lock; whichever transaction commits first wins: if the job deleted the row, the save finds fewer rows and answers `400 upload_not_found` (the admin uploads again). Tested with two connections.
- **An upload that was ever attached is never deleted automatically in v1**: removing it from the media list, deleting the product (draft only, cascades `media` rows) or changing a brand logo leaves the file and the row. Reasons: order snapshots (`order_item.image_url`) keep the URL forever; caches and the Next optimizer may hold it; reference counting across three tables with a free-text `url` column is error-prone. Disk growth is bounded by `catalog.write` users and the rate limit; a "purge unreferenced uploads" command that checks all three tables is a later plan.

### 5. Serving (open question 7; recommendation: option 1)
- **Route**: `GET /media/{key}` and `HEAD` in the API (new `MediaFilesController`, outside `/admin` and `/store`, public, no cookie read, no database query: the content type follows from the key's extension, which the server chose from the sniffed type). A key that fails `isMediaKey` or a missing file answers `404` with `Cache-Control: no-store` and no body echo.
- **Headers** (pinned by a test):

| Header | Value | Why |
|---|---|---|
| `Content-Type` | `image/jpeg`, `image/png` or `image/webp` from the extension | Never derived from the client |
| `X-Content-Type-Options` | `nosniff` | No MIME sniffing into HTML |
| `Content-Security-Policy` | `default-src 'none'; img-src 'self'; style-src 'unsafe-inline'; sandbox` | If a browser ever renders the response as a document, no script runs and the origin is opaque. (`img-src`/`style-src` keep the browser's own image viewer page usable; to be checked in Chromium in step 8) |
| `Content-Disposition` | `inline; filename="<key>"` | Our own name; nothing from the client |
| `Cache-Control` | `public, max-age=31536000, immutable` | A key never gets other bytes (random name, no overwrite) |
| `ETag` | the key | Revalidation is cheap |
| `Cross-Origin-Resource-Policy` | `cross-origin` | Product images are public and may be embedded by any page (a CDN or a client's other site) |
| `Referrer-Policy` | `no-referrer` | |
| `X-Frame-Options` | `DENY` | No framing of the image document |

- **URL shape**: `MEDIA_PUBLIC_BASE_URL/<key>`, for example `https://shop.example.com/media/3f2a...9c.webp`. The edge proxy routes `/media/*` of the shop host to the API (next to `/store/*` and `/admin/*`). A client may instead put a cookie-less host or a CDN in front (`MEDIA_PUBLIC_BASE_URL=https://media.shop.example.com`) without a code change; the CDN pulls from the API route.
- **Same origin as the admin**: the default puts uploads on the origin that also serves `/admin-ui/` and `/admin/*` (ADR 0027). The admin cookie (`Path=/admin`) is never sent to `/media/*`. Script execution from an upload is prevented in three independent layers: only re-encoded raster bytes are stored; the exact image type plus `nosniff`; the `sandbox` CSP. A separate media host removes the residual risk entirely and is the documented hardening option (same as the admin's own-host option).
- **Storefront**: no code change. The shop host (or the media host) goes into `STOREFRONT_IMAGE_HOSTS` (https only, already required by `allowedImageUrl`); the Next optimizer then fetches `https://<host>/media/<key>` over the network. Requirement written into the README: from the storefront server, that host must resolve to a PUBLIC address (Next 16.4.1 refuses private IPs; split-horizon DNS inside a private network breaks it). Development over `http://` shows the placeholder for uploaded images in the storefront (the storefront accepts https only); the admin preview works. Not changed: `allowedImageUrl`, the storefront CSP code.
- **Admin**: `img-src 'self'` covers `/media/*` on the same origin; a separate media host goes into the admin's `imageHosts` (proxy configuration, README). No change to `security-headers.ts` code.
- **Proxies**: the admin e2e proxy and the storefront e2e proxy route `^/media(/|$)` to the API; the Vite dev proxy adds `/media` (target `ADMIN_DEV_API_URL`, a text change of that variable's contract row); README Caddy and nginx examples add `/media/*` to the API matcher, and nginx gets `client_max_body_size` (for example `12m`) on the `/admin/` location (its default 1 MB would refuse uploads). The examples stay untested (as today).
- **Draft products** (open question 8): files are public to anyone who knows the 128-bit random URL; nobody can list them (no index route, no directory listing). An image uploaded for a draft is therefore "unlisted", not private. The store API never returns media of a draft product.

### 6. Admin UI (proposal)
- **Media tab**: an "Upload images" button (a visually hidden `<input type="file" multiple accept="image/jpeg,image/png,image/webp">` behind a labelled button: the keyboard path) and a drop zone on the list (pointer enhancement only; it calls the same handler). The URL field stays as it is.
- **Flow**: client-side checks first (type from `file.type`, size from `GET /admin/config` `media.maxBytes`, at most `MAX_MEDIA` rows minus the current ones, at most 20 files per selection), then the files are uploaded ONE AT A TIME (bounded server load, simple state). Each file shows `queued`, `uploading`, `added` or `failed` with the translated reason, plus a live-region summary ("3 of 7 uploaded"). Byte progress is not shown: `fetch` has no upload progress and a second transport (`XMLHttpRequest`) only for this is not worth it for files of at most 10 MB (assumption to confirm).
- **Each successful upload** appends a media row (`url` = the returned URL, empty alt, no option value) to the UNSAVED list; the existing whole-list `PUT /admin/products/{id}/media` saves it with alt texts and positions. The unsaved-changes guard (step 13 L4) warns before leaving; leaving anyway orphans the uploads, which the job deletes after 24 h. The editor says so in the hint text.
- **Brand form**: an "Upload logo" button next to `logoUrl`; success fills the field; the form's normal save (`POST`/`PATCH`) attaches it.
- **Lost answer** (network error, timeout of 60 s for uploads; raised to 120 s by the step 9 review, L-2): the file shows "result unknown: the file may have been stored; upload it again if needed". No automatic retry, no replay (ADR 0027 decision 5). A duplicate upload costs one orphan at most.
- **Double submit**: one upload queue per screen; the button is disabled while the queue runs; the save button is disabled while uploads are in flight (a save must not race the rows being added).
- **Errors**: the problem map and its coverage test gain `file_too_large`, `empty_file`, `unsupported_type`, `corrupt_image`, `animated_not_supported`, `dimensions_too_large`, `too_many_pixels`, `processing_timeout`, `length_required`, `upload_not_found`, `storage_unavailable`, `uploads_disabled` in `uk` and `en`; `429` shows the wait.
- **Preview**: the existing `safeHttpUrl` preview with `referrerpolicy="no-referrer"` and `loading="lazy"`; nothing new is rendered as HTML.
- **Permissions**: the controls render only with `catalog.write` (viewer sees the list read-only, as today) and only when `media.uploadsEnabled`.
- **api-client**: `createAdminClient(...).uploadMedia(file: Blob, {signal})` -> `POST /admin/media/uploads`. `buildRequest` gains a binary body variant (`rawBody: Blob` with the fixed content type `application/octet-stream`; `body` and `rawBody` are mutually exclusive; JSON stays the default); the CSRF header rule is unchanged (on every write). `ADMIN_OPERATIONS` gets the row; the contract test learns a binary request body (`requestBody.content["application/octet-stream"].schema` `{type: string, format: binary}`) and checks `x-fluxkit-permission: catalog.write` and the CSRF header parameter.

### 8. Security analysis
| Threat | Mitigation (proposed) | Residual |
|---|---|---|
| Polyglot (valid JPEG that is also HTML/JS/ZIP) | Re-encode drops everything but pixels; exact `Content-Type`, `nosniff`, `sandbox` CSP | None known with re-encode; without re-encode (Q1 option 2/3) appended data must be cut by our parser |
| SVG, HTML, XML, script content | Magic-byte allow-list rejects them before any decoder (sharp would rasterize SVG through librsvg); never served as anything but an image type | SVG logos are not supported (Q4) |
| Path traversal | Key generated by the server, regex-checked, resolved-path check; the read route validates the key; no file name read | None |
| Decompression bomb | Header dimensions checked before decode; `limitInputPixels`; `pages: 1`; animated refused; concurrency 2 | CPU of up to 2 x 30 s per process under abuse by a signed-in admin |
| EXIF privacy (GPS, serials) | Re-encode without metadata; orientation applied first | None with re-encode |
| MIME confusion / content-type spoofing | Declared type ignored; output type from the sniffed and decoded format; extension and header derived from it | None |
| Stored XSS through file name or alt | File name never read; alt texts are the existing i18n fields rendered as text (React, no `dangerouslySetInnerHTML`, guard test) | None new |
| SSRF | No server-side fetch of URLs in v1. The Next optimizer fetches only allow-listed https hosts and refuses private IPs (existing) | Unchanged |
| DoS by many uploads | Auth before body read, `catalog.write` only, 60 per 10 minutes per admin, 2 concurrent per process, size and pixel limits, 24 h cleanup of abandoned files | Disk growth by a malicious manager within the limits: worst case 8 640 uploads of at most `MEDIA_MAX_BYTES` (10 MiB) per user per day, about 84 GiB, whether attached or not (unattached files live 24 h before job 7 deletes them); no per-user quota (later plan); disk-full answers `503`. Corrected by the step 9 review (M-1): before the output cap a two-colour PNG grew about 6.5 times when re-encoded, so the real figure was about 340 GB per day without attaching anything; since the fix the output is capped at `MEDIA_MAX_BYTES` (`400 output_too_large`) |
| CSRF on the upload | `X-Fluxkit-CSRF` required; only `application/octet-stream` (not CORS-safelisted, forces a preflight); `SameSite=Strict`; no CORS. Multipart (a safelisted type) is NOT accepted | None new |
| Auth bypass | Under `/admin`: the global default-deny guard; permission `catalog.write` declared and checked by the route walk; the read route is public by design and reads no cookie | None |
| Unauthenticated reads of draft images | 128-bit random URLs, no listing (Q8) | A leaked URL is readable by anyone (accepted for product images) |
| Script on the admin origin through an upload | Three layers above; the admin cookie path is `/admin`, not `/media` | Residual relies on browsers honouring `nosniff`/CSP; a separate media host removes it |
| Race: delete vs attach | Row-level atomic `UPDATE ... RETURNING` vs `DELETE ... WHERE first_attached_at IS NULL`; the file is deleted only after the row delete committed | A crash after the row delete leaves an invisible file |
| Overwrite of a file | Random key, `wx`/no-overwrite rename, unique `storage_key` | None |
| Library vulnerabilities (libvips, libjpeg, libpng, libwebp) | Exact pin, Dependabot, `pnpm audit:prod`; decoders run only on sniffed JPEG/PNG/WebP; upload restricted to trusted staff | A decoder CVE is reachable by a signed-in manager; no sandboxed worker process in v1 (Risks) |
| Malware inside an image | Re-encoded pixels only; never executed | No virus scanner (out of scope) |
| Log injection / data leaks | Log fields are ours (ids, numbers); no header values or bytes logged | None |

### 9. Core or feature, and the flag (open question 9; recommendation: core)
Media are part of the catalog (core in AGENTS.md section 2.1), and a storage provider is a core abstraction like currencies and payment providers (section 1). Making uploads a feature package would need new extension points into the catalog's media and brand saves, the CSRF guard, the admin config and the scheduler, plus an admin UI slot mechanism that does not exist (admin plan: "the admin route and navigation registry stays internal in v1"). Recommendation: core, switched by configuration (`MEDIA_STORAGE_DRIVER=none` turns it off: no upload, no read route content, no job work, no UI controls), not by a feature flag; the feature matrix CI job is unaffected.

## Step 4 outcome (2026-10-23, `feature/media-api`)

Decisions taken where the plan and ADR 0028 were silent (the owner may revisit):
- **Body parser order**: Express' JSON parser runs before the guards, so a malformed JSON body sent to the upload route is answered `400` by the parser; a well-formed JSON body reaches the guard and is `403`. No body parser reads `application/octet-stream`.
- **Early refusals close the connection**: `411`, `413` (declared or counted) and `503 uploads_disabled` set `Connection: close`, so Node does not read an unread body to its end. `401`/`403` from the guards keep the existing behaviour (Node discards the body).
- **A body that ends early** (the client went away) is `400 validation_failed` without `errors[]` (no new reason code; nobody reads the answer).
- **Insert failure after the file was stored**: the file is removed and the database error is answered as usual (a missing creator maps to `409 in_use` through the existing foreign-key mapping).
- **Read route**: `ETag` is the quoted key (`"<key>"`); a matching `If-None-Match` answers `304`; every path under `/media/` that is not exactly `/media/<key>` (raw, not decoded) is `404` with `no-store`.
- **Attach marking** compares the parsed origin (host case, default port) and the path prefix without case (Express routes are case-insensitive); a URL under the prefix with a query, fragment, credentials or a decorated key is `upload_not_found`. Without a `MEDIA_PUBLIC_BASE_URL` nothing is checked.
- **Development default directory**: with `MEDIA_DIR` unset outside production, the API and `pnpm jobs:run-once` create `<repo>/var/media` (0750) at start, so a fresh checkout, the e2e suites and the feature matrix keep starting without a setup step; a set `MEDIA_DIR` (always in production) must exist, as ADR 0028 decision 8 says.
- **Processing budget** stays 30 s: the measured worst cases below take 1 to 3.5 s on one core, so 30 s leaves room for slow hosts.
- `MEDIA_STORAGE_DRIVER=local` without `MEDIA_DIR` or `MEDIA_PUBLIC_BASE_URL` cannot happen through `loadEnv`; `MediaModule` still refuses to start then.

Memory (peak RSS of one Node process running only the pipeline, `process.resourceUsage().maxRSS`, sharp 0.35.5, linux-x64, sandbox; Node with sharp loaded starts at about 75 MB):

| Input | Output | Time | Peak RSS |
|---|---|---|---|
| JPEG 8 000 x 6 250 (50 MP), 14 MB (above the 10 MiB limit, pipeline only) | 4 096 x 3 200 JPEG, 3.7 MB | 1.2 s | 202 MB |
| JPEG 50 MP, 2.4 MB | 4 096 x 3 200, 1.3 MB | 0.8 s | 187 MB |
| PNG 7 071 x 7 071 noise (49.99 MP), 158 MB (pipeline only) | 4 096 x 4 096 PNG, 46 MB | 1.6 s | 151 MB |
| PNG 7 071 x 7 071 of 8 px blocks, 4.2 MB | 4 096 x 4 096 PNG, 50 MB (re-encoded output is not size-capped) | 1.5 s | 157 MB |
| WebP 7 000 x 7 000 (49 MP), 3.8 MB | 4 096 x 4 096 WebP, 1.4 MB | 2.8 s | 302 MB |
| two of that WebP at once (both slots) | | 3.5 s | 523 MB |
| 50 MP JPEG and the 4.2 MB PNG at once | | 1.6 s | 265 MB |

So the "about 512 MB headroom" of ADR 0028 holds: the worst measured case (two near-limit WebP uploads at once) adds about 450 MB to the process. Note: a 4 MB upload can be stored as a 50 MB PNG.

## Step 5 outcome (2026-10-23, `feature/media-cleanup-job`)

Decisions taken where the plan and ADR 0028 were silent (the owner may revisit):
- **Two statements per page, one transaction.** `lockAbandonedUploadIds` (`SELECT ... FOR UPDATE SKIP LOCKED`, oldest first by `created_at, id`, through the partial index) and `deleteAbandonedUploadsByIds` (`DELETE ... WHERE id IN (page) AND first_attached_at IS NULL AND created_at < cutoff RETURNING storage_key`). The lock makes the job skip a row a save is attaching instead of waiting for `lock_timeout`; the repeated predicate keeps the DELETE safe on its own (tested by handing it ids of attached and young rows, and by a delete that waits on a save's row lock).
- **Time is a parameter.** The cutoff is `now - 24 h` from the injected `now`, like the other jobs (the plan wrote `now()`); an upload exactly 24 hours old is kept ("older than 24 hours"), like the 7-day rule for dispatched events.
- **`MEDIA_STORAGE_DRIVER=none`: no row is deleted** (ADR 0028 decision 1: "the cleanup job does nothing"); a row deleted without its file would leave an untracked file when the driver is switched back on.
- **File errors are logged at error level** with the key and the error code (the innermost cause's `code`, else its class name), never the message or a path; the file is left and counted, the run goes on.
- **Crash between commit and file delete** leaves an unreferenced file that nothing deletes later (accepted by the plan's order "row first, file second"; documented in `docs/api/jobs.md`).
- **Position in the tick**: last (after the three cleanups), because it is the only job that does file I/O.
- ADR 0028 and this plan still say "six bounded jobs" in their context sections; they describe the state when written (ADRs are not edited), `docs/api/jobs.md` says seven.

## Step 7 outcome (2026-10-23, `feature/media-admin-ui`)

Decisions taken where the plan and ADR 0028 were silent (the owner may revisit):
- **Where the code lives**: the queue model, controller, hook and panel are in `apps/admin/src/areas/catalog-dictionaries/` (not `src/lib/`): the lazy-message rule only lets files of an area use that area's lazy keys, and the products area already loads the dictionaries' messages. `lib/upload-media.ts` is the single call site of `uploadMedia`; `lib/request-timeout.ts` gives `POST /admin/media/uploads` 60 s (other writes keep 30 s; 120 s since the step 9 review, L-2). The nine upload reasons are eager (`errors.json`, with the problem map); everything else is lazy.
- **A 401 or 403 ends the queue** (the remaining files become "not uploaded (cancelled)", nothing is sent): the shell's sign-in or permission handling runs once instead of once per file. Every other failure, 429 included, lets the next file go on, as the plan says.
- **A 429 names the wait** from `Retry-After` in whole minutes rounded up (the 5 s of a busy server reads "about 1 min"); without a usable header the generic `too_many_requests` text is shown.
- **A request cut by the screen going away or an abort is `unknown`**, not cancelled: it may have reached the server.
- **"Cancel the waiting files"** cancels only files that have not started; the request in flight finishes and is kept.
- **A repeat of the same file in one selection** (same name, size and modified time) is refused as a duplicate; two files with one name but different sizes are both taken.
- **The size in the refusal text** is the limit in MB with one decimal (10 MiB reads "10 MB", a 1 KiB limit "0.1 MB"), not localized to KiB.
- **`file.type` is compared lower-cased** with `media.contentTypes`; a file whose browser type is empty is refused as an unsupported type (the server would decide by content, but a type-less file is far more likely a non-image than a WebP).
- **Row buttons and Add are disabled while files upload**, so the room counted when the selection is made stays true; if a row still no longer fits when an answer arrives, the file is shown as failed ("no room") and stays an unattached upload for the 24 h job.
- **Unsaved-changes guard**: running uploads count as unsaved input (leaving mid-queue ends the queue and asks first); for the brand form the same.
- **No local previews** (no object URLs): the server's URL is shown after the upload, which needs `/media` routed to the API (step 8; `vite dev` and `vite preview` do not proxy it yet, so the preview of an uploaded image shows the translated "could not be shown" text there).
- **Bundle**: initial JS 407 698 bytes raw, 122 326 gzip against 405 221 and 121 705 before (budget 440 000 and 135 000).

## Step 8 outcome (2026-10-24, `feature/media-proxies-e2e`)

What was built: `/media` routed by both e2e proxies and the Vite dev and preview proxy; both e2e API processes on a temp `MEDIA_DIR`; `apps/admin/e2e/tests/media-upload.e2e.ts` (5 tests) and `apps/storefront/e2e/tests/media-route.e2e.ts` (1 test); the README "Uploaded images" deployment notes and the Caddy and nginx examples; `.env.example`, the `ADMIN_DEV_API_URL` row wording, READMEs and file maps.

Decisions taken where the plan was silent (the owner may revisit):
- **Temp upload directory in both suites.** The path is fixed per proxy port (`<system temp>/fluxkit-admin-e2e-media-3112`, `fluxkit-storefront-e2e-media-3102`) because Playwright evaluates the config in its main process and every worker. `prepare-database.ts` wipes and creates it before the API starts (the API refuses to start without it), a new `global-teardown.ts` removes it. Every `MEDIA_*` variable is SET in `apiEnvironment()`, so the shell cannot change a run. The storefront suite needed the same, otherwise its API would create the repository's `var/media` (the development default).
- **The uploaded URL is on the proxy origin** (`MEDIA_PUBLIC_BASE_URL` = proxy origin + `/media`), so the browser loads it through the proxy, as in production with the default same-origin setup.
- **The guard** allows `/media/` only as an `image` resource of the proxy origin; a script, fetch or any other request to `/media` is still a problem. The CSP, console, CSRF and detail checks are unchanged and stay on.
- **Files are generated in code** (`support/images.ts`, no image file committed): a PNG is built from chunks with `node:zlib`; the 272-byte JPEG and 74-byte WebP are base64 constants made once with `sharp` from flat colours; the EXIF block (a valid big-endian TIFF with an ImageDescription marker) is spliced into the JPEG by hand, a `tEXt` and an `eXIf` chunk into the PNG. The test checks that the SENT bytes carry the marker and the STORED bytes do not.
- **What the browser, not the server, refuses.** An SVG and a file over `media.maxBytes` (read from `GET /admin/config`) are refused by the admin before any request, so those two scenarios assert "no upload request". The server's gate is exercised in a browser only by a text file called `.jpg`. The server's own `411`, `413`, `429` and `503` are not exercised through the UI (the API specs cover them); a raw oversized POST through the proxy was not tried (the API closes the connection after a `413` without reading the body, which may race the proxy's piping: reasoned, not tested).
- **Test data**: each test creates its own product type (no attributes, no options) and product through the API, so a product can be published with one price without touching the seed.
- **Brand logo uses the WebP** so that all three types are uploaded by the suite.
- **The nginx and Caddy examples** now match the bare prefixes (`/admin`, `/store`, `/media`) as well as the paths below them (this closes the old "bare `/admin`" caveat in the examples; still untested), nginx has `location ~ ^/admin(/|$)` with `client_max_body_size 12m`, and the `/media` locations add no header (the lessons of the cache headers and HSTS inheritance already in the README are repeated for it).
- **`vite-config.spec.ts`** (outside the listed paths) changed with the config: it asserted exactly one proxy key. `docs/api/media.md` "Not built yet" became "Routing and operations" (doc only; the section was stale).
- **Vite and previews**: an upload's URL is `MEDIA_PUBLIC_BASE_URL/<key>`, whose default is the API's own origin, so the `/media` proxy rule helps only when the API is started with that variable set to the dev server's origin plus `/media`; `apps/admin/README.md` says so.

Finding (fixed by the step 9 review, see "Step 9 review outcome"): `/media` and `/media/` (no key segment) answer the router's `404` without `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`; every path with a segment has both. `docs/api/media.md` and the step 4 outcome say every path under `/media/` is a `no-store` 404. Low impact.

## Risks
- **Decoder vulnerabilities in libvips and its codecs** reachable by any `catalog.write` admin. Mitigation: allow-list before decode, exact pin, Dependabot, audit. A sandboxed worker process (or a separate image service) is the later hardening.
- **Licence scope**: using the LGPL libvips binaries in the API widens an exception the owner gave for Next only; the licence script would not notice (name-based). Needs an explicit owner decision and updated policy text; arm64 deployments bring `@img/sharp-*-arm64` packages that the policy does not list (`check:licenses` would fail there until added).
- **Memory and CPU** per upload; the API may need more memory than today (measured in step 4).
- **Local disk with several instances** silently splits files: README and ADR say one instance or a shared volume.
- **Next optimizer and private IPs**: a deployment whose storefront resolves the media host to a private address shows placeholders. README check; no code workaround in v1.
- **Base URL changes** strand stored URLs (no rewrite tool).
- **Disk growth**: attached uploads are never deleted in v1.
- **Tightened validation** on `PUT .../media` and brand saves for URLs under our own prefix (pre-1.0, CHANGELOG).
- **Untested proxy examples** (as before) plus a new body-size pitfall in nginx.
- **Re-encoding changes the bytes** (generation loss on JPEG, larger PNGs in rare cases). Accepted for product photos.

## Open questions (owner quiz; recommended option first; ordered by importance)
1. **Store the uploaded file as is, or re-encode it?**
   - **(Recommended) Re-encode every image** (same format, orientation applied, sRGB, no metadata, downscaled to the output cap). Strips GPS/EXIF, kills polyglots and trailing data, normalizes. Costs CPU, memory and an image library (Q2); slight JPEG generation loss.
   - Validate only, strip metadata with a small hand-written parser (JPEG segments, PNG chunks, WebP chunks), no decoding. No dependency; but EXIF orientation is lost (phone photos appear rotated unless we keep or apply that tag), polyglot defence depends on our parser cutting trailing data, and we own a binary parser for untrusted input.
   - Validate type and dimensions only, store the bytes unchanged. Simplest; GPS coordinates and camera data of staff photos are published, polyglots survive (served safely by headers only).
2. **Which library re-encodes (if Q1 = re-encode)?**
   - **(Recommended) `sharp` 0.35.5 in `apps/api`** (Apache-2.0; already in the lockfile through Next, same version), with an owner decision that extends the LGPL-3.0-or-later exception for the unmodified prebuilt `@img/sharp-libvips-*` binaries from "Next image optimization" to "API image re-encoding"; fast, streaming, bounded by `limitInputPixels`. Adds about 19 MB per platform to an API deployment.
   - Pure JavaScript/WebAssembly encoders with permissive licences (for example `jpeg-js` and `pngjs`, plus a WebAssembly WebP codec): no LGPL; three or more new dependencies, much slower, whole images in memory, weaker bomb protection. Licences and sizes not verified for this plan.
   - A separate image service container run unmodified (for example imgproxy) called by the API: isolates decoders from the API process; a new service in Compose and production, its own licence review (not verified), network hop.
3. **Allowed formats?**
   - **(Recommended) JPEG, PNG, WebP** (static only). Covers photos and transparent product shots; every browser shows them; smallest decoder surface.
   - Also AVIF (decoded by libheif/aom in sharp): smaller files; more CPU per upload and a larger decoder surface; iPhone HEIC still refused.
   - Also GIF (first frame only, or animated kept): legacy assets; animation handling or silent loss of frames.
4. **SVG (brand logos are often SVG)?**
   - **(Recommended) Refuse SVG uploads**; a logo is uploaded as PNG or WebP (an SVG logo hosted elsewhere can still be entered as a URL, as today).
   - Rasterize SVG to PNG on upload (sharp/librsvg): logos work from SVG sources; librsvg parses untrusted XML in our process (external references, entity expansion, CPU); output loses vector sharpness.
   - Accept SVG after sanitizing and serve it as `image/svg+xml` with the sandbox CSP: vector logos; needs an XML sanitizer dependency and still serves a script-capable format from the admin's origin.
5. **Size and dimension limits?**
   - **(Recommended) 10 MiB per file, 50 megapixels and 12 000 px per side on input, output downscaled to fit 4 096 px** (never enlarged). Phone photos (12 to 48 MP) pass; storage and optimizer work stay modest.
   - 5 MiB, 25 MP, no downscale: stricter on memory; many raw phone photos must be shrunk by the admin first; full-size files stored.
   - 20 MiB, 100 MP, no downscale: almost nothing refused; up to 400 MB decoded per upload; large files stored and served.
6. **How are uploads recorded?**
   - **(Recommended) New table `media_upload` (metadata, creator, `first_attached_at`); `media.url` and `brand.logo_url` keep the URL** (store API unchanged). Enables safe orphan cleanup and the `upload_not_found` check; one migration.
   - No table: the file system is the record, the URL is the only reference. No migration; no creator or dimensions; orphan cleanup means scanning the disk against three unindexed URL columns, or never cleaning up.
   - Table plus foreign keys from `media` and `brand` (`upload_id`, with "url or upload" CHECKs; URL built when read): strongest integrity and exact reference counts; changes two catalog tables and the read path, larger migration, no v1 benefit.
7. **Who serves the files, and from where?**
   - **(Recommended) The API route `GET /media/{key}` with fixed safe headers, reached through the edge proxy at `/media/*` of the shop host by default; `MEDIA_PUBLIC_BASE_URL` lets a client put a separate cookie-less host or a CDN in front without code change.** Headers are code and tested; works in dev and e2e; one Node process streams files.
   - The edge proxy serves `MEDIA_DIR` as static files with headers in its configuration: fastest, no Node work per image; headers live in untested proxy examples, and the API and the proxy must share the directory.
   - S3-compatible object storage from day one with the bucket or CDN URL: scales to several instances; a new SDK dependency or hand-written request signing, provider choice, and integration tests need an S3 server (MinIO's server is AGPLv3: a licence decision).
8. **Images of unpublished (draft) products?**
   - **(Recommended) Public by unguessable 128-bit URL, not listed anywhere.** Simple and cacheable; a leaked URL shows the image.
   - Served only to signed-in admins until the product is published (a second read route under `/admin`, a database check per request, a copy or switch on publish): private drafts; much more code, uncacheable previews.
   - Public, and the admin is warned in the editor that uploads are visible to anyone with the link: same as the first, plus a hint text.
9. **Core or optional feature?**
   - **(Recommended) Core, switched by configuration** (`MEDIA_STORAGE_DRIVER=local|none`; `none` hides the controls and refuses uploads). Matches "providers are core abstractions"; no new extension points.
   - An optional feature package with a flag (`FEATURES_ENABLED=media-upload`): removable by deleting a folder; needs new extension points into catalog saves, the CSRF guard, the admin config, the scheduler and an admin UI slot system that does not exist.
   - Core, always on (no `none`): one less mode; every deployment must provide a writable directory and a public base URL.
10. **Alt text for uploaded images?**
    - **(Recommended) Keep the model as is**: alt texts stay on the product media rows (i18n, already exist); a brand logo's alt is the brand name; the upload row has no alt.
    - Store a default alt on the upload and copy it into each media row that uses it: less typing when an image is reused; a second place for the same text.
    - Require an alt text in the default locale for every product image at publish: better accessibility; a new publish rule (`400` at `media.N.alt`), a behaviour change for existing URL-based media.
11. **Upload request format?**
    - **(Recommended) Raw body, `Content-Type: application/octet-stream`, one file per request.** No parser dependency, no file name, a content type that forces a CORS preflight; needs one route-scoped CSRF exception.
    - `multipart/form-data` through Nest's `FileInterceptor` (multer and busboy are already transitive dependencies): the common web form shape; the content type is CORS-safelisted (the CSRF header still forces a preflight), carries a client file name and fields we must ignore, and multer's limits must be set exactly.
    - JSON with base64 (`{data: "..."}`): no CSRF change; 33 % larger, the whole file in memory, and the 100 KB JSON limit must be raised for that route.
12. **What is deleted, and when?**
    - **(Recommended) Only abandoned uploads (never attached within 24 h) are deleted by a scheduler job; an attached upload is kept even after the image is removed from the product** (order snapshots may still show it). Disk grows with the catalog's history.
    - Also delete an upload as soon as no `media`, `brand` or `order_item` row references its URL (checked by the job): less disk; three-table scans on free-text URLs and a risk of deleting an image a cache or an email still shows.
    - Never delete anything automatically (no job): simplest; every lost or abandoned upload stays on disk.
