# Deploy review: production images, edge proxies and the deploy pipeline (2026-11-27)

- Status: review done; non-red-zone fixes in progress (column "Status"). Red-zone and host items wait for the owner (section 3).
- Source: `docs/HANDOFF.md` section 2 item 3 ("an independent review of the images, proxy and deploy workflow").
- Checked against `main` at `4ff58978` (2026-11-27). Line numbers refer to that commit.
- Scope: `Dockerfile`, `.dockerignore`, `infra/docker-compose.prod.yml`, `infra/proxy/` (nginx, Caddy), `infra/docker/stop-linger.sh`,
  `infra/deploy/fluxkit-deploy`, `.github/workflows/deploy.yml` (and the image jobs of `ci.yml`), `.github/dependabot.yml`,
  `scripts/deploy-smoke.sh`, `docs/deployment.md`, `docs/plans/2026-11-10-hetzner-first-deploy.md`, `docs/plans/2026-11-12-deploy-workflow.md`, ADR 0057.
- Method: three independent passes that did not see each other's findings: Codex `gpt-6.2-astra` (high effort, read-only), a Claude
  Sonnet subagent, and the orchestrator (Claude Opus). Findings below were merged and each one used for a fix was re-checked in the
  files. Read only from outside the host: public response headers of the test server and GitHub repository settings
  (`gh api`). Nothing on the test server was read or changed over SSH.

Severity: **critical** = a single leaked credential or one mistake gives host control or loses data; **high** = a likely failure
that loses data, breaks a deploy or leaks a secret; **medium** = real but needs an unusual condition; **low** = hardening.
Found by: C = Codex, S = Sonnet, O = orchestrator.

## 3. For the owner (red zone or host changes)

1. D1: choose the host trust model for the release archive (host-side Compose file, GitHub-fetched archive by full sha, or signed manifests). Then reinstall the host script.
2. D10: repository settings: move `DEPLOY_SSH_KEY` and `DOCKERHUB_TOKEN` into the `production` environment (deployment branch `main`); add "block force pushes" and "restrict deletions" to the `main` ruleset; decide whether admins keep the bypass.
3. D9: Docker Hub token scope (write for CI, read-only or none on the host); private image repositories for client forks; later, deploy by digest.
4. D4: the off-host backup target (Hetzner Storage Box, another server, or a pull to the owner's machine) and a restore drill of real data on a scratch host.
5. D7: measure memory on the test server (rollout overlap, upload, reindex), then set limits or resize the host.
6. D8: create the runtime database role on the test server and switch the API to it (`docs/deployment.md`, "Database roles").
7. D19: host hardening (key-only SSH, firewall, non-root deploy user).
8. Reinstall `/usr/local/sbin/fluxkit-deploy` after the D3 and D5 fixes merge; the test server already has `fluxkit-backup`, so D3 changes nothing there.

## 4. Done well (keep)

- Node and nginx base images pinned by digest; runtime images drop npm/Corepack; API and storefront run as uid 1000, the edge as uid 101.
- `read_only`, `cap_drop: ALL`, `no-new-privileges`, `init`, tmpfs and log rotation on every application container; only the edge publishes ports.
- The Meilisearch master key is in its own file and never reaches the API (`deploy-smoke` checks it).
- nginx: `server_tokens off`, TLS 1.2/1.3 without session tickets, HSTS in one place, `X-Forwarded-For` replaced (not appended), per-route body limits, redirect target from `FLUXKIT_DOMAIN`, health check on loopback, admin CSP; `/docs`, `/docs-json`, `/health` not routed (checked publicly 2026-11-27: 404).
- Rollout: flock, images pulled before any change, a failing backup aborts before the switch, migrations to completion before any API replacement, one unready replica at a time, digest labels, DNS-aware drain; `deploy-smoke` runs the real host script under traffic.
- Workflow: `contents: read`, the `workflow_run` trust checks, the ancestor-of-main check, pinned host key with strict checking, forced command with `restrict`, hex-only input.
