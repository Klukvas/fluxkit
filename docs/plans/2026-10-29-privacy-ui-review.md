## Findings

### F1 (Major): the legal release check guards one message, not the legal texts; the placeholder box is unconditional; the identity is never checked

- Where: `apps/storefront/next.config.ts:38-69` (`assertNoLegalPlaceholders`: refuses only a `legal.*` message whose VALUE contains `LEGAL_MARKER`); `apps/storefront/src/messages/en.json:601` and `uk.json:619` (`legal.placeholder.marker`, the only two messages that carry the marker); `en.json:603` `legal.privacy.intro` = "The shop's own privacy notice goes here." and `:609` `legal.terms.intro` = "The shop's own terms go here." (no marker; same in uk); `apps/storefront/src/components/legal-page.tsx:125-128` (the "Template placeholder" `Alert` with `legal.placeholder.title/body/marker` is rendered on every legal page, always); `apps/storefront/src/config/legal.ts:63-68` (`legalIdentity`, four `null` members shown as "[to be filled in by the shop]" and "Last updated: [to be filled in by the shop]", never read by the check).
- Scenario: a client fork follows `docs/privacy/README.md` section 5 ("put your texts in the `legal.*` messages, fill the controller identity, build with `STOREFRONT_REQUIRE_LEGAL_TEXT=true`"). The warning box on every legal page says "This text comes from the shop template and is not the shop's legal text", so the fork empties `legal.placeholder.marker` (and `title`/`body`) to make it go away. The build now PASSES whatever the state of `legal.privacy.intro`, `legal.terms.intro` and the identity: a shop can ship "The shop's own privacy notice goes here." under "Privacy notice" with "[to be filled in by the shop]" as its name and address, and the release check that section 15 of AGENTS.md relies on ("a production build refuses them", HANDOFF owner list) says nothing. Even a fork that keeps the marker message but blanks it to `""` still renders an empty warning `Alert` on every legal page, because the box is not tied to the marker; removing it needs an edit of `legal-page.tsx` (a core file, section 17).
- Proof (scratch script against the real `assertNoLegalPlaceholders`, `node --experimental-strip-types`):
  ```
  en.json keys carrying the marker: [ 'legal.placeholder.marker' ]
  uk.json keys carrying the marker: [ 'legal.placeholder.marker' ]
  en.json legal.privacy.intro = "The shop's own privacy notice goes here."
  (copy of both files with legal.placeholder.marker = "" and nothing else changed)
  RESULT: the release check PASSED although legal.privacy.intro / legal.terms.intro are still the template placeholders
  CONTROL: master refused: ... en.json: legal.placeholder.marker | uk.json: legal.placeholder.marker
  ```
  Mutation M11 (`key.startsWith("legal.")` narrowed to `key.startsWith("legal.placeholder")`): `next.config.spec.ts` 21 of 21 pass. The spec's "only legal messages count" case never places the marker in a legal TEXT key.
- Suggested fix: make the marker part of every placeholder legal text (`legal.privacy.intro`, `legal.terms.intro`; decide for `legal.cookies.intro`, which is real template content under "TODO legal review"), so a fork cannot pass without touching the texts themselves; render the "Template placeholder" box only while the page's own intro still carries the marker (and drop the separate `legal.placeholder.marker` message, or keep it as the box's text); extend the release check to the identity: `shopLegalName`, `shopLegalAddress`, `privacyContact` and `lastUpdated` must be non-null (the check runs in plain Node and cannot import `config/legal.ts`; either move the identity to a JSON file both can read, or add the identity rule as a spec that `legal-pages.spec.ts` inverts when `STOREFRONT_REQUIRE_LEGAL_TEXT=true`). Add a `next.config.spec.ts` case: marker only in `legal.privacy.intro`, `legal.placeholder.marker` clean, the check must refuse. Update `docs/privacy/README.md` section 5, `apps/storefront/README.md` "Release check" and `docs/contracts/config.md` to say what the check really covers.

### F2 (Minor): the storefront shows an anonymised order of a live account without a label

- Where: `apps/storefront/src/components/order-details.tsx:324-333` (the "Contact" section prints `order.contact.firstName lastName`, `email`, `phone` as they are); `packages/api-client/src/types.ts:267-273` (`OrderContact`: all four `null` once erased, the store `Order` has no `contactErasedAt`; `apps/api/src/orders/order-view.ts:151-158` serialises the nulls as they are); `apps/api/src/privacy/retention/privacy-retention.service.ts:31-47` (`candidates()`: every closed order past the cut-off with `contact_erased_at IS NULL`, no condition on `customer_id`, so the orders of a live account are anonymised once `ORDER_CONTACT_RETENTION_DAYS` is set).
- Scenario: a customer with an account opens `/{locale}/account/orders/<number>` for an order older than the retention period. The admin sees "Erased" and an alert with the date (step 9); the customer sees a "Contact" heading over three empty paragraphs and the address section gone (`viewAddress` returns `null` for an erased order), with nothing that says why.
- Proof (scratch spec rendering `OrderDetailsView` with the real `en` messages and `contact: {email: null, phone: null, firstName: null, lastName: null}`):
  ```
  <section aria-labelledby="order-contact-heading" ...><h2 ...>Contact</h2><p class="text-foreground"> </p><p class="break-all text-foreground"></p><p class="text-foreground"></p></section>
  ```
- Suggested fix: when `order.contact.email === null` (the four are null together by the type's contract) replace the three lines by one message ("The contact data of this order was removed after the retention period"; uk too) and hide the address heading; a unit case in `order-details.spec.tsx`. Exposing `contactErasedAt` in the store order would be a contract change (red zone) and is not needed for the label.

### F3 (Minor, docs vs code): two claims that overstate the code

- `apps/storefront/README.md:348` "The password is cleared after every answer." Code: `apps/storefront/src/components/account-data.tsx:139-153`: `form.setValue("password", "")` only in `case "other"`; the `blocked` and `rate_limited` branches keep it. Proof (scratch Playwright scenario on the real stack, after the `409 erasure_blocked` answer): `password field after the blocked answer: "a long e2e password 123"`, `word field: "DELETE"`. The password therefore stays in the DOM field and in React state while the shopper reads the blockers, and a second press of the button sends it again without being retyped. Suggested fix: clear the password in every failure branch (one line before the `switch`), keep the typed word; a unit case (mutation M24 below shows none exists) and the README sentence then becomes true.
- `docs/privacy/README.md` section 5: "a guard fails CI if the API sets another cookie or the storefront touches `document.cookie`". The API guard is whole-tree (`apps/api/src/privacy/inventory/source-guards.spec.ts:154-195`). The storefront guards (`apps/storefront/src/source-guards.spec.ts:118-123, 185-189, 395-401, 560-566`) scan the cart/account files, the payment files, the emailed-link files and the search files only. No storefront file uses `document.cookie` today (grep), so the statement is true by luck, not by a guard. Suggested fix: one whole-`src` assertion for `document.cookie` (and `cookies().set` in route files), or word the guide as "the named files".

### F4 (Minor, i18n): count sentences without plural forms

- Where: `apps/admin/src/messages/en/privacy.json:126` ("The file {file} was downloaded: {orders} orders, {mail} mails, {sessions} sessions.") and `:129` ("The contact data of {orders} orders was erased and {mail} stored mails were deleted."); rendered by `request-detail-view.tsx:147-156, 163-166`. The same file uses `t.plural` for `personal.lookup.mailCount.one/other` (`:71-72`), so the mechanism exists. The uk sentences put the noun before the number and read fine.
- Proof: `apps/admin/e2e/tests/privacy.e2e.ts:112` asserts "was downloaded: 1 orders, 0 mails, 0 sessions." and `:174` "The contact data of 1 orders was erased and 0 stored mails were deleted." (both pass: the screen really says it).
- Suggested fix: `.one/.other` forms for the three counts composed into the sentence (or three short plural fragments), update the e2e expectations.
