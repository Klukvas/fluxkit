# Review: Nova Post carrier plugin (shipping plan step 7b, PR #131)

Status: independent review, 2026-10-25. Reviewer: a different agent than the author (Opus 5.5), read-only on the code.
Scope: `origin/feat/shipping-nova-post` at `a5e35b2` (base `main` `d37264c`): `packages/providers/nova-post`, the port changes in `packages/core/src/shipping` (`fetchLabel` `trackingNumber`, `validateSettings`, `provider-contract.ts`) and their call sites (`apps/api/src/shipping/admin/shipping-providers.*`, the registry, `shipments.service.ts`, the in-repo test carrier, `_fake`).
Measured against: `docs/plans/2026-10-24-shipping.md` ("Spike 7a — production run 2026-10-25" and its 21:50 UTC rerun), ADR 0030, `docs/plans/2026-10-25-nova-post-plugin.md`, AGENTS.md.
No call to the real Nova Post API was made; the key was not asked for. Every repro ran against the plugin's own stub carrier on `127.0.0.1`.

## Verdict
No BLOCKER. Two MAJOR findings (a false "certainly not found" in `findWaybill` that can lead to a duplicate real shipment, and the city point list failing completely within the observed latency range), then MINOR test and hardening gaps. The verified request shapes, the JWT handling, the "never repeat a create" rule, the size caps, the base URL pinning and the call-site wiring are correct.

## What was checked and is clean
- **Request shapes vs spike 7a**: raw JWT in `Authorization`, never `Bearer` (`http.ts:329`; the stub refuses anything but an issued token); key only in `GET /clients/authorization?apiKey=` (`http.ts:291-300`); `name[]` parameters via `URLSearchParams`; `type=marking` not `type[]` (`nova-post-provider.ts:701`); delete by uuid only, a non-uuid refused without a call (`:579-588`); the create body equals the spike tool's verified `createBody` field by field (`scripts/spikes/nova-post-verify.mjs:1317-1359` vs `nova-post-provider.ts:414-454`); `payerContractNumber` only when the sender pays; `clientOrder` = the order number, 9 characters (`ORDER_NUMBER_PATTERN`), within 50; `Accept-language` on settlements (H11) and `uk` on divisions (H14); limits 100 (H15); `ids[]` lookup with `limit=2` and fail-closed on more than one item (H16).
- **JWT**: cached until `exp - 5 min` (50 min without `exp`), single flight with per-caller abort (`untilAborted`), the authorization with its own 5 s limit, a `401` on a read or delete refreshes once, a second `401` is `invalid_credentials`, a newer token is not dropped by an older `401` (`invalidate` compares).
- **Create never repeated**: `retryOn401: false`; a `401` is `invalid_credentials` (the token is checked before the body, 8.6), `5xx`, `429`, timeout, network, a body over the cap and an unreadable `2xx` are `unavailable`, so the API's `unknown` + reconcile (tests and mutation M8 killed). Only finding 3 remains.
- **findWaybill** besides finding 1: window inclusive on both sides, early stop only on a page sorted newest first, at most 10 pages then `scan_limit`, one unreadable row fails the scan, two matches `ambiguous_reference`, invalid window refused without a call; ids deduplicated across pages. The newest-first order was observed with 2 shipments only (H23): the code does not rely on it across pages beyond the early stop, which is the right posture.
- **Status mapping**: unknown and non-digit codes are `null` (the shipment keeps its status, the raw code is stored); `returned` never reported; the table is frozen. Only finding 7.
- **Money**: carrier amounts are read with `parseDecimalString` (more than two decimals, negative or non-finite: refused, never rounded); UAH only (the answer names no currency); the carrier cost is informational. Rounding the declared value UP to whole hryvnias is not a money-correctness problem: `insuranceCost` is the carrier's insured value, never part of our totals, and it can only exceed the order value by under 1 UAH (insurance fee difference under a kopeck at the usual rates). The estimate's unit and the sum of `services[].cost` are unverified (never a `200` on production), as the README says.
- **Label**: `200` + `application/pdf` + `%PDF-` + 10 MiB cap or a typed failure; never a made-up PDF; the API checks the PDF again.
- **Security**: base URL is one of two constants (no URL variable); `redirect: "error"`; size caps checked on `content-length` and while streaming (mutation M6 killed); fetch errors are reduced to `timeout`/`network` (the key-bearing URL is never logged); lookups throw fixed messages; `NOVA_POST_ENVIRONMENT` defaults to sandbox, production only when written, unknown values stop the startup without echo; the key check never shows the value. The settings validator handles `__proto__`, `constructor`, keys no path can name, non-objects and 500 unknown keys (probe: `[{"path":"__proto__","code":"unknown_key"}]`, `defaultParcel.__proto__`, path `""` for odd keys, at most 50 issues); the API's generic check runs first, a provider validator that throws or breaks the shape is a logged `500` with nothing saved and nothing echoed (spec). Sender data in `shipping_provider_setting` is the shop's own contact (name, phone, optional email): admin-only (`shipping.manage`), never logged; acceptable, worth a line in the privacy notes when they exist.
- **Integration**: the shipment stores the create answer's uuid as `provider_ref` and the 14-digit number as `tracking_number`; cancel passes `provider_ref` (uuid, H28), label passes both (number used, H27 shape), tracking passes `tracking_number`, reconcile's found waybill stores the same pair. A label needs both (`shipments.service.ts:316-331`). A disabled or deleted provider answers `409 provider_not_enabled` (unchanged). The registry checks `validateSettings` at startup; `.env` reaches `process.env` through `node --env-file` before the module factory reads it.
- **Contract check** (`checkShippingProviderContract`) runs against the fake and the plugin and covers lookups, create, find, track, label, cancel, invalid window, aborted signals and the settings validator.
- **AGENTS.md**: no new third-party dependency (zod 4.6.7 already pinned), env vars in `.env.example` and `docs/contracts/config.md`, core imports no provider (boundaries clean), docs updated in the same change, no client data.
