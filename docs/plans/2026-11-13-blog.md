# Plan: blog as an optional feature (SEO)

Status: approved (owner, 2026-11-13: every red zone of section 15 and the recommended option of every question in section 17).
Revised after the independent review of 2026-11-13 (section 18). Owner request 2026-11-13,
direction approved: an optional feature package with flag `blog`,
posts in Postgres edited in the admin (sanitized Markdown, never raw HTML), storefront `/{locale}/blog` and `/{locale}/blog/{slug}`
with full SEO. Nothing is built yet; delivery follows section 14.

## 1. Goal

- An admin with the catalog permissions writes posts (title, excerpt, Markdown body, SEO title and description per content locale,
  a cover picture from the media service, a slug), keeps them as drafts, publishes, schedules (a future `publishedAt`), unpublishes
  and deletes them.
- Shoppers and crawlers read `/{locale}/blog` (paginated list, newest first) and `/{locale}/blog/{slug}` (one post): server-rendered,
  with `generateMetadata` (title, description, canonical, hreflang alternates, Open Graph with the cover), JSON-LD `BlogPosting` and
  `BreadcrumbList`, sitemap entries, and a header and footer link.
- `blog` is a real feature (AGENTS.md 2.1): with `blog` missing from `FEATURES_ENABLED` there is no UI, no link, no sitemap entry, no
  route (404 like an unknown path), no API endpoint and no database write; removing it means deleting its folders, its flag and its
  migration, checked by the feature matrix.
- Most of the work is the extension points a feature with tables, permissions, media, admin screens and storefront pages needs. None
  exists today (ADR 0046 "Context" listed them when banners went into core). They are built once, as public contracts, and every
  later feature (reviews, wishlist, coupons) reuses them. The blog itself is the smaller part.

## 3. Scope

**v1 (this plan):** posts with draft/published status and `publishedAt` (a future date schedules), slug, title, excerpt, Markdown body,
SEO title and description, cover picture and its alt text, per content locale; admin list, form (Markdown errors shown by line
when saving), publish, unpublish, delete; storefront list (12 per page) and post page; metadata, JSON-LD, sitemap, header and footer
link; feature-matrix modes.

**Out of scope (later, each its own plan):** categories and tags, comments, RSS/Atom, related products and product links in posts,
inline images in the body (Q10), authors (Q8), redirects for changed slugs, search over posts, a home-page "latest posts" section
(needs a home slot for features), demo posts in `pnpm seed` (needs a feature seed hook), admin help articles from features, an
on-demand cache revalidation hook, audit entries for post edits, per-locale slugs (Q5), AMP. Cut from v1 by the review (section 18):
a Markdown preview in the admin (route and live view), a `pnpm db:feature-down` command, a `featureLinks` opt-out for the header and
footer, moving `ZodValidationPipe` into the API kit.

## 4. Architecture: the shape of a feature and its extension points

### 4.1 Where the blog lives (recommended, Q1)

A feature is **one package plus one slice folder per app**, each deletable, none imported by core code:

| Part | Folder | Holds |
|---|---|---|
| API | `packages/features/blog/` (`@fluxkit/feature-blog`, `"fluxkit": {"feature": "blog"}`) | Nest module (store and admin controllers, service, repository), Drizzle table, `drizzle/` migrations with `.down.sql`, `personalDataInventory`, README, specs |
| Storefront | `apps/storefront/src/app/[locale]/(feature-blog)/` | `layout.tsx` (re-exports `(site)/layout` like `(pages)` does, no `loading.tsx`), `blog/page.tsx`, `blog/[slug]/page.tsx`, private `_feature/` (manifest `feature.ts`, data reads, views, metadata and JSON-LD builders, `messages/{uk,en}.json`, specs) |
| Admin | `apps/admin/src/features/blog/` | manifest `feature.ts`, lazy area (list, form), `messages/{uk,en}.json`, specs |

Why slices instead of one package with storefront and admin entry points: a slice inside its app reuses the app's own helpers (SEO
builders, `JsonLd`, `StoreImage`, the data cache, the admin form, upload panel and request helpers) without making each of them a
public SemVer contract, and the apps keep one React instance (a package rendered into Next needs a workspace dependency, which breaks
`pnpm install` once the folder is deleted, or a path import outside the app root). Cost: removal deletes three folders, and AGENTS.md
2.1 says "deleting its folder" (owner's file; wording change needed, section 15).

Core never imports a slice: a dependency-cruiser rule refuses imports from app code into `apps/storefront/src/app/[locale]/(feature-*)/`
and `apps/admin/src/features/*/`, except from the one registry module of each app; slices may import their app (feature -> core
direction) and never each other.

### 4.2 Extension points (all new public contracts, listed in a new `docs/contracts/features.md`, ADR 0049)

- **E1. Feature migrations.** A feature with tables ships `drizzle.config.ts` (its own schema file), `drizzle/` with its own
  `meta/_journal.json` and a hand-written `.down.sql` per migration. `pnpm db:migrate` applies the core journal first, then the
  journal of every feature in `FEATURES_ENABLED`, each recorded in its own table `drizzle.__drizzle_migrations_feature_<name>`, all
  under the existing `MIGRATION_LOCK_KEY`, with the same "newer than this code" refusal. A disabled feature is never migrated (no
  database side effect). The API refuses to start when an enabled feature has unapplied migrations (names the feature, not the
  database). `check-schema-drift.sh` also checks every feature that has a `drizzle.config.ts`.
  - **No down command in v1.** The `.down.sql` files are kept and tested up, down, up, down by the feature's own spec; removal runs
    them by hand (`psql "$DATABASE_URL" -f packages/features/blog/drizzle/0000_blog_post.down.sql`, documented in the feature README)
    before the folder is deleted. A `pnpm db:feature-down` command is later.
  - **Foreign keys to core tables (decided, recorded in ADR 0049).** A feature cannot import the core Drizzle table objects (they live
    in `apps/api`, `packages-must-not-import-apps`), so its schema declares such a column as a plain `uuid` without `.references()`,
    and the constraint is added by hand at the end of the generated migration SQL (`ALTER TABLE ... ADD CONSTRAINT
    blog_post_cover_upload_id_fkey FOREIGN KEY (cover_upload_id) REFERENCES media_upload(id) ON DELETE RESTRICT`). The drift check
    builds from the feature schema, which never declares the key, so it stays blind to it by construction; a feature spec asserts the
    constraint in the migrated database (`pg_constraint`). Rejected: a stub of `media_upload` exported from the API kit (a second
    definition of a core table that can drift from the real one).
  - **Down order.** Feature migrations go up after the core and down before it: a core down migration that drops a referenced table
    (`0005_media_upload.down.sql`) fails while `blog_post` exists, so the feature's down runs first (documented in ADR 0049 and
    `docs/deployment.md`). Core never references a feature table.
  - **Test database reset.** `apps/api/src/test/migrate.ts` drops every `public` table with `CASCADE` and the `drizzle` schema, so the
    feature table, its foreign key and its migrations table go with it; PR 1 adds the enabled feature journals to its "state differs"
    comparison so a database migrated with a feature is reset for a run without it, and the reverse.
  - **Production image.** The API image keeps the monorepo layout (`Dockerfile`: `COPY . .`, `api-tree` installs
    `./packages/features/*`; `.dockerignore` drops only `dist`, `node_modules` and build output), so each feature's `drizzle/` folder
    and `.down.sql` files are in the image. The `migrate` service of `infra/docker-compose.prod.yml` reads the same env file as the API,
    so `FEATURES_ENABLED` reaches it. `deploy-smoke` asserts the blog journal is present in the API image (PR 6).
  - **Enabling a feature on a live host:** set `FEATURES_ENABLED` in the env file, run the migrate step (the next deploy runs it, or
    `docker compose run --rm migrate`), then start the API; started before the migration, the API refuses to start (loud, by design).
    Written into `docs/deployment.md` and the notes of `infra/deploy/fluxkit-deploy` (PR 6).
- **E2. API kit for features (Q2).** New package `packages/api-kit` (`@fluxkit/api-kit`; depends only on `@nestjs/common` and
  `@fluxkit/core`, both already pinned: no new external dependency). Minimum export set, nothing more:
  - `ProblemException` and its code type (one class identity, so the global problem filter keeps its `instanceof`);
  - `RequirePermission` and `AdminController` (with the default-permission metadata they set);
  - three DI tokens: `FEATURE_DATABASE` (the API's own Drizzle instance, one pool, typed loosely so a feature uses its own table
    objects; its transactions are ordinary Drizzle transactions), `MEDIA_PORT` (interface in core `media`, implementation in
    `apps/api/src/media`: `markAttachedByIds(tx, refs)`, the existing method inside the caller's transaction with `upload_not_found` at
    the caller's field, and `describeUploads(ids)` giving `{id, url, width, height}`; a feature never reads `media_upload`), and
    `LOCALE_CONFIG` (the existing symbol of `apps/api/src/common/locale.ts`, moved because `DEFAULT_LOCALE` and `LOCALES` are only
    known there and `validateI18nText` needs them).
  - **A mechanical move:** the classes, decorators and symbols move unchanged, the old `apps/api` paths re-export them, so no other
    import changes; the metadata key strings (`fluxkit:admin:permission`, `fluxkit:admin:public`, `fluxkit:admin:authenticated`,
    `fluxkit:admin:default-permission-by-method`) stay exactly as they are; the existing `AdminPathGuard` and `problem.filter` specs are
    not edited. `ZodValidationPipe` is NOT moved: a feature validates with `zod` (already pinned) and throws `ProblemException`.
  - **PR 1 acceptance:** a spec pins the four key strings; a fixture feature route without any decorator is denied by default (`401`
    signed out, `403` signed in); a `ProblemException` thrown by a feature keeps its `errors[]` in the answer.
- **E3. Privacy inventory of a feature.** The feature package also exports `personalDataInventory` (the core entry shape); the
  loader merges entries of enabled features; a spec inside each feature checks that every column of its Drizzle tables is classified.
  The feature README holds its inventory rows (deleted with it). **The guard change, exactly:** the test "a feature or provider package
  declares no database table" (`apps/api/src/privacy/inventory/source-guards.spec.ts`, pattern `drizzle-orm/pg-core|pgTable(`) keeps
  refusing every provider file and every feature file except `packages/features/<name>/src/schema.ts`, and that one file is allowed only
  when the same package's `src/index.ts` exports `personalDataInventory`. Its non-vacuity assertion (`files.length > 0` over both
  roots) stays valid: the `deleted` mode removes the features but not the providers, and `providers-deleted` the reverse; no mode removes
  both (a comment in the spec and in `feature-matrix.sh` says so).
- **E4. Enabled features in the config endpoints.** Additive `features: string[]` (the names in `FEATURES_ENABLED` that loaded, sorted)
  on `GET /store/config` and `GET /admin/config`. One runtime flag (the API's) switches all three apps; the storefront and the admin
  read no new variable (`pnpm check:env` unchanged).
- **E5. Storefront slice.** A route group `app/[locale]/(feature-<name>)/` with a `layout.tsx` and no `loading.tsx` above any page
  (added to `mustAnswerRealNotFound`). Every page and `generateMetadata` first reads the config (60 s cache) and calls `notFound()`
  when `<name>` is not in `features`, before any feature API call. A spec refuses a feature path that is also a shop page slug.
- **E6. Storefront feature registry (a generator, decided).** Next 16 with Turbopack has neither `import.meta.glob` nor
  `require.context`, so `scripts/generate-feature-registry.mjs` writes `apps/storefront/src/features/registry.generated.ts`
  (git-ignored) from the slices present on disk, empty without slices. It runs from the storefront's `predev`, `prebuild`,
  `pretypecheck` and `pretest` scripts (the slices are Turbo inputs), so it also runs inside the Docker build (`RUN pnpm build`) and in
  the feature matrix `deleted` mode after the folders are removed. A manifest `_feature/feature.ts` exports `{name, navigation:
  [{placement: "header" | "footer", labelKey, path}], sitemap(ctx) => Promise<{path, lastModified?}[]>, messages: {uk, en}}`. Messages
  live under `features.<name>.` (a key outside it, or already present, fails the build, like `custom.`), merged before the fork
  overrides, and the legal release guard reads them too.
- **E7. Feature links in the header and footer.** `layout/header-layout.ts` appends the `header` links of enabled features after
  `navigation.links`; `layout/footer-layout.ts` appends `footer` links to the `shopPages` group (or a group of their own at the end when
  the config has none). No opt-out switch in v1 (a fork that wants no link leaves the feature off); the behaviour is described in
  `docs/contracts/header-footer.md`, and the fork-owned config files are not edited. With no enabled feature the markup is byte for
  byte unchanged (frozen markup specs stay green).
- **E8. Admin feature registry.** `apps/admin/src/features/registry.ts` finds `./*/feature.ts` with Vite `import.meta.glob` (lazy,
  so a feature costs the entry chunk only its manifest; `build-output.spec.ts` keeps the budget). A manifest declares
  `{name, routes: [{id, path, permission, titleKey, load}], navigation: {group, labelKey, routeId}, messages}`; route ids are
  `feature.<name>.<screen>`. A route shows only when its feature is in `GET /admin/config` `features` and the role has the permission.
- **E9. Generic safe Markdown** (section 8): parser and AST types in core `content/markdown`, renderer `MarkdownView` in `@fluxkit/ui`.
  Not blog-specific: product descriptions could use it later.

## 5. Data model (feature migration `packages/features/blog/drizzle/0000_blog_post.sql` + `.down.sql`)

Table `blog_post`:

| Column | Type | Rule |
|---|---|---|
| `id` | uuid pk | |
| `slug` | text not null | core `SLUG_PATTERN`, 1 to 160; UNIQUE (`blog_post_slug_key`); one slug for every locale (Q5); locked once the post was first published (`published_at` not null) |
| `status` | text not null default `'draft'` | CHECK in (`draft`, `published`) |
| `published_at` | timestamptz null | set on the first publish (default now, an admin may pick another instant in [2000, 2200)); kept on unpublish, so republishing keeps the date; CHECK `status = 'draft' OR published_at IS NOT NULL` |
| `title` | jsonb not null | `I18nText`, 1 to 120; default locale required on create |
| `excerpt` | jsonb null | plain text, 0 to 300; the list teaser and the meta description fallback |
| `body` | jsonb not null default `'{}'` | Markdown source per locale, 0 to 40 000 characters, must parse (section 8) |
| `seo_title` | jsonb null | 0 to 70 |
| `seo_description` | jsonb null | 0 to 160 |
| `cover_upload_id` | uuid null | a plain `uuid` in the feature's Drizzle schema; the FK `blog_post_cover_upload_id_fkey` to `media_upload(id)` ON DELETE RESTRICT is added by hand in the migration SQL (E1); marked attached in the save's transaction (`MEDIA_PORT`, E2) |
| `cover_alt` | jsonb null | 0 to 150; empty = decorative |
| `created_at`, `updated_at` | timestamptz not null | `updated_at` is `dateModified` and the sitemap `lastModified` |

- Every jsonb column has `CHECK (jsonb_typeof(x) = 'object')` like the catalog.
- Public = `status = 'published' AND published_at <= now()`. Publishing requires title and body in every content locale (Q6), checked
  by the service (locales are configuration, not schema).
- Slug uniqueness is global, not per locale (Q5): one row, one URL tail in every locale, so hreflang pairs are trivial and the
  product slug rule is reused; per-locale slugs need a child table and a mapping for alternates (later if wanted).
- Indexes: `blog_post_public_idx` on `(published_at DESC, id DESC) WHERE status = 'published'` for the store list and sitemap;
  `blog_post_updated_idx` on `(updated_at DESC, id DESC)` for the admin list.
- No author, no admin id column (Q8): the table holds no personal data.
- Down: `DROP TABLE blog_post` and `DELETE FROM drizzle.__drizzle_migrations_feature_blog WHERE created_at = <journal when>`. Posts are
  lost; cover uploads stay attached with their files. Tested up, down, up, down on a `_test` database by the feature's own spec,
  which also asserts the hand-added foreign key exists after up and is gone after down; feature drift check clean.
- Down order: this down runs before any core down that drops `media_upload` (E1); otherwise the core down fails on the foreign key.

## 6. API (feature `blog`; with the flag off none of these routes exists: `404` like an unknown route)

Store (public, no cookie, no `Cache-Control`, like `GET /store/banners`; `locale` must be in `LOCALES`, else `400`):

- `GET /store/blog/posts?locale=&page=&limit=` - public list, newest first. `limit` 1 to 50 (default 12), `page` >= 1 within the
  catalog offset cap. 200 `{items: [{slug, title, excerpt, publishedAt, updatedAt, cover: {url, width, height, alt} | null}], total,
  page, limit}`. 400 `validation_failed`.
- `GET /store/blog/posts/{slug}?locale=` - one public post. 200 `{slug, title, excerpt, seoTitle, seoDescription, publishedAt,
  updatedAt, cover, content: MarkdownDocument, locales}` (`content` is the parsed AST of the locale's body, never HTML; `locales` are
  the content locales). 404 `not_found` for an unknown slug, a draft or a scheduled post (same body for all three).
- `GET /store/blog/sitemap` - `{items: [{slug, updatedAt}], truncated}`, the public posts, newest first, at most 5 000 (documented
  cap). Over the cap the route answers the newest 5 000 with `truncated: true` and logs a warning with the count; the storefront
  sitemap uses them and logs a warning too. Throwing instead would take every catalog URL out of the sitemap for the sake of the
  oldest posts; a sitemap index is later.

Admin (`/admin/blog/...`, `X-Fluxkit-CSRF: 1` on writes, strict request schemas, `no-store`, `x-fluxkit-permission`):

- `GET /admin/blog/posts?status=&page=&limit=` - `catalog.read`; every post with computed `state` (`draft`, `scheduled`, `published`),
  paginated (default 50). 400.
- `GET /admin/blog/posts/{id}` - `catalog.read`; full post (all locales, source Markdown, cover upload id and URL). 404.
- `POST /admin/blog/posts` - `catalog.write`; `{slug?, title, excerpt?, body?, seoTitle?, seoDescription?, coverUploadId?, coverAlt?}`,
  slug generated from the default-locale title when omitted (`-2`, `-3` on collision). 201 draft, `Location`. 400 (`invalid_slug`, i18n
  codes, `markdown_invalid` at `body.<locale>` with the `line` and a code, `markdown_too_long`, `upload_not_found` at
  `coverUploadId`), 409 `conflict` at `slug`. These save-time errors are the only Markdown feedback in v1 (no preview route).
- `PATCH /admin/blog/posts/{id}` - `catalog.write`; partial, same validation; a published post is re-checked for complete
  translations. 400, 404, 409 `conflict` at `slug`, 409 `rule_violation` `slug_locked` / `translation_incomplete`.
- `POST /admin/blog/posts/{id}/publish` - `catalog.publish`; `{publishedAt?}` (default: the stored date, else now). 200 post. 404,
  409 `rule_violation` `translation_incomplete` (errors name the locale and field).
- `POST /admin/blog/posts/{id}/unpublish` - `catalog.publish`; back to draft, date kept. 200. 404.
- `DELETE /admin/blog/posts/{id}` - `catalog.write`; 204, cover upload stays. 404.

The core OpenAPI document (`docs/api/openapi.json`) stays core-only; the feature's routes are documented in
`docs/api/features-blog.md` (like `features-example.md`).

## 7. Permissions

Recommended (Q7): `catalog.read` (owner, manager, viewer) to read, `catalog.write` (owner, manager) to edit and delete,
`catalog.publish` (owner, manager) to publish and unpublish, the same split as products. No role table change. No audit events
(like banners and catalog edits; recorded in `docs/api/audit.md` known gaps). No domain events.

## 8. Markdown: parsing, sanitizing, rendering (Q4)

- **No HTML at any stage.** Core `content/markdown` parses the source into a typed AST (`MarkdownDocument`); the API returns the AST;
  `MarkdownView` in `@fluxkit/ui` maps each node to a React element (React escapes all text). `dangerouslySetInnerHTML` stays limited
  to `json-ld.tsx`; the storefront source guard is unchanged and a new guard covers `packages/ui`.
- **Subset ("Fluxkit Markdown", ADR 0050 and the admin form's help):** paragraphs, headings `##` to `####` (`#` is a validation error:
  the page title is the only `h1`), emphasis, strong, inline code, fenced code blocks (no highlighting), block quotes, ordered and
  unordered lists (two levels), thematic break, links `[text](href)`. Hard breaks: a trailing backslash.
- **Links:** a storefront path (the rule of core `checkBannerLink`: one leading `/`, no `//`, no dot segments, also `%2e`, no locale
  prefix; the renderer adds `/{locale}`) or an `https` URL with a host and no credentials. Anything else (`http:`, `javascript:`,
  `data:`, `mailto:`, relative paths) is a save error with its line. External links render `rel="noopener noreferrer"`. A link target
  with a control character (`\r`, `\n`, tab, NUL or any other C0/C1 character) or a Unicode bidi control (U+200E, U+200F, U+202A to
  U+202E, U+2066 to U+2069) is refused, also percent-encoded. As built (ADR 0050 decision 4): a raw tab, CR or LF ends the target, so
  those brackets stay literal text and make no link; other raw and every percent-encoded control or bidi character is a save error.
- **Input hygiene:** `\r\n` and lone `\r` are read as line ends; NUL anywhere in the body is a save error (`markdown_invalid`,
  `control_character`); bidi controls in text are kept as text (they are legitimate in prose), never in link targets.
- **Everything else is text:** raw HTML, images (`![...]`, Q10), tables, footnotes and autolinks render literally as text.
- **Limits:** 40 000 characters per locale, 2 000 blocks, nesting depth 4, 300 links, at most 20 000 AST nodes in total, and a
  serialized document of at most 256 KB; a hand-written single-pass scanner with no backtracking regular expressions; a spec feeds
  adversarial inputs (`*` x 40 000, `[` x 40 000, `` ` `` x 40 000, deep `>` and list nesting, many one-character emphasis runs) and
  asserts linear time, the limits AND the size of the output (node count and `JSON.stringify` length under the caps).
- **Never trust storage:** the database keeps only the source; every store read parses it again with the current rules and limits
  (no stored AST). A body that no longer parses (rules tightened after it was saved) is never served: the post answers `404` to the
  store, the API logs the post id and the error code, and the admin shows the line error on the next open.
- **Plain text:** `markdownPlainText(doc)` gives the description fallback (`trimDescription`) and `wordCount` for JSON-LD.
- **Styling:** `MarkdownView` uses existing type-scale, spacing and radius tokens only. If the reviewer finds a new token is needed it
  is a theme-token contract change (red zone).
- No new dependency. The alternatives (Q4 b, c) are dependencies: a red zone with license, size and alternatives stated there.
