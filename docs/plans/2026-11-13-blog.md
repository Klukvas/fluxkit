# Plan: blog as an optional feature (SEO)

Status: proposed (Architect, 2026-11-13). Owner request 2026-11-13, direction approved: an optional feature package with flag `blog`,
posts in Postgres edited in the admin (sanitized Markdown, never raw HTML), storefront `/{locale}/blog` and `/{locale}/blog/{slug}`
with full SEO. Nothing is built. Several steps are red zones (section 15) and wait for the owner's approval; the open decisions are a
quiz in section 17 (recommended option first).

## 1. Goal

- An admin with the catalog permissions writes posts (title, excerpt, Markdown body, SEO title and description per content locale,
  a cover picture from the media service, a slug), keeps them as drafts, publishes, schedules (a future `publishedAt`), unpublishes
  and deletes them.
- Shoppers and crawlers read `/{locale}/blog` (paginated list, newest first) and `/{locale}/blog/{slug}` (one post): server-rendered,
  with `generateMetadata` (title, description, canonical, hreflang alternates, Open Graph with the cover), JSON-LD `BlogPosting` and
  `BreadcrumbList`, sitemap entries, and a header and footer link.
- `blog` is a real feature (AGENTS.md 2.1): with `blog` missing from `FEATURES_ENABLED` there is no UI, no link, no sitemap entry, no
  route (404 like an unknown path), no API endpoint and no database write; removing it means deleting its folders, its flag and its
  migration, checked by the feature matrix.
- Most of the work is the extension points a feature with tables, permissions, media, admin screens and storefront pages needs. None
  exists today (ADR 0046 "Context" listed them when banners went into core). They are built once, as public contracts, and every
  later feature (reviews, wishlist, coupons) reuses them. The blog itself is the smaller part.

## 3. Scope

**v1 (this plan):** posts with draft/published status and `publishedAt` (a future date schedules), slug, title, excerpt, Markdown body,
SEO title and description, cover picture and its alt text, per content locale; admin list, form with preview, publish, unpublish,
delete; storefront list (12 per page) and post page; metadata, JSON-LD, sitemap, header and footer link; feature-matrix modes.

**Out of scope (later, each its own plan):** categories and tags, comments, RSS/Atom, related products and product links in posts,
inline images in the body (Q10), authors (Q8), redirects for changed slugs, search over posts, a home-page "latest posts" section
(needs a home slot for features), demo posts in `pnpm seed` (needs a feature seed hook), admin help articles from features, an
on-demand cache revalidation hook, audit entries for post edits, per-locale slugs (Q5), AMP.

## 4. Architecture: the shape of a feature and its extension points

### 4.1 Where the blog lives (recommended, Q1)

A feature is **one package plus one slice folder per app**, each deletable, none imported by core code:

| Part | Folder | Holds |
|---|---|---|
| API | `packages/features/blog/` (`@fluxkit/feature-blog`, `"fluxkit": {"feature": "blog"}`) | Nest module (store and admin controllers, service, repository), Drizzle table, `drizzle/` migrations with `.down.sql`, `personalDataInventory`, README, specs |
| Storefront | `apps/storefront/src/app/[locale]/(feature-blog)/` | `layout.tsx` (re-exports `(site)/layout` like `(pages)` does, no `loading.tsx`), `blog/page.tsx`, `blog/[slug]/page.tsx`, private `_feature/` (manifest `feature.ts`, data reads, views, metadata and JSON-LD builders, `messages/{uk,en}.json`, specs) |
| Admin | `apps/admin/src/features/blog/` | manifest `feature.ts`, lazy area (list, form, preview), `messages/{uk,en}.json`, specs |

Why slices instead of one package with storefront and admin entry points: a slice inside its app reuses the app's own helpers (SEO
builders, `JsonLd`, `StoreImage`, the data cache, the admin form, upload panel and request helpers) without making each of them a
public SemVer contract, and the apps keep one React instance (a package rendered into Next needs a workspace dependency, which breaks
`pnpm install` once the folder is deleted, or a path import outside the app root). Cost: removal deletes three folders, and AGENTS.md
2.1 says "deleting its folder" (owner's file; wording change needed, section 15).

Core never imports a slice: a dependency-cruiser rule refuses imports from app code into `apps/storefront/src/app/[locale]/(feature-*)/`
and `apps/admin/src/features/*/`, except from the one registry module of each app; slices may import their app (feature -> core
direction) and never each other.

### 4.2 Extension points (all new public contracts, listed in a new `docs/contracts/features.md`, ADR 0049)

- **E1. Feature migrations.** A feature with tables ships `drizzle.config.ts` (its own schema file), `drizzle/` with its own
  `meta/_journal.json` and a hand-written `.down.sql` per migration. `pnpm db:migrate` applies the core journal first, then the
  journal of every feature in `FEATURES_ENABLED`, each recorded in its own table `drizzle.__drizzle_migrations_feature_<name>`, all
  under the existing `MIGRATION_LOCK_KEY`, with the same "newer than this code" refusal. A disabled feature is never migrated (no
  database side effect). The API refuses to start when an enabled feature has unapplied migrations (names the feature, not the
  database). New `pnpm db:feature-down <name>` runs that feature's `.down.sql` files newest first (refuses `NODE_ENV=production`
  without `--allow-production`, like the seed); it is the first removal step while the folder still exists. `check-schema-drift.sh`
  also checks every feature that has a `drizzle.config.ts`. Feature tables may reference core tables (here `media_upload`); core never
  references a feature table.
- **E2. API kit for features (Q2).** New package `packages/api-kit` (`@fluxkit/api-kit`; depends only on `@nestjs/common`, `zod` and
  `@fluxkit/core`, all already pinned: no new external dependency). It receives, moved from `apps/api` with re-exports left in place
  so no other import changes: `ProblemException` and the problem codes (one class identity, so the global filter keeps its `instanceof`),
  `RequirePermission`, `AdminController` and the default-permission metadata, `ZodValidationPipe`. It adds the DI tokens below.
  Features and providers import it; it never imports `apps/`.
- **E3. Database handle.** Token `FEATURE_DATABASE`: the API's own Drizzle instance (one pool), typed loosely so a feature uses its
  own table objects; transactions through it are ordinary Drizzle transactions that core ports accept (E4).
- **E4. Media port.** Token `MEDIA_PORT` (interface in core `media`, implementation in `apps/api/src/media`): `markAttachedByIds(tx,
  refs)` (the existing method, inside the caller's transaction, `upload_not_found` at the caller's field) and `describeUploads(ids)`
  (`{id, url, width, height}` for the store answer). A feature never reads `media_upload` directly.
- **E5. Locale settings.** Token `LOCALE_SETTINGS` (`defaultLocale`, `locales`) for `validateI18nText`.
- **E6. Privacy inventory of a feature.** The feature package also exports `personalDataInventory` (the core entry shape); the
  loader merges entries of enabled features; a spec inside each feature checks that every column of its Drizzle tables is classified;
  the core source guard that refuses feature tables (ADR 0033) is changed to accept them through this export. The feature README holds
  its inventory rows (deleted with it).
- **E7. Enabled features in the config endpoints.** Additive `features: string[]` (the names in `FEATURES_ENABLED` that loaded, sorted)
  on `GET /store/config` and `GET /admin/config`. One runtime flag (the API's) switches all three apps; the storefront and the admin
  read no new variable (`pnpm check:env` unchanged).
- **E8. Storefront slice.** A route group `app/[locale]/(feature-<name>)/` with a `layout.tsx` and no `loading.tsx` above any page
  (added to `mustAnswerRealNotFound`). Every page and `generateMetadata` first reads the config (60 s cache) and calls `notFound()`
  when `<name>` is not in `features`, before any feature API call. A spec refuses a feature path that is also a shop page slug.
- **E9. Storefront feature registry.** `apps/storefront/src/features/registry.generated.ts` (git-ignored) is written from the slices
  present on disk by `scripts/generate-feature-registry.mjs`, run before `dev`, `build`, `typecheck` and `test` of the storefront
  (Turbo `dependsOn`), and empty without slices. First check in PR 4a whether the Next 16.4.3 docs in `node_modules/next/dist/docs/`
  support a glob import (`import.meta.glob` or `require.context`) under Turbopack; if so use it and drop the generator. A manifest
  `_feature/feature.ts` exports `{name, navigation: [{placement: "header" | "footer", labelKey, path}], sitemap(ctx) => Promise<{path,
  lastModified?}[]>, messages: {uk, en}}`. Messages live under `features.<name>.` (a key outside it, or already present, fails the
  build, like `custom.`), merged before the fork overrides, and the legal release guard reads them too.
- **E10. Feature links in the header and footer.** `layout/header-layout.ts` appends the `header` links of enabled features after
  `navigation.links`; `layout/footer-layout.ts` appends `footer` links to the `shopPages` group (or a group of their own at the end when
  the config has none). Optional `featureLinks?: boolean` (default `true`) on `HeaderConfig` and `FooterConfig` lets a fork hide them,
  additive to `docs/contracts/header-footer.md`; the fork-owned config files are not edited. With no enabled feature the markup is byte
  for byte unchanged (frozen markup specs stay green).
- **E11. Admin feature registry.** `apps/admin/src/features/registry.ts` finds `./*/feature.ts` with Vite `import.meta.glob` (lazy,
  so a feature costs the entry chunk only its manifest; `build-output.spec.ts` keeps the budget). A manifest declares
  `{name, routes: [{id, path, permission, titleKey, load}], navigation: {group, labelKey, routeId}, messages}`; route ids are
  `feature.<name>.<screen>`. A route shows only when its feature is in `GET /admin/config` `features` and the role has the permission.
- **E12. Generic safe Markdown** (section 8): parser and AST types in core `content/markdown`, renderer `MarkdownView` in `@fluxkit/ui`.
  Not blog-specific: product descriptions could use it later.

## 5. Data model (feature migration `packages/features/blog/drizzle/0000_blog_post.sql` + `.down.sql`)

Table `blog_post`:

| Column | Type | Rule |
|---|---|---|
| `id` | uuid pk | |
| `slug` | text not null | core `SLUG_PATTERN`, 1 to 160; UNIQUE (`blog_post_slug_key`); one slug for every locale (Q5); locked once the post was first published (`published_at` not null) |
| `status` | text not null default `'draft'` | CHECK in (`draft`, `published`) |
| `published_at` | timestamptz null | set on the first publish (default now, an admin may pick another instant in [2000, 2200)); kept on unpublish, so republishing keeps the date; CHECK `status = 'draft' OR published_at IS NOT NULL` |
| `title` | jsonb not null | `I18nText`, 1 to 120; default locale required on create |
| `excerpt` | jsonb null | plain text, 0 to 300; the list teaser and the meta description fallback |
| `body` | jsonb not null default `'{}'` | Markdown source per locale, 0 to 40 000 characters, must parse (section 8) |
| `seo_title` | jsonb null | 0 to 70 |
| `seo_description` | jsonb null | 0 to 160 |
| `cover_upload_id` | uuid null, FK `media_upload(id)` ON DELETE RESTRICT | marked attached in the save's transaction (E4) |
| `cover_alt` | jsonb null | 0 to 150; empty = decorative |
| `created_at`, `updated_at` | timestamptz not null | `updated_at` is `dateModified` and the sitemap `lastModified` |

- Every jsonb column has `CHECK (jsonb_typeof(x) = 'object')` like the catalog.
- Public = `status = 'published' AND published_at <= now()`. Publishing requires title and body in every content locale (Q6), checked
  by the service (locales are configuration, not schema).
- Slug uniqueness is global, not per locale (Q5): one row, one URL tail in every locale, so hreflang pairs are trivial and the
  product slug rule is reused; per-locale slugs need a child table and a mapping for alternates (later if wanted).
- Indexes: `blog_post_public_idx` on `(published_at DESC, id DESC) WHERE status = 'published'` for the store list and sitemap;
  `blog_post_updated_idx` on `(updated_at DESC, id DESC)` for the admin list.
- No author, no admin id column (Q8): the table holds no personal data.
- Down: `DROP TABLE blog_post` and `DELETE FROM drizzle.__drizzle_migrations_feature_blog WHERE created_at = <journal when>`. Posts are
  lost; cover uploads stay attached with their files. Tested up, down, up, down on a `_test` database; feature drift check clean.

## 6. API (feature `blog`; with the flag off none of these routes exists: `404` like an unknown route)

Store (public, no cookie, no `Cache-Control`, like `GET /store/banners`; `locale` must be in `LOCALES`, else `400`):

- `GET /store/blog/posts?locale=&page=&limit=` - public list, newest first. `limit` 1 to 50 (default 12), `page` >= 1 within the
  catalog offset cap. 200 `{items: [{slug, title, excerpt, publishedAt, updatedAt, cover: {url, width, height, alt} | null}], total,
  page, limit}`. 400 `validation_failed`.
- `GET /store/blog/posts/{slug}?locale=` - one public post. 200 `{slug, title, excerpt, seoTitle, seoDescription, publishedAt,
  updatedAt, cover, content: MarkdownDocument, locales}` (`content` is the parsed AST of the locale's body, never HTML; `locales` are
  the content locales). 404 `not_found` for an unknown slug, a draft or a scheduled post (same body for all three).
- `GET /store/blog/sitemap` - `{items: [{slug, updatedAt}]}`, every public post, newest first, at most 5 000 (documented cap; a sitemap
  index is later).

Admin (`/admin/blog/...`, `X-Fluxkit-CSRF: 1` on writes, strict request schemas, `no-store`, `x-fluxkit-permission`):

- `GET /admin/blog/posts?status=&page=&limit=` - `catalog.read`; every post with computed `state` (`draft`, `scheduled`, `published`),
  paginated (default 50). 400.
- `GET /admin/blog/posts/{id}` - `catalog.read`; full post (all locales, source Markdown, cover upload id and URL). 404.
- `POST /admin/blog/posts` - `catalog.write`; `{slug?, title, excerpt?, body?, seoTitle?, seoDescription?, coverUploadId?, coverAlt?}`,
  slug generated from the default-locale title when omitted (`-2`, `-3` on collision). 201 draft, `Location`. 400 (`invalid_slug`, i18n
  codes, `markdown_invalid` with the line, `markdown_too_long`, `upload_not_found` at `coverUploadId`), 409 `conflict` at `slug`.
- `PATCH /admin/blog/posts/{id}` - `catalog.write`; partial, same validation; a published post is re-checked for complete
  translations. 400, 404, 409 `conflict` at `slug`, 409 `rule_violation` `slug_locked` / `translation_incomplete`.
- `POST /admin/blog/posts/{id}/publish` - `catalog.publish`; `{publishedAt?}` (default: the stored date, else now). 200 post. 404,
  409 `rule_violation` `translation_incomplete` (errors name the locale and field).
- `POST /admin/blog/posts/{id}/unpublish` - `catalog.publish`; back to draft, date kept. 200. 404.
- `DELETE /admin/blog/posts/{id}` - `catalog.write`; 204, cover upload stays. 404.
- `POST /admin/blog/preview` - `catalog.write`; `{markdown}` (at most 40 000 characters) -> 200 `{content: MarkdownDocument, errors:
  [{line, code}]}`; the admin bundle never contains the parser (it does not bundle core). 400 for an oversized body.

The core OpenAPI document (`docs/api/openapi.json`) stays core-only; the feature's routes are documented in
`docs/api/features-blog.md` (like `features-example.md`).

## 7. Permissions

Recommended (Q7): `catalog.read` (owner, manager, viewer) to read, `catalog.write` (owner, manager) to edit and delete,
`catalog.publish` (owner, manager) to publish and unpublish, the same split as products. No role table change. No audit events
(like banners and catalog edits; recorded in `docs/api/audit.md` known gaps). No domain events.

## 8. Markdown: parsing, sanitizing, rendering (Q4)

- **No HTML at any stage.** Core `content/markdown` parses the source into a typed AST (`MarkdownDocument`); the API returns the AST;
  `MarkdownView` in `@fluxkit/ui` maps each node to a React element (React escapes all text). `dangerouslySetInnerHTML` stays limited
  to `json-ld.tsx`; the storefront source guard is unchanged and a new guard covers `packages/ui`.
- **Subset ("Fluxkit Markdown", ADR 0050 and the admin form's help):** paragraphs, headings `##` to `####` (`#` is a validation error:
  the page title is the only `h1`), emphasis, strong, inline code, fenced code blocks (no highlighting), block quotes, ordered and
  unordered lists (two levels), thematic break, links `[text](href)`. Hard breaks: a trailing backslash.
- **Links:** a storefront path (the rule of core `checkBannerLink`: one leading `/`, no `//`, no dot segments, also `%2e`, no locale
  prefix; the renderer adds `/{locale}`) or an `https` URL with a host and no credentials. Anything else (`http:`, `javascript:`,
  `data:`, `mailto:`, relative paths) is a save error with its line. External links render `rel="noopener noreferrer"`.
- **Everything else is text:** raw HTML, images (`![...]`, Q10), tables, footnotes and autolinks render literally as text.
- **Limits:** 40 000 characters per locale, 2 000 blocks, nesting depth 4, 300 links; a hand-written single-pass scanner with no
  backtracking regular expressions; a spec feeds adversarial inputs (`*` x 40 000, `[` x 40 000, deep `>` and list nesting) and
  checks linear time and the limits.
- **Plain text:** `markdownPlainText(doc)` gives the description fallback (`trimDescription`) and `wordCount` for JSON-LD.
- **Styling:** `MarkdownView` uses existing type-scale, spacing and radius tokens only. If the reviewer finds a new token is needed it
  is a theme-token contract change (red zone).
- No new dependency. The alternatives (Q4 b, c) are dependencies: a red zone with license, size and alternatives stated there.

## 9. Storefront

- **Routes:** `/{locale}/blog` (`?page=N`; a missing or bad page redirects to the canonical like the catalog) and
  `/{locale}/blog/{slug}` in the slice (E8). Real 404 for a draft, scheduled or unknown post and for the flag off.
- **List page:** heading, cards (cover 16:9 in a fixed frame via `StoreImage`, title link, date in the locale's format, excerpt),
  pagination; empty state ("No posts yet", link to the catalog); outage: the inline error of the other data pages; never a broken page.
- **Post page:** breadcrumbs (Home, Blog, title), `h1`, date, cover (priority image, width and height from the API: no layout shift),
  `MarkdownView`, a link back to the list.
- **Metadata (`generateMetadata`, builders in the slice in the style of `lib/page-metadata.ts`):** list: title and description from
  messages, canonical `/{locale}/blog` (`?page=N` from page 2, `noindex, follow` from page 2 like `listingRobots`), hreflang via
  `languageAlternates` (every locale plus `x-default`), brand `og:image`. Post: title `seoTitle ?? title`, description `seoDescription
  ?? excerpt ?? trimDescription(plainText)`, canonical `/{locale}/blog/{slug}`, alternates for every locale (complete translations,
  Q6), Open Graph `type: article`, `publishedTime`, `modifiedTime`, cover as `og:image` with width, height and alt (else the brand image).
- **JSON-LD (through `JsonLd`):** `BlogPosting` {`headline` (title, at most 110 characters), `description`, `image` [cover URL],
  `datePublished`, `dateModified`, `inLanguage`, `wordCount`, `author` and `publisher` = `Organization` {shop name from the messages,
  `url` origin, `logo` when `config/brand.ts` has an image logo}, `mainEntityOfPage` canonical}; `BreadcrumbList` on both pages
  (`breadcrumbJsonLd`).
- **Sitemap:** `loadSitemap` asks each enabled feature of the registry for its paths; blog gives `/blog` and `/blog/{slug}` (with
  `updatedAt`) from `GET /store/blog/sitemap` (1 h cache); `buildSitemap` takes them as `featurePages` after the shop pages, per
  locale with alternates. A refused feature read throws, like a refused product page (a silently short sitemap hides pages).
- **Navigation:** the manifest declares one header link and one footer link "Blog" (`features.blog.nav`), shown only with the flag on
  (E10).
- **Caching:** list and post reads in the Next data cache for 60 s (`CATALOG_REVALIDATE_SECONDS`), tag `feature:blog`; sitemap 1 h.
  A publish, edit or unpublish shows within 60 s. The last-good copy on an outage applies to blog reads too, so during an API outage
  an unpublished post can be served from memory: accepted and documented.
- **Images:** the cover follows the product image rule (`allowedImageUrl`; production needs the media host in `STOREFRONT_IMAGE_HOSTS`).
- **i18n:** every string under `features.blog.*` in `_feature/messages/{uk,en}.json`; dates through the existing date helper; no
  hardcoded text or colour (source guards cover the slice).

## 10. Admin

- Navigation group "Storefront" (next to Home banners): "Blog" (E11), shown with the flag on and `catalog.read`.
- **List:** title (UI language, else the default locale), state badge (text, not colour only), published and updated dates, filter by
  state, pagination, "New post"; states: loading, empty, error with retry, `403`.
- **Form (create and edit page):** slug (suggested from the title; read-only with a note once published), per content locale: title,
  excerpt, body (textarea with a short syntax help), SEO title and description with character counters; cover through the existing
  upload panel and queue (blocked with an explanation when `media.uploadsEnabled` is false) and its alt text; preview tab per locale
  (`POST /admin/blog/preview`, debounced, rendered by `MarkdownView`, labelled "approximate"); save, publish (date and time with the
  time zone shown), unpublish, delete with a confirmation dialog; unsaved-changes guard; server errors on their fields
  (`submit-errors.ts`); focus via `useFocusAfterCommit`. Viewer: read-only.
- Rules repeated client-side only where the form needs them (lengths, slug pattern) with a parity spec against core, the banners
  pattern; Markdown errors come from the preview route.
- Messages under `features.blog.*` in the slice; tokens only.

## 11. Privacy, security, limits

- **Privacy:** `blog_post` holds no personal data: every column classified `none` in the feature's `personalDataInventory` (E6) and
  the feature README; no author, no admin id. The form and the README say that posts are public and must not contain personal data.
  Logs and errors carry ids and codes only.
- **XSS:** no HTML anywhere (section 8); link schemes restricted at save and again at render; JSON-LD through `serializeJsonLd`.
- **Authorization:** every admin route declares its permission (E2); store routes return public posts only and never `status`, ids or
  upload ids.
- **Rate limits:** none on the store blog routes, the same known launch blocker as the other plain catalog store routes (HANDOFF next
  step 5); each is one indexed query. `POST /admin/blog/preview` is admin-only, size-capped and linear.
- **CSRF and caching:** existing `/admin` middleware.

## 16. Risks, rollback, not verified

- **Size:** the extension points are about two thirds of the work; a smaller path is Q1 (c) (blog UI in core apps) at the cost of 2.1.
- **Next routing assumptions** (static `blog` over `(pages)/[page]`, route-group layouts, real 404 without `loading.tsx`, generator vs
  glob under Turbopack) come from reading the code and the existing route guards, not from the Next 16.4.3 docs; PR 4a checks them
  first and stops with findings if one fails.
- **Header width:** one more header link can overflow small screens in some fork orders (the known 320 px limit); navigation links
  show only from `xl`; `featureLinks: false` is the escape.
- **E2E with the flag on** changes the header for every storefront spec; header assertions and first-HTML caps may need updates
  (PR 4b), or the blog specs get their own API process.
- **Deploy:** the migrate step must see `FEATURES_ENABLED`, or the API refuses to start after enabling (loud, by design).
- **Cache:** up to 60 s stale after publish or unpublish; outage last-good copies can show an unpublished post.
- **Slug lock:** a typo in a published slug cannot be fixed without delete and re-create (redirects are later).
- **Removal of a used blog:** `db:feature-down` deletes every post; uploads stay attached (known media "no purge" gap).
- **Rollback:** each PR reverts on its own; with only PR 1 merged nothing changes for a shop without features (defaults identical).
- **Not verified:** everything; this is a plan.

## 17. Open decisions (quiz; recommended option first)

1. **Shape across apps:** (a) package for the API plus one slice folder per app, discovered by registries (recommended);
   (b) one package with storefront and admin entry points and host "kits" passed in (one folder, but a large public kit contract and
   React/build resolution risk); (c) only the API as a feature, blog pages and admin screens in core apps gated by `features`
   (smallest, breaks 2.1: core names the feature).
2. **How features reach API building blocks:** (a) new `@fluxkit/api-kit` package with the moved classes and the tokens (recommended);
   (b) constants and types in core only, features use raw Nest and the filter recognises a marked problem body (ADR 0018 style, two
   problem paths to keep in sync); (c) the loader passes a kit object to a `featureModule(kit)` factory (decorators built in closures,
   awkward to test).
3. **Feature migrations:** (a) own journal and migrations table per feature, applied by `db:migrate` for enabled features, startup
   refuses unapplied ones (recommended); (b) feature migrations in the core journal (removal leaves core files and history); (c) the
   feature creates its tables at startup (no down, drift-blind).
4. **Markdown:** (a) own subset parser in core, AST over the API, `MarkdownView` in ui, never HTML, no dependency (recommended);
   (b) `mdast-util-from-markdown` + `micromark` (MIT, about twenty small packages, size not measured) feeding the same AST and
   renderer (full CommonMark, a dependency to approve); (c) `marked` (MIT) + `sanitize-html` (MIT, pulls `htmlparser2` and `postcss`)
   rendered as an HTML string through `dangerouslySetInnerHTML` (breaks the storefront guard; the sanitizer config becomes
   security-critical).
5. **Slug:** (a) one slug for all locales, globally unique, locked after the first publish (recommended; the product rule); (b) a slug per
   locale (`blog_post_slug(post_id, locale, slug)`, unique per locale; better local keywords, more schema and hreflang mapping);
   (c) one slug, editable at any time (broken URLs until redirects exist).
6. **Translations:** (a) publishing needs title and body in every content locale (recommended; complete hreflang, banners precedent);
   (b) publish per locale, untranslated locales 404 and drop from hreflang and the sitemap; (c) per-field fallback to the default
   locale like the catalog (text in the wrong language under `/en`).
7. **Permissions:** (a) `catalog.read`/`catalog.write`, publish with `catalog.publish` (recommended); (b) `catalog.read`/`catalog.write`
   only; (c) new `content.read`/`content.write` (role table and auth contract change).
8. **Author:** (a) none; JSON-LD author and publisher = the shop as `Organization` (recommended; no personal data); (b) a free-text
   display name per post (public personal data, inventory and erasure rules); (c) the signed-in admin as author (links staff accounts
   to public content).
9. **Template default:** (a) flag off in code and `.env.example`; on in e2e, the feature matrix and wherever the owner enables it
   (recommended: an empty blog link on a fresh shop looks broken); (b) on in `.env.example` with the empty state; (c) on with demo posts
   (needs a feature seed hook first).
10. **Images in the body:** (a) none in v1, cover only (recommended); (b) uploaded images by id (`![alt](upload:<id>)`), attached in the
   save's transaction; (c) any `https` image (image hosts, CSP and tracking concerns).
