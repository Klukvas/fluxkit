## Goal

A shop built from this template can be deployed on one Linux host with Docker: reproducible images for the API and the storefront, the admin SPA served by the edge proxy, a production Compose example, an edge proxy configuration that is actually run and checked, and a readiness checklist (secrets, migrations, backups, logs, limits). Every claim below is either verified by a command in this sandbox or marked "not verified".

## Existing functionality found (verified 2026-10-29 on `origin/main` at `b6421e0`)

- **Docker is available in this sandbox** (`docker --version` 29.8.2, Compose v5.6.0, buildx 0.37.1; the daemon was not running and was started by hand with `dockerd`; images can be pulled). `nginx`, `caddy` and `hadolint` are not installed on the host, but their images can be pulled (`nginxinc/nginx-unprivileged:1.29.8-alpine`, `caddy:2.10-alpine`), so `nginx -t`, `caddy validate` and a running stack are possible. (`docs/HANDOFF.md` says "no Docker daemon"; that is no longer true here.)
- **API start**: `apps/api/dist/main.js` (`loadEnv(process.env)`, refuses without `ORDER_TOKEN_SECRET`, `prepareDefaultMediaDirectory` creates nothing in production, Swagger UI at `/docs`, `app.listen(PORT)`). `createApp` sets Express `trust proxy` to `TRUST_PROXY` (hop count, default 0) and mounts the raw-body reader on `/webhooks/payments` before the JSON parser (64 KiB, `PAYMENT_LIMITS.webhookBodyMaxBytes`). The npm scripts use `node --env-file=../../.env`; an image must call `node dist/...` directly with the environment from the orchestrator.
- **The API depends on the monorepo layout at run time**: `DEFAULT_FEATURES_DIR` is `<dist>/../../../../packages/features` and the provider loader scans `<repo>/packages/providers` (dynamic `import()` of each enabled package's `dist`); the migrator reads `apps/api/drizzle` relative to `dist`. Feature and provider packages are NOT dependencies of `@fluxkit/api` in the lockfile graph, so `turbo prune @fluxkit/api` or `pnpm deploy` would leave them out. Plugins resolve `@nestjs/common` as a peer through the pnpm virtual store (same physical copy as the API's).
- **Commands**: `dist/database/migrate.js` (forward only, advisory lock `7426002`, safe with several starters, refuses a database newer than the code), `dist/jobs/run-once.js` (exit 2 when a scheduler holds lock `7426003`), `dist/auth/create-admin.js`, `dist/auth/unlock-admin.js`, `dist/seed/seed.js` (refuses `NODE_ENV=production`).
- **Scheduler**: in process (`SCHEDULER_ENABLED`, default true; `SCHEDULER_INTERVAL_SECONDS`), jobs 1 to 11 (`docs/api/jobs.md`: order expiry, reservation sweep, event dispatch, cart, session and event cleanup, media cleanup job 7, tracking job 8, mail send and purge jobs 9 and 10, payment jobs). One instance works per tick (Postgres advisory lock). No queue: **Redis, BullMQ and Meilisearch are not used by any running code** (only by `apps/api/src/spikes/*.spec.ts`; `grep` for `ioredis|bullmq|meilisearch|redisUrl` outside specs finds nothing).
- **Per-process state** (why the API must run as ONE instance today): the IP rate limits and the login throttle (`IpWindowLimiter`, ADR 0009, 0016), the reset and verification limits (email step 7), the shipping directory cache and provider gate (shipping step 6), the mail pacing (8 calls per second per process), and the local media driver (one disk, ADR 0028). Several instances multiply every limit and split media files.
- **Health**: `GET /health` (database `select 1`, 3 s timeout, `503` otherwise). No scheduler or provider status.
- **Storefront**: `next build` / `next start` (Next 16.4.2), no `output: "standalone"`; `next.config.ts` is evaluated again by `next start` (image optimizer allow-list from `STOREFRONT_IMAGE_HOSTS`; the CSP is frozen at build time, so the variable is needed at build AND at start with the same value). It sends its own security headers including `Strict-Transport-Security: max-age=31536000` in production. The e2e suite runs `pnpm start` (`next start`), so that is the tested way to run it. `.next/cache` is written at run time (fetch cache, image cache).
- **Admin**: static `vite build` into `apps/admin/dist` (base `/admin-ui/`); headers in `apps/admin/security-headers.ts` (incl. the new `style-src-attr 'unsafe-inline'`), pinned by `security-headers.spec.ts`; the README shows nginx and Caddy blocks that were never run.
- **Webhooks**: `POST /webhooks/payments/{provider}` (ADR 0032), rate limit `paymentWebhook` per address, JSON only, 64 KiB, `200`/`401`/`404`/`413`/`503`. **The README proxy examples do not route `/webhooks`**: behind them a provider's notification would reach the storefront (404) and paid orders would only be found by the reconcile job.
- **Trusted proxy**: `apps/api/src/rate-limit/trust-proxy.spec.ts` already proves hop count 1 (forwarded address counted, IPv6 by /64, client-prefixed entries ignored) and 0 (header ignored). The keying is correct for an edge proxy that REPLACES `X-Forwarded-For` with `$remote_addr`. No code fix is needed (checked again in step B).
- **Headers**: Express sends `X-Powered-By: Express` and Next sends `X-Powered-By: Next.js` (neither app disables it).
- **`.env.example`**: no automated check that it lists every variable the code reads.
- **CI**: `compose` job starts `infra/docker-compose.yml`; no image build. Dependabot watches Docker images in `/infra` only.

## Decisions (with evidence)

1. **Images: one root `Dockerfile` with three targets** `api`, `storefront`, `edge` sharing one build stage (`pnpm fetch` from the lockfile, then `pnpm install --offline --frozen-lockfile`, `pnpm build`). One build of the workspace serves all three; the targets differ only in what they copy.
   - **No `turbo prune` / `pnpm deploy`**: the API loads features and providers by directory scan, which neither tool can see (evidence above). Instead each runtime stage reinstalls production dependencies only (`pnpm install --offline --prod --filter <app>... --filter ./packages/features/* --filter ./packages/providers/*`) in the monorepo layout and copies the built `dist` folders, so the image layout is the one the tests and the feature matrix run.
   - **Base `node:22.22.0-bookworm-slim` pinned by digest** (glibc: the same `sharp` binary family as CI and the media memory measurements in ADR 0028; Alpine would switch to the musl build, unmeasured). pnpm 10.28.0 through corepack (from `packageManager`). The runtime stages run as the image's `node` user (uid 1000), no pnpm or compilers in the final layers.
   - **Storefront runs `next start`** (not `output: "standalone"`): it is what the e2e suite tests, and standalone would freeze `next.config.ts` (the image allow-list) at build time and change the e2e start command. Cost: a bigger image (measured in step B). Follow-up candidate if size matters.
   - **Edge image = nginx (unprivileged) + the built admin SPA** (ADR 0027: the proxy serves `/admin-ui`). Listens on 8080/8443 as a non-root user; Compose maps 80/443.
2. **No separate worker image.** The scheduler runs inside the single API instance (it already does, under its lock). A second process would add nothing while every limit and cache is per process. `SCHEDULER_ENABLED=false` plus `node dist/jobs/run-once.js` from a host cron stays possible. Documented: **run exactly one API replica** until the in-memory limits move to Redis (HANDOFF next step 4) and media moves to shared storage.
3. **Production Compose example `infra/docker-compose.prod.yml`**: `postgres` (17-alpine, no published port), `migrate` (the API image running `dist/database/migrate.js`; `api` waits for it with `service_completed_successfully`, so migrations run before every start), `api`, `storefront`, `edge` (the only published ports, 80 and 443). **Redis and Meilisearch are left out** because no running code uses them (evidence above); they are added with the search or queue plan. Secrets come from an env file the owner writes (`infra/production.env`, git-ignored; template `infra/production.env.example`); nothing is baked into an image. Only the API gets the API's secrets; the storefront and the edge get only their own variables. Read-only root file systems with `tmpfs` where a process writes (`/tmp`, `.next/cache`, nginx's runtime dirs), `no-new-privileges`, all capabilities dropped, log rotation for the `json-file` driver, named volumes for Postgres and media.
4. **Edge proxy: nginx is the default and is tested; Caddy stays an alternative** (`infra/proxy/Caddyfile`, checked with `caddy validate` and the same smoke test if time allows, otherwise marked "validated only"). nginx terminates TLS from mounted certificate files (`fullchain.pem`, `privkey.pem`; how to obtain and renew them is the owner's choice: certbot `--webroot` through the port-80 ACME location, DNS-01, or a load balancer); port 80 serves `/.well-known/acme-challenge/` and redirects everything else to https.
   - Routes: `/store`, `/admin`, `/media`, `/webhooks/payments` (bare prefixes and subpaths) to the API; `/admin-ui` from the files with the `index.html` fallback; everything else to the storefront. **`/docs`, `/docs-json` and `/health` are not routed** (the owner's open decision about Swagger in production stays open; the default is "not public").
   - `X-Forwarded-For $remote_addr` (replace, the stricter choice) and `TRUST_PROXY=1`; `X-Forwarded-Proto https`.
   - `/webhooks/payments/`: `client_max_body_size 64k` (the API's own limit), request buffering ON (bodies are tiny; nginx forwards the bytes unchanged, so the raw-body signature check sees what the provider sent), no caching, POST-only is left to the API (it answers 404/405 itself).
   - `/admin`: `client_max_body_size 12m`, `proxy_request_buffering off` with HTTP/1.1 (as the README advises, now run against a real nginx).
   - `/media`: no `add_header`, no cache rule (the API owns `Cache-Control`).
   - **Headers**: the edge is the one owner of HSTS (`max-age=31536000`, no `includeSubDomains`/`preload` without the owner): set on the server and repeated in the `/admin-ui` locations, and Next's own copy is hidden (`proxy_hide_header`) so a response never carries two. `X-Powered-By` is hidden for the API and the storefront. The `/admin-ui` headers are copies of `apps/admin/security-headers.ts` (with `style-src-attr 'unsafe-inline'`); image hosts come from `STOREFRONT_IMAGE_HOSTS` at container start (validated with the same host-name rule). A new spec keeps the copies in sync (decision 6).
   - Real client IPs through Docker: published ports keep the client's IPv4 address (DNAT), but an IPv6 client reaching an IPv4-only bridge goes through `docker-proxy` and is seen as the gateway address, so all IPv6 shoppers would share one window. Documented with the remedies (enable IPv6 in Docker, or run the edge with `network_mode: host`, or a host proxy); verified as far as the sandbox allows.
5. **`docs/deployment.md`**: the readiness checklist and runbook (prerequisites, env var checklist with the secrets list, first start, migration order and manual rollback, admin creation, updates with zero-downtime notes, backups of Postgres AND the media volume, logs and retention, limits of one instance, what is not verified). README links to it; the README proxy sections point to the tested files.
6. **Guards (cheap, deterministic)**:
   - `scripts/check-env-example.mjs` (`pnpm check:env`, run in the CI `verify` job): every environment variable that runtime code reads (the `loadEnv` and `loadStorefrontEnv` schema keys, the provider parsers, `process.env.X` reads in apps and packages; tests, e2e helpers and spikes excluded or listed) must appear in `.env.example` as `NAME=` or `# NAME=`; an explicit allow-list with reasons for the rest (`NODE_ENV`, tooling variables). Fails with the missing names.
   - `apps/admin/edge-proxy-headers.spec.ts`: renders the nginx template's `/admin-ui` header lines and compares them with `adminSecurityHeaders()` (with and without image hosts) and the cache headers with `ADMIN_CACHE_CONTROL`; fails when one copy drifts.
7. **CI job `docker`** (only if it is deterministic and reasonably fast when run here): build the three targets without pushing and run `scripts/deploy-smoke.sh` (self-signed certificate, the production Compose file, curl checks of routing, headers, the webhook route, `/docs` not public, a migration on an empty database). If the measured time is too long, it is proposed as a follow-up instead. Dependabot gets the root directory for Docker so the pinned base images are updated.

## Not changed (and why)

- No application code change is planned. If step B finds the trust-proxy handling wrong, the fix comes with a failing spec first and is called out; the evidence above says it is right.
- No new runtime dependency. Docker images (node, nginx-unprivileged, postgres, caddy) are external services/tools; their licences go into `docs/dependencies.md` (nginx: BSD-2-Clause; Caddy: Apache-2.0; Postgres: PostgreSQL licence; node image: MIT for Node, Debian packages).
- `docs/HANDOFF.md` and `AGENTS.md` are not edited by this task (owner files); the needed edits are listed in the report.

## Risks

- The images are only as tested as the smoke test: no TLS certificate from a real CA, no real DNS, no payment provider, no real mail, one host.
- `next start` with a read-only root needs `.next/cache` writable (tmpfs: the fetch and image caches are lost on restart, which is acceptable).
- The Next image optimizer fetches uploaded images from the PUBLIC shop URL from inside the storefront container (ADR 0028): the host must reach its own public address (hairpin NAT), or images show the placeholder.
- Migrations run forward automatically on every `up`; a rollback is manual (`apps/api/drizzle/NNNN_*.down.sql`), so take a backup before an update.
- Zero downtime is NOT provided by the example (one API instance; `docker compose up -d` recreates it). Additive migrations keep the old code working while they run; a rolling update needs a second instance, which the in-memory limits forbid today.
