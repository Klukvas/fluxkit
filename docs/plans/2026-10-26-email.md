## Goal
A shop sends transactional email through a provider plugin (Resend first) behind a core port. Customers reset a forgotten password and verify their address by email; shoppers get an order confirmation, payment, cancellation and "shipped, here is your tracking number" mails in their order's language; an admin sees whether mail is configured, sends a test to the own address, and sees what was sent, what failed and why (codes only). Delivery never runs inside a database transaction, survives restarts, never sends one logical mail twice to the provider within its idempotency window, and stores no bearer secret. With no provider configured the shop behaves exactly as today, and every flow that needs mail is hidden or refused with a clear message.

## Scope (proposed v1; the owner fixes it with questions 1 to 4)
**In v1:**
- Core `EmailProviderPort` (types, typed result, no I/O), template contract and pure rules (token derivation input, address and header checks, retry schedule, rendering helpers with escaping) in `packages/core/src/email/`.
- Provider loader `EMAIL_PROVIDER` (one provider, not a list) reusing the shipping loader's manifest scan with `kind: "email"`; `packages/providers/resend` (Node `fetch` + zod, no new dependency) and a test-only `packages/providers/_fake-email`.
- Persistent email outbox `email_message` with claim, lease, backoff, deadline, dead status, retention; job 9 `send-emails` plus an immediate post-commit attempt.
- Customer password reset, customer email verification (optional, question 2), "password changed" notice.
- Order mails: `order.placed` (confirmation, with the guest order link for guests), `order.paid`, `order.cancelled`, `order.expired`, `shipment.created` (tracking number).
- Admin: status page, test send to the own address, outbox list with resend and cancel, template preview; permission `email.manage` (question 6).
- Storefront: forgot password, reset password, verify email pages; "verified" state and "send again" in the profile.

**Later (each its own plan or step):** Resend webhooks (bounce/complaint into a local suppression list, question 5); admin password reset and admin invitations by email (question 3); a shop notification mail to staff ("new order"); attachments (invoice PDF); per-shop template editing in the admin; a second provider (SMTP, SES); `customer.registered` emission; a customer locale column; scheduled sends.

**Non-goals:** marketing or bulk mail, newsletters, consent management, open or click tracking (no pixels, no rewritten links: Resend tracking stays off), any provider key or call in a browser, storing rendered bodies or raw tokens.

**`EmailProviderPort` (proposed; internal until the first external plugin):**
```ts
interface EmailProviderPort {
  readonly code: string;                                  // "resend"
  readonly capabilities: { idempotencyKeys: boolean; maxRecipients: number };
  send(message: OutgoingEmail, options: { idempotencyKey: string }, signal: ProviderAbortSignal):
    Promise<EmailProviderResult<{ providerMessageId: string }>>;
}
interface OutgoingEmail { from: EmailAddress; replyTo?: EmailAddress; to: EmailAddress; subject: string; html: string; text: string;
  tags: { category: string } }                            // one recipient per message in v1; no cc/bcc; no attachments
// EmailProviderResult = {ok: true, value}
//   | {ok: false, reason: "unavailable" | "rate_limited" | "rejected" | "misconfigured" | "quota_exceeded" | "idempotency_conflict" | "not_sent",
//      retryAfterSeconds?: number, providerCodes: string[]}
```
`not_sent` = the provider proves nothing left the process (local validation, abort before the request): always safe to retry. `unavailable` and a timeout may have sent: retried with the SAME idempotency key. Codes only, never provider message text (it can echo addresses). The API passes the abort signal and decides timeouts (10 s per send), logging and retries. No `checkConnection`: a Resend sending-only key cannot call other endpoints (`restricted_api_key`, errors page), so "test" is a real test send (section 9).

### 3. Delivery architecture (red zone: schema)
**Decision: a dedicated outbox `email_message`, fed by domain-event handlers and by auth flows; NOT the `domain_event` table itself.** Evidence: a `domain_event` retry calls every handler of the event again (ADR 0021), so a slow or failing provider would re-run unrelated handlers; delivery state per mail (sent, provider id, dead, resend, cancel) has no home there; retries are anchored to `created_at` (ADR 0025 known gap) and capped at 10; dispatched rows are deleted after 7 days; and auth mails (reset) have no domain event. Reuse what exists: the event handler only INSERTS an `email_message` row (idempotent by a unique dedupe key `<eventId>:<templateKey>`, `ON CONFLICT DO NOTHING`), which is a fast database write inside the 30 s handler budget; the auth flows insert the row in the SAME transaction as the token row. Sending happens later, outside transactions.

**Sending (claim, call, result; the ADR 0025 shape with real columns):**
1. **Claim** (short transaction): `UPDATE email_message SET status='sending', attempts=attempts+1, lease_until=now()+interval '2 minutes' WHERE id IN (SELECT id ... WHERE status='pending' AND next_attempt_at <= now() OR status='sending' AND lease_until < now() ... FOR UPDATE SKIP LOCKED LIMIT n) RETURNING ...`. Committed before any network call.
2. **Render and send** with NO transaction open: render from the stored template key, version, locale and frozen variables (section 4); derive any token or guest link at render time; call `send` with `Idempotency-Key = email_message.id` (a UUID, within R4 limits) and a 10 s timeout.
3. **Result** (short transaction, guarded by `status='sending' AND attempts = <claimed>`): `sent` with `provider_message_id`; or back to `pending` with `next_attempt_at` from core `nextEmailAttempt(attempts, reason, retryAfter)` (1, 2, 5, 10, 20, 40 minutes, then hourly; honours `retry-after`); or `failed` (dead) with `last_error_code`.
- **Deadline:** a message is never sent after `deadline_at` = `created_at + 12 hours` (auth mails: the token's expiry, at most 1 hour): past it the next claim marks it `failed` `deadline_passed`. 12 h stays inside the 24 h idempotency window (R4), so every retry of one message is deduplicated by Resend; nothing can send twice through a retry.
- **Reasons to status:** `rejected` (400 field errors, 422) -> `failed` at once; `idempotency_conflict` (409 `invalid_idempotent_request`: an earlier attempt with this key reached Resend with another body, so a mail may have gone out) -> `unknown`, never retried automatically; `misconfigured` (401, 403) -> `pending` with an hourly retry until the deadline and an error log once per process and code (the operator fixes the key or domain); `rate_limited` and `quota_exceeded` (429) -> `pending` after `retry-after` (quota: next 00:05 UTC, capped by the deadline); `unavailable` (timeout, network, 5xx, 409 `concurrent_idempotent_requests`, `resource_locked`) and `not_sent` -> retry. A thrown error or malformed answer counts as `unavailable` (the mail may have gone; the same key protects the retry).
- **Statuses:** `pending`, `sending`, `sent`, `failed`, `unknown`, `cancelled` (admin, only from `pending`); transitions are data in core. `sent` means accepted by the provider, not delivered.
- **Who sends:** job 9 `send-emails` (runs after job 3 `dispatch-events` in the tick so an order mail created by a handler goes out in the same tick; pages of 20, budget 30 s, a pause when the provider reports `rate_limited`; at most 8 sends per second per process to stay under R7). Plus an **immediate attempt** after the commit of an auth flow (reset, verification): the request process claims that one row through the same claim statement, outside the request's transaction, without blocking the answer (fire and forget with its own error log); a lost attempt is picked by the job after the lease. Without this, a reset link waits up to `SCHEDULER_INTERVAL_SECONDS` (60 s default).
- **No mail from inside transactions; no transaction around a network call** (the claim and result transactions are short and carry `withJobTransaction` limits).
- **Retention and PII minimisation (question 7):** rendered bodies are never stored; `variables` hold the minimum the template prints (order number, line titles, quantities, totals, method title, tracking number; for auth mails only the token row id); never a raw token, password, guest link, key or provider message text. Job 10 `purge-email-messages`: rows in a final status older than 30 days are deleted (`unknown` and `failed` after 90 days, for the operator). Logs carry the message id, template key, status and codes, never the address.
- **Transactional only:** every mail is caused by an action of its recipient or by their order. No unsubscribe link (not required for transactional mail); a short footer says why the person received it. No `List-Unsubscribe` header in v1.
- **Multi-instance:** the claim uses `SKIP LOCKED` and leases, so several API instances and `pnpm jobs:run-once` never send one row at the same time; the scheduler lock already runs the job on one instance per tick.

**Token derivation (question 9).** Recommended: `token = base64url(HMAC-SHA256(ORDER_TOKEN_SECRET, "fluxkit:customer-auth-token:v1\n" + purpose + "\n" + tokenId))`, the ADR 0023 technique with its own domain-separation label; the row stores only `SHA-256(token)`; the outbox stores only `tokenId`; the sender derives the token while rendering. A database leak alone yields no usable token (the secret is not in the database) and the outbox never holds a bearer secret. 256-bit output; lookup by the hash (index); expiry, single use and the email match are checked in core `evaluateAuthToken`. Rotating the secret invalidates links not yet clicked (at most 48 h of verification links; documented).

**Not stored:** rendered HTML or text, raw tokens, guest order tokens, provider message texts, IP addresses or user agents, open or click data. `customer.email_verified_at` exists already (no column added).

### 5. Templates
- **Contract (core, public once listed):** `EmailTemplate<V>` = `{key, version, category: "account" | "order", variablesSchema (zod), sampleVariables, render(vars, ctx)}` with `ctx = {locale, messages, theme, links, shopName}`; output `{subject, html, text}`; plain text is mandatory (a template without it fails registration). Rendering is pure, deterministic and synchronous (same input, same bytes: R4 refuses a changed body under the same key).
- **Registry:** built-ins in `apps/api/src/email/templates/`; a feature or plugin registers more, or overrides a built-in, with a Nest provider marked `fluxkit:email-template` (metadata `{key, override?: true}`), discovered at startup like event handlers; a duplicate key without `override`, a missing locale catalog or a schema-less template stops the startup. A feature's templates disappear with the feature (feature-matrix `deleted` stays green).
- **i18n:** message catalogs `templates/messages/uk.json` and `en.json` (keys per template), parity checked by a spec like the storefront's; locale fallback = `resolveTextWithFallback` order (requested, default, first). Dates and money formatted with `Intl` and core money helpers in the mail's locale; product titles come from the order snapshot maps.
- **Theming:** one table-based layout with inline styles built from `emailTheme` (resolved light-mode token values from `tokens.css`; dark mode not attempted), system font stack, no web fonts, no external images, no scripts, no tracking pixel; the shop name is the display name of `EMAIL_FROM` (no new setting, no client branding in master; the demo value is `Fluxkit Demo Shop`). A client delivery changes tokens, catalogs or overrides templates; never core files.
- **Escaping:** every variable passes through core `escapeHtml` in HTML and through a header-safe check in the subject (no CR/LF; max 200 characters); links are built only from `STOREFRONT_PUBLIC_URL` + fixed paths + encoded segments; template authors get a tagged-template helper `html\`...\`` that escapes by default, and a lint/spec forbids raw string concatenation into HTML in `templates/`.
- **Preview:** `POST /admin/email/templates/{key}/preview {locale}` renders `sampleVariables` (no database, no send); the admin shows it in a sandboxed `iframe srcdoc` (`sandbox=""`) and the text part next to it. A CLI is not added (question 11 lists it).

### 6. Flows
**6.1 Customer password reset (v1).**
- `POST /store/account/password-reset {email, locale}` (public, CSRF header, strict body): always `202 {}` with the same body and headers whether or not an account exists, is active or locked. For an active customer with that email: in one transaction, invalidate earlier unused reset tokens of the customer (`used_at = now`), insert a token and an `email_message` (`customer.password_reset`, `variables {tokenId}`, deadline = token expiry); then the immediate send attempt. Limits: per address `passwordReset` 5 per 15 minutes; per email at most 3 tokens per hour counted in the database (spans instances; over the limit nothing is created and the answer is the same `202`). Unknown emails send nothing (no mail to non-customers: no relay for arbitrary addresses). Timing: both branches run the email validation and one indexed select; the answer is sent after a fixed floor of 400 ms (measured spread recorded in the step report).
- `POST /store/account/password-reset/confirm {token, newPassword}` (public, CSRF): token format check, hash lookup, core `evaluateAuthToken` (exists, purpose, not used, not expired, customer active, email unchanged); every token failure is ONE answer `400 validation_failed` `path: "token"`, `code: "invalid_or_expired"`. Password policy as registration. Then scrypt outside the transaction; in one transaction lock the customer row, re-check the token and the hash it saw, set the password, `password_changed_at`, clear the lockout, mark the token used, invalidate the customer's other reset tokens, **revoke every session** of the customer; enqueue `customer.password_changed` (no token, tells the person to contact the shop if it was not them). Answer `204`; no automatic sign-in (question 10). Limit `passwordResetConfirm` 10 per 10 minutes per address.
- Link: `{STOREFRONT_PUBLIC_URL}/{locale}/account/reset-password#t={token}` (fragment, as the guest order link: never in access logs, `Referer` or the Next server).

**6.2 Email verification (question 2; recommended: optional, not required to sign in or order).**
- On registration (when a provider is configured) the register transaction also inserts a verification token and `customer.verify_email`. `POST /store/account/verify-email {token}` (public, CSRF; the page reads the fragment) sets `email_verified_at` and marks the token used; the same single `400 invalid_or_expired` for every failure; idempotent for an already verified customer with a valid used token (`204`). `POST /store/account/verify-email/resend` (customer session, limit `verificationResend` 3 per hour per customer, invalidates older tokens). `GET /store/account/me` gains `emailVerified: boolean` (additive).
- What verification unlocks in v1: nothing yet (shown in the profile). It is the prerequisite for attaching guest orders by email later (ADR 0016 refused it for unverified addresses) and for the non-enumerating registration of question 2 option 2.
- Registration enumeration: with option 1 the `409` on a taken email stays (ADR 0016 trade-off, rate limited); the reset request is non-enumerating on its own, but registration still reveals accounts. Option 2 closes it (see question 2).

**6.3 Order and shipment mails (v1).**
| Event | Template | Recipient | Content (frozen variables) |
|---|---|---|---|
| `order.placed` | `order.placed` | order email | number, lines (title, variant title, quantity, line total), subtotal, shipping, total, shipping method and pickup point or address city, "awaiting payment" text with the payment deadline (`expires_at`); for a guest the order link with the token derived at render time from `order_id` and `idempotency_key` (ADR 0023; valid `ORDER_GUEST_ACCESS_DAYS`); for a customer the account order link |
| `order.paid` | `order.paid` | order email | number, total, "being prepared" |
| `order.cancelled` | `order.cancelled` | order email | number; no reason text in v1 |
| `order.expired` | `order.expired` | order email | number, "not paid in time, stock released" |
| `shipment.created` | `shipment.created` | order email | number, carrier name (method title snapshot), tracking number from `OrderReadPort` shipments |
- Handlers in `apps/api/src/email/handlers/` read the order through `OrderReadPort` (no direct table reads), build variables, insert with `dedupe_key = <eventId>:<template>`; with `EMAIL_PROVIDER=none` they do nothing. `order.fulfilled` and `shipment.status_changed` send nothing in v1 (fulfilment is manual; tracking mails would multiply). A customer with no account, a deactivated customer: the order email still gets the order mails (they concern the order).
- Guest link security: the mail is a bearer link to one order (read and cancel while unpaid). Accepted: the same address placed the order; documented in the privacy notes. Not derivable without the secret; never stored in the outbox.

**6.4 Admin (question 3; recommended: no email flows for admins in v1).** Today the owner creates users with a password and resets them, and `pnpm admin:unlock` recovers a lockout (ADR 0010). Self-service reset by mail makes the mailbox a key to the back office without two-factor; invitations replace the owner-set password. Both reuse this plan's token and outbox code later with a separate `admin_auth_token` table. The admin's own address is used in v1 only for the test send.

### 11. Security and privacy
- **Tokens:** 256-bit HMAC output, derived (section 4), only SHA-256 stored, single use, 60 minutes (reset) and 48 hours (verification), bound to the address at issue, invalidated by a newer token of the same purpose, by a password change and by deactivation (cascade on customer delete). Comparison through a hash index lookup (the secret input has 256 bits; no early-exit compare on user input).
- **Enumeration and timing:** the reset request answer is identical for every case, padded to a fixed floor; confirm and verify have one error for every token failure; registration enumeration depends on question 2.
- **Rate limits:** per address (`passwordReset`, `passwordResetConfirm`, `verificationResend`, `emailTest`) in memory, plus the per-email database count for reset requests (spans instances and IP rotation); the provider's own 10 requests per second is respected by job 9's pacing.
- **Session invalidation:** reset revokes every customer session; the existing lockout is cleared by a successful reset (as the admin owner reset does).
- **Header injection:** one recipient per message, addresses validated in core (no CR, LF, NUL, commas, angle brackets in the local part); `EMAIL_FROM` and `EMAIL_REPLY_TO` checked at startup; subjects sanitized; no custom headers from data; JSON to Resend (no SMTP header assembly in v1).
- **HTML escaping:** default-escaping template helper, a spec that renders every template with hostile sample values (`<script>`, `"><img`, `javascript:` in names and titles) and asserts escaped output; links only from config plus encoded path segments.
- **Link base:** `STOREFRONT_PUBLIC_URL` only; a spec sends a forged `Host` and `X-Forwarded-Host` and asserts the mail's links ignore them.
- **SSRF:** the Resend base URL is a constant; the plugin calls one path; response size cap 64 KiB before parsing.
- **Logging:** message id, template key, status, provider codes, durations; never addresses, tokens, links, variables, subjects or provider text; a log-capture spec (as the order specs) proves it.
- **Owner checklist before production (DNS and account):** verify the sending domain in Resend (SPF and DKIM records as the dashboard lists them, R16), publish DMARC (`p=none` first with a reporting address, then `quarantine`), use a subdomain for sending (`mail.shop.example`), create a sending-only API key, set `EMAIL_FROM` on the verified domain, leave open and click tracking off for the domain, send the admin test to two mailbox providers (Gmail, Ukr.net) and check SPF/DKIM/DMARC pass in the headers. Resend's testing mode sends only to the own address until the domain is verified (R8).
- **Privacy (input to the privacy plan, not written yet):** Resend is a processor of addresses and mail content (R18: region and DPA unknown, owner to obtain); legal basis is contract performance (order and account mails); retention 30/90 days (section 3); a customer deletion sets `customer_id` NULL, so the privacy plan must also delete or anonymize that customer's `email_message` rows (an erasure query is documented); Ukrainian personal data law (Law No. 2297-VI) and GDPR both need the processor named in the shop's privacy notice; no marketing consent is collected because no marketing mail exists.

### 12. Failure handling (summary)
| Situation | Behaviour |
|---|---|
| Provider down, timeout, 5xx | retry with the same idempotency key, backoff, until the deadline; then `failed deadline_passed` |
| Process crash after claim | lease expires after 2 minutes; the next claim retries with the same key |
| Wrong key, unverified domain | `pending` with hourly retries until the deadline, one error log per code and process, admin status shows the code |
| Quota or rate limit | wait for `retry-after` or the quota reset, capped by the deadline |
| Invalid recipient, refused field | `failed` at once with the code; no retry |
| Same key, different body (a template changed between attempts) | `unknown`; the admin decides (resend creates a new row and key) |
| Template missing or variables invalid at render (deploy removed it) | `failed template_unavailable` / `variables_invalid`, error log |
| Event handler failure | the domain event is retried (ADR 0025); the dedupe key prevents a second mail row |

## Risks
- **A reset link is an account takeover path:** mitigated by derived tokens, single use, short expiry, session revocation, the "password changed" notice, rate limits and the review; the mailbox owner is still trusted (no two-factor).
- **Registration enumeration remains** unless question 2 option 2 is chosen.
- **Ambiguous Resend errors** (`validation_error` on 400/401/403, R8): a bad key may look like a bad field (`failed` instead of retried). Mitigated by full local validation before the call (so a 400 is unlikely to be ours) and S1.
- **Duplicates after 24 h** are impossible by the 12 h deadline; a mail that Resend accepted but whose answer was lost and whose retries end in `unknown` may be resent by an admin (one duplicate, a human decision).
- **Latency:** reset mails go out at once; order mails wait for the tick (up to 60 s by default) plus the event dispatch.
- **Deliverability** depends on the owner's DNS (section 11); without DMARC some Ukrainian and EU mailbox providers file mail as spam.
- **Per-process limits** (in-memory windows) multiply with instances; the per-email reset limit is in the database.
- **Secret reuse** (`ORDER_TOKEN_SECRET` for two purposes with separate labels): rotating it invalidates unclicked links of both kinds.
- **Unknown Resend facts** (R3, R9, R13 tolerance, R14 success codes, R15, R17, R18) may change the plugin; S1 and the docs pass in step 6 close what they can.
