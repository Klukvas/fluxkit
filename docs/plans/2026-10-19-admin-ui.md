## Goal
An admin opens the admin UI, signs in, and sees only what the role allows: the **viewer** browses the catalog read-only; the **manager** manages the catalog (attributes, options, product types, brands, categories, products, variants, media links, prices, stock adjustments, reservations view), orders (list with filters, detail, mark paid, mark fulfilled, cancel with a reason) and customers (list, detail, deactivate or activate, unlock); the **owner** additionally manages admin users. Authorization stays on the API; the UI only hides what the API would refuse. Every screen uses design tokens and translated strings only (`uk`, `en`), handles empty, loading, error and forbidden states, works with the keyboard, never shows an optimistic money or stock value, and is fed by a typed admin API client checked against `docs/api/openapi.json`.

### Out of scope (each gets its own plan)
Payment providers and refunds, shipping, email (password reset, invitations, order mails), search indexing and full-text product search (ADR 0005), file uploads and a media library (see open question 5), audit log of admin actions (ADR 0010 follow-up; needs a schema), bulk actions (bulk publish, bulk stock, CSV import or export), multi-location stock management (locations are read-only in the API), two-factor auth, session lists and token rotation, discounts, taxes, reports and dashboards with charts, an admin Docker image and a production deployment, a dark-mode switch, UI slots for optional features (the admin route and navigation registry stays internal in v1), SEO fields, slug redirects.

### The admin API (all documented, all contract per `docs/contracts/api.md`)
Conventions (`docs/api/catalog.md`, `docs/api/auth.md`, ADR 0009 and 0010):
- **Session cookie** `fluxkit_admin_session`: `HttpOnly`, `SameSite=Strict`, **`Path=/admin`**, host-only (no `Domain`), `Secure` unless `ADMIN_COOKIE_SECURE=false`, `Max-Age` = `ADMIN_SESSION_MAX_HOURS` (default 168); idle timeout `ADMIN_SESSION_IDLE_MINUTES` (default 720). Only the cookie authenticates. The cookie name is NOT contract; the attributes are (`docs/contracts/api.md`).
- **CSRF**: every `POST|PUT|PATCH|DELETE` under `/admin` (login included, anonymous included) needs `X-Fluxkit-CSRF: 1` and, with a body, `Content-Type: application/json`, else `403 forbidden`. No CORS headers.
- **Admin path matching** (`apps/api/src/common/admin-path.ts`): `^/admin(?:/|$)`, case-insensitive. `/admin-ui` does NOT match; `/admin`, `/admin/` and `/ADMIN/x` do.
- **Order of checks**: CSRF, then `401 unauthorized`, then `403 forbidden` (permission). Role and `isActive` are read from the database on every request.
- **Permissions** (`packages/core/src/auth/roles.ts`): owner all eight; manager `catalog.read|write|publish`, `orders.read|write`, `customers.read|write`; viewer `catalog.read`. Route rule: catalog `GET` = `catalog.read`, other methods `catalog.write`, lifecycle routes `catalog.publish`; customers `GET` = `customers.read`, others `customers.write`; orders `GET` = `orders.read`, `POST` = `orders.write`; users = `users.manage`; `logout`, `me`, `change-password` = any session.
- **Login**: one identical `401` for unknown email, wrong password, locked and inactive; lockout 5 failures for 15 minutes (database); per-address limit 20 attempts per 10 minutes (memory, IPv6 per /64, `429` with `Retry-After`); recovery `pnpm admin:unlock`, owner reset, or waiting.
- **Every `/admin` response** carries `Cache-Control: no-store`. JSON bodies above 100 KB are `413` before any guard (`docs/contracts/api.md`, Default deny).
- **Errors**: `application/problem+json` with `code` (`validation_failed`, `unauthorized`, `forbidden`, `not_found`, `conflict`, `in_use`, `invalid_transition`, `rule_violation`, `too_many_requests`, `internal_error`, plus the order codes), `errors[] {path, code}`, `field`, `constraint`, `rule`.
- **Pagination**: admin lists `limit` 1 to 100 (default 50; orders 20), `offset` 0 to 10 000, `{items, total, limit, offset}`; admin list routes ignore unknown query keys (orders reject them).

Facts that shape the screens:
- **Media are URLs only** (`PUT /admin/products/{id}/media`: `{url (http or https, max 2048), alt?, position?, optionId?, optionValueId?}`, max 100; brand `logoUrl` likewise). There is no upload route, no storage and no image processing; the seed uses `https://example.com/placeholder/*.jpg`.
- The product summary carries no image, price, stock or variant count; the product list cannot be searched by title, slug or SKU.
- The product type detail gives attribute ids and codes only, not definitions or options; a select attribute's options need `GET /admin/attributes/{id}` each (up to 100 attributes per type).
- The product detail's `options` give option and value ids and codes only; labels need `GET /admin/options/{id}` (at most 3 per product).
- Prices and stock are read per variant (up to 250 variants per product): no product-level read.
- There is **no reservations route**: the stock level shows the `reserved` total per location, and the admin order shows each line's reservations as `{status, quantity}`. Which orders hold a variant's units is not readable.
- The order history and the stock journal name the acting admin by id (`actorAdminId`, `actorId`); only `users.manage` can read users.
- No admin write route takes an idempotency key: a lost response to `POST .../inventory/adjustments` or a create cannot be retried safely. `mark-paid` is idempotent by `reference`.
- No admin resource has a version or `If-Match`: concurrent edits are last-write-wins (PATCH changes only the listed fields).
- `openapi.json` describes the store CSRF header (storefront step 2) but not the admin one, and does not say which permission an operation needs.

## Decisions (owner, quiz 2026-10-18/19)
1. **Next work is the admin UI**: React SPA on Vite, sharing `packages/ui` and the tokens with the storefront (ADR 0002).
2. **v1 scope is the whole set at once**: sign-in with roles (owner, manager, viewer; the SPA shows only what the role allows, authorization stays on the API); catalog management (products, variants, options, attributes, product types, brands, categories); prices; inventory (stock adjustments, reservations view); orders (list, filters, detail, mark paid, mark fulfilled, cancel with reason); customers (list, detail, deactivate, unlock); admin user management (owner only).
3. **Out of scope**: payments, shipping, email, search indexing.
4. **uk/en i18n**, accessibility and tokens-only styling (AGENTS.md 2.2, design guard) as in the storefront.
5. **Auth is ADR 0009/0010 unchanged**: the admin cookie, the CSRF header, the login limits and the lockout stay as they are. The SPA must be served on the same origin as the `/admin/*` API it calls (cookies, no CORS).

### Consequences of the non-recommended answers (to be turned into steps and ADR text)
- **Q1, `/admin-ui/` on the storefront origin.** Risk accepted by the owner: a storefront XSS shares the origin with the admin SPA and could call `/admin/*` with an admin's cookie and the CSRF header (the cookie is `Path=/admin`, `SameSite=Strict`, so it is not sent to `/admin-ui/` itself, but fetches to `/admin/*` from that origin carry it). Mitigations required: strict CSP on `/admin-ui/*` (`script-src 'self'`, `frame-ancestors 'none'`, no external resources); the SPA base path is `/admin-ui/` and no SPA route may start with `/admin` (route-table test); the edge proxy keeps routing `/admin/*` to the API, `/store/*` to the API, `/admin-ui/*` to the static SPA with an `index.html` fallback, the rest to the storefront; the storefront CSP must not weaken for the rest; an e2e test for the fallback and the headers. ADR 0027 records the risk and supersedes nothing in ADR 0026 (the storefront host still routes `/admin/*` to the API); the storefront gains a static `/admin-ui` route in the deployment guidance and in the e2e/dev proxies. The "admin on its own host" text below is kept only as the later hardening option.
- **Q4, `react-router`.** New runtime dependency (red zone): the step that adds it states license (MIT, to be verified by `pnpm check:licenses`), size (measured against the bundle budget), alternatives (hand-written router, TanStack Router) and pins an exact version. Route-table test, permission-per-route test and base-path `/admin-ui` still apply. No `@tanstack/react-query`.
- **Q5, file upload now.** This is a red-zone area of its own (storage, API, schema, security). It gets a **separate early step (2b) with its own plan file and ADR** before the Products step: storage provider abstraction (local disk driver first), an admin upload endpoint (type allow-list by content, size limit, never executes uploads, random file names), serving through the edge with safe headers (`X-Content-Type-Options: nosniff`, CSP for images), `img-src` in the storefront CSP (`STOREFRONT_IMAGE_HOSTS`), a schema decision if media metadata needs a table, tests first, docs and `.env.example`. URL-based media stays supported. Image processing and a media library stay out of scope unless the media plan says otherwise. Step 6 (Products) depends on it only for the upload control; it may ship with the URL list first.

## Assumptions to confirm (my defaults; approving this plan approves them)

### Where the SPA lives: the URL-space collision and the recommendation
The problem, from the facts above: the API owns every path matching `^/admin(?:/|$)` (case-insensitive) on whatever origin routes it, and the admin cookie has `Path=/admin`. If the SPA were served at `/admin/...`, the edge proxy could not tell a page request (`/admin/orders/123`, a deep link or a reload) from an API request (`GET /admin/orders/123`); both are `GET`s with the same path. Content negotiation by `Accept` is fragile (prefetchers, `curl`, the API's own `404` for unknown routes), so the SPA and the API cannot share the `/admin` prefix. Same origin is required (the API sends no CORS headers and the cookie is host-only).

| Option | How | Cookies and collisions | Security | Cost |
|---|---|---|---|---|
| **A. Separate admin host (recommended)**, e.g. `admin.shop.example` | Edge proxy on that host: `/admin/*` to the API, every other path is the static SPA (`apps/admin/dist`, fallback to `index.html`). The SPA's routes live at the root (`/`, `/orders/…`) and none may start with `/admin`. The storefront host stops routing `/admin/*` | The cookie is set host-only on the admin host with `Path=/admin`; SPA pages (`/orders`) never receive it, API calls (`/admin/...`) do. No collision as long as no SPA route starts with `/admin` (enforced by a test of the route table) | Origin isolation: an XSS in the storefront (a Next app rendering catalog content) cannot call the admin API with an admin's cookie (cross-origin: the CSRF header forces a preflight, which fails without CORS). Own strict CSP (`script-src 'self'`, no `'unsafe-inline'`). Residual: if both hosts share a registrable domain, the storefront host can set a `Domain=shop.example` cookie that reaches the admin host (cookie tossing, ADR 0010 "Known limits"); a separate registrable domain removes it | A second host name and certificate; README examples gain a second server block; no API change |
| B. Same origin, SPA under a distinct prefix, e.g. `https://shop.example/admin-ui/` | Edge proxy: `/admin/*` to the API, `/admin-ui/*` to the static SPA (Vite `base: "/admin-ui/"`), the rest to Next | `Path=/admin` is not sent to `/admin-ui` pages (RFC 6265 path match needs `/` after the prefix) and `/admin-ui` does not match the API's `^/admin(?:/|$)`; works technically | Same origin as the storefront: any storefront XSS can `fetch("/admin/...")` with the admin's cookie and the CSRF header (same-origin script may set it) = full admin takeover; one CSP for both; `'unsafe-inline'` scripts of the storefront (ADR 0026) apply to the origin | One host; easiest to deploy |
| C. SPA takes `/admin/*`, the API moves to `/admin/api/*` (or `/api/admin/*`) | Proxy splits by prefix | Cookie path, CSRF matcher, guard, OpenAPI, docs and every client change | Same as A or B depending on host | Breaking change of the public API contract (major version, migration guide), ADRs 0009/0010 superseded; no benefit over A |

Recommendation: **A**, recorded in ADR 0027 (step 1), which supersedes in part ADR 0026 decision 1 ("and later `/admin/*`" on the storefront host). Development: the Vite dev server (`http://localhost:5173`) serves the SPA at `/` and proxies `^/admin(/|$)` to the API (`server.proxy` in `vite.config.ts`, target from an environment variable read by the config file only, default `http://127.0.0.1:3000`), with `ADMIN_COOKIE_SECURE=false` and `TRUST_PROXY=0` on the API (one developer). Production: the edge proxy serves the files and sets `X-Forwarded-For` (same `TRUST_PROXY` rule as ADR 0024/0026). Option B stays possible for a client who insists, documented as "not recommended, storefront XSS reaches the admin", with Vite `base` as a build-time setting; it is not tested.

### Serving the built SPA
- `vite build` writes static files to `apps/admin/dist/` (already a turbo `build` output); the build never calls the API.
- **The edge proxy serves the files** (Caddy `file_server` with `try_files {path} /index.html`, nginx `try_files $uri /index.html`) and sends the headers: `index.html` with `Cache-Control: no-cache`, hashed assets under `/assets/` with `Cache-Control: public, max-age=31536000, immutable`; the security headers of "Security" below on every SPA response. Example configurations in the README (not tested here, like the storefront ones). Alternatives rejected: the API serving the files (mixes static hosting and CSP into the API; `/admin` prefix rules); a separate static container (no images exist yet).
- No Compose change: `infra/docker-compose.yml` keeps Postgres, Redis, Meilisearch. No admin image in v1 (the API and the storefront have none).

### Routing, data and state (no new dependency)
- **Router, hand-written** (`src/router/`, about 200 lines, unit-tested): a route table of `{pattern, permission, load: () => import(...), titleKey}`; History API (`pushState`, `popstate`), a `Link` that lets modified clicks and `target` through, query-string state for list filters and paging (shareable URLs), `document.title` per route, focus to the new `h1` after a path change (storefront `RouteFocus`), a "leave with unsaved changes?" confirmation for dirty forms (in-app navigation and `beforeunload`). A test asserts that no route pattern starts with `/admin` (the API's prefix) and that every route declares a permission or is explicitly public (`/login`).
- **Bundle splitting by route**: the shell, sign-in and the router are the entry chunk; each area (catalog dictionaries, products, orders, customers, users) is a `React.lazy` chunk. `build.manifest: true` and a test after `pnpm build` checks that the area chunks are separate and the entry chunk stays under a budget (set in step 4b from the measured size).
- **Data access, hand-written**: one admin client instance (`createAdminClient({baseUrl: ""})`); a `useResource(loader, deps)` hook with `AbortController` (aborted on unmount and navigation), states `loading | ready | error | forbidden | notFound`, and `reload()`; per-request timeouts (15 s reads, 30 s writes, storefront `request-timeout.ts` pattern). No global cache library: the session (`me`), the admin config and small dictionaries (locations, product types, options for pickers) are kept in context for the session and reloaded after writes in their own screens. Lists always come from the server (no client-side filtering of a page).
- **Writes**: never optimistic. The button is disabled while pending, the screen shows the server's answer (every admin write returns the full resource, except `204`s, which reload). A `NetworkError` or timeout on a non-idempotent write (create, stock adjustment, option changes) is shown as "the result is unknown": the screen reloads the resource (or the journal) and shows what the server has, and never retries automatically. `mark-paid` may be retried with the same reference (idempotent by reference).
- **PATCH sends only the changed fields** (a tested `diffForPatch`), so two admins editing different fields of one product do not overwrite each other; same-field edits remain last-write-wins (no version on the API; API gap 13).

### Forms and validation
- **The server is the authority.** Forms use native constraints (`required`, `maxlength` from `TEXT_LIMITS`, `pattern` for codes `^[a-z][a-z0-9_]{0,63}$`) for early feedback, then map `400 validation_failed` `errors[].path` to fields (nested paths such as `title.uk`, `items.3.amount`, `variants.2`) with translated `errors[].code` messages and an error summary that receives focus.
- **No zod in the SPA, no shared request schemas**: the API's zod schemas live in `apps/api` and apps may not import each other; moving them into a package is a large refactor of the API outside this plan. Pure core helpers MAY be used on the client where they exist (`parseDecimalString`, `toDecimalString`, the currency table, `permissionsOf`, `TEXT_LIMITS`, `CATALOG_LIMITS`, the password policy) if the bundle check of step 4b shows that importing `@fluxkit/core` does not pull in zod or the whole core; otherwise the admin copies nothing and relies on the server (a decision recorded in step 4b; adding `"sideEffects": false` to core is an internal change the orchestrator may approve).
- **Money input**: the admin types a decimal string; `parseDecimalString(text, currency)` turns it into minor units (no float ever; `too_many_decimals`, `invalid_format`, `amount_out_of_range` translated); display with `toDecimalString` plus `Intl.NumberFormat` (exponent from the currency table). Never `amount / 100`.
- **Locale maps** (`title`, `name`, `description`, `label`): one field per configured content locale (from the admin config, API gap 1), the default locale required and marked; an empty optional locale is omitted from the map; a PATCH sends the whole map (the API replaces maps).
- **Attribute values are data-driven** (ADR 0002 "forms generated from attribute metadata", AGENTS.md 2.3): the product and variant attribute forms are generated from the product type assignments and the attribute definitions (`inputType` text, number, boolean, select, multiselect, date; `isLocalized`; `unit`; `validation`; `isRequired`; level product or variant). No niche field (size, color) appears anywhere in the code. `isInternal` attributes are shown to admins with an "internal" badge (they are admin data; the store hides them).

### Permissions in the UI
- On start the shell calls `GET /admin/auth/me`: `200` gives `{user, permissions}`; `401` shows sign-in. `can(permission)` reads ONLY that permission list (never the role name), so the UI follows the API's table.
- One table (`src/permissions.ts`) maps every route, navigation item and action to the permission its API route needs (the route rule in `docs/contracts/api.md`). Without it: the navigation item is hidden, a direct URL shows a translated "not allowed" page, write controls are not rendered and forms render read-only (viewer: catalog read-only; manager: no users area).
- A test checks that table against the API: with API gap 10 approved, against the `x-fluxkit-permission` of each operation in `openapi.json`; otherwise against a hand-copied table from `docs/contracts/api.md`.
- A `403` from the API (role changed meanwhile) shows "not allowed" for that action and reloads `me`, so the navigation follows the new role at once.

### Session expiry, sign-in and CSRF
- **Sign-in page** at `/login` (the only public route): email and password, `method="post"` without `action` (storefront H1 guard), the identical `401` shown as one message ("email or password not correct, or the account is temporarily locked; ask an owner"), `429` with the wait from `Retry-After`, the password cleared after a failure (as the storefront does).
- **Expiry**: the SPA cannot know when the idle (`ADMIN_SESSION_IDLE_MINUTES`) or absolute (`ADMIN_SESSION_MAX_HOURS`) limit ends. Any `401` outside `/login` opens a **re-sign-in dialog over the current page** (open question 6), keeping the page's in-memory state (an unsaved form survives); the failed write is NOT replayed automatically, the admin presses Save again. After sign-in the shell reloads `me`; if another user signed in, the SPA drops all state and goes to the start page.
- **Sign-out** calls `POST /admin/auth/logout` and drops all state. **Own password** at `/account` (`POST /admin/auth/change-password`; ends the other sessions).
- **CSRF**: only the admin client sends writes, and it always adds `X-Fluxkit-CSRF: 1` and the JSON content type with a body (unit-tested for every write operation). `credentials: "same-origin"`. The SPA has no token, no `localStorage` credential, and never reads the cookie (it is `HttpOnly`).
- `next` after sign-in: only relative SPA paths (no `//`, no scheme, not `/login`, not `/admin...`), storefront `safe-next` rules.

### Errors, empty and loading states
- A problem-code map translates every `code`, every `rule` and every `errors[].code` the admin routes document (catalog, pricing, inventory, orders, customers, auth) to `uk` and `en` messages; a test walks `ProblemDetailsDoc.code` in `openapi.json` and the rule lists of `docs/api/*.md` (copied into a fixture) and fails on a missing message. Unknown codes get a generic message plus the code in small print (admins need it for support); the English `detail` is never shown.
- `409 in_use`, `rule_violation` (for example `options_frozen`, `has_stock_history`, `has_order_lines`, `last_variant`, `last_shop_price`, `below_reserved`, `last_owner_cannot_be_demoted`, `awaiting_stock`, `amount_mismatch`) explain what to do instead (switch the variant off, release reservations, unpublish first).
- Publish failures (`400` with `errors[]` at `variants.N`, `title.uk`, `attributes.<code>`) are mapped onto the editor tabs and the variant rows (`N` is the index in the product detail's variant order).
- `413` (body over 100 KB, possible with long descriptions in several locales plus attributes) gets its own message.
- Each list has loading (skeleton rows), empty ("no products yet", with the create action when allowed), error (retry) and forbidden states; each detail has not-found.

### i18n
- Admin UI strings in `apps/admin/src/messages/{uk,en}/<area>.json` (one file per area, so parallel steps touch disjoint files), merged in `messages/index.ts`; `createTranslator` throws on a missing key; a test asserts both locales have the same keys and placeholders (storefront pattern).
- UI language: default from the browser (`detectLocale`, exists), switchable in the header, remembered per browser in `localStorage` (a convenience, wrapped in try/catch; open question 10); `<html lang>` and `document.title` follow it.
- Content locales (the locale maps the admin edits) are the API's `LOCALES`/`DEFAULT_LOCALE`, independent of the UI language.
- Money with `Intl.NumberFormat` from minor units (above); dates and times with `Intl.DateTimeFormat` in the browser's time zone; the order date filter turns local day boundaries into ISO strings with offset (`placedFrom` inclusive, `placedTo` exclusive). There is no shop time zone setting (gap 18).

### Theming and layout composition (AGENTS.md 2.2)
- Tokens only; the design guard already covers `apps/admin/src`; the contrast scan of `packages/theme/src/contrast.spec.ts` is extended to `apps/admin/src` (step 4a). No new token is planned; if a step needs one it is an additive theme contract change (red zone) stated in that PR.
- **Dumb components in `packages/ui`** (props in, markup out, no fetching, no API types, labels from props, `renderToStaticMarkup` tests, `no-hardcoded-text` coverage): `DataTable` (caption, `th scope`, row header, empty and loading rows), `Dialog` and `ConfirmDialog` (native `<dialog>` with `showModal`: focus trap, Escape, return focus; a client component like `ProductImage`), `Tabs` (WAI-ARIA tabs with roving tab index), `DescriptionList`, `Toolbar`/`FilterBar`, `SideNav` (`aria-current`), `LocaleTextField` (one labelled field per locale given by props), `StatusBadge` (text plus tone, never colour only), `LiveRegion` (`aria-live="polite"` for "saved").
- **Logic in `apps/admin/src/lib`** (client, formatting, permissions, router, diffing, error mapping) and **data components in `apps/admin/src/areas/<area>/`**; screens only compose. A redesign touches tokens, `packages/ui` and `src/layout/`, not the logic.
- **Layout is configuration**: `src/layout/navigation.ts` lists the navigation groups and items (message key, route, permission) and `src/layout/product-editor.ts` the editor tabs in order; both are internal in v1 (a feature module that needs an admin screen later gets a registry contract, `docs/contracts/slots.md`, in its own plan).

## Decisions to take (ADR 0027, step 1)
**ADR 0027 Admin UI architecture: own host, static SPA, permission-aware client** (draft text):

> Context: the admin API owns `^/admin(?:/|$)` on any origin that routes it, its cookie is host-only with `Path=/admin` and `SameSite=Strict`, writes need `X-Fluxkit-CSRF: 1`, there is no CORS (ADR 0009, 0010). A SPA at `/admin/...` would collide with the API's paths. On the storefront origin any storefront XSS could drive the admin API with an admin's cookie. A static SPA cannot read server configuration at runtime.
> Decision: (1) The admin SPA is served on its own host (for example `admin.shop.example`); the edge proxy of that host routes `/admin/*` to the API and serves the static build for every other path with an `index.html` fallback; SPA routes never start with `/admin`. The storefront host no longer routes `/admin/*` (supersedes that part of ADR 0026 decision 1). In development the Vite dev server proxies `/admin`. (2) The SPA is static (`apps/admin/dist`), served by the edge proxy with a strict CSP (`script-src 'self'`, `frame-ancestors 'none'`); the build never calls the API. (3) Authorization stays on the API; the SPA shows what `GET /admin/auth/me` `permissions` allow, through one route/action-to-permission table checked against the API. (4) The admin client lives in `@fluxkit/api-client` (one entry, hand-written types, contract test), owns the CSRF header and never retries writes. (5) Router, data access and forms are hand-written (no routing, query or form library); no optimistic updates; PATCH sends changed fields only. (6) Product and variant attribute forms are generated from the product type and attribute metadata.
> Consequences: a second host name and certificate per shop; cookie tossing remains possible when the two hosts share a registrable domain (ADR 0010); the admin works without any API change for the basic screens, but some screens need the additive admin API additions of the plan; replacing the router or adding a cache library later is a local change.

## Open questions (owner quiz; recommended answer first; ordered by importance)
1. **Where is the admin SPA served?** Recommended: **its own host** (`admin.shop.example`): `/admin/*` to the API, every other path is the SPA; the storefront host stops routing `/admin/*`; no API change. Alternatives: same origin as the storefront under `/admin-ui/` (works with the cookie path and does not collide, but any storefront XSS becomes an admin takeover and both share one CSP), or move the admin API to `/admin/api/*` and give the SPA `/admin/*` (a breaking API contract change: major version, migration guide, ADR 0009/0010 superseded).
2. **Small additive admin API PR before the screens** (API gaps 1 to 4 and 6 to 10 below; each is additive, minor, tested first; one PR, step 2). Recommended: **yes, the listed set**: `GET /admin/config`; product search `q` (slug prefix or exact SKU) on `GET /admin/products`; attribute definitions with options embedded in the product type detail; product-level reads of prices and stock; a reservations list per variant; `customerId` filter on `GET /admin/orders`; OpenAPI documentation of the admin CSRF header, of `parentId` and of each operation's permission. Alternatives: no API change at all (the editor makes up to 100 + 2 x 250 requests for a large product, there is no reservations view beyond the reserved totals, a customer's orders are found by exact email, the product list has no search), or a larger API PR that also adds bulk actions, an audit log and full-text search (each a plan of its own; delays the UI).
3. **Typed admin client.** Recommended: **extend `@fluxkit/api-client`** with `createAdminClient`, hand-written admin types and the same contract test against `openapi.json` (one entry point; the storefront's bundle does not grow because it imports only the store functions; `openapi-typescript` 7.13.0 still requires TypeScript 5). Alternatives: a separate package `@fluxkit/admin-api-client` (duplicates the request and response modules or needs a third shared package), or untyped `fetch` calls with types local to each screen (no drift protection for about 90 operations).
4. **Routing and data libraries.** Recommended: **hand-written** router and data hook (no dependency; about 400 lines with tests; enough for one SPA with about 30 routes). Alternatives: `react-router` (MIT) plus `@tanstack/react-query` (MIT) as runtime dependencies (less code of ours, two libraries to keep current and justify), or TanStack Router plus Query (MIT; typed routes, larger).
5. **Product images.** Recommended: **URL only in v1** (the API accepts http(s) URLs; the editor shows a preview, alt text and position, and the option-value link), uploads and a media library in a separate media plan (storage provider abstraction, validation, image processing, a new dependency). Alternatives: an upload route storing files on the API's disk now (schema, storage, security work and a red zone in this plan), or S3-compatible storage now (new dependency and configuration, provider choice).
6. **What happens when the session expires mid-work.** Recommended: **a re-sign-in dialog over the current page**; in-memory form state survives; the failed save is not replayed, the admin presses Save again. Alternatives: redirect to `/login?next=` (unsaved input is lost), or a proactive idle warning (needs the session expiry from the API: an API change).
7. **Admin end-to-end tests.** Recommended: **a separate Playwright suite `apps/admin/e2e`** (same pinned `@playwright/test` 1.56.1, Chromium, one worker, its own test-only proxy that serves the built SPA and routes `/admin/*` to the built API), root `pnpm test:e2e` runs both suites one after the other, the CI job `e2e` runs both (the owner edits AGENTS.md sections 1 and 18). Alternatives: add the admin scenarios to the storefront suite (one proxy that also serves the SPA by host name; one larger suite), or a written manual script only for v1.
8. **Mark-paid amount.** Recommended: **the amount is the order total, shown read-only, plus a required payment reference and a "I received this amount" confirmation** (v1 has no partial payments, and the API refuses any other amount with `amount_mismatch`). Alternatives: an editable amount prefilled with the total (allows a typo that the API then refuses), or an empty amount the admin types (most typing, same refusal).
9. **Component interaction tests.** Recommended: **`renderToStaticMarkup` plus Playwright**, no DOM test library (as the storefront). Alternatives: `@testing-library/react` (MIT) with `happy-dom` (MIT) as devDependencies of `apps/admin` and `packages/ui` (many forms could profit), or Playwright component testing (experimental).
10. **UI language of the admin.** Recommended: **browser language by default, a uk/en switch in the header remembered in `localStorage`**, no locale in the URL. Alternatives: always the API's `DEFAULT_LOCALE` (no switch), or the locale in the path like the storefront (`/uk/orders`; longer URLs, no SEO need in an admin).
11. **Who did it, in journals.** Recommended: **no API change in v1**: the order history and the stock journal show "you" for the signed-in admin's id, the email for owners (they can read users), otherwise "another admin" with a short id. Alternatives: an additive `actorEmail` in the order history and stock movements (staff emails visible to managers), or ids only.
12. **Stock adjustments after a lost response.** Recommended: **no automatic retry; the screen reloads the level and the journal and shows the last movement**, so the admin sees whether the adjustment landed. Alternatives: an additive `Idempotency-Key` on `POST .../inventory/adjustments` (an API and schema change: a key column or table, migration), or nothing (the admin may double-count a receipt).
13. **Concurrent edits.** Recommended: **PATCH sends only changed fields; same-field edits stay last-write-wins**, documented in the admin README. Alternatives: an additive `If-Match`/`updatedAt` precondition on admin PATCH routes (`409` on a stale edit; an API change on every editor), or a soft lock per resource (schema, complexity).

## Security (admin side)
- **XSS**: React text rendering only; no `dangerouslySetInnerHTML` anywhere in `apps/admin` (a source guard test). Product descriptions, attribute values, customer names, addresses, order contact data and cancellation reasons are rendered as text (line breaks via CSS `whitespace-pre-line`). URLs from data (media, brand logo) are rendered as links or images only when they parse as `http:`/`https:` (a tested `safeHttpUrl`; the API already validates them, the UI does not rely on that). Images are `referrerpolicy="no-referrer"` and `loading="lazy"`.
- **No uploads in v1** (open question 5), so no file handling.
- **Clickjacking**: `frame-ancestors 'none'` and `X-Frame-Options: DENY` on every SPA response.
- **CSP for the SPA** (set by the edge proxy; checked against the built `index.html` in step 4b: Vite must emit no inline script): `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data: <image hosts>; connect-src 'self'; font-src 'self'; object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'`; plus `Referrer-Policy: same-origin`, `X-Content-Type-Options: nosniff`, `Permissions-Policy` denying camera, microphone and geolocation, HSTS at the proxy. Image hosts: the same list as the storefront's `STOREFRONT_IMAGE_HOSTS` (documented in the README example; a static SPA has no runtime config).
- **Cookies and tokens**: the SPA holds no credential; the `HttpOnly` cookie is sent only to `/admin/*`; nothing personal in `localStorage` (only the UI language); no `sessionStorage` use.
- **CSRF**: header on every write by the client (unit test per operation); `SameSite=Strict`; no CORS.
- **Rate limits and lockout**: unchanged (login 20 per 10 minutes per address; 5 failures lock 15 minutes); the UI shows `429` waits and the generic `401`; the README warns that the edge proxy must set `X-Forwarded-For` (ADR 0024) or all admins share one login window.
- **Confirmation dialogs** (`ConfirmDialog`, focus on the safe choice, the consequence spelled out) for: delete (any dictionary entry, product, variant, price, media removal on save), archive and unpublish, replacing a draft product's options (regenerates variants), cancel order (reason required; for a paid order: "sold units are not restocked and nothing is refunded; record a stock return by hand"), mark paid (amount, reference), mark fulfilled, stock adjustments that lower stock or use `setOnHand`, deactivate a customer or an admin user (ends their sessions), role changes, password reset (ends all sessions of that user), category move.
- **Audit of dangerous actions**: the order journal and the stock journal exist and are shown; everything else has no audit trail (gap 14), stated in the admin README.
- **Role checks**: UI gating is convenience only; every action's `403` is handled; owners cannot demote or deactivate the last owner (the API's `409` is explained).
- **Personal data**: customer and order screens are `orders.read`/`customers.read` only; nothing personal is logged to the console; error reports do not exist.
- **Swagger UI and `/docs-json`** stay an open owner decision (HANDOFF); the admin host does not route them.

## Accessibility (WCAG 2.1 AA target, AGENTS.md section 3)
Landmarks (`header`, `nav`, `main`), skip link, one `h1` per screen and focus to it after navigation, `aria-current` in the side navigation, breadcrumbs and pagination, data tables with `caption`, `th scope` and a row header, every control labelled through `Field` with errors linked by `aria-describedby` and an error summary that receives focus, WAI-ARIA tabs in the product editor, native modal dialogs with focus return, `aria-live` for "saved" and background reloads, status as text plus badge (never colour only), visible focus (`ring` token), contrast enforced by the extended contrast scan, keyboard-only operation of every flow (one e2e test), `lang` follows the UI language.

## Performance
Pagination on every list (admin default 50; orders 20; never "load all" except the bounded dictionaries used by pickers, page by page); no N+1 on the server (the step 2 additions are tested for a fixed statement count) and no unbounded fan-out on the client (at most 6 requests in flight if a fallback needs several); route-level code splitting with an entry-chunk budget; requests aborted on navigation; search inputs debounced (300 ms) and reflected in the URL; no polling; images lazy with explicit dimensions.

### Decisions taken where the plan was silent

- Routing is `react-router` 8.4.0 in data-router mode (owner answer 4). Data access, forms, the permission table and i18n are hand-written; no query or cache library.
- The admin does not import `@fluxkit/core`. Core has no `"sideEffects": false`, so one import pulled zod and the whole core (88.6 KB minified). The constants and rules the admin needs are copied and compared with core in tests. The flag would cut that to 1.5 KB; the change is for the orchestrator.
- Messages are lazy per area (`catalog-dictionaries`, `products`, `orders`, `customers`, `users`). The namespaces `order.*`, `customer.*` and `user.*` avoid the permission names `orders.read`, `customers.read` and `users.manage`, which the messages spec would read as keys.
- Initial JavaScript at the last measure (step 10): 400 678 bytes raw, 120 320 gzip. Budget: 440 000 and 135 000.
- `Referrer-Policy: no-referrer` (ADR 0027) replaces this plan's `same-origin`; `Cross-Origin-Opener-Policy: same-origin` was added.
- Writes are never optimistic, are sent once and are never retried. A lost answer is "result unknown": the screen reloads and shows the stored state. A `mark-paid` may be retried by the admin with the same reference (idempotent by reference).
- Session expiry opens a re-sign-in dialog over the page; the failed request is not replayed.
- The product editor's tabs are keyed by `productRevision`, not by the product's `updatedAt`, because a variant, media or option write does not change that timestamp (step 6b).
- Fixed in step 11: `Tabs` (`packages/ui`) dropped the second of two fast arrow keys. Every key that moves focus now selects that tab.

## Risks
- **Scope size** (13 PRs; the product editor alone is large): strict step boundaries, the editor split 6/7, area folders and message files per area for parallel work.
- **Storefront XSS reaching the admin** if a client deploys the SPA on the storefront origin against the recommendation: ADR 0027 and the README say so; option B is documented as not recommended.
- **Cookie tossing** between sibling hosts of one registrable domain (ADR 0010): documented; a separate registrable domain for the admin host is the strong mitigation.
- **Hand-written types for about 90 admin operations drift**: the contract test compares every operation and type with `openapi.json` and fails on any difference.
- **Permission drift** between UI and API: one table, tested against the API (gap 10), `403` handled everywhere.
- **Client-side N+1** if open question 2 is answered "no": bounded concurrency, documented slowness for large products.
- **Lost responses on non-idempotent writes** (stock adjustments, creates): no automatic retry, reload and show; double-counting stays possible if an admin retries blindly (open question 12).
- **Last-write-wins** on same-field concurrent edits (open question 13).
- **`413` on large product bodies** (gap 17).
- **No audit log** for prices, catalog, users and customers changes (gap 14): accepted for v1, stated in the README.
- **Untested proxy configurations** (Caddy, nginx examples): the e2e proxy is the tested reference, as in the storefront.
- **Bundle growth from `@fluxkit/core`** (zod): measured in step 4b; fallback is no core on the client.
- **Vite inline scripts breaking the strict CSP**: checked against the built HTML in step 4b.
- **Rate limit sharing behind a wrong proxy** (all admins one login window): README checklist (ADR 0024).
