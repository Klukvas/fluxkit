## Summary for the owner

- The client creates provider accounts, enters keys in the admin, checks setup, then explicitly activates email, payments or shipping. DNS and subscriptions start in provider dashboards.
- Provider keys are encrypted in PostgreSQL. The admin can replace them but never read them back; public settings are stored separately.
- The encryption key, infrastructure, trusted URLs and security-alert destination stay in server env. Back up the encryption key separately: losing it can strand existing work.
- Sensitive changes require the owner's current password. Creating/promoting/reactivating owners and resetting any owner password must require it too, or a stolen session can bypass this protection.
- A stolen owner password still permits abuse and service disruption; encryption is not account-takeover protection. Independent security alerts are mandatory; MFA is deferred.
- Monobank is permanently tied to the merchant verified from the trusted existing server token, or explicitly enrolled by the operator. Disabling/re-enrolling cannot change that merchant.
- Existing mail, invoices and shipments keep their exact credential version. Rotation retains needed old versions; emergency revocation stops their authority and can strand refunds or labels.
- Email counts show retained Fluxkit sends through a provider across all accounts, not the current account's remaining quota. Changing accounts can make the comparison misleading.
- Ship approved suppression and fallback plus the usage meter first. The managed-settings MVP then requires encryption, step-up, bindings, revocation, strict limits and alerts (§9).
- Faster replica invalidation, automatic env fingerprints, request-settings snapshots and domain automation can follow with the conservative MVP restrictions in §9. Resend's optional later DNS flow uses a full-access key for one request only.
- Owner decisions (§10): approve DB secrets/key escrow, the expanded auth scope, merchant enrollment/retention, independent alerts, strict outage behavior and DNS automation timing. This draft authorizes no implementation or live change.

## 2. One configuration store and permission boundary

- One API-owned `IntegrationConfiguration` service/repository/crypto/revision mechanism under `apps/api/src/integrations/`, keyed by `(kind, provider_code)` (codes can repeat across kinds). Core owns pure validation/ports; dynamically discovered plugins supply typed configuration/factories.
- Separate public settings from encrypted versions; allowlist provider/global-route fields and reject nested credential-looking fields. No generic SQL/config editor.
- Add owner-only **`integrations.manage`** for keys, enablement, sender/fallback, domains/webhooks and quotas; deny manager/viewer. Keep `email.manage` for usage/outbox and `shipping.manage` for operational profiles, never credentials.
- Move shipping profiles into the same store with compatible responses/validation and manager access; one writable copy, shared revision/audit. Profile edits cannot expose secrets or enable integrations.
- Secret reads return only `{state: "not_set" | "set" | "env", last4: null}`: “Not set”, “Set”, “Set on the server”. Env fields are read-only. **No suffix for any provider**; use revision/time for identification. Never return plaintext, ciphertext, nonce, digest or key ID; no reveal/export endpoint.
- Audit proposed actions `integration.settings_changed`, `integration.secret_changed`, `integration.enabled`, `integration.disabled`, `integration.secret_retired`, `integration.secret_revoked`, `integration.webhook_replaced`, `integration.check_requested`; target kind `integration`, target UUID. Only actor/target/version IDs, provider/kind/field/action codes; no values, suffixes, sender/domain/merchant names, fingerprints or provider response text. Mutation and audit commit together; read-only remote checks record invocation and code-only outcome, never raw payloads.

## 3. Encryption, rotation and recovery

- AES-256-GCM via `node:crypto`, no dependency: new random **12-byte nonce**, **16-byte tag**, 32-byte key. Never reuse nonce/key; validate plaintext bounds and authenticate before use. [Node crypto API](https://nodejs.org/api/crypto.html#cryptocreatecipherivalgorithm-key-iv-options).
- AAD canonically length-prefixes `fluxkit.integration-secret/v1`, final secret-row/integration UUIDs, kind, provider code, field, generation and key ID. Bind before insert; row/field/provider swaps fail authentication with a generic unavailable code, never fallback decryption.
- Env-only **`SECRETS_ENCRYPTION_KEY`**: `<key-id>:<base64>`, ID `[A-Za-z0-9_-]{1,32}`, canonical standard Base64 of exactly 32 random bytes, never a password or derivative of `ORDER_TOKEN_SECRET`. **`SECRETS_ENCRYPTION_KEY_PREVIOUS`** has the same format, different ID/bytes; at most one. Envelopes store key ID.
- Validate supplied master keys at boot even when integrations are off: malformed/blank, duplicate IDs or previous-without-current fail by variable/code only. Both absent disables managed configuration and preserves legacy env-only deployments. Existing ciphertext never silently falls back to env: refuse its work, fail required-credential readiness, retain unused rows for explicit recovery.
- Future operator rotation command: install old-current/new-previous on every replica, verify both, promote new-current/old-previous everywhere, then rewrap bounded pages under a Postgres advisory lock with fresh nonces/AAD and row/key-ID CAS. Resume after interruption; surface failures. No credential-generation/pin/cooldown change, network calls or startup rotation.
- Remove previous key only after live envelopes and replicas no longer need it and old backups have separate escrow or expire. Rewrap does not change historical backups. Keep DB/key backups separately access-controlled, never in one dump/image; restore drills require both and reapply ADR 0033 erasures.
- No usable master/previous/escrow means **irrecoverable ciphertext**. Restore or authenticate replacement; old work may remain stranded. Never clear pins or fake decryption. Revoke compromised keys at the provider; deleting ciphertext does not revoke them.

## 4. Settings ownership and exact precedence

- Resolution is **explicit env override → committed DB setting/secret → documented default**. Env is read once at boot, never modified by admin. DB changes apply live; changing env still needs an operator rollout. Validation failures never fall through to a lower-priority source.
- For `RESEND_API_KEY`, `BREVO_API_KEY`, `MONOBANK_TOKEN`, `NOVA_POST_API_KEY`, `RESEND_WEBHOOK_SECRET`, `BREVO_WEBHOOK_SECRET`: a nonblank env value wins the corresponding secret field. Unset/blank means no override (keep blank examples usable); validate nonblank values with the plugin's existing rules. An env key alone does not enable a provider. Disabled plugins retain today's lazy secret validation in env-only mode; enabling a stored plugin validates its full effective configuration.
- For `EMAIL_PROVIDER`, `EMAIL_FALLBACK_PROVIDERS`, `PAYMENT_PROVIDERS_ENABLED`, `SHIPPING_PROVIDERS_ENABLED`: **presence**, including blank, is an override. Blank retains today's off/empty semantics; `EMAIL_PROVIDER=none` explicitly locks email off. Each variable overrides its own complete list, not individual members; resolve all fields, then validate the resulting route atomically. No hidden DB fallback may survive an explicitly empty env fallback list. Remove the variable to delegate that selection to admin; existing example defaults keep their meaning.
- `EMAIL_FROM`: nonblank env wins, blank/unset delegates; email cannot be enabled without a valid effective sender. `EMAIL_REPLY_TO`: presence wins, blank explicitly clears. `NOVA_POST_ENVIRONMENT`: presence wins, blank means existing `sandbox` default; absent delegates to DB then `sandbox`. `EMAIL_USAGE_LIMITS`: nonblank env replaces the complete limits object; absent/blank delegates to DB then defaults. No merge of lists/JSON that conceals operator intent.
- The admin shows effective source per field, rejects writes to env-locked fields (`409 integration_env_override`), and shows the effective route before save. DB settings shadowed later by env remain inactive; removing env can reactivate them, so deployment preview must show this. No automatic import of env secrets into DB.
- All replicas must share the same env overrides/key ring. **Later, before multiple replicas or live env-generation changes:** record a keyed HMAC of the canonical effective env overrides (domain-separated from the master key), never a raw key/digest in API/logs; register its generation at boot and refuse serving with a different override generation until an operator coordinates cutover. HMACs are internal secret metadata, not configuration identities that reset on every restart. Master rotation recomputes them under the coordinated key-ring procedure, without changing credential bindings. MVP instead requires the stopped-worker/drain procedure in §5; no automatic env rebinding.

## 5. Runtime changes and work already in flight

### Discovery, publication and several API instances

- Managed mode discovers manifests/factories without credentials at boot through the shared loader. Legacy env mode retains selected-module loading; plugins lacking the new factory are restart-only/unavailable for managed activation. No arbitrary runtime Nest attachment.
- Admin configures discovered code only; package changes need deployment/restart and matrix checks. No installs/scripts/uploads; production refuses fake providers, including DB configuration.
- Replace boot-time booleans/conditional routing in config, email auth guards and webhook ingress with runtime effective-state checks in managed mode. Disabled new-work routes answer their existing off behavior; installed route handlers do not imply an enabled integration. Preserve legacy callers through registry facades. A change from none to active must update `/store/config`, `/admin/config`, immediate senders, jobs and storefront capability caches; bound capability-cache staleness and revalidate on API refusal.
- PostgreSQL singleton `integration_revision` increases in the **same transaction** as settings/active-version/audit changes. Writes use `expectedRevision`; stale editors get 409. Validate the complete candidate (installed package, format, production constraints, sender, fallback webhook/suppression readiness) before commit. Separate explicit check/test calls make external calls; a save never silently sends or charges.
- MVP reads authoritative DB state at admission and webhook fact commit; immutable clients are keyed by version, never authority. Later revision caches have at most **5-second** TTL and optional ID-only pub/sub; loss recovers by DB reads. Fast invalidation is optional, authoritative revocation checks are not. DB unavailability refuses work; a cached client cannot authorize it.
- Admission checks revision and version authority under the integration row lock while durably claiming mail/payment/shipment. Stale snapshots defer; retries keep their binding. Disable stops new admissions; previously admitted work may finish. **Revocation is stricter:** queued/pacing work rechecks authority at the final transport-start gate (§5 below). This adds a DB check after pacing and requires adjusting the existing pacing budget/contract; do not preserve the old no-query assumption at the cost of revocation safety.
- Scheduler lock coordinates passes, not admin changes/immediate sends. Reuse current row locks/fencing and short transactions; test two independent API processes. This plan does not authorize scaling the production example before multi-instance PR 4.

### Credential generation is distinct from encryption key ID

- Every credential/account/environment replacement produces an immutable credential version. Encrypt all fields of that version separately; active pointer changes atomically. Re-encrypting under a new master key retains the credential version. Never mutate an HTTP client in use or share JWT/public-key caches across versions.
- Add nullable `integration_credential_version_id` on `email_message`, `payment`, `shipment` for durable binding; refunds use their parent payment's binding. Pin email credential generation at dispatch admission (not enqueue). Proven non-acceptance may release that binding before selecting another provider/version; ambiguity or acceptance preserves it permanently with the existing provider pin. Safe fallback updates the attempted version atomically; an expired lease pins the version selected by the crashed claim. UUID/idempotency key and original retry window never change.
- Preserve request settings as well as keys: mail currently reads from/reply-to at send time (`apps/api/src/email/outbox/email-sender.ts:227`, `:268`). **MVP:** refuse sender/profile/environment/template/origin changes while dependent work may retry or need those settings, including through the shipping compatibility API; drain/reconcile first. **Later:** bounded immutable operation-settings snapshots on mail/shipment allow new settings while old work survives. Bind snapshots at first admission; keep template version/UUID/window, no rendered bodies/auth links. Proven-safe unsent attempts may refresh. Never silently re-render a pinned retry with changed settings.
- Bind legacy attempted/open records during quiesced cutover; DB credentials remain encrypted, env credentials remain references (no silent copy). **MVP env rotation:** stop workers/admissions, prove no env-bound work needs the old key, then replace/restart under an operator-recorded generation. Otherwise refuse rotation; restore the exact old env or reconcile stranded work, never assign old rows to a new value. This may block rotation for long-lived refunds/labels. Later keyed fingerprints detect mismatches automatically; no automatic rebinding. Env-only deployments keep their existing drain requirement.

Profile changes are validated separately and do not change an existing shipment's credential binding. |

- **Merchant baseline:** during stopped-worker cutover, authenticate `GET /api/merchant/details` using the existing trusted env token; record merchantId + environment in a separate immutable authenticated baseline before candidate activation is exposed. If none exists, an operator must explicitly approve first enrollment against independently confirmed merchant details; an owner-session wizard cannot establish it. Failures leave activation blocked. The baseline is independent of credential rows, protected against identity update/delete (rewrapping only), and retained through disable, retire, revoke and re-enroll. A transfer needs a separate operator-approved migration; no writable `merchant_identity` secret field.
- **Retention:** the two-slot bound applies only to email webhook current+previous verifiers. Outbound operations select **one exact version ID**, never try a list. Retain any number of needed versions: email until terminal, payments throughout supported refunds/reconciliation, shipments through fulfilment/cancellation/label access. Retire secrets only after reference checks and the owner-approved service window; keep tombstones, clean unused candidates, expose counts/age for review. A third rotation must not fail merely because two older versions still service work.
- **Emergency revocation:** a separate terminal `revoked` state, timestamp and code-only audited action immediately removes authority without deleting references, envelopes or merchant baseline. Never reactivate that version. Recheck verifier state under lock in the transaction recording webhook facts/receipts; concurrent revocation wins if committed first. Unavailable DB means no facts and a provider-retryable response (§6). Recheck **every** later network admission, including bound retries, adapter retries, JWT/key refresh, checks, refunds and tracking. For work waiting after admission, serialize the final transport-start gate with revocation under a short version lock; the durable claim already exists, release the lock after invoking transport, never await the remote response under it. Re-budget/re-reserve email pacing if the DB check exhausts its slot. Only already-started remote calls may finish after revocation; cancellation is best-effort and completion remains fenced/ambiguous as appropriate. Revoke at the provider separately and reconcile missed events; local revocation cannot recall a remote effect.
- Replacing a revoked key for the same account cannot be assumed safe for email idempotency or Nova Post historical access. Cross-key deduplication/account equivalence is **UNKNOWN** until provider evidence/live checks; choose holding/manual reconciliation rather than automatic rebinding. Monobank merchant identity equality is necessary, not proof that every old resource is accessible.

## 8. Security review requirements

- **Owner compromise / step-up (MVP auth red zone):** current-password verification is required on secret change/removal, activate/disable/revoke, sender/route change, webhook replacement, temporary DNS key use and candidate sends. Also require the **actor's current password** on `POST /admin/users` creating an owner, `PATCH /admin/users/:id` promoting/reactivating an owner, and `POST /admin/users/:id/reset-password` targeting any owner, including self. Otherwise a stolen session can mint a password it knows (§1). Use shared throttling; verify/hash (dummy verify for missing/locked principals) outside locks, then transactionally recheck actor active owner, live session, unchanged actor hash and locked target's current/resulting role (including promotion/reset races). Preserve last-owner/session-revocation rules. Failed step-up attempts get durable code-only audit records in a separate transaction, never rolled back with the refused mutation; audit failure refuses the action.
- **Security notifications (MVP):** commit a durable code-only notification with credential changes, activation, webhook replacement and emergency revocation (also owner-account changes above). Deliver via a **dedicated env-only Resend security-alert account/key**, with `SECURITY_ALERT_FROM` and `SECURITY_ALERT_TO` set by the operator to a previously trusted owner address. Neither integration changes nor newly created/promoted owners redirect this channel; do not resolve it from the normal email route or current admin email. Dynamically load the existing adapter with a separate dispatcher/outbox and fixed origin, independent of commerce enablement/suppression. No SDK; removing Resend remains build-safe but blocks managed activation until an approved replacement alert channel exists. Operator verifies enrollment/delivery before managed activation; changing channel/destination is an out-of-band operator procedure, not this UI. Pending alerts cannot switch channel generation silently. Retry durably with visible failed/pending state; delivery outage must not block emergency revocation. Never include secrets, sender/domain/merchant values or provider text. A stolen **password** still allows same-account abuse/denial of service; alerts detect, not prevent, takeover. MFA remains deferred; server or alert-account compromise can defeat alerts.
- **Strict composite limits (MVP):** `RedisWindowStore.hit` falls back locally and `RateLimitGuard` takes one limit (§1); add an atomic `attemptStrict(windows)` operation returning allowed / denied+retryAfter / **unavailable**, without local fallback or a racy preflight. All step-up paths share 5/15 min/admin + 20/15 min/IP. Checks/domain reads share 10/min/admin + 30/min/IP and 30/min/provider; shipping checks retain their tighter 30/10 min/admin cap. Candidate and existing `/admin/email/test` share 5/hour/admin + 20/hour/IP + 20/hour/provider. Apply the same provider/check budgets to `/admin/shipping/providers/{code}/check` and new endpoints; budgets are keyed by provider, not credential ID or route. Active-route tests reserve provider budgets for every possible route member before enqueue. Both admin and IP windows are consumed **before** hash/verify or network work, after CSRF/principal validation. Managed mode requires Redis even on one API; login/checkout otherwise keep existing policies. Tests cover concurrency, cross-endpoint/replica exhaustion, failed passwords, timeouts and Redis loss without downstream work.
- **Secret lifecycle (MVP):** password inputs, `autocomplete="off"` for provider/temporary keys and step-up passwords; `new-password` for newly assigned passwords. Treat attributes as hints, not a security guarantee. Clear secret/password values on submit/error/cancel, session expiry (including mounted reauth overlay), principal change, navigation, pagehide and pageshow/Back/Forward restoration. Exclude them from unsaved-form snapshots, stores, persistence, debug output and request replay. Browser tests must inspect values beneath the expiry dialog and after same/different-user login and Back/Forward. No reveal/export, URL/history, DOM attribute values, analytics or telemetry; responses no-store. OpenAPI request fields are writeOnly, without examples.
- **Redaction (MVP):** `problem.filter.ts:249` logs ordinary error messages/causes; `:102` passes explicit 5xx bodies. Universal redaction at proxy/request/logger/error/response boundaries is an implementation requirement, not an existing guarantee. Allowlist operation/ID/code outputs; protect passwords, key values, auth/cookie/signature headers, envelopes and Nova Post auth query. Never attach raw provider errors/causes/bodies. Test hostile sentinels in nested causes, validation/DB errors, explicit 5xx and all new/compatibility endpoints; preserve documented safe health responses by allowlist.

Fixed provider origins only, no admin-supplied API/callback URLs; bound/escape responses and reject redirects. Constant-time webhook comparisons and generic decrypt failures. Decrypt for bounded invocation/client lifetime, no Redis plaintext; clear buffers where feasible (JS GC cannot guarantee zeroization). Protect dumps, DB/Redis and separate key escrow; encryption cannot protect against a compromised application/server or malicious DB rollback.
