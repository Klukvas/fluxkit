## Goal
A shopper opens the storefront in `uk` or `en`, browses the home page, the catalog and categories (filtered by category and brand, newest first, paginated), opens a product, picks a variant through its options, adds it to the cart, sees current prices with price-change and availability notices, and places an order as a guest or as a signed-in customer. The order stays `awaiting_payment` (payment is the next plan). A guest reopens and cancels the order through a private link; a customer registers, signs in and out, edits the profile, changes the password and sees the order history. Every screen uses design tokens and translated strings only, handles empty, loading and error states, works with the keyboard, and is fed by a typed API client generated from `docs/api/openapi.json`.

### Out of scope (each gets its own plan)
Online payment and payment-provider UI (next plan); full-text search, attribute filters, facets and price or name sorting (search plan, blocked by ADR 0005); shipping methods and shipping cost; email flows (password reset, email verification, order emails, "find my order by email"); discounts and coupons; wishlist, reviews and other optional features, and the storefront extension point (UI slots) that such features need; customer address book; multi-currency; the admin UI; a storefront Docker image and a production deployment (the API has none either, AGENTS.md section 1); analytics, telemetry and third-party scripts; CMS pages or blog; a dark-mode switch (the tokens support `data-theme="dark"`, nothing toggles it); on-demand revalidation (no catalog events exist); slug redirects (`docs/contracts/api.md`, "Stability of identifiers"); rich-text product descriptions.

## Assumptions to confirm (my defaults; approving this plan approves them)

### Topology: how `/store/*` reaches the API
- The browser only ever talks to ONE origin. Requests to `/store/*` on that origin go to the API unchanged (path, query, body, `Cookie`, `Set-Cookie`, status, headers); every other path is the Next.js app. Because the API sets host-only cookies (no `Domain`) with `Path=/store`, they land on the storefront origin and the browser sends them only to `/store/*`.
- **Local development**: a Next.js `rewrites()` entry `/store/:path*` -> `${API_INTERNAL_URL}/store/:path*` in `apps/storefront/next.config.ts`. One command per app, no extra service. `TRUST_PROXY=0` on the API (every shopper in the dev window is `127.0.0.1` anyway).
- **Any deployed environment**: an edge reverse proxy (Caddy or nginx, operator's choice) in front of both, that routes `/store/*` straight to the API and everything else to Next, and that SETS (not appends to) `X-Forwarded-For` from the connecting address; the API runs with `TRUST_PROXY` = the exact hop count (1 for that single proxy). Reason: through a Next rewrite the per-address limits (`checkout` 10 per 10 minutes, `login`, `registration`, `orderLookup`, `guestCancel`, `cartWrite`) are either ONE shop-wide window (`TRUST_PROXY=0`: one shopper can block checkout for everyone) or spoofable (`TRUST_PROXY=1`: the browser's own `X-Forwarded-For` is the last hop). This refines the README/ADR 0024 note "behind a proxy or the Next.js server". Example configurations live in the README Deployment notes (documentation only; no new Compose service, see open question 1). The finding comes from reading the Next source (above) and is verified at runtime in step 3 (a test that sends a forged `X-Forwarded-For` through the dev rewrite and looks at what the API received).

### Rendering and caching model (per route)
- **Public catalog pages are rendered on the Next server; personalized pages are rendered in the browser.** Personalized data needs the `Path=/store` cookies, which the browser never sends to `/uk/...` page requests, so the Next server cannot read them (changing the path is a breaking cookie contract and widens exposure; rejected). Consequences: no Server Actions and no Route Handlers that call store writes; the Next server never forwards a shopper's cookies; cart, checkout, account and order pages are a server-rendered shell plus a client component that calls `/store/*` from the browser with `cache: "no-store"`.
- **No API at build time.** `next build` runs inside `pnpm build` and in CI without an API, so no page fetches the API during the build: catalog pages render at request time (`dynamic = "force-dynamic"` or the equivalent of the installed Next version; checked against `node_modules/next/dist/docs` in step 4) and cache the API RESPONSES in the Next data cache (`fetch(..., { next: { revalidate: CATALOG_REVALIDATE_SECONDS, tags } })`, 60 seconds, an internal constant). `generateStaticParams` stays limited to the locales. `cacheComponents` is NOT enabled in v1 (one more moving part; revisit when on-demand revalidation exists). If the API fails while a cached response exists, the cached one is used; without one, the route's `error.tsx` renders (no blank page, no silent fallback data).
- Server-side catalog fetches go to `API_INTERNAL_URL` directly (not through the public origin), without cookies, with `?locale=` from the route.

| Route | Rendering | Data | Cache | Indexing |
|---|---|---|---|---|
| `/` | redirect to `/{defaultLocale}` (exists) | - | - | - |
| `/{locale}` home | server, per request | `/store/config`, `/store/categories`, `/store/products?limit=8` (and per-section queries from the layout config) | API responses 60 s | index |
| `/{locale}/catalog` | server, per request (`page`, `brand` query) | `/store/products` | 60 s | index page 1; `noindex, follow` on filtered views |
| `/{locale}/c/{categorySlug}` | server, per request (`page`, `brand`) | `/store/categories` (breadcrumbs, children), `/store/products?category=` | 60 s | index (canonical without `brand`) |
| `/{locale}/p/{productSlug}` | server, per request; client island for the variant picker and add-to-cart | `/store/products/{slug}` | 60 s; `404` -> `notFound()` | index |
| `/{locale}/cart` | shell + client | `GET /store/cart` | `no-store` | `noindex` |
| `/{locale}/checkout` | shell + client | cart, `me` (optional), `POST /store/checkout` | `no-store` | `noindex` |
| `/{locale}/order/{number}` (guest, token in the fragment) | shell + client | `POST /store/orders/lookup`, `/cancel` | `no-store` | `noindex`, `Referrer-Policy: no-referrer` |
| `/{locale}/account/login`, `/register` | shell + client | login, register | `no-store` | `noindex` |
| `/{locale}/account`, `/account/orders`, `/account/orders/{number}`, `/account/profile` | shell + client | `me`, orders, cancel, `PATCH me`, change-password | `no-store` | `noindex` |
| `/sitemap.xml`, `/robots.txt` | server, per request | products (pages of 100), categories | 1 hour | - |

- Header: the category navigation is server-rendered with the page; the cart badge and the "Sign in / Account" link are a client component (`GET /store/cart` and `GET /store/account/me` once per page load; a `401` from `me` simply means "guest").
- Availability and prices on catalog pages can be up to 60 seconds old. The cart and the checkout always show the server's current values (`docs/api/cart.md`), so a stale page never charges a stale price.

#### Runtime test of the dev rewrite (step 3, run 2026-10-18; confirms the claim above)
Setup: the built API (`pnpm --filter @fluxkit/api start`, migrated and seeded `_dev` database, `STORE_COOKIE_SECURE=false`) and `next dev -p 3001` of this branch with `API_INTERNAL_URL` pointing at it (Next 16.4.1, Turbopack, Node 22.22). Method: (a) a throwaway echo server on port 3999 standing in for the API printed the raw request it received through the rewrite; (b) the real API, restarted for each `TRUST_PROXY` value (its limiter is in memory), received 130 `DELETE /store/cart` calls (the `cartWrite` limit is 120 per minute per `request.ip`) through the rewrite. The probe scripts were not committed.
- **What the API receives (echo server).** A request sent with `X-Forwarded-For: 1.2.3.4` arrives with `x-forwarded-for: 1.2.3.4` unchanged and the socket address `127.0.0.1` (the Next process); `1.2.3.4, 5.6.7.8` also arrives unchanged (Next does not append the connecting address); a request without the header arrives WITHOUT any `x-forwarded-for`; Next adds `x-forwarded-host: 127.0.0.1:3001` and replaces a forged `X-Forwarded-Host`; `Cookie`, `X-Fluxkit-CSRF`, `Content-Type`, the query string and the method pass through. So the rewrite neither sets nor appends `X-Forwarded-For` and forwards the client's own value: the claim is confirmed.
- **Effect on the limits (real API, through the rewrite).**

| `TRUST_PROXY` | Forged `X-Forwarded-For` | 130 requests give | Meaning |
|---|---|---|---|
| 0 | different on every request | 120 x 204, 10 x 429 | one shop-wide window (the key is `127.0.0.1`) |
| 1 | different on every request | 130 x 204, 0 x 429 | the limit is evaded: the forged value is the key |
| 1 | the same `1.2.3.4` | 120 x 204, 10 x 429; then `7.7.7.7` gets 204 and `1.2.3.4` 429 | the shopper chooses the bucket |
| 1 | none | 120 x 204, 10 x 429 | falls back to the socket address: one shop-wide window |
| 1, direct to the API (no Next) | different on every request | 130 x 204 | same evasion without Next: `TRUST_PROXY=1` needs a proxy that SETS the header |

- **Conclusion.** Both failure modes exist exactly as ADR 0026 describes, so a Next rewrite must not be used outside development, and a deployed edge proxy must set (not append to) `X-Forwarded-For`. `next dev` with `TRUST_PROXY=0` is fine for development (one developer, one address).
- The `Set-Cookie: fluxkit_cart=...; Path=/store; HttpOnly; SameSite=Lax` of the API reaches the browser unchanged through the rewrite (host-only, no `Domain`), the cookie is sent back on `/store/*`, the cart reads back, and a write without `X-Fluxkit-CSRF` is `403`. The built client (`@fluxkit/api-client`) was run against both `:3001` (rewrite) and `:3000` (direct) with identical results for config, products, `401` problem, validation problem and an empty cart.

### Typed API client (`packages/api-client`)
- **Types are generated from `docs/api/openapi.json`; the runtime is a hand-written thin `fetch` wrapper** (about 200 lines, no runtime dependency). Proposed generator: `openapi-typescript` as a **devDependency of `packages/api-client` only** (red zone: new dependency, approval needed; see open question 4 for license, size and alternatives). The generated `paths` type is written to `packages/api-client/src/generated/` during `build` and `typecheck` (git-ignored and Prettier-ignored: AGENTS.md section 12, no generated files in git), so a contract change in `openapi.json` breaks the storefront's type check, not its users.
- The wrapper: `createStoreClient({ baseUrl, fetch? })` with one typed function per store operation; on every non-`GET`/`HEAD` request it adds `X-Fluxkit-CSRF: 1`, and `Content-Type: application/json` when there is a body; `checkout(body, { idempotencyKey })` sets `Idempotency-Key`; responses are parsed by status into `{ ok: true, status, data }` or `{ ok: false, status, problem }` where `problem` is the parsed `application/problem+json` (`code`, `errors[]`, `rule`, `cart`, `Retry-After`); a network failure or a non-JSON body is a thrown error (no silent fallback). `baseUrl` is `""` in the browser (same origin) and `API_INTERNAL_URL` on the server. No admin routes in v1.
- **Fallback if `openapi-typescript` is not approved or does not accept TypeScript 6.0.3** (its peer range must be checked before step 2; TypeScript is pinned, AGENTS.md section 1): hand-written response types in the wrapper plus a test that walks `openapi.json` and asserts each hand-written type's required keys exist in the schema (no dependency, weaker drift protection).
- **Step 3 outcome (2026-10-18): the generator is not used; the fallback above is implemented.** `openapi-typescript` 7.13.0 (MIT, 858 KB unpacked, 32 packages with its dependencies) declares `peerDependencies.typescript: ^5.x` in every 7.x release, which does not accept the pinned TypeScript 6.0.3, so the owner's condition applied. `packages/api-client` has hand-written types and `contract.spec.ts` compares every type, operation, parameter, header, status and content type with `docs/api/openapi.json`; no generated files, so `.gitignore`, `.prettierignore` and turbo/CI needed no change. See `packages/api-client/README.md`. Re-evaluate the generator when it supports TypeScript 6 (a later, separate change).

### Guest order token: storage, passing, threat model
- After a guest checkout the storefront navigates to `/{locale}/order/{number}#t={accessToken}`. The client page reads `location.hash`, calls `POST /store/orders/lookup {number, accessToken}` (POST, so the token is never in a URL the server sees) and offers cancel while `awaiting_payment`. The confirmation shows "save this link" with a copy button (the link is the only way back until the email plan).
- The token lives only in the fragment and in memory. It is not written to a cookie (it would be sent to servers), not to `localStorage` or `sessionStorage` (open question 8), not logged, not put in page titles, analytics or error reports (there are none), and never sent to the Next server.
- Threat model. Protected against: server and proxy access logs and `Referer` (fragments are never sent); other customers (one identical `404`, constant-time comparison, `orderLookup` limit). Not protected against, accepted and documented: anyone with the link (browser history, sync, a shared screenshot) can read and cancel the unpaid order until `ORDER_GUEST_ACCESS_DAYS`; script running on the storefront origin (XSS) can read the fragment, hence the XSS rules in "Security". Pages that show the token set `Referrer-Policy: no-referrer` and load no third-party resource.

### Checkout idempotency and retries
- The client keeps one **checkout attempt** `{key, requestHash}` in `sessionStorage` (survives a reload in the same tab; no personal data: `requestHash` is the SHA-256 of the request body through `crypto.subtle`). On submit: if the body's hash equals `requestHash`, the same `key` is reused; otherwise a new `crypto.randomUUID()` key replaces it. The server fingerprint covers the body and the cart, so "same body, same key" is exactly what the API accepts as a replay.
- Outcomes: `201`/`200` -> clear the attempt, refresh the cart badge, navigate (guest: order link with fragment; customer: `/account/orders/{number}`); network error, timeout, `5xx`, `503` -> keep the key, show "try again", the next submit replays safely (a lost `201` comes back as `200` with the same token, ADR 0023); `429` -> keep the key, show the wait from `Retry-After`, no automatic retry; `409 cart_changed` -> show the fresh cart from the problem body and its notices; the shopper must confirm the new total, which changes `expectedTotal` and therefore the key; `409 checkout_refused` -> mark the lines from `errors[].path` (`lines.N` = position in the cart) with the translated code; `409 cart_empty` -> clear the attempt, go to the cart (a parallel tab already ordered); `409 too_many_open_orders` -> explain that unpaid orders must be paid or cancelled first (link to the account orders for customers); `409 idempotency_key_reused` -> clear the attempt and ask to submit again (lost cart cookie or changed principal); `400` -> map `errors[]` to form fields.
- The submit button is disabled while a request is in flight (no double click), but the key makes a double submit harmless anyway. `crypto.randomUUID` and `crypto.subtle` need a secure context: HTTPS or `localhost` (documented for local network testing).

### Price-change and cart notices UX
- Each line shows its notice next to the price: `price_changed` ("was X, now Y"), `unavailable` (no price, "no longer available", remove button), `out_of_stock` (badge; still purchasable as the API allows), `line_total_out_of_range` ("lower the quantity"). ### CSRF header handling
- Only the API client sends store writes, and it always adds `X-Fluxkit-CSRF: 1` (unit-tested for every write operation). The storefront exposes no state-changing endpoint of its own in v1 (no Server Actions, no mutating Route Handlers), so it needs no CSRF scheme of its own. `SameSite=Lax`, the header and the absence of CORS keep cross-site forms out (`docs/api/customers.md`, CSRF on the store).

### i18n
- Locale in the path (`/uk`, `/en`), as today. Every user-facing string in `src/messages/{uk,en}.json`; a missing key keeps throwing (`createTranslator`). Added in `packages/ui` `i18n.ts`: `{name}` interpolation and plural forms through `Intl.PluralRules` (Ukrainian one/few/many/other), no dependency. A test asserts both message files have the same keys and the same placeholders.
- API texts arrive translated (`?locale=` from the route). Problem `detail` texts are English and not contract, so they are never shown: every `code`, `rule` and `errors[].code` the storefront handles has a translated message (`errors.<code>`), with one generic message for anything unknown (and the code logged to the console in development only).
- Money: `formatMoney({amount, currency}, exponent, locale)` turns minor units into a decimal STRING with integer arithmetic (BigInt), then `Intl.NumberFormat(locale, {style: "currency", currency}).format(decimalString)`; no float ever holds an amount; the storefront never adds or multiplies money (all totals come from the API). Dates with `Intl.DateTimeFormat`. Country names with `Intl.DisplayNames`.
- The storefront's locales (`packages/ui` `locales`) and the API's `LOCALES` are configured separately; the storefront checks at request time that each of its locales is in `GET /store/config` `locales` and fails loudly (logged error, `error.tsx`) when not.

### Errors, empty and loading states
- Every route segment gets `loading.tsx` (skeletons), `error.tsx` (translated message and retry; the error digest only) and `not-found.tsx`. ### Security (storefront side)
- No `dangerouslySetInnerHTML` except the JSON-LD script, whose JSON is escaped (`<` as `<`); product descriptions are rendered as plain text (line breaks preserved). Text from the API is never rendered as HTML.
- Security headers from `next.config.ts` `headers()`: `Content-Security-Policy` with `default-src 'self'`, `img-src 'self'` plus the configured image hosts, `connect-src 'self'`, `frame-ancestors 'none'`, `base-uri 'self'`, `form-action 'self'`, and `script-src 'self' 'unsafe-inline'` (Next's inline bootstrap without nonces, because nonces force every page dynamic; open question 13); `Referrer-Policy: strict-origin-when-cross-origin` (and `no-referrer` on the order page); `X-Content-Type-Options: nosniff`; `Permissions-Policy` denying camera, microphone, geolocation.
- No third-party scripts, fonts or analytics (AGENTS.md section 3, approval needed). No personal data in `localStorage`; the checkout form is not persisted across reloads.
- `next` redirect parameters accept only paths that start with `/{locale}/` and contain no `//` or scheme.
- Image optimisation, if enabled, uses an explicit host allow-list (no wildcard): an open optimiser is a server-side request and resource-exhaustion risk.

## Decisions to take (ADR 0026, step 1)
**ADR 0026 Storefront architecture: one origin, rendering split and the typed client** (draft text):

> Context: the store API keeps its cookies on `Path=/store`, needs `X-Fluxkit-CSRF: 1` on writes and sends no CORS headers (ADR 0015, 0016); per-address limits rely on `request.ip` and `TRUST_PROXY` (ADR 0024); the storefront build runs in CI without an API.
> Decision: (1) the browser reaches the API as `/store/*` on the storefront origin; in development through a Next.js rewrite, in every deployed environment through an edge reverse proxy that routes `/store/*` to the API and sets `X-Forwarded-For`, never through the Next rewrite (it forwards the client's header unchanged and adds none). (2) Public catalog pages render on the Next server at request time from cached API responses (60 s), without cookies; personalized pages render in the browser and call `/store/*` directly; the Next server never handles store cookies, Server Actions and mutating Route Handlers are not used for store operations. (3) The build never calls the API. (4) The guest order token travels only in the URL fragment and the lookup POST body. (5) Checkout idempotency keys are per request body and reused for retries of that body. (6) `@fluxkit/api-client` types are generated from `docs/api/openapi.json` at build time; the runtime is a thin wrapper that owns the CSRF header.
> Consequences: personalized pages have a loading state after first paint and are not indexed; prices on catalog pages may be 60 s old (the cart is authoritative); deployment needs a reverse proxy (documented), which also serves the admin later; on-demand revalidation needs catalog events (later); changing the cookie path or adding CORS would supersede this ADR.

## Open questions (owner quiz; recommended answer first)
Ordered by importance.
1. **Production routing of `/store/*`.** Recommended: an edge reverse proxy (Caddy or nginx) routes `/store/*` to the API and sets `X-Forwarded-For`; Next rewrites only in development; README gives example configs, no new Compose service in v1. Alternatives: add a Caddy service to `infra/docker-compose.yml` now (Apache-2.0, an external process: needs a `docs/dependencies.md` decision), or Next rewrites everywhere with `TRUST_PROXY=0` (one shop-wide limit window: 10 checkouts per 10 minutes for the whole shop; not acceptable for a launch).
2. **Personalized pages render in the browser** (cookies never reach page requests). Recommended: yes, as above. Alternatives: change both cookies to `Path=/` (breaking cookie contract, cookies then reach every page request and the Next server), or a backend-for-frontend session in Next (a second session system: large, security-heavy).
3. **API change: tell the storefront whether the cart needs a shipping address** (API gap 1). Recommended: a small additive API PR before the checkout step: `requiresShipping` (boolean) on the cart shape, computed with core `shippingAddressRequired`, plus the store `403` and the CSRF header described in `openapi.json`. Alternatives: always ask for an address (wrong for digital-only shops), or ask optionally and react to `400 shipping_address_required` (a confusing second round).
4. **Typed client generator** (new devDependency). Recommended: `openapi-typescript` (MIT; types only, nothing shipped to the browser; peer TypeScript range to be checked against 6.0.3 first) plus the hand-written wrapper. Alternatives: `openapi-typescript` plus `openapi-fetch` (MIT, a small runtime dependency; less code of ours, less control over the CSRF and problem handling), or hand-written types with a key-existence test (no dependency, weaker drift protection). Not recommended: `openapi-generator` (Java), Orval or Hey API (larger generators and runtimes for six resource groups).
5. **Playwright in this plan.** Recommended: yes, step 8, `@playwright/test` (Apache-2.0, dev only), Chromium only, a CI job `e2e` added by the owner to AGENTS.md section 18, `pnpm test:e2e` added to the root scripts. Alternatives: a separate e2e plan after payments, or a written manual test script only for v1.
6. **Component interaction tests.** Recommended for v1: `renderToStaticMarkup` only (no dependency) plus Playwright for interaction. Alternative: add `@testing-library/react` (MIT) and `happy-dom` or `jsdom` (MIT) as devDependencies of `packages/ui` and the storefront.
7. **Product images.** Recommended: `next/image` with an explicit host allow-list (`STOREFRONT_IMAGE_HOSTS`) and a placeholder for anything else (sharp is already approved for Next image optimisation, AGENTS.md section 16). Alternative: plain `<img>` with dimensions and lazy loading, no optimisation in v1.
8. **Guest token on the device.** Recommended: fragment only, "save this link" prompt. Alternative: also keep "recent orders on this device" in `localStorage` (readable by any script on the origin, survives on shared computers).
9. **What the order page says about payment while payments do not exist.** Recommended: message keys with a neutral default ("the shop will contact you to arrange payment") that each client replaces, the expiry time shown, `ORDER_PAYMENT_TTL_MINUTES` unchanged; the README states that v1 is not for live sales until the payment plan (an unpaid order expires after 30 minutes by default unless an admin marks it paid). Alternative: recommend `ORDER_PAYMENT_TTL_MINUTES=1440` for manual-payment shops.
10. **Sorting in the catalog.** Recommended: no sort control in v1 (the API sorts newest first only); price and name sorting come with the search plan. Alternative: an additive `sort` parameter on `GET /store/products` now (a public contract change and new query-count tests).
11. **Brand filter UI and layout contract.** Recommended: brand links on product cards and pages filter the catalog (`?brand=`), no brand list, no API change; the layout config stays internal until a feature needs UI slots. Alternatives: an additive `GET /store/brands` endpoint for a brand facet list (API gap 2); or publish `docs/contracts/slots.md` now.
12. **New design tokens** (`success`, `warning`, `ring`). Recommended: add them (additive, minor). Alternative: reuse `primary` and `danger` for notices (weaker meaning, no distinct focus colour).
13. **Content-Security-Policy strength.** Recommended: the header set above with `script-src 'self' 'unsafe-inline'` (keeps cached rendering; no third-party script exists). Alternative: per-request nonces (every page dynamic, no cached HTML) or no CSP in v1.

## Risks
- **Per-address limits behind the wrong proxy** (shop-wide checkout lock-out or spoofed addresses): topology decision, README configs, a runtime test of the dev rewrite in step 3, a deployment checklist item.
- **XSS on the storefront origin** would act with the shopper's cookies (same origin, CSRF header can be added) and read order tokens from the fragment: no HTML from the API, escaped JSON-LD, CSP, no third-party scripts, review focus.
- **Stale catalog data** (60 s): the cart and checkout are authoritative; notices explain changes.
- **Build depending on the API**: forbidden by design and checked by CI (`pnpm build` without an API must pass).
- **Next.js 16 differences** from older knowledge (Proxy, caching model): developers read `node_modules/next/dist/docs` first (`apps/storefront/AGENTS.md`); the rendering choices are verified in step 4 against the installed version.
- **Generator compatibility with TypeScript 6.0.3**: checked before step 2; fallback documented.
- **No real sales possible without payments**: unpaid orders expire; stated in the README (open question 9).
- **Locale drift** between storefront and API: runtime check.
- **Scope size**: ten PRs (4a and 4b separately) plus the review; the split keeps each reviewable.
