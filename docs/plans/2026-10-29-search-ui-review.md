# Review: search UIs (storefront step 10a, admin step 10b)

Independent QA review of PR #184 (storefront search box, results page, facet panel) and PR #183 (admin Search area), on `origin/main` at `cf698db`. Reviewer: a different model than the authors. Plan: `docs/plans/2026-10-29-search.md`, rows 10a and 10b. No product code is changed by this review; the orchestrator assigns the fixes.

How it was checked: code reading of every file of the two PRs; the real stack (Postgres `fluxkit_revui_test`, Redis, Meilisearch v1.55.0 with a key scoped to `revui_*`, the built API on port 3300 with `TRUST_PROXY=1`, then `2`, then `SEARCH_ENABLED=false`; the built storefront on port 3301 with `next start`) probed with `curl`; the three e2e suites once; 18 mutation experiments on the security, gating and URL-state lines (each reverted, `git status` clean afterwards). Scratch databases, the key, the `revui_*` indexes and the processes were removed at the end.

## Findings

Severity: Blocker (must not ship), Major (fix before a client launch), Minor (fix when convenient). Only proven findings; "proof" names what was run.

### Major

**F1. The Next server is now a trusted proxy hop: a client that reaches `next start` directly chooses the search rate-limit key (evasion and framing).**
- Files: `apps/storefront/src/lib/forwarded-address.ts:16-21`, `apps/storefront/src/lib/search-data.server.ts:18`, `apps/storefront/src/lib/search-data.ts:57-72`.
- Scenario: the page's server read passes the request's `X-Forwarded-For` to the API; Next itself fills the header only when absent (`next/dist/server/base-server.js`, `req.headers['x-forwarded-for'] ??= socket.remoteAddress`), so whatever a client sends to the storefront port is passed on. With `TRUST_PROXY=1` the API counts the rightmost address: a client that can reach the storefront around the edge (a misbound port, an internal network, the development set-up of `README.md` with `TRUST_PROXY=0` excepted) names any address, so it (a) dodges the 60 a minute `search` window by rotating addresses (up to 20 engine requests per page, ADR 0036 decision 3) and (b) uses up the window of a victim address, whose results page then says "Too many searches".
- Proof: API `TRUST_PROXY=1`, storefront reached directly. 60 × `curl -H "X-Forwarded-For: 203.0.113.9" http://127.0.0.1:3301/en/search?q=demo`; then `GET /store/search` on the API as `203.0.113.9` → `429`, `Retry-After: 56`; as `203.0.113.10` → `200`; the page as `203.0.113.9` → "Too many searches / Try again in 56 seconds"; the page without the header → results (Next's own address counts). A chain of 11 addresses and `unknown, 1.2.3.4` are dropped (`200`, counted as the Next server).
- Why it matters: before this PR the storefront never forwarded a client header, so "keep the API reachable only through the proxy" (`README.md:133`, ADR 0024) covered the whole trust model. Now the same rule holds for the storefront port, and it is written nowhere: `apps/storefront/README.md:362` asks the edge to set the header but not that the storefront must be unreachable around it; `docs/deployment.md` and ADR 0036 do not mention the storefront's forwarding at all (the decision lives in a plan row and the storefront README). The guard specs do not pin the check either (F5, M6).
- Suggested fix: (1) state the rule in `README.md` "Deployment notes" (the API AND the storefront reachable only through the edge when `TRUST_PROXY > 0`), in `docs/deployment.md` and in the storefront README; record the forwarding decision in an ADR note (it changes the trust model, AGENTS.md section 14 "public contract / auth"); (2) a spec that fails when `search-data.server.ts` passes the header without `forwardableAddresses` (F5); (3) optional hardening: forward only when an explicit `STOREFRONT_TRUST_FORWARDED=true` (or when `API_INTERNAL_URL` is loopback or private) so a storefront exposed by mistake cannot be used to pick keys.

**F2. Following the runbook's CDN instructions puts every shopper of a CDN node into ONE search window for the results page.**
- Files: `docs/deployment.md:62`, `infra/proxy/nginx/templates/fluxkit.conf.template:122` (storefront location, `proxy_set_header X-Forwarded-For $remote_addr;`), `infra/proxy/nginx/snippets/proxy-to-api.conf:9-10`, `apps/storefront/README.md:362` ("checked for 1 and 2 hops").
- Scenario: `docs/deployment.md` says that with a CDN the operator sets `TRUST_PROXY=2` and switches `proxy-to-api.conf` to `$proxy_add_x_forwarded_for`. The storefront location does not include that snippet: it keeps REPLACING the header with `$remote_addr` (the CDN's address). The page path then hands the API the chain `[cdn]`; with two trusted hops the API keys on the CDN address, so all shoppers behind that CDN node share one 60 a minute window for `/{locale}/search`, while their direct `/store/*` calls (through the snippet) stay per shopper. Before this PR the storefront location's header did not matter for rate limits.
- Proof: API `TRUST_PROXY=2`. Two-entry chains are keyed per client: 60 × `X-Forwarded-For: 203.0.113.21, 198.51.100.2` → the same chain `429`, `203.0.113.22, 198.51.100.2` → `200`, and the page as `203.0.113.41, 198.51.100.2` after its 60 → "Too many searches / Try again in 57 seconds" (so the README's "2 hops" claim holds when the edge APPENDS). One-entry chain, as the storefront location produces: 60 page renders with `X-Forwarded-For: 198.51.100.3`, then the next shopper with the same chain → "Too many searches".
- Suggested fix: move `proxy_set_header X-Forwarded-For` of the storefront location into the same snippet (or a shared one) so one change covers both paths; say in `docs/deployment.md:62` that the storefront location must change too; add a two-hop case to `scripts/deploy-smoke.sh` if the CDN mode is meant to be supported.

### Minor

**F3. Without a script, a typo in a price box is a 404 page, not the "Check the filters" state.**
- Files: `apps/storefront/src/app/[locale]/(catalog)/search/page.tsx:31` (`if (!parsed.ok) notFound();`), `apps/storefront/src/lib/search-query.ts:143-154`.
- Scenario: `isCanonicalSearch` turns a script-less submit into the short address, but a submit the parser refuses (`priceMin=12.505` with a 2-digit currency, or min above max) is treated like a malformed shared link. The browser's `pattern` stops letters, not too many fraction digits or a reversed range.
- Proof: `GET /en/search?q=demo&priceMin=12.505` → `404`; `GET /en/search?q=demo&priceMin=20&priceMax=10` → `404`; `GET /en/search?q=demo&priceMin=12.50&priceMax=&sort=&page=1` → `307` to `/en/search?q=demo&price=1250..` (the good case works).
- Suggested fix: when the form fields (`priceMin`, `priceMax`, `rmin.*`, `rmax.*`) are present and refused, render the results page for the address without them with the form error (`describeFormFailure` already names the box) instead of `notFound()`; keep the 404 for the canonical parameters.

**F4. The range boxes accept a number the API refuses, and the page then blames a missing filter.**
- Files: `apps/storefront/src/lib/search-query.ts:60` (`RANGE_NUMBER`, up to 10 fraction digits), `:105-109`; API rule in `docs/api/search.md` ("nothing JavaScript would print with an exponent, so `0.0000001` is `invalid_range`"), core `packages/core/src/search/selection.ts:59`.
- Scenario: `0.0000001` passes the client and server-side form check, becomes `f=attr.length:0.0000001..`, the API answers `400 invalid_range`, and the shopper reads "These filters are not available. A filter in this address does not exist, or no longer does."
- Proof: `GET /en/search?rmin.attr.length=0.0000001` → `307` to `/en/search?f=attr.length%3A0.0000001..` → `200` with "These filters are not available". (`01..1.50` is accepted by both, `200` with results.)
- Suggested fix: refuse in `parseRangeBox` what `String(Number(text))` prints with an exponent (the same test as core), so the box is named before anything is sent; the `search.invalid.*` wording can stay for vanished facets.

**F5. Test gaps found by mutation (survivors).** Each line is a mutation that left every relevant spec green (the mutations were reverted).
- `search-data.server.ts:18`: passing `(await headers()).get("x-forwarded-for")` on WITHOUT `forwardableAddresses` survives `security-headers.spec.ts:220-231`, `source-guards.spec.ts`, `header-search.spec.tsx` and `search-data.spec.ts`. The security guard pins the header read but not the check that makes it safe (F1). Add `expect(text).toMatch(/forwardableAddresses\(\(await headers\(\)\)\.get\("x-forwarded-for"\)\)/)`.
- `search-money.ts:19`: `Math.round(Number(\`${whole}.${fraction}\`) * 10 ** exponent)` survives `search-money.spec.ts` (the 0.29 case rounds right) and the float guard `source-guards.spec.ts:81-86`, whose regex needs `* 100` or `Math.round(...amount`. Widen the guard (`Math\.round\(`, `\*\s*10\s*\*\*`) and add an amount near 2^53 (`"90071992547409.91"` with exponent 2 must be exactly `9007199254740991`), where the float product is no longer exact.
- `search-query.ts:80`: dropping `!/\s/.test(value)` (a facet value may hold a space) survives `search-query.spec.ts`. Add a refused `f=brand:a b`.
- `page.tsx:32-34`: removing the canonical redirect survives every unit spec; only `e2e/tests/search.e2e.ts` ("redirects a hand-made form address") catches it. `page.tsx:51-53`: removing the past-last-page 404 survives everything (the e2e checks `page=418`, a parse 404, not `page=2` of a one-page result). A spec on `page.tsx` text (like `header-search.spec.tsx:103-107` does for the gating) or a rendered test of the route would pin both.
- Admin `status-page.tsx:34`: removing `if (!canManage) return;` in `confirmRebuild` survives `search-screens.spec.tsx` and `search-permissions.spec.ts` (the button is hidden for viewers; the re-check is defence in depth, untested). `canManageSearch` with `some` instead of `every` also survives, but is an equivalent mutant today (all four operations map to `catalog.write`).
- Killed (for the record): non-IP entries and the 11th hop in `forwarded-address.ts`; control characters in `q`; `cache: "no-store"` of the read; `q` unescaped in `searchPath`; the slug unescaped in `suggestionHref`; `>=` → `>` of the 10 000 message; the abort of the request in flight; `aria-activedescendant`; admin `maxWords` 3 → 4 (compared with core); the create route's 404 read as "gone".

**F6. Selected-filter chips are keyed by their label.**
- File: `apps/storefront/src/components/search-results.tsx:189` (`<li key={chip.label}>`).
- Scenario: two facets can share a title and a value label (a client catalog with an option `color` and an attribute `color`, both labelled "Color", both with "Black"); React then warns about duplicate keys and may reuse the wrong `<li>`. Not reproduced with the demo catalog (no such pair); proven by reading. Key by `${facet.key}:${code}` (the entry) and `price`.

**F7. The e2e READMEs name the wrong Playwright version.**
- Files: `apps/storefront/e2e/README.md:12,73`, `apps/admin/e2e/README.md:12`: "1194 for the pinned `@playwright/test` 1.56.1"; `apps/storefront/package.json:15` pins `1.64.1`, and the suites ran here with Chromium 1248 from `PLAYWRIGHT_BROWSERS_PATH`. Pre-existing text, but the search PRs extended both files; fix the number or drop it.

## Verified OK

- **E2E suites, run once on this machine** (real Postgres, Redis, Meilisearch): `apps/storefront/e2e/tests/search.e2e.ts` 16 passed (34 s); `search-off.e2e.ts` with `E2E_SEARCH=off` 4 passed; `apps/admin/e2e/tests/search.e2e.ts` 6 passed. The counts in the READMEs match.
- **XSS**: `q` of `"><img src=x onerror=alert(1)><script>…</script></title>&amp;` reaches the page only escaped: `<title>`, `<h1>`, the hidden `q` field, the canonical URL (`encodeURIComponent`), no `<script>` or `onerror` as markup, no JSON-LD on the page; `noindex, follow`. The CSP of the page is unchanged (`connect-src 'self'`, no new source). Facet values and suggestion titles are rendered as React text; a space or a control character in a facet value is a 404.

- **PII in logs**: a canary query (`q=xsscanary9931&f=brand:canaryfacet`, also on suggest) left no trace in the API log or the Next log, also not during the engine outage.

- **Combobox ARIA** (markup specs and e2e): `role="combobox"`, `aria-expanded` only with a visible list, `aria-controls`, `aria-activedescendant` only on a highlighted option, `role="listbox"`/`option` with `aria-selected`, a polite `role="status"` live region, Escape closes and keeps the text, Tab leaves, Enter opens the highlighted suggestion or submits, focus stays in the box (`onMouseDown` prevented on options), blur closes. - **Money**: minor units in the address, major units in the boxes; `decimalToMinorUnits` and `minorUnitsToInput` are text and BigInt based; specs cover 0, 2 and 3 digits (F5 notes the guard gap).

## Fixes (branch `fix/search-ui-review`)

Developer decisions taken while fixing the findings above; each finding is one commit.

- **F1, decision (ADR 0037):** the forwarding is OFF by default and switched on by the new optional `STOREFRONT_FORWARD_CLIENT_ADDRESS=true` (exactly `true` or `false`, parsed by `loadStorefrontEnv`; a typo stops the start). Chosen over "forward when `API_INTERNAL_URL` is loopback or private" (the review's other option): the API's address says nothing about whether the STOREFRONT port is reachable around the edge, so only the operator can state that. Off, the request headers are not read at all. `infra/production.env.example` sets `true` (the Compose example publishes no storefront port; the edge sets the header on every path, F2); the development set-up and `.env.example` leave it off. Not a build variable (read per request), so `turbo.json` and the `Dockerfile` need no entry; the production Compose file passes it to the storefront container. The storefront e2e runs its main `next start` with `true` and a second one with `false`.
- **F2, decision:** one nginx snippet `infra/proxy/nginx/snippets/forwarded-headers.conf` (`Host`, `X-Forwarded-For $remote_addr`, `X-Forwarded-Proto`) included by `proxy-to-api.conf` and by the storefront location; the CDN switch is one line there (ADR 0037 decision 4). Caddy needed no change (both `reverse_proxy` blocks take the same default, `trusted_proxies` is server-wide); the guard pins that no `header_up X-Forwarded-For` or `trusted_proxies` appears. The static guard is in `apps/api/src/payments/webhook/edge-proxy-config.spec.ts` (it already parses the template's locations and the snippet); the admin spec covers the `/admin-ui` headers only. Checked beyond static: `nginx -t` with the pinned `nginxinc/nginx-unprivileged:1.29.8-alpine` image passes, `caddy validate` (caddy:2.10-alpine) passes, and a run of the edge on a private Docker network in front of two echo upstreams showed the invented `X-Forwarded-For: 203.0.113.66` replaced by the client address on `/store`, `/admin`, `/webhooks/payments` and the storefront path, and appended (`203.0.113.66, <client>`) on all four with the snippet switched to `$proxy_add_x_forwarded_for`. A two-hop case in `scripts/deploy-smoke.sh` was NOT added (the CDN mode stays a documented operator change; the guard and the run above cover the shared rule).
- **F3, decision:** `resolveSearchAddress` (pure, `lib/search-query.ts`) decides the route: when the full parse fails and the address holds a form-only field (`priceMin`, `priceMax`, `rmin.*`, `rmax.*`), the address without those fields is parsed; if that succeeds the page renders it (page 1, `200`, not redirected, still `noindex`) with the refused box's message in the form's "Check the filters" alert (server-rendered: `SearchFilterForm`'s `initialError`; above the problem state when there are no results); otherwise it is the 404 as before. The refused box is named by the message only (no `aria-invalid` without a script). `search-page.spec.tsx` runs the route as a function; the no-script e2e submits a reversed price.
- **F4, decision:** the storefront copies core's rule (`DECIMAL_PATTERN` on `String(Number(text) + 0)`, magnitude at most `1e15`) as `RANGE_DECIMAL_PATTERN` and `MAX_RANGE_NUMBER` in `lib/search-query.ts`, and `search-query.spec.ts` compares them with the text of `packages/core/src/search/patterns.ts` (the storefront keeps `@fluxkit/core` out of its imports, `client-boundary.spec.ts`; a shared package would be a new dependency edge). The rule is not a fraction-digit count: `0.0000012` prints plainly and is accepted by the API, `0.0000001` prints `1e-7` and is not, so the box message says "none closer to 0 than 0.000001". A `400 validation_failed` whose `errors[].code` holds `invalid_range` (the API's shape, `store-search.spec.ts`) becomes `{ kind: "invalid", reason: "range" }` with its own words; every other 400 keeps the old "not available" state.
