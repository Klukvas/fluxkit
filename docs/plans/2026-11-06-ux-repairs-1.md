## Results

Environment: this sandbox has no Docker, and Postgres cannot be started here (the agent's sandbox refuses to switch to the `postgres` user and
Postgres refuses to run as root), so the e2e suites and the API integration tests were NOT run. Browser checks ran against the admin under
`vite dev` (port 3360, `localhost`) with `/admin/*` answered by Playwright route mocks (a test harness outside the repository).

1. **Dialogs (fixed).** `nativeCloseAction` in `dialog-focus.ts`; `Dialog.onClose` ignores a `close` event while the element is open again.
   Failing first: 4 of the new spec's cases failed (`nativeCloseAction` missing). In the browser under `vite dev` before the fix: 0 dialogs open
   1.5 s after clicking "Дозволити опцію" (product type) and "Додати значення" (option values); after: 1 and 1, Escape still closes. No admin
   e2e: the suite runs the production build, where StrictMode never re-runs effects, and `@fluxkit/ui` has no DOM test environment.
2. **Variants without options (fixed).** `variantsNeedOptions`; both buttons hidden, a hint with "Open the product type"; `validateVariantCreate`
   answers `products.variants.needsOptions` (failing first: the old code answered `combinationTaken`, because the empty combination matched the
   default variant). Help article "Variants tab" has the sentence.
3. **Banners (fixed).** (a) `banner-visibility.ts`: a live banner after the first 3 live ones shows "Live, but not shown: only the first 3 are"
   (warning tone) INSTEAD of "Live now"; a scheduled or switched-off one after them gets "When it goes live it will still not appear ... Move it
   up"; the form says the same (the editor reads the list once), and a new banner warns when 3 are live already (it is appended). The admin
   e2e `banners.e2e.ts` asserted "Live now" for banners appended after the seed's 3 live ones; it now expects the text from the API's
   `shownOnStorefront`. (b) The API requires the alt text of an `image` banner in the DEFAULT locale only (core `checkBannerContent`); the form
   additionally requires every language's naming text to switch a banner ON (owner plan `2026-11-05-admin-home-banners.md` section 7, kept).
   Wording now says so per field ("Required in the main language" / "Needed to switch the banner on") and the main picture is called required.
   (c) A refused save focuses the first invalid field (the main picture's upload button when the picture is missing), scrolled into view.
4. **Zero price (warning, not a block).** Saving a 0 price, publishing with an active variant at 0 in the shop currency, and switching such a
   variant on in a published product ask first. Failing first: `savePrices` sent the 0 price without asking. No API or calculation change.
   Browser: the dialog shows, "Go back and change it" sends nothing; publish shows its dialog. Not checked in a browser: the switch-on dialog.
5. **Phone width (fixed).** At 390 px before: the content started 1250 px down (the menu filled the screen); the Variants tab stretched the page
   to 946 px. Root cause of the stretching: the `sr-only` texts in table cells are absolutely positioned and the `overflow-x-auto` box was not
   their containing block, so they widened the document. After: `relative` scroll box (all `DataTable`s), content at 219 px, page width 390
   on the orders list, Stock, Variants and banner form; a Menu button (`aria-expanded`, `aria-controls`, Escape returns the focus, closes on
   navigation); tables say "Swipe the table sideways" below 768 px; date fields repeat the chosen date in the UI language under the field
   (Chrome draws `type=date` in the BROWSER's locale, which no page can change). Screenshots: `item5-*-390-{before,after}.png` (scratchpad).
6. **Texts.** UI language: no defect found. `locale-preference.ts` keeps the choice in `localStorage` (try/catch) and otherwise follows the
   browser (owner answer 10); nothing removes it at sign-out. A browser profile without stored data and an English browser language (a fresh
   automated browser per session) opens in English every time; that matches the review. A different default (the shop's default locale
   instead of the browser's) is an owner decision, not changed. Product form `noValidate` plus a title length count; shipping hints; paid
   cancel warning ("the money and the stock are not returned automatically", accurate to `docs/api/orders.md`); a cancelled or expired order
   holding a captured payment says to refund it, or that the automatic refund of a late or duplicate payment is on its way; Email setup "done
   by whoever installs the shop (a developer)"; help: the orders article now says waybill first, then "Mark fulfilled" (as the shipping
   article; `docs/api/shipping.md`: a fulfilled order is refused `order_not_paid`).
7. **Investigation (no code change).**
   - (a) "Pay now" -> "Таке значення вже використовується" (`errors.conflict`). Cause found in code, not reproduced (no database here):
     the test-only fake provider numbers its invoices from an in-memory counter, `fake-pay-${invoiceById.size + 1}`
     (`packages/providers/_fake-payment/src/fake-payment-provider.ts:545`). After an API restart it hands out `fake-pay-000001` again; the API
     stores it in `PaymentCreateService.record` (`apps/api/src/payments/payment-create.service.ts:349-389`) and hits the unique constraint
     `payment_provider_code_provider_payment_id_key` (`apps/api/src/database/schema/payments.ts:140`). That error is not caught there; the global
     filter maps every unique violation to `409 conflict` (`apps/api/src/common/postgres-errors.ts:105-110`). The record transaction rolls back,
     so the attempt stays `creating`: the order page shows "payment processing", the return page says not to pay again, and job 11 closes the
     attempt only after `createRecoveryMs` (2 minutes, `payments-config.ts:28`). A real bug of the fake provider (the demo stack uses it and restarts); a robustness gap of the API
     for any provider that reuses an id. Proposed, not applied: (1) the fake builds ids with a per-process random part (the e2e that reads
     `fake-pay-000002` must keep a predictable number: e.g. `fake-pay-<run>-000002`, the spec derives the time from the trailing number);
     (2) `record` treats a `payment_provider_code_provider_payment_id_key` violation like a malformed answer (`create_unknown`, logged) instead
     of a 500/409 and a stuck `creating` row. Payment code, so a red zone: needs approval.
   - (b) Order page rate limit: `orderLookup` is 20 requests per 10 minutes per client address (`apps/api/src/rate-limit/rate-limiter.ts:14`,
     `docs/api/orders.md` `POST /store/orders/lookup`); 341 s is the rest of that window. The guest page reads the order in an effect; under
     `next dev` React StrictMode runs it twice per load, and a payment poll re-reads it (`onOrderChanged`), so ~6 reloads use the 20. On the
     demo stack every shopper shares one address: `next dev` rewrites `/store/*` to the API, which sees `127.0.0.1`. In production each shopper
     counts on their own address, but an office or mobile-carrier NAT shares one. The token is 32 random bytes, so the limit does not protect the
     token, only against number probing and load. Proposed, not applied: 60 per 10 minutes, and the storefront message in minutes ("about 6
     minutes") instead of seconds.
   - (c) Hammer card "Залишилось мало" vs page "Немає в наявності": the card shows the LIST item's product-level availability, the page the
     selected variant's, read fresh (`apps/storefront/src/components/product-card.tsx:62-69`, `product-purchase.tsx:141`). The demo hammer has one
     variant with stock 4 (`seeds/src/products.ts:159-171`); a reservation of the last units makes it out of stock at once on the page, while the
     list comes from the search index (job 13, every scheduler tick) through the storefront's 60 s list cache (ADR 0040, up to 6 minutes on
     errors). Read on the shared demo API on 2026-11-06: both answer `low_stock` now, so the difference was temporary. The discount: the list item
     has no compare-at price at all (by design, PR 217; `product-card.tsx` comment), so cards never show one. No small storefront-local fix:
     not changed. Options for a plan: an additive `compareAt` on list items (public API change, red zone); a shorter list cache for stock.
