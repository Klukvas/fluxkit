## 0. Orchestrator decisions, 2026-11-27 (override the body below)

The Architect's body is kept as the reference design. These decisions narrow it so that every item stays inside the owner-approved plan (no new owner approval needed); where the body and this section differ, this section wins.

| # | Decision | Why |
|---|---|---|
| 1 | **No legacy cutover helper, no `env_fields` column, no env-referencing versions.** A managed (DB) payment or shipping provider cannot be activated while a payment or shipment of the same provider code with a null binding is still non-terminal (`409 integration_legacy_work_open`). Null-bound rows are never served by a DB key; in managed mode they get the existing code-only attention (`credential_unavailable`). `docs/deployment.md` describes the switch: finish or reconcile env-bound work first, then remove the variables. | Plan §5 MVP: "refuse rotation ... never assign old rows to a new value"; refusing is conservative. Template clients start with no legacy payments. Cutover automation is later. |
| 2 | **No `integration_verification_material` table.** The Monobank public key lives in the bound version's client cache and is refetched with the bound token through the final gate after a restart. | Persisting it only saves one gated read; a revoked token has no authority anyway. Fewer tables, same safety. |
| 3 | **No AAD v2 and no `aad_version` column.** Envelopes keep the v1 AAD of ADR 0058. Version identity (`environment`, purpose, generation) is protected by the immutability trigger of migration 0022. | AAD already binds row, integration, kind, provider, field, generation and key id; a DB writer able to edit `environment` can do worse. |
| 4 | **Environment is an optional `environment` property of the existing `PUT /admin/integrations/{id}/secrets/{field}` body** (validated against the manifest's `fluxkit.environments`), not a new route. Changing it means saving the key again; the new candidate has the chosen environment. Absent: the current candidate's environment, else the manifest default. | Additive field on an approved route; an environment switch already must create a new generation (plan §5). |
| 5 | **No `GET /admin/integrations/{id}/versions` route.** `GET /admin/integrations/{id}` and the list gain a bounded `versions` array (at most 20 non-retired versions per integration: candidate, active, draining, revoked) with metadata only, so a draining key stays revocable after rotation. | Additive response metadata; one route fewer. |
| 6 | **Unknown webhook in managed mode:** locate the payment by the plugin's `locateWebhook`; bound version found → verify with it only. Not found → verify with the currently active version only (one key, no fan-out); a valid signature then follows the legacy unknown-payment behaviour, otherwise `401`. | Keeps the legacy response contract; still bounded (plan §5 "unknown candidate does not trigger unbounded key fetching"). |
| 7 | **No `checkoutActionOrigins` manifest field and no `fluxkit.integrationRuntime` marker.** A package is managed-capable when its entry exports `createOutboundClient` (and `locateWebhook` for a payment provider with webhooks); it binds a permanent merchant baseline when it exports `accountIdentity`. The handoff origin allowlist is the sibling WayForPay plan's concern. | Smaller public surface; the handoff allowlist is not part of activation. |
| 8 | **No storefront/admin config caching changes** beyond refreshing admin config after activate/disable. Backend admission is the authority; a stale storefront option is refused at payment/waybill creation with the existing error. | Plan §5 says "bound capability-cache staleness"; the existing caches are already short (verify in PR 2/3, change only if a cache is unbounded). |
| 9 | **Lock order needs no refactor of existing flows.** Revocation, disable and activation lock `integration` then `integration_credential_version` and never take order, payment, refund or shipment locks; admission and the final gate lock the same two rows `FOR SHARE` in the same order after any existing order/payment lock. | No inversion is possible, so existing payment flows keep their locking. |
| 10 | **PR split as §11:** PR 1 shared contract, multi-field bundles (fixes LiqPay listing), `/check`, `versions`, alerts, migration 0022; PR 2 payments (Monobank, LiqPay), migration 0023; PR 3 shipping (Nova Post), migration 0024; slice 3 afterwards with its own short design. | Reviewable units; payments land early for the sibling `payment-choice` session. |

With 1 to 9 applied, §12's two "needs owner approval" rows reduce to: the provider-package exports (`createOutboundClient`, `checkCredentials`, `accountIdentity`, `locateWebhook`, the context's transport gate) and the manifest relaxations (a purpose may hold several fields; optional `fluxkit.environments`). Both are additive refinements of the approved plan's "plugins supply typed configuration/factories" (§5) and "unique field per version" (§7), recorded in ADR 0060 with PR 1. ## 2. Plugin contract: one extension point

- **New pure types:** `packages/core/src/integrations/provider-runtime.ts`, exported from `packages/core/src/integrations/index.ts` and the core barrel. No Nest, DB, filesystem, env reads or provider imports.
- Extend the existing manifest parser in `packages/core/src/integrations/secrets.ts`; retain field/env uniqueness, own-provider env prefix, maximum eight secret fields, and installed-package path/production checks.
- Managed module contract is a discriminated union by manifest `kind`. Validate exports and the resulting existing port's code, methods and capabilities at load; an installed but unsupported package is visible as unavailable, never silently activated.

| Declaration/export | Exact proposed contract (type notation, not executable code) |
|---|---|
| `fluxkit.secrets` | Existing array `{field, purpose: outbound\|webhook, env}`; repeated purpose is valid, repeated field or env is invalid. Every field declared for a purpose is required for that purpose. |
| `fluxkit.environments` (optional) | `{values: string[], default: string, env: string, blank: string}`; 1–8 unique bounded code strings, default/blank members of values, env has the provider's prefix. Absent means fixed environment `default`, no selector. |
| `fluxkit.integrationRuntime` | `{version: 1, accountBinding: none\|permanent, checkoutActionOrigins?: string[]}`; at most eight fixed HTTPS origins, no credentials/query/fragment, and never supplied by an admin. Legacy packages without it remain env-only. |
| `createOutboundClient(secrets, context)` | Required synchronous export; `Readonly<Record<string,string>>` of the complete outbound purpose → `PaymentProviderPort` or `ShippingProviderPort` according to kind. Construction performs no network call. Email's existing one-argument factories stay compatible. |
| `checkCredentials(secrets, context, signal)` | Optional asynchronous export → `Promise<CredentialCheckOutcome>`; outcome is `{code, retryAfterSeconds?}`, code union `ok`, `invalid_credentials`, `unavailable`, `rate_limited`, `not_supported`; retryAfterSeconds is an integer 0–86400. Uses `ProviderAbortSignal`; no arbitrary provider text. |
| `accountIdentity(secrets, context, signal)` | Optional asynchronous export → `{ok:true, identity:string}` or `{ok:false, code, retryAfterSeconds?}` (check failure codes, excluding `ok`), wrapped in Promise. Identity is canonical opaque UTF-8, 1–256 bytes, server-only. Required for `accountBinding=permanent`; missing hook or non-success blocks enrollment/activation. |
| `locateWebhook(input)` | Required pure synchronous export for a managed payment port with `capabilities.webhooks=true`. Takes existing `PaymentWebhookInput`; returns null or `{reference?: string, providerPaymentId?: string}` with at least one validated bounded identifier. No network, signature verdict or payment fact. |
| `ManagedProviderContext` | Readonly `kind`, `providerCode`, `versionId`, `environment`, API-owned `now()` clock, `transport`, and optional `verificationMaterial`; no env object, DB executor, logger accepting raw errors, configurable URL or ability to select another version. |
| `transport.start<T>(signal, start)` | API-injected asynchronous gate; `start` is a synchronous thunk returning `{completion: Promise<T>}`. Gate invokes the thunk under authority locks, releases/commits the lock transaction, then awaits completion. Denial throws a typed code-only `CredentialAdmissionDenied` before the thunk runs. |
| `verificationMaterial` | Optional API capability with `read(slot)` and `write(slot, bytes)` promises for bounded authenticated public verifier material scoped to this exact version. No secret storage or arbitrary key-value store; slot `webhook_public_key` is the initial supported slot. |

- Each managed adapter routes **every** actual transport through `context.transport.start`, including internal retries, pagination, authorization and pubkey refresh. The thunk calls transport synchronously: no `await`, timer or queue before `fetch`/request initiation.
- The shared commerce client context captures only immutable version identity. Resource binding/operation admission belongs to the facade before invoking the port; the final transport gate rechecks that version's authority. Never store a mutable “current payment/request” on a cached client. Candidate checks/enrollment use separate short-lived restricted contexts, not commerce-cache entries.
- Keep per-version HTTP clients separate from revision snapshots: bounded idle cache keyed by `(kind, provider, versionId)`, never provider alone. Eviction only releases memory; rebuild from that version, never the latest. In-use references survive eviction.
- Monobank's `MonobankKeyCache` belongs to that version's client (`packages/providers/monobank/src/monobank-provider.ts:114`); Nova Post JWT/single-flight belong to that version/environment's HTTP client (`packages/providers/nova-post/src/http.ts:286`). JWT is memory-only.
- Public-key persistence uses the optional material capability; Monobank restores validated P-256 material on restart and refetches only with the bound token under existing bounds. Cached material never grants authority after revoke.
- Monobank implements identity/check via merchant details; Nova Post implements check via existing fresh-JWT/division lookup. LiqPay omits identity and initially returns `not_supported` for an online check unless a documented harmless check is established; no invoice/refund is a credential probe.
- A WayForPay package supplies its manifest, factory, bounded locator and optional check/identity hooks. Generic DTOs/UI render unknown field/provider/environment codes with escaped fallback labels; no central provider allowlist or provider-name switch for activation.
- `checkoutActionOrigins` removes the LiqPay-only handoff allowlist (`apps/api/src/payments/payment-handoff.service.ts:26`) through trusted installed-package metadata, retaining HTTPS/field bounds. This is a public extension/red-zone item, not approval of WayForPay payment semantics.
- Cash on delivery has no credentials: an absent/empty secrets declaration stays outside the credential wizard and cannot acquire a fake version. Its payment-method enablement/state behavior belongs to the sibling plan.

## 3. Multi-field candidate generations

1. Keep `PUT /admin/integrations/{id}/secrets/{field}` and its existing `{expectedRevision, value, currentPassword}` body unchanged. Validate bounds/declared field/env lock before consuming step-up.
2. After strict limits/password verification, one transaction rechecks principal/session, CASes revision, locks the integration, then its candidate and active version in a fixed order.
3. Choose the current candidate of this purpose as base; if absent choose the active version; if neither, start incomplete. Never merge fields from several generations or another purpose. Do not clone revoked/retired material.
4. Allocate a new version ID/generation and secret-row ID per field. Decrypt the base's other declared fields inside that transaction; replace the submitted field; re-seal **every** retained DB field with fresh nonce/new row and generation AAD. No ciphertext copying across generations.
5. Use a new `fluxkit.integration-secret/v2` AAD label for new bundles, preserving v1 identity components and adding purpose/environment; stored `aad_version` selects the reader. Existing v1 email envelopes remain readable and unchanged until explicitly replaced/rewrapped.
6. After opening/re-sealing the base fields, retire the superseded unbound candidate **before inserting** the next candidate (the partial unique index permits one). Insert all new envelopes/version, touch/audit/advance revision atomically. Any failure rolls back everything; unreadable base is an error, never an omitted field.
7. Candidate summaries show one version ID for all fields in that purpose, missing field codes and completeness. They also expose active and retained generation metadata separately; no plaintext, suffix, key ID, ciphertext or merchant value.
8. Activation checks **all declared fields** from that same purpose/version, successful decryption and cross-field plugin construction. A partially saved LiqPay pair stays a candidate; rotation leaves the prior active pair serving until explicit activation.
9. Saving one LiqPay field after activation clones the other from active. The UI shows which fields were carried forward and requires explicit activation; it does not imply the pair belongs to the same account. Saving the second field creates another complete generation.
10. Candidate retirement is version-wide, not field-wide. Keeping the current endpoint shape avoids turning a per-field write into an accidental deletion of the other field. Lost CAS reloads metadata and requires a fresh submission, never replay of the secret/password.

## 4. Resolution, environments and legacy cutover

| Input | Effective rule |
|---|---|
| `PAYMENT_PROVIDERS_ENABLED`, `SHIPPING_PROVIDERS_ENABLED` | Presence, including blank, selects the unchanged boot/env registry for that kind. Blank explicitly disables new providers; no DB list fallback. Absence selects the managed facade; empty DB selection defaults off. |
| `MONOBANK_TOKEN`, `LIQPAY_PUBLIC_KEY`, `LIQPAY_PRIVATE_KEY`, `NOVA_POST_API_KEY` | Nonblank env overrides its field; blank/unset delegates to DB. Apply manifest-driven field rules, not an API-side list of provider names. Invalid effective input fails, never falls through. |
| `NOVA_POST_ENVIRONMENT` | Presence wins; blank means `sandbox`; absence uses the selected version environment, then manifest default `sandbox`. Manifest declares `sandbox`, `production` and its fixed origin mapping stays inside the plugin. |
| Enablement/field mutations | Env-owned enablement or targeted field returns `409 integration_env_override`. Activating a DB candidate with any outbound env field override also returns 409, including a partial LiqPay override. Other unlocked fields may be saved but cannot be activated around that lock. |

- Add payment/shipping delegation booleans in config parsing before defaults erase presence information; carry them through `CreateAppEnv`, factory/module and integrations config. Preserve legacy startup validation and zero-provider behavior.
- Managed discovery scans all installed manifests without constructing env Nest modules. Import only packages needed for candidate validation/check/activation or retained work; missing active/bound packages fail closed with attention, never route to another package.
- Environment is public immutable metadata on **the credential version**, not `integration` or the shipping profile. Add `PUT /admin/integrations/{id}/environment` with `{expectedRevision, environment, currentPassword}`; it clones the outbound purpose bundle into a new candidate under new AAD. This endpoint does not rotate independent webhook-purpose secrets.
- First key save uses the manifest default if no candidate exists. The owner can choose environment first, creating an incomplete candidate, or switch afterward; both paths use the same generation writer. Environment selection alone never activates.
- Env presence locks that selector, even when blank. Re-sealing is required on environment changes; a production candidate cannot inherit a successful sandbox check. This public endpoint is an additive contract requiring owner approval (§12).
- Precedence applies to new effective configuration; **an existing binding always means the original version**. Never overlay a newly supplied env token/environment onto an already bound DB version.
- For transition from env to managed, quiesce admissions/jobs/webhooks, inventory every legacy payment/shipment still requiring access (including refund/label windows), and establish the Monobank baseline from the existing env token before accepting replacement keys.
- Use an explicit operator cutover transaction/helper in the payments/shipping PR, not startup auto-import: create retained versions whose `env_fields` map records only field→env-variable names; bind legacy rows to them. Do not copy env secret bytes into Postgres. DB fields in a mixed effective bundle are re-sealed under the new version.
- `env_fields={}` denotes an all-DB version; nonempty denotes env or mixed provenance. Before managed runtime starts, each effective override bundle has its own version/environment; operator-selected new-work pointer and revision are recorded during quiescence. The admin cannot activate an env-shadowed candidate.
- New env overrides on an existing managed installation require the same coordinated cutover; if sources/environment do not match the selected version, refuse admission rather than silently use shadowed DB data or relabel an old version. Env still wins resolution, but unsafe cutover is not executable configuration.
- Without fingerprints, same-name env-value changes cannot be detected automatically: require one managed API, immutable env per deployment and operator proof that no env-referencing version still needs old bytes before replacement/removal. Otherwise retain exact env values or reconcile; no automatic rebinding.
- Legacy mode keeps sync registries, boot behavior and null bindings unchanged. Once a managed binding exists, bound lookup always uses it even if an operator later sets an enablement variable; the boot registry only controls new-work selection. Returning to old binaries requires guarded cutover/rollback.
- Keep shipping profiles in `shipping_provider_setting`. Lock edits affecting dependent work in the compatibility write transaction; do not migrate them. Without snapshots, refuse environment/profile/origin/request-template changes until dependent work drains/reconciles, including deployment changes. Same-environment credential rotation remains allowed.

## 5. Authority, bindings and final revocation gate

- Extend `IntegrationRuntime`/`IntegrationsRepository` with reusable credential loading, authority and transport admission; keep the existing cipher, revision and lifecycle. Kind-specific thin facades live under the current registry directories.
- Facades provide asynchronous `activeSnapshot()`, `forBound(versionId, operation)` and transaction-aware `admitNew(tx, selection, resourceId)`; legacy implementations wrap the existing synchronous sources. A snapshot carries version IDs/capabilities, not durable authority.
- Read `integration_revision` for every snapshot resolve, reuse `RevisionCache` for at most 5 s, and fail closed on DB errors. Never treat a cached client or a browser's config as authorization.
- New payment creation writes `payment.integration_credential_version_id` in the transaction creating `creating`; new shipment creation writes its binding in `prepare` before the external call. Revalidate selected active pointer/enabled/state under the integration row lock; stale selection refuses/defer, never silently changes an idempotent attempt.
- Persist the existing claim before transport. A retry/idempotent existing-row response keeps its binding even when another generation is active. Refunds always load the parent payment's version; add no independently editable refund binding.
- Bound read/refund/reconcile/invalidate/handoff and shipment lookup/cancel/label/tracking allow `active` or `draining` regardless of current enablement. New creates/directory/estimate require enabled active authority. Candidate permits only explicit owner check/enrollment, never commerce.
- Disable drains the current active generation and stops new admissions; it keeps its pointer/history and does not disable late payment webhooks or bound service. Rotation drains the old version and selects the complete candidate atomically.
- Activation selects the current candidate, or, when there is none, the disabled integration's own retained draining pointer after the same readiness checks. Re-enable does not create a generation or revive revoked/retired material; the UI identifies the exact generation before submission.
- Revoke accepts candidate/active/draining, is terminal, preserves bindings/baseline/envelopes, and clears the new-work pointer only if it points to that version. It must work with an unavailable provider/master key/email route and must never wait for remote verification.
- Final start: after all queues/pacing/JWT prerequisites, lock the integration then version, re-read allowed state, check deadline/signal, invoke the transport thunk, release locks **without awaiting response**. Revocation uses the same lock order. The facade has admitted the operation and its binding is immutable; already-admitted work may finish after disable, but not start another call after revoke.
- Establish one lock order for callers: admin principal/revision locks where needed → integration → version IDs sorted → existing order/payment/shipment/refund locks. Refactor only acquisition order where existing order-first flows would invert it; keep existing order serialization and claims. No network response wait while any lock is held.
- Every retry/page/JWT/pubkey fetch gets a separate final gate. Revocation committed first means no transport starts; transport invoked first may finish. A DB/commit failure after transport invocation is ambiguous, never `not_sent`; preserve the original claim and reconcile.
- A rejected gate before the commerce request starts maps to existing typed local failure/attention codes (`credential_revoked`, `credential_unavailable`); do not invent successful/failed provider facts. Nova Post may use existing `not_sent` proof only when no waybill POST started.
- Webhook receipt/fact commit rechecks authority and exact binding under the same locks before any dedupe/event/order/refund mutation; revocation winning that lock means zero facts. Poll/refund/create responses already in flight retain existing claim/fencing rules; never start follow-up calls after revoke.
- LiqPay form signing is local but grants a future browser submission: gate immediately before signing/releasing a handoff, using the bound pair. Revoke stops new handoffs; already delivered signed forms cannot be recalled. Never return the private key.
- Retirement initially remains candidate-only, conservatively retaining draining/revoked secrets. Later retention eligibility considers supported refund/reconciliation/cancellation/label windows, not just terminal status or zero open attempts. No two-version cap; revoked tombstones never become active or ordinary retired rows.

## 6. Merchant baseline, checks and webhook routing

- Monobank manifest declares permanent account binding. The generic service calls its `accountIdentity` hook on the **first key save and every replacement**, using `GET /api/merchant/details` (approved parent §5/§11.3); identity is merchantId, never merchantName/edrpou.
- Saving a Monobank token is the explicit exception to local-only format saves: UI explains the read. Consume step-up and check budgets first; perform a bounded read outside the save transaction, then recheck step-up, revision and baseline under lock before inserting candidate/baseline/audit atomically.
- Before that first read there is no saved version: allocate submission/version IDs and use the same transport gate with a short-lived enrollment context authorized by current owner/session/expected revision under the integration lock. It permits only identity read, not commerce; after the read no authority survives the request.
- First successful save inserts baseline and candidate together; timeout, invalid token or stale revision writes neither. Concurrent first saves serialize at commit: only the same verified identity may follow the winner. Foreign identity returns `409 integration_merchant_mismatch` and stores no candidate; discard the fetched identity.
- Baseline is one immutable row per `(kind, provider_code, environment)` with integration FK RESTRICT and permanent integration identity. Monobank currently has no user-selectable environment: use `default`; do not invent sandbox/production by parsing the token or permit a selector to bypass merchant binding.
- Missing/unreadable baseline on an enrolled provider blocks saves/activation, never creates a replacement. Disable/retire/revoke/package removal/reinstall cannot erase it. Merchant transfer is a separate owner-approved migration.
- Existing pre-slice-2 Monobank candidates have no verified identity: require an explicit owner re-save to enroll/compare before activation. If legacy env payments exist, first perform env-baseline cutover; a new pasted key cannot establish a different first merchant over that history.
- `/check` takes `{expectedRevision, versionId}`; owner-only, explicit, no current password for this read-only action. Allow candidate/active/draining only, verify completeness and effective sources, run the optional hook under final gates and return `{versionId, code, checkedAt, retryAfterSeconds?}`. No secret accepted in this request.
- Audit check invocation before network and code-only outcome afterward; no persistent readiness flag required. Recheck version/revision before publishing success; concurrent retirement/revocation/edit makes the result stale/unavailable. The UI associates results with exact version/revision and clears them on edits. `ok` is a point-in-time observation; `not_supported` is visibly unverified, not invalid credentials.
- Activation requires full fields, available cipher, valid fixed environment, installed compatible factory, currency/public-origin prerequisites and permanent baseline where declared. A failed check is shown prominently; optional check availability is not a universal activation requirement. No automatic payment or waybill test.
- Strict Redis budgets: shared step-up 5/15 min/admin + 20/15 min/IP; checks/enrollment reads 10/min/admin + 30/min/IP + 30/min/provider, plus shipping 30/10 min/admin. Consume applicable windows atomically before hashing/network; Redis loss/ambiguity is 503, never local fallback. Reuse `AdminStepUpService` and strict limiter primitives.
- Webhook path remains `/webhooks/payments/{code}`. Bounded `locateWebhook` parses only an untrusted routing hint from raw JSON/form bytes; locate one payment by provider+reference/provider ID, require hints to agree, then select its **bound** version. No attempt row creation from hints.
- Verify original raw bytes with that client's key only, then run existing fact validation/amount/currency/reference/order checks and dedupe. Monobank uses the bound version's persisted/refetched pubkey; LiqPay uses that version's private key and public-key comparison.
- Unknown/malformed hints never fan out across keys or fetch a public key; managed mode returns generic 401 without a fact. Known revoked/missing authority or transient DB/key failure returns retryable 503; invalid signature returns 401. Legacy mode keeps existing unknown-payment acknowledgment behavior. Document this managed-mode response refinement (§12).
- “Retryable 503” describes Fluxkit's temporary-failure response, not a verified delivery guarantee: LiqPay callback retry policy is still UNKNOWN (`packages/providers/liqpay/README.md:52`). Retain scheduled reconciliation and operator attention; do not promise webhook replay.
- Do not erase the locator/verifier when disabled; retained versions remain discoverable. A removed package makes bound work unavailable with code-only attention, not a fallback to the latest provider. Existing ingress size/type/rate limits remain.
