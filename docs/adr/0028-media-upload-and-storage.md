# 0028. Media upload and storage

Status: accepted 2026-10-23 (owner's quiz answers on `docs/plans/2026-10-23-media-upload.md`, step 1). The red-zone items named in that plan's "Needs approval" section (the `sharp` dependency and the LGPL scope, migration 0005, the upload and `GET /media/{key}` contracts, the `media` block of `GET /admin/config`, the new problem codes and validation reasons, the CSRF exception for one route, the configuration variables) are approved by those answers, except the owner's own file edits (AGENTS.md section 16 and `scripts/license-policy.json`), which are the owner's. Builds on ADR 0004 and 0006 (media rows hold a URL), ADR 0007 (store media filter), ADR 0009 (admin CSRF header), ADR 0018 (ports in core, implementations in the API), ADR 0021 and 0025 (bounded scheduler jobs), ADR 0026 and 0027 (one origin, edge proxy, admin SPA). Supersedes nothing; nothing in those ADRs changes.

Nothing described under Decision is built yet. Each item is a requirement for the implementation steps 2 to 9 of the plan.

## Context

- **Media are URLs only.** `media.url` (ADR 0006: `text NOT NULL`, max 2048, with `alt` i18n and `position`) and `brand.logo_url` (`text NULL`) hold absolute `http`/`https` URLs; `PUT /admin/products/{id}/media` and the brand `POST`/`PATCH` validate them with `z.url({protocol: /^https?$/})`. The checkout copies the product image URL into `order_item.image_url`, so order history depends on that URL staying valid. The store API returns `image.url` and `media[].url` as plain strings (`docs/contracts/api.md`).
- **No storage exists.** The API stores no files, has no upload route, no media directory and no configuration for one. `infra/docker-compose.yml` runs Postgres, Redis and Meilisearch only.
- **The CSRF rule admits JSON bodies only.** `assertCsrfSafe` (`apps/api/src/auth/csrf.ts`) refuses every state-changing request without `X-Fluxkit-CSRF: 1`, and every such request with a body whose `Content-Type` is not `application/json`, with `403`. For `/admin` it is called by `AdminGuard.canActivate` (`apps/api/src/auth/admin.guard.ts`) as its first check, before the public-route check and authentication; `AdminGuard` is reached through the global `AdminPathGuard` and through `@AdminController`. The same function is called with scope `store` by `StoreCsrfGuard` for `/store`. Today no binary or multipart body can reach any admin route. The API sends no CORS headers.
- **Body parsing.** Nest's Express adapter registers only the JSON and URL-encoded parsers (100 KB); a body of another content type is not consumed and can be streamed by a handler.
- **Rate limits** (`apps/api/src/rate-limit/`) are named in-memory windows keyed by `request.ip`, applied by `@RateLimit(name)` as a route guard (after the global guards); none is keyed by admin user.
- **Scheduler**: one in-process timer under a Postgres advisory lock runs six bounded jobs (`JOB_NAMES` in `apps/api/src/jobs/jobs-runner.ts`); `pnpm jobs:run-once` runs them by hand.
- **Next image optimizer (16.4.1).** A relative image path is fetched inside the Next server, never through the edge proxy; an absolute URL is fetched over the network and refused when its host resolves to a private IP (`dangerouslyAllowLocalIP` is not set). The storefront's `allowedImageUrl` passes only absolute `https` URLs on a host in `STOREFRONT_IMAGE_HOSTS` (no port, no credentials); the storefront CSP `img-src` and `images.remotePatterns` come from the same list. The admin CSP has `img-src 'self' data:` plus the proxy configuration's `imageHosts`.
- **Licence check gap.** `scripts/license-policy.json` allows the LGPL-3.0-or-later `@img/sharp-libvips-linux-x64` and `-linuxmusl-x64` binaries with the reason "next -> sharp" (owner, 2026-10-14). `scripts/check-licenses.mjs` matches an exception by package name and licence only, not by the dependency path, so it would not notice the API using the same binaries. `sharp` 0.35.5 (Apache-2.0) and those binaries (1.3.4) are already in the lockfile as optional dependencies of `next`.

## Decision

### 1. Scope and non-goals
- In scope: an admin with `catalog.write` uploads product images and brand logos, one file per request; the API checks the file by content, re-encodes it, stores it through a storage port (local disk driver only) under a random name, and answers with a URL that the existing media and brand saves accept unchanged; a public read route serves the files with fixed headers; a table records uploads; a scheduler job deletes abandoned uploads; admin UI controls; configuration; docs; tests.
- Not in scope (each needs its own plan): a media library screen; video, PDF or any non-image file; editing, cropping, focal points; responsive variants generated by us; CDN integration and signed URLs; the S3-compatible driver; processing through a queue; virus scanning; fetching a URL server-side ("import from URL"); deleting files that were ever attached; per-user quotas; seeds with real image files.
- URL-based media keeps working exactly as today.

### 2. Boundaries
- `packages/core/src/media/` holds pure rules only: the magic-byte sniffer (`jpeg | png | webp | null`), the allowed-type table, `MEDIA_LIMITS` (including `MEDIA_MAX_DIMENSION` 12 000 and `MEDIA_OUTPUT_MAX_SIDE` 4 096 as constants), the key format (`isMediaKey`), the validation reason codes, and the `MediaStoragePort` interface with its string token `MEDIA_STORAGE_PORT` (types and constants only; Node stream types by `import type`). No I/O in core (`core-must-not-import-infrastructure` and the "pure TypeScript" convention).
- `MediaStoragePort` has `put(key, sourcePath, contentType)` (atomic, never overwrites), `open(key)` (stream and size, or `undefined`) and `delete(key)` (idempotent). It stays internal until listed in `docs/contracts/`; it becomes a contract when the first external driver exists. A later driver package implements it without importing `apps/api` (ADR 0018).
- `apps/api/src/media/` (`MediaModule`) holds the local-disk driver, the image pipeline (`sharp`), the upload service and route, the read route, the repository and the cleanup job's media part.
- Media upload is **core, not a feature**: no feature flag, no feature package, the `feature-matrix` job is unaffected. It is switched by `MEDIA_STORAGE_DRIVER=local|none`. Any other value (for example `s3` before such a driver exists) fails startup. With `none`: the upload route answers `503 uploads_disabled`, `GET /admin/config` reports `uploadsEnabled: false`, the read route answers `404`, the cleanup job does nothing, the admin hides the upload controls, URL entry stays.

### 3. Upload route contract
- `POST /admin/media/uploads`, controller `@AdminController("media")`, permission `catalog.write` (in `x-fluxkit-permission`), documented in OpenAPI with request body `application/octet-stream` (`{type: string, format: binary}`).
- Body: the raw file bytes, `Content-Type: application/octet-stream`, one file per request; no file name, form fields or JSON. The declared content type and any name or extension are ignored for type decisions.
- `Content-Length` is required: missing, or `Transfer-Encoding: chunked`, answers `411` (`validation_failed`, reason `length_required`). A declared length above `MEDIA_MAX_BYTES` answers `413` (reason `file_too_large`) before the body is read; the stream counter enforces the limit again and cuts a lying client off at limit + 1 byte; `0` answers `400 empty_file`.
- Limits: 10 MiB (`MEDIA_MAX_BYTES` default), 50 megapixels (`MEDIA_MAX_PIXELS` default), 12 000 px per side.
- Type gate before any decoder: the first bytes must match JPEG `FF D8 FF`, PNG `89 50 4E 47 0D 0A 1A 0A` or WebP `RIFF....WEBP`; anything else (SVG, HTML, XML, PDF, TIFF, GIF, AVIF, HEIC included) answers `400 unsupported_type`. `sharp` never sees a file the gate did not accept (its libvips also decodes SVG, TIFF, GIF, HEIF and more). **SVG is refused.**
- Decoding: header width and height checked before decoding (`dimensions_too_large`, `too_many_pixels`); `limitInputPixels` = `MEDIA_MAX_PIXELS`, `failOn: "warning"` (`corrupt_image`), `pages: 1`, an animated WebP is refused (`animated_not_supported`), the format libvips reports must equal the sniffed one (else `unsupported_type`).
- Re-encode with `sharp`, same output format as input: `.rotate()` applies the EXIF orientation, sRGB, resize to fit 4 096 px without enlargement, JPEG quality 85 progressive, PNG lossless, WebP quality 85, alpha kept for PNG and WebP. `withMetadata` is never called, so EXIF (GPS included), XMP, IPTC, comments and ICC profiles are dropped and trailing bytes do not survive.
- Resources: `sharp.cache(false)`, `sharp.concurrency(1)`; at most 2 uploads processed at once per process; a third waits up to 10 s, then `429 too_many_requests` with `Retry-After: 5`. Processing budget 30 s, then `400 processing_timeout`; the final budget is set from measurements in step 4.
- Rate limit `mediaUpload`: 60 uploads per 10 minutes **per admin user id**, counted after the admin guard and before the body is read (needs a key function in the rate-limit guard; still in-memory, single process).
- Response `201` `{id, url, contentType, byteSize, width, height, createdAt}` describing the stored output; `url` = `MEDIA_PUBLIC_BASE_URL + "/" + key`; no `Location`; `Cache-Control: no-store` like every `/admin` response. No idempotency key; the client never retries automatically.
- Problem answers: `400 validation_failed` with one `errors[] {path: "body", code}` of `empty_file`, `unsupported_type`, `corrupt_image`, `animated_not_supported`, `dimensions_too_large`, `too_many_pixels`, `processing_timeout`; `411` `length_required` and `413` `file_too_large` (both `validation_failed`, the problem filter keeps the status); `401`; `403` (CSRF or permission); `429`; new problem codes `503 storage_unavailable` (`ENOSPC`, `EDQUOT`, unwritable directory) and `503 uploads_disabled` (driver `none`). New codes are additive.
- Logging: one info line per upload (admin id, upload id, bytes in and out, type, dimensions, duration); never bytes, never a client-supplied header value.
- `GET /admin/config` gains the additive block `media: {uploadsEnabled, maxBytes, contentTypes}`.

### 4. The CSRF exception
- Exactly one exception: a route that declares `@AcceptsBinaryUpload()` accepts a body with `Content-Type: application/octet-stream` (media type compared like `isJson`: before `;`, trimmed, case-insensitive). Only `POST /admin/media/uploads` declares it.
- `X-Fluxkit-CSRF: 1` stays mandatory on that route. `multipart/form-data`, `text/plain`, `application/x-www-form-urlencoded`, `image/*` and every other type are still refused with `403`. `application/octet-stream` is not a CORS-safelisted type, so a cross-site sender needs a preflight, which the API never grants; the custom header already forces one as well.
- How it is declared: route metadata, read with the `Reflector` by `AdminGuard` (where `assertCsrfSafe` is called for `/admin`) and passed to `assertCsrfSafe` as an explicit option. It is not a global relaxation, not a path pattern and not a content-type list in configuration. `StoreCsrfGuard` never passes the option: `/store` keeps the JSON-only rule.
- Tests required: the upload route refuses a missing or wrong header and each refused content type above; a route walk over every admin route proves that no other route accepts `application/octet-stream`; the store guard refuses it; `docs/contracts/api.md` "CSRF header" and the OpenAPI `403` text name the exception.

### 5. Data
- New table `media_upload`, migration `0005_media_upload.sql` with a hand-written `0005_media_upload.down.sql` that also deletes its `drizzle.__drizzle_migrations` row; tested up, down, up, down, plus `db:drift`:

| Column | Type | Rule |
|---|---|---|
| `id` | uuid PK | |
| `storage_key` | text NOT NULL UNIQUE | `CHECK (storage_key ~ '^[0-9a-f]{32}\.(jpg\|png\|webp)$')` |
| `content_type` | text NOT NULL | `CHECK IN ('image/jpeg','image/png','image/webp')` |
| `byte_size` | integer NOT NULL | `CHECK > 0` |
| `width`, `height` | integer NOT NULL | `CHECK > 0` |
| `sha256` | text NOT NULL | hex of the stored bytes; not unique |
| `created_by` | uuid NULL -> `admin_user(id)` ON DELETE SET NULL | |
| `created_at` | timestamptz NOT NULL default `now()` | |
| `first_attached_at` | timestamptz NULL | set when a media list or a brand first references the upload |

- Index `(created_at) WHERE first_attached_at IS NULL`.
- URLs stay in `media.url` and `brand.logo_url`; neither table gets a column or a foreign key. The public store API shape is unchanged.
- Attach marking: `PUT /admin/products/{id}/media` and brand `POST`/`PATCH`, in the same transaction as the save, look up every URL that starts with `MEDIA_PUBLIC_BASE_URL + "/"`: each must name an existing `media_upload` row, else `400 validation_failed` at `media.N.url` or `logoUrl` with reason `upload_not_found`; those rows get `first_attached_at = now()` where it is null (atomic `UPDATE ... RETURNING`). URLs on other prefixes are untouched. This tightens validation on existing routes (breaking by `docs/contracts/api.md`); the template is unreleased (`0.0.0`, CHANGELOG "Unreleased"), so it is recorded in `CHANGELOG.md` without a migration guide.

### 6. Serving
- `GET /media/{key}` and `HEAD` in the API (`MediaFilesController`, outside `/admin` and `/store`), public. It reads no cookie and no database row: a key that fails `isMediaKey` or names no file answers `404` with `Cache-Control: no-store` and no echo of the key. The content type follows from the key's extension, which the server chose from the sniffed type.
- Storage key: 128 random bits (`randomBytes(16)`) as 32 lowercase hex plus the output extension; laid out as `MEDIA_DIR/<2 hex>/<2 hex>/<key>`; the resolved path must stay inside `MEDIA_DIR`. No client input reaches a key or a path; the original file name is never read.
- Fixed headers, pinned by a test: `Content-Type` (`image/jpeg`, `image/png` or `image/webp`), `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; img-src 'self'; style-src 'unsafe-inline'; sandbox`, `Content-Disposition: inline; filename="<key>"`, `Cache-Control: public, max-age=31536000, immutable`, `ETag` (the key), `Cross-Origin-Resource-Policy: cross-origin`, `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY`.
- URL shape `MEDIA_PUBLIC_BASE_URL/<key>`. By default the edge proxy routes `/media/*` of the shop host to the API; `MEDIA_PUBLIC_BASE_URL` may instead name a cookie-less host or a CDN that pulls from the API route, without a code change. The admin cookie (`Path=/admin`) is never sent to `/media/*`.
- Draft images are public to anyone who knows the URL and listed nowhere (no index route, no directory listing): unlisted, not private. The store API still never returns media of a draft product.
- Storefront: no code change. The storefront can render an uploaded image only when `MEDIA_PUBLIC_BASE_URL` is an absolute `https` URL whose host is in `STOREFRONT_IMAGE_HOSTS` and resolves to a public address from the storefront server (the Next optimizer refuses private IPs). Over `http` (development) the storefront shows the placeholder; the admin preview works.
- Admin: `img-src 'self'` covers `/media/*` on the same origin; a separate media host goes into the proxy configuration's `imageHosts`. No change to `security-headers.ts`.
- Proxies: the admin and storefront e2e proxies and the Vite dev proxy route `/media` to the API; the README Caddy and nginx examples add `/media/*` and set nginx `client_max_body_size` on `/admin/` (its 1 MB default would refuse uploads).

### 7. Deletion
- Job 7 `delete-abandoned-uploads` (bounded like ADR 0025: pages of 100, at most 50 pages per run) deletes rows with `first_attached_at IS NULL` older than 24 hours, commits, then calls `storage.delete(key)` for each; an absent file is success, other file errors are logged by code and counted (`deleted`, `truncated`, `fileErrors`). It also runs through `pnpm jobs:run-once`.
- Race with an attaching save: whichever transaction commits first wins; a save that finds its row deleted answers `400 upload_not_found`. Tested with two connections.
- An upload that was ever attached is never deleted automatically: removing it from a media list, deleting a draft product or changing a brand logo keeps the row and the file, because `order_item.image_url` snapshots, caches and the optimizer may still reference it. A purge of unreferenced uploads is a later plan.
- The local driver writes through temp files under `MEDIA_DIR/.tmp` (`wx`, mode `0640`), `fsync`, then an atomic no-overwrite rename, then the row insert (the file is unlinked if the insert fails); `.tmp` entries older than one hour are removed at start. A crash between rename and insert leaves an invisible file (known limit).

### 8. Configuration
New `apps/api` variables, parsed by `loadEnv` in `packages/config`, listed in `.env.example` and `docs/contracts/config.md` (a config-schema contract change, additive):

| Variable | Required | Default | Rule |
|---|---|---|---|
| `MEDIA_STORAGE_DRIVER` | when `NODE_ENV` is `production` | `local` outside production | `local` or `none`; anything else fails startup |
| `MEDIA_DIR` | with `local` in production | `<repo>/var/media` outside production (git-ignored) | absolute path; must exist and be writable at start (probe file), else startup fails |
| `MEDIA_PUBLIC_BASE_URL` | with `local` in production | `http://127.0.0.1:<PORT>/media` outside production | absolute `http`/`https` URL, no query, fragment, credentials or trailing slash; `https` in production. Changing it does not rewrite stored URLs, and URLs under the old prefix are then no longer checked by attach marking |
| `MEDIA_MAX_BYTES` | no | `10485760` | digits only, 1 KiB to 50 MiB |
| `MEDIA_MAX_PIXELS` | no | `50000000` | digits only, 1 to 100 000 000 |

The `ADMIN_DEV_API_URL` contract row changes its wording only (the Vite proxy also forwards `/media`). Operations notes (README): a persistent volume for `MEDIA_DIR` (directory `0750`, files `0640`), backed up together with Postgres; one API instance or a shared volume (the read route and the cleanup job must see every file); about 512 MB memory headroom (to be measured in step 4); nginx body size; `/media/*` routing; the public-IP requirement of the optimizer.

### 9. Licence and dependency
- `sharp` 0.35.5 (Apache-2.0) becomes a direct, exactly pinned runtime dependency of `apps/api`. Recorded in `docs/dependencies.md`.
- The owner widens the LGPL-3.0-or-later exception for the unmodified, dynamically loaded prebuilt `@img/sharp-libvips-*` binaries from "Next image optimization" to "API image re-encoding" as well. This ADR records that decision; the text of AGENTS.md section 16 and the reasons in `scripts/license-policy.json` are edited by the owner.
- `check:licenses` matches exceptions by name and licence only, so it passes whether or not the policy text names the API. The step 2 PR therefore must not rely on it: it lands together with the owner's edits of `license-policy.json` (both reasons name `next -> sharp` and `apps/api -> sharp`) and AGENTS.md section 16, records the use in `docs/dependencies.md`, and runs `pnpm install --frozen-lockfile`, `check:licenses`, `audit:prod` and `notices`. Deployments on another platform (for example `linux-arm64`) bring `@img/sharp-libvips-*` packages that the policy does not list; `check:licenses` fails there until the owner adds them.

### 10. Security properties the implementation keeps (each covered by a test)
1. No file reaches `sharp` without passing the magic-byte gate; SVG, HTML, TIFF, GIF and AVIF fixtures are refused.
2. The stored bytes are always a re-encode: no EXIF, XMP or ICC data, orientation applied, trailing data (polyglots) gone.
3. The declared `Content-Type` never decides the stored or served type.
4. Keys are server-generated, match `isMediaKey`, and resolve inside `MEDIA_DIR`; traversal attempts (`..`, `/`, `%2f`, NUL, upper case) on the read route answer `404`.
5. The read route always sends `nosniff`, the `sandbox` CSP and an image `Content-Type`, and reads no cookie and no database row.
6. Anonymous and viewer uploads are refused (`401`, `403`) before the body is read, also with a body above the size limit.
7. Only the upload route accepts `application/octet-stream`; the CSRF header is required there; multipart is refused.
8. Size, dimension and pixel limits hold for a lying `Content-Length` and for a decompression-bomb header.
9. The rate limit is per admin user; at most 2 uploads are processed at once per process.
10. A key is never overwritten; `storage_key` is unique.
11. The cleanup job deletes only never-attached rows older than 24 hours and a file only after its row delete committed; attach marking happens in the save's transaction.
12. Logs contain ids, numbers and error codes only.

## Consequences

- **Cost.** One more runtime dependency with native binaries (about 19 MB per platform in an API deployment) and more API memory and CPU per upload. The API now owns state outside Postgres: `MEDIA_DIR` needs a volume, a backup with the database, and one instance or a shared volume. Disk grows with the catalog's history, because attached uploads are never deleted.
- **Risks.** Decoder vulnerabilities in libvips and its codecs are reachable by any `catalog.write` admin (mitigated by the allow-list, exact pin, Dependabot and `audit:prod`; no sandboxed worker). A deployment whose storefront resolves the media host to a private address shows placeholders. Changing `MEDIA_PUBLIC_BASE_URL` strands stored URLs. The licence check cannot enforce the scope of the LGPL exception. The nginx and Caddy examples stay untested. Re-encoding changes bytes (JPEG generation loss, sometimes larger PNGs). Several API instances on separate disks silently split the files.
- **Contracts.** New public items once built: `POST /admin/media/uploads`, `GET /media/{key}`, the `media` block of `GET /admin/config`, problem codes `storage_unavailable` and `uploads_disabled`, the new validation reasons, the tightened URL check on media and brand saves, the CSRF exception, five configuration variables.
- **What would supersede this ADR (in part):** an S3-compatible storage driver (then `MEDIA_PUBLIC_BASE_URL` points at the bucket or CDN and the API read route is unused; the port becomes a public contract); a separate image service or sandboxed worker for decoding (replaces `sharp` in the API process and possibly the LGPL scope); signed or private URLs for draft images (replaces decision 6's "unlisted, not private"); deleting attached uploads by reference counting (replaces decision 7).
