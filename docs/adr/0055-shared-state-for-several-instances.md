# 0055. Shared state for several instances

Status: accepted by the owner 2026-11-14 (multi-instance plan, all four decisions). PR 2 implements request/service rate limits and admin login; PR 3 implements the shared email pacer; replica deployment remains a later PR.

## Context

Process-local request windows multiply limits with each API instance. Postgres already shares sessions, account lockout, reset-token counts, scheduler locks and outbox claims. Redis and ioredis 6.0.0 are already approved dependencies.

## Decision

- Select `RATE_LIMIT_STORE=memory` (default) or `redis` (requires `REDIS_URL`, unreachable Redis fails startup). One ioredis client per API process, offline queue off, bounded command/connect timeout, closed on shutdown.
- `WindowStore.hit(name, key, limit)` is async. Memory keeps the existing fixed-window rules, IPv6 /64 grouping, mapped IPv4 normalization and bounded oldest-client eviction. Redis uses one atomic Lua call: `INCR`, first-hit `PEXPIRE NX`, `PTTL` for `Retry-After`. Numbers and window durations stay unchanged. Admin and customer login remain separate windows. Reset email, verification resend, account deletion and data export share the selected store too.
- Redis keys are `fluxkit:{prefix}:rl:{limitName}:{HMAC-SHA256(key)}`. Prefix is the URL-encoded database name. HMAC key is HKDF-SHA256 of `ORDER_TOKEN_SECRET`, empty salt, info `rate-limit`, 32 bytes. Subject normalization precedes HMAC. Redis sees integer counts and window TTLs only, never raw addresses/emails/ids. These are ephemeral pseudonyms, retained at most 24 hours and excluded from exports; see the privacy guide.
- Runtime Redis failure falls back to bounded per-process windows for that request. Log only `rate_limit_store_unavailable`, at most once a minute per process. Existing readiness route `GET /health` adds `rateLimitStore: memory | redis | degraded`; it remains 200 when Postgres is reachable. A successful shared hit clears degradation. Do not fail closed.
- Email pacing uses Redis in PR 3 (details below). Storefront caches stay per process (ADR 0040/0051); URL hashing at the edge, shared media volume and replica rollout are PR 4. Shipping caches/gates, payment read single-flight, search lane/definitions/diagnostics, media slots and log-once sets stay per instance. Multi-host media storage is a separate plan.

## Consequences

- Supersedes the single-process/Redis-later limitation for rate limits in ADR 0009, 0010, 0016, 0031 and 0036. No migration or new dependency.
- Redis outage temporarily multiplies allowable traffic by process count. Recovery restores shared windows; no attempt to merge local fallback counters. Changing the database namespace or the secret starts fresh counters; switching to memory and back within a window resumes the Redis counts that have not expired. Redis must be private, password protected and shared by the shop's instances.
- One API/storefront instance remains the deployment recommendation until PR 4 finishes. No replica or production compose changes in PRs 2 and 3.

## Email pacing (PR 3)

- `SendPacer` uses the same `WindowStore` selection and Redis client as the request windows. Memory mode keeps per-process pacing at `1000 / sendsPerSecond` ms between actual provider starts. Redis mode reserves slots atomically using Redis `TIME`, `max(now, nextSlot)`, and `ceil(1000 / sendsPerSecond + replyAllowanceMs + 6)` ms spacing. Reply allowance is the last observed local Redis round-trip duration (initially zero); the extra 6 ms covers 5 ms of allowed timer lateness and 1 ms of Redis clock rounding; it never increases the configured rate. Admissions are serialized per process through synchronous provider invocation, with no database I/O; provider answers remain concurrent, outside transactions.
- Key: `fluxkit:{prefix}:email-pacer`, with the same database-name prefix as the windows; its sole value is the next slot timestamp, with no personal data. Expiry is the queued wait plus the interval (at least one second), retaining outstanding reservations until idle.
- Delayed replies and timers never catch up missed slots. Wait from reply receipt so a call cannot precede its Redis slot. The interval reserves room for reply uncertainty separately from the 5 ms timer allowance. If the reply exceeds the reserved padding, leave that slot unused and reacquire with the observed round-trip duration; steady reply latency therefore continues sending at a conservative rate below the configured maximum. A timer over 5 ms late also reacquires within the remaining budget. Timing uses the local monotonic clock; no synchronized application wall clocks are needed. Repeated lateness can exhaust admission's wait budget and defer a mail. Every actual start advances the same local schedule across shared success, fallback and recovery, including queued callers. Early timers are waited again.
- The safety margin trades throughput for spacing: measurements at a configured 8/s give about 94.7% of the rate at 1 ms Redis RTT (the slot lateness tolerance costs about 5%), 7.30/s at 6 ms, 6.62/s at 20 ms and 5.52/s at 50 ms. Redis RTT lowers throughput, never raises it above the configured rate while shared pacing is active. Keep Redis on the same host or a low-latency network.
- A Redis failure uses process-local pacing, the same `rate_limit_store_unavailable` once-a-minute log budget and `rateLimitStore: degraded` readiness state as the windows. A successful shared reservation or window hit restores `redis`. During an outage, independent processes can exceed the shared provider rate; ambiguous or stale reservations may remain unused. Local continuity survives recovery; independent fallback schedules are not globally merged.
- Sender admission is bounded by the earlier of `deadline_at` and the 120-second lease expiry minus the provider timeout and a 5-second safety margin. The budget includes the local admission queue, Redis calls and sleeps. The provider timeout comes from `config.tuning.sendTimeoutMs` (core default `EMAIL_SEND_TIMEOUT_MS`), rather than a second timeout constant. A slot outside that budget is refused without sleeping for it; Lua leaves the shared schedule unchanged so repeated deferrals cannot inflate the backlog. A refused claim returns to `pending`, clears its lease, restores the attempt count and reschedules for one second later (capped at the deadline); job 9 counts it as skipped, with no provider attempt. The next claim at the deadline closes it normally. The existing 50-waiter immediate cap remains per process.
- Ownership during the wait is guaranteed by the lease: another sender cannot reclaim it before expiry. Local time is checked immediately before provider invocation: no send starts at or beyond the deadline or the safe lease boundary. There is no database read between the wait and the send. Guarded result recording and deferral detect a newer claim and never overwrite or release it. The provider retains `idempotencyKey = email_message.id`; claim/record transactions never span the provider call.
