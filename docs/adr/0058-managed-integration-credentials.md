# 0058. Managed integration configuration and versioned credentials

Status: accepted (owner, 2026-11-16, plan `docs/plans/2026-11-16-admin-integrations.md` section 11). Slice 1 (the encrypted store and owner key entry) is implemented; activation and runtime use are not (plan section 12). The plan named this ADR 0057; that number was taken by the replica rollout.

Supersedes, once slice 2 lands, the "credentials come from the environment only" parts of ADR 0030 (Nova Post), ADR 0031 (email) and ADR 0032 (payments). Until then those parts stay true at runtime: every provider still reads its key from the server environment. ADR 0056 (pins, suppression, fallback) is unchanged.

## Context

- The template is sold to shop owners who register with providers themselves. Editing `.env` on a server is not something they can do; a deployment for every key change is not acceptable either.
- All provider keys and webhook secrets came from the environment, one accessor per plugin, captured at start in the plugin's Nest factory.
- A key in the database must not be readable by whoever reads the database or a backup, must never come back through the API, and a stolen admin session must not be enough to replace it.

## Decision

1. **One store** under `apps/api/src/integrations/`, keyed by `(kind, provider_code)` with kinds `email`, `payment`, `shipping`. Core holds the pure vocabulary and rules (`packages/core/src/integrations`). Provider packages stay removable: nothing imports one statically.
2. **Plugins declare their secrets** in the manifest: `"fluxkit": {"secrets": [{"field", "purpose", "env"}]}` with purposes `outbound` and `webhook` (each at most once per provider) and the environment variable that overrides the field. A plugin may export `validateIntegrationSecret(field, value)` for its own format rule (a problem text that never contains the value, or nothing). The store lists every installed package that declares secrets, enabled or not; being listed does not enable a provider. Test-only providers are not offered when `NODE_ENV=production`.
3. **Encryption:** AES-256-GCM through `node:crypto`, no dependency. Every envelope has a fresh random 12-byte nonce and a 16-byte tag. The additional authenticated data is the length-prefixed list `fluxkit.integration-secret/v1`, secret row id, integration id, kind, provider code, field, generation, key id, so an envelope moved to another row, field, provider, generation or key fails authentication. A failure is one generic error (`integration_secret_unavailable`) and never falls back to another source.
4. **Master keys in the environment only:** `SECRETS_ENCRYPTION_KEY=<key-id>:<base64 of exactly 32 random bytes>` and at most one `SECRETS_ENCRYPTION_KEY_PREVIOUS` of the same form with another id and other bytes. The key id is stored with every envelope. Both are validated at start, also while nothing is stored. Neither set: the store is off (routes answer, `storage: "disabled"`, nothing can be saved) and an env-only deployment behaves as before. Deviation from the plan's wording: a blank value counts as unset, because Compose passes unset variables as empty strings.
5. **Credential versions.** Every save creates an immutable version (a generation number per integration, never reused) holding one encrypted field. States: `candidate`, `active`, `draining`, `revoked`, `retired`. Slice 1 writes `candidate` and `retired` only; a new save retires the earlier candidate of the same credential. Retiring deletes the envelope and keeps the version row as a tombstone.
6. **Write-only.** A response says only `not_set`, `set` or `env` per field, plus the version id, generation and save time; never the value, a suffix, the ciphertext, the nonce or the key id (`last4` is always `null`). `keyAvailable` tells whether this server holds the key that sealed the stored value.
7. **Precedence:** a non-blank environment variable wins over the stored value, field by field; such a field is read-only in the admin (`409 integration_env_override`). Nothing is copied from the environment into the database.
8. **Permission `integrations.manage`, owner only**, for reads too (the screen tells which providers hold credentials). Every change also needs the owner's current password (step-up): shared strict limits first, then the password check (a locked account gets the dummy check), then a transaction that re-checks under the row lock that the account is still active, unlocked, an owner and has the same password hash. A wrong password answers `403` with `rule: current_password_incorrect`, counts toward the account lockout and writes the audit event `admin_user.step_up_failed` in its own transaction.
9. **Strict limits fail closed.** Step-up attempts are counted per admin (5 in 15 minutes) and per client address (20 in 15 minutes) in one Redis script that consumes every window, refused attempts included. Redis unavailable or not configured: `503` (`rule: step_up_unavailable`), no password hashing, no write; never a local fallback. The store therefore needs Redis for changes whatever `RATE_LIMIT_STORE` says; the connection opens with the first such action, not at start. Existing endpoints keep the ordinary limiter.
10. **Revision.** One row `integration_revision` rises in the transaction of every change; writes send `expectedRevision` and a stale one answers `409 integration_revision_stale`. Reads go to the database on every request (no cache in slice 1), so every API instance sees a change at once.
11. **Audit:** `integration.secret_changed` and `integration.secret_retired` (target kind `integration`) commit with the change and hold codes, ids and numbers only.
12. **Privacy:** new inventory class `encrypted_secret` (reversible, so not `secret_hash`): always excluded from export and outside a subject erasure. Row D26 of the data inventory.

## Consequences

- A saved credential is not used yet. The admin says so; providers run from the environment until slice 2 (per-version clients, activation, durable bindings on mail, payments and shipments, the final revocation gate, the Monobank merchant baseline, alert mails).
- Whoever deploys the shop keeps a backup of `SECRETS_ENCRYPTION_KEY` apart from the database backup (`docs/deployment.md`). Losing it loses no shop data: the stored credentials become unreadable (`keyAvailable: false`) and are entered again.
- Encryption protects a database dump or backup, not a compromised application or server, and not against a stolen owner password. Password re-entry is weaker than intended until creating, promoting or reactivating an owner and resetting an owner's password also need it (HANDOFF section 4): a stolen owner session can still mint a password it knows. In slice 1 that reaches only unused candidates, which cannot be read back.
- A deployment without Redis cannot change stored credentials. Redis Cluster is not supported by the strict limits (one script touches two keys); they then answer unavailable.
- The step-up budget counts every attempt, successful ones too (plan section 8: consumed before the password check). An owner who enters more than five credentials in fifteen minutes waits for the window; the screen says how long. Raising the numbers or counting failures only is an owner decision.
- `keyAvailable` compares key ids, not key bytes: never reuse a key id for other bytes. A key check value per id comes with the rewrap work (it needs a column).
- The transaction of a change also requires the acting session to still exist ("sign out everywhere" during the password check refuses the change with `401`).
- Saving a credential imports the entry of that provider package to ask its format rule, also when the provider is not enabled, so its top-level code runs in the API process. Listing imports nothing. A provider may only name variables that start with its own code in upper case (`RESEND_`, `NOVA_POST_`); a package that names another variable is not offered.
- All API instances must share the same key ring. An instance with another key reports the value as stored but unreadable and cannot use it.
- The migration `0019_integration_credentials` adds four tables and the audit target kind `integration`. Its down script refuses while a credential version (also a retired one) or its audit evidence exists.
- Not built yet, by design: master-key rewrap command, connection checks, DNS help, settings (sender, route, limits) in the store, the move of shipping profiles, emergency revocation.
- The Brevo rule "webhook secret differs from the API key" needs both values; it is checked when the provider is activated (slice 2), not at save.
