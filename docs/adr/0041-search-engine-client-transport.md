# 0041. Search engine client: keep-alive transport and a bounded interactive lane

Status: accepted 2026-10-31 (owner approval of both fixes, through the orchestrator; plan `docs/plans/2026-10-31-search-engine-client.md`). Builds on ADR 0034 and 0036; changes no decision of them. Adds two optional variables (`docs/contracts/config.md`).

## Context

- The engine client (`apps/api/src/search/engine/search-engine.ts`) used global `fetch`. The measurements at 20 000 products (search plan, "Measurements at scale", F1) showed `fetch` waiting about 40 ms for every engine answer above about 1.4 KB (44.3 ms against 1.6 ms for `node:http` with a keep-alive agent, same request), so most store searches spent more time in the client than in the engine.
- At concurrency 32 the engine saturated (about 85 search requests a second with the full mix). Nothing bounded the engine calls of one API process, so every shopper's call joined the engine's own queue; slow calls (deep pages) passed the 2 s search timeout: 22 of 12 870 searches and 19 % of the catalog-through-search mix answered `503`, while the SQL fallback had no errors.
- The indexer (jobs 13, 14, `pnpm search:reindex`) uses the same client; it must keep working while shoppers saturate the engine.

## Decision

1. **Transport:** `node:http` or `node:https` (by the URL scheme), no new dependency. One deadline per call covers everything (the wait for a slot, the connection, the request and the whole answer); on expiry the request and its socket are destroyed. Behaviour kept from the `fetch` client and pinned by a loopback spec: 301, 302, 303, 307 and 308 are never followed and fail as `engine_unreachable` without a status (what `redirect: "error"` did); other statuses are answers; a body cut after the headers is `engine_unreachable` with the status; body decoding as `Response.text()`; the same error codes, and never the URL, the key or the engine's message.
2. **Two lanes, each with its own keep-alive pool.** `interactive`: `multiSearch`, `filterableAttributes`, `sortableAttributes` (the store's search and suggest calls); `background`: every other call (indexer writes, task polling, stats, the admin status health check), at most 8 sockets. Idle sockets close after 4 s and never keep the process alive. The background lane is never queued behind shoppers and never takes their slots.
3. **A FIFO concurrency limit on the interactive lane** (`engine/concurrency-limiter.ts`): at most `SEARCH_ENGINE_MAX_CONCURRENCY` calls in flight (default 8), at most `SEARCH_ENGINE_MAX_QUEUE` waiting (default 512), each waiting at most 1 s and never past its own deadline. A call that cannot get a slot fails at once with the new code `engine_busy`; the store already answers every engine failure except `engine_rejected` with `503 search_unavailable` (`Retry-After: 30`), so the storefront falls back to SQL exactly as for an unreachable engine. `engine_busy` is never stored: the indexer and the admin status do not use this lane.
4. **One more try for reads only:** a read (GET or `multi-search`) whose REUSED keep-alive socket is reset before any answer is sent once more on a new socket, within the same deadline (the engine closed the idle socket as it was reused). A write is never sent twice.
5. **Lifecycle:** `SearchEngine.close()` destroys both pools and refuses waiting calls; `SearchModule` calls it in `onApplicationShutdown`.
6. **Defaults:** 8 calls in flight because concurrency 8 had no error and the engine already used 3.4 of 4 cores at saturation (more concurrent calls only queue inside the engine, where nothing bounds them); a 1 s wait leaves half of the 2 s search timeout for the engine call, and it, not the queue length, sheds load: one search fans out into up to about 7 parallel engine calls, so the first choice of a queue of 64 refused a quarter of the searches at a load the unlimited client served without errors (reduced run, plan). 512 waiting calls cost nothing but memory for their callbacks. All per process (like the rate limits: one API instance, HANDOFF section 2).

## Consequences

- Searches no longer pay about 40 ms per engine answer; the indexer's polls and stats get faster too.
- Under overload a shopper gets a `503` (and the SQL fallback) after at most 1 s instead of after a 2 s timeout, and the engine no longer works on calls whose callers have already given up: in a reduced run (3 000 products, indicative, plan) the catalog mix kept about 85 successful searches a second at concurrency 192 where the old client collapsed to 1 to 13 (86 to 99 % `503`). The price: with the full search mix at concurrency 192 the old client answered everything slowly (page p95 2.3 to 2.6 s) and the limited one sheds about 16 % of searches to the SQL fallback (page p95 1.5 to 2.0 s). Below saturation (concurrency 32 and 64) nothing is refused and p95 is equal or lower.
- An engine with more cores needs a higher `SEARCH_ENGINE_MAX_CONCURRENCY`; too high brings the timeouts back. With several API instances each has its own limit.
- No proxy support (neither `fetch` nor this client honoured `HTTP_PROXY`); no compression is asked for (the engine is on the private network).
