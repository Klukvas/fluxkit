# 0056. Email: Brevo, shared suppression and fallback

Status: accepted (owner, 2026-11-16, plan docs/plans/2026-11-15-brevo-email-failover.md).

- Basis: [approved plan](../plans/2026-11-15-brevo-email-failover.md), especially section 11. These are implementation decisions; **nothing in steps 1, 1b or 2 is built yet**.
- Supersedes in part [ADR 0031](0031-transactional-email.md): decision 4 (one provider / no failover), decision 5 (`provider_message_id` pattern), decision 7 (12-hour retries assumed inside the provider's idempotency window), and the affected portions of 1/3/6/12/15/17 (deferred providers/webhooks, capabilities, outcomes, config and admin contracts). Other email/auth rules remain. Follows [ADR 0033](0033-personal-data.md), [0035](0035-privacy-subject-scope.md) and [0055](0055-shared-state-for-several-instances.md).

## Context

- Existing email uses one configured provider, a durable outbox and the same message UUID on retries. `provider_code` and `provider_message_id` already exist; there is no durable ambiguity pin or shared suppression list. The current sender selects the configured provider again on a later claim.
- A second provider can help after a proven refusal at a quota limit. It cannot safely help after a timeout or lost answer: the first provider may already have accepted the mail.
- Brevo documents bracketed message IDs and a 30-minute idempotency TTL, shorter than the outbox's 12-hour deadline. Its Free plan can queue accepted mail beyond the limit. Exact inline-request deduplication, quota responses and delivery behaviour remain unverified; evidence and live checks are in plan sections 3 and 6.
- Skipping a provider on quota/cooldown can bypass its prior recipient blocks. Refusing to switch on the current message's `rejected` result alone does not solve that gap.

## Decision

### 1. Step 1 — Brevo alone, with compatibility prerequisites

- Add removable `packages/providers/brevo`, selected by `EMAIL_PROVIDER=brevo`, with plugin-owned `BREVO_API_KEY`. Use Node fetch, existing discovery/port/templates/outbox and pinned dependencies; no SDK or new third-party dependency. Provider code stays outside core/apps imports.
- Separate provider-message-ID validation from error-code validation: preserve existing IDs and a bounded bracketed form, maximum 255 characters, verbatim. Widen the database check through a reversible migration; never truncate IDs to permit rollback.
- Add optional `idempotencyWindowSeconds`; absence preserves existing behaviour. `idempotencyKeys=false` forbids replay after ambiguity. Brevo stays false until the exact inline request is live-verified; then it declares true with 1,800 seconds. [Brevo idempotency documentation](https://developers.brevo.com/docs/heterogenous-versions-batch-emails).
- Persist `pinned_provider_code` and `pinned_at` on ambiguous results and expired-lease recovery, using the original ambiguous attempt's claim time. Conservatively backfill open attempted rows. Never clear the pin or change the message UUID: a later config change cannot send pinned mail through another provider.
- A pinned retry ends before `min(deadline_at, pinned_at + provider window - 5 minutes)`. Without established dedupe protection, or after the cutoff, stop automatically as `unknown`. Unpinned proven refusals retain normal backoff/deadlines; Resend's 24-hour window already exceeds them.
- **Ambiguity takes precedence:** a later safe refusal, render failure, missing pinned provider or deadline cannot prove earlier non-acceptance. Such a terminal result is `unknown`, not `failed`; add `pending -> unknown`. An unavailable pinned provider is held until expiry. Only authoritative success gives `sent` (provider acceptance, not inbox delivery). Cancellation preserves the pin and warns that an earlier send may still arrive.

### 2. Step 1b — shared local suppression, before any fallback

- Add public, rate-limited `POST /webhooks/email/resend` and `/webhooks/email/brevo`. Plugins authenticate/verify RAW bytes before parsing into allowlisted facts; core applies hard-bounce, complaint and reported transactional unsubscribe/blocked suppression (Resend also `suppression.added`, read as `blocked`). No delivery tracking, automatic unsuppression or routing decisions from webhooks.
- Resend uses `svix-id`, `svix-timestamp`, `svix-signature` and a `whsec_` secret: HMAC-SHA256 over ID, timestamp and raw body, constant-time comparison and ±5-minute signed-delivery tolerance. [Resend verification](https://resend.com/docs/webhooks/verify-webhooks-requests), [Svix specification](https://docs.svix.com/receiving/verifying-payloads/how-manual), [timestamp tolerance](https://www.svix.com/resources/webhook-university/reliability/idempotency-and-deduplication/).
- Brevo documents **no transactional body signature**; choose its configured bearer-token authentication over HTTPS, constant-time comparison, optionally strengthened by official source-IP allowlisting. URL credentials are not used. A stolen token can forge body/timestamp values; this is an explicit residual risk, not signed-body verification. [Brevo authentication options](https://developers.brevo.com/docs/secured-webhooks).
- Add plugin-owned `RESEND_WEBHOOK_SECRET` and `BREVO_WEBHOOK_SECRET`. Atomically deduplicate provider events and upsert `email_suppression`; acknowledge only after commit. Resend uses its stable event ID. Brevo's documented webhook `id` alone is insufficient: use the validated event tuple/digest in plan 4.5 until unique event identity is verified. The local event-age window is 7 days, future tolerance 5 minutes, receipts expire after 8 days; this does not authenticate Brevo's unsigned timestamp. [Brevo payload definitions](https://developers.brevo.com/docs/transactional-webhooks).
- Store a unique normalized address, opaque entry ID, reason, source provider, first/last seen, plus minimal webhook receipts. Normalized addresses support admin inspection and scoped erasure without a new hash key; a keyed hash would still be personal data. Classify all columns under D16; never persist raw payloads or put addresses, secrets or provider text in logs, URLs, errors or audit records.
- Default erasure deletes suppression/receipts only in verified address scope; unverified customer deletion cannot clear a global block (ADR 0035). Retention after customer deletion on legitimate-interest grounds, possibly as a keyed hash, remains an **owner/legal open item, non-blocking for implementation**. No legal exemption is assumed. Active suppression remains until authorized removal/erasure; finite receipt retention is separate.
- Check shared suppression before every attempt in job 9 and immediate auth, including fallback, test and resend. Suppressed unpinned mail ends `failed/suppressed`; pinned mail ends `unknown/suppressed`. Auth mail has no exemption: a complaint or undeliverable address is unsafe for reset/verification mail too; public auth responses and token rules stay unchanged. DB lookup failure sends nothing. Preserve pacing invariants; feedback after admission cannot recall an already admitted/in-flight send.
- Admin list/removal uses `email.manage`, CSRF on removal, masked/reveal UI and an atomic IDs-only audit entry. Keep receipts after manual removal, never automatically resend or alter remote blocklists. Webhooks never unpin, extend the 30-minute window, change cooldowns/routes or prove non-acceptance by their absence.

### 3. Step 2 — primary plus ordered fallback

- Keep `EMAIL_PROVIDER` as primary; add comma-separated ordered `EMAIL_FALLBACK_PROVIDERS`, default empty. Empty/unset preserves single-provider/off behaviour. Normalize codes; reject `none`, unknown/test-only production codes, empty interior entries, duplicates and primary repetition. Nonempty fallback with primary `none` fails startup; all selected packages/API keys must be valid.
- With a nonempty normalized fallback list, refuse API startup unless step 1b is in place: applied migration/journal, queryable suppression/receipt schema, shared sender guard, and registered authenticated webhook route/verifier with a valid secret for **every configured provider including primary**. An empty suppression table is valid. No bypass flag, startup migration or provider call. Startup cannot prove remote subscriptions or historical completeness; operator subscription tests and reconciliation of existing remote blocks are required before production fallback.
- Switch only when all previous attempts are proven unsent and the current result is `quota_exceeded`, `rate_limited`, `misconfigured` or `not_sent`. Never switch on `rejected`, suppression, conflict, ambiguous history, success, remote queueing or later bounce. A pinned A remains A even after a later safe quota refusal; use the same UUID on every permitted attempt.
- Choose the minimal design: existing accepting-provider fields, step-1 pin, `route_provider_code` for a deferred next provider, and Postgres `email_provider_state` for shared cooldowns and a fenced recovery-probe lease. **No attempt ledger or admin attempt history.** Keep the message-level attempt counter/backoff.
- Commit outcome, pin, deferred route and cooldown atomically under claim fencing. Defer B durably if the current budget cannot cover it. One provider per routing pass position, bounded job/lease/deadline budgets, no transaction around HTTP; Postgres failure permits no unrecorded fallback. Postgres, not Redis/process memory, owns durable routing state. Keep ADR 0055's shared/global pacing and local outage fallback.
- Recommend **Resend primary, Brevo fallback**: a definitive Resend quota refusal can advance, whereas Brevo may accept into a queue and never return a switch-safe quota answer. Unverified quota shapes remain ambiguous. Admin status shows the ordered chain, pin and cooldown; privacy/export docs list every configured real processor.

### 4. Branding, rollout and verification

- Accept Brevo Free branding and queue/deadline limitations (owner decision 2). The Brevo README and client-facing config/deployment provider notes state that removing branding requires a paid Brevo plan. No delivery-time guarantee at the free cap.
- **Live checks remain pending; no Brevo key is available.** Implement from documented behaviour and fakes, mark each unverified behaviour `TODO(fluxkit): not live-verified` in code/README and list it in HANDOFF. Stub results never establish live semantics. Domain/key setup, sends, DPA review and production cutover require separate owner action.
- Each step has its own tests/docs and reversible migration where required; down scripts remove the exact Drizzle journal row and refuse unsafe loss of active pins/suppression. Stop old senders during state backfill/cutover. Plan sections 5–7 define fake, real-Postgres/Redis, matrix, privacy and admin acceptance evidence.

## Consequences

- Step 1 enables a single Brevo plugin with conservative retry safety; it enables no fallback. Step 1b adds shared suppression and its authenticated ingestion/admin/privacy controls. Only step 2 enables an ordered chain, after the local prerequisite gate and production setup checks.
- More mail can be attempted after proven refusals; ambiguous mail may stop `unknown` even when that reduces availability. Neither provider idempotency nor webhooks promises exactly-once inbox delivery.
- New public routes/config/contracts and personal-data tables require matching API/OpenAPI, `.env.example`, privacy inventory, setup docs and changelog updates during implementation. Extra processors, bearer-token compromise, delayed/missing feedback, historical blocks and erasure retention remain operational/privacy concerns with the explicit limits above.
- No implementation, migration application, production activation or live verification is asserted by this ADR. The existing auth, pricing, payments and template-content decisions are unchanged.
