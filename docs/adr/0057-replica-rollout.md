# 0057. Single-host replica rollout

Status: implements the owner's approved multi-instance PR 4 design (2026-11-16, plan section 9); built, not merged. Supplements ADR 0055. No migration or new dependency.

## Context

Redis already shares request windows and email pacing, and Postgres shares sessions, scheduler locks and claims. All API replicas mount the existing named media volume on one host. A plain Compose update can stop serving replicas before replacements are healthy. Nest's default lifecycle order can close resources before HTTP requests finish. Docker DNS can still list a retiring replica while a connection is attempted.

## Decision

- Production Compose reads positive `FLUXKIT_API_REPLICAS` / `FLUXKIT_STOREFRONT_REPLICAS` (default 1), with 30 s stop grace per application container. The host script validates both counts and refuses more than one API without `RATE_LIMIT_STORE=redis` in the env file before pulling images.
- Keep the existing release archive, pull, backup, env-tag switch and `current` switch. Start healthy Postgres, Meilisearch and Redis, then run `migrate` to completion. Roll API, then storefront: compare running count and `com.docker.compose.config-hash` with `compose config --hash`; skip matching services, otherwise stage N new replicas alongside the old (`--no-recreate --no-deps --scale old+1`, then `old+2`, up to `old+N`), waiting for health after each addition, then drain/stop/remove the old replicas individually. This refines the plan's single `old+N` start: Docker DNS exposes starting containers before health, and two retries can avoid only one unready address. All old replicas remain until the whole new set is healthy. Wait for the edges' 10 s DNS cache before retirement and between removals. Final `up --wait --no-build` reconciles edge/rest.
- Failed replacement health removes only the new containers, newest stage first with DNS refresh waits between removals (the unready address disappears before healthy staged replicas). Restore env/current and use the same rolling/hash logic for the previous release: matching serving old replicas stay untouched; an earlier successfully rolled service returns through healthy previous-version replacements. No automatic down migration. An incompatible database upgrade still needs the backup. The installed `/usr/local/sbin/fluxkit-deploy` must be reinstalled by the owner once; release archives do not replace it. `FLUXKIT_DEPLOY_SKIP_PULL=1` is test-only for local smoke images.
- API uses an Express adapter's `beforeClose`: Nest invokes it before `onModuleDestroy`, `beforeApplicationShutdown` and `onApplicationShutdown`. Node HTTP stops accepting, closes idle keep-alive connections and waits for in-flight requests before scheduler/database/Redis teardown. From that moment every answer carries `Connection: close`: a proxy that keeps sending on a busy keep-alive connection would otherwise hold the close open until Docker's SIGKILL (seen with Node: a client sending without pause kept `server.close()` waiting indefinitely); now it opens a new connection, is refused and tries another replica. Both SIGTERM and `createApp(...).close()` use it.
- Storefront defaults in `store-data.ts` (including feature reads) and `search-data.ts` use one wrapper: GET/HEAD retries once only when fetch rejects before a response with refused/reset/unreachable/socket-closed error in the cause chain. Preserve URL/options/signal, including the original timeout budget. Never retry writes, an abort/timeout, any HTTP answer or body parsing failure; the second rejection surfaces unchanged. Browser transport stays unchanged. This is best-effort: a second direct API DNS lookup can still select the same unavailable address.
- nginx retains `zone`, runtime `resolve`, `keepalive`, API round robin and storefront `hash $request_uri` (plain, not `consistent`: see Consequences). Both proxy paths use 2 s connect timeout and `proxy_next_upstream error timeout`, two attempts. `non_idempotent` is absent: nginx does not replay a non-idempotent request already sent upstream. Caddy uses dynamic A upstreams (10 s refresh), storefront `uri_hash`, 5 s retry duration / 250 ms interval / 2 s dial timeout and passive failure exclusion. A connected request retries only for GET/HEAD. Dynamic A needs separate host/port overrides; existing non-upstream environment names stay unchanged.
- The edge remains one container and is recreated for a new image tag. A brief connection-refused gap during edge restart remains; uninterrupted edge availability needs another edge or host load balancer.

## Consequences

- Media is shared on one host; multi-host object storage is a separate decision. Storefront caches remain per process (ADR 0040/0051); replacement or changed membership can move a URL to a cold cache. Shipping gates/caches, payment read single-flight, search lane/diagnostics and media processing slots remain per API process.
- Budget 1 GB limit per API/storefront replica plus overlap (old + new replicas of the service being rolled). The 30 s stop grace bounds drain time; longer requests can still be killed. Infrastructure upgrades are not made highly available by application rollout.
- The plan named `hash $request_uri consistent`. With `resolve`, nginx 1.29.8 computes the consistent-hash points from the server name, so every address of the one `storefront` name gets the same points and a URL is spread over all replicas (checked 2026-11-16 with the pinned image and three backends behind one DNS name: `consistent` sent each URL to all three, plain `hash $request_uri` sent each URL to one). Plain hash is used: it pins a URL to one replica while the set of replicas is stable; when a replica is added or removed, more URLs move than with a consistent ring, which only means colder caches for a while. Caddy's `uri_hash` pins as well.
- The Bash helper regression (`infra/deploy/fluxkit-deploy.spec.sh`) covers sequential starts, second-stage failure cleanup order/DNS waits with preserved old IDs, and matching hash/count skips, using in-memory Docker boundaries. Smoke coverage adds two replicas per application, the shared login Redis key and shared uploaded file, real-script successful and failed releases under live reads (including cold missing-product paths), and failed-release preservation of prior API IDs/env/current. The smoke test runs in CI (`deploy-smoke`, Linux: the host part needs `flock` and GNU `sed`). The Caddyfile passes `caddy validate` (caddy:2.10-alpine); with three backends behind one DNS name, Caddy `uri_hash` over `dynamic a` and nginx plain `hash $request_uri` each sent every URL to one backend, nginx `consistent` to all three (2026-11-16).
