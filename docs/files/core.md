# packages/core

Pure TypeScript domain logic of the catalog (ADR 0006, AGENTS.md section 2.3), of admin authentication rules (ADR 0009) of money and price rules (ADR 0011), of stock (ADR 0011), of the cart (ADR 0015), of orders (ADR 0017), of media uploads (ADR 0028), of shipping (ADR 0029), of transactional email (ADR 0031) and of online payments (ADR 0032). Rules only: no Nest, no Drizzle, no database, no network, no filesystem, no clock (time is a parameter). Enforced by dependency-cruiser (`core-must-not-import-infrastructure`, `core-must-not-import-node-builtins`, `core-must-not-import-providers`). The one runtime dependency is `zod`, used only by `attribute-values.ts`.
The API (`apps/api`) reads facts from the database, calls these functions inside a transaction, and maps the results to HTTP problems. Core never decides HTTP status codes.

- `package.json` - `@fluxkit/core`, private; runtime dependency `zod` only; devDependencies typescript and vitest.
- `src/index.ts` - public entry; re-exports `./auth/index.js`, `./cart/index.js`, `./catalog/index.js`, `./email/index.js`, `./inventory/index.js`, `./media/index.js`, `./orders/index.js`, `./payments/index.js`, `./pricing/index.js`, `./search/index.js` and `./shipping/index.js`. Must not export anything else.
- `src/catalog/index.ts` - barrel of the catalog modules below. Add new modules here.

## Entities and shared types

- `src/catalog/types.ts` - plain data shapes (`I18nText`, `AttributeDefinition`, `ProductTypeDefinition`, `OptionDefinition`, `VariantSnapshot` (carries `hasShopPrice`, a fact the API supplies), `ProductSnapshot`, `CategoryNode`, `LocaleConfig`). Must not carry ORM or framework types; the API maps rows to these and back.
- `src/catalog/limits.ts` - `CATALOG_LIMITS` (options per product 3, values per option 30, variants 250, depth 5, page size 100, offset 10 000, ...), `TEXT_LIMITS`, `ATTRIBUTE_VALIDATION_DEFAULTS`, code patterns and `isValidCode` / `isValidValueCode`. Must not read configuration; limits are constants.
- `src/catalog/text-safety.ts` - `hasJsonbUnsafeCharacters` (exported): NUL and unpaired surrogates, which Postgres rejects or the driver silently replaces. Turns a 500 into a field error; the admin schemas use it for every free-text column (barcode, URLs, unit).

## Text, slugs, SKUs

- `src/catalog/i18n.ts` - `validateI18nText` (shape, default locale required, allowed locales, length), `resolveText` (requested locale, else default; per field), `resolveTextWithFallback` (requested, default, first available non-empty locale in code order; the one rule of the store read, the cart and the order views), `codePointLength`.
- `src/catalog/slug.ts` - `validateSlug`, `isValidSlug`, `transliterateUkrainian` (KMU resolution 55/2010), `slugify`, `slugLookupPrefix` (the prefix a caller queries taken slugs with; not the plain slug, because the candidates of a 160 character slug are `base158-2`, ...), `generateUniqueSlug` (slugifies the title and adds `-2`, `-3` against the set of taken slugs the caller passes in; it must contain every taken slug that starts with `slugLookupPrefix(title)`). Must not query the database for collisions itself.
- `src/catalog/sku.ts` - `normalizeSku` (trim, uppercase), `validateSku`, `proposeSku` / `proposeSkus` (`<SLUG>-<VALUE_CODE>...` uppercased, skipping SKUs in the taken set the caller passes in).

## Attributes and values

- `src/catalog/attribute-defaults.ts` - `normalizeAttributeDefinitionInput`: defaults (`isLocalized` only for text, `isVisibleOnStorefront` is `!isInternal`) and definition consistency errors (for example `internal_cannot_be_public`).
- `src/catalog/attribute-values.ts` - `parseAttributeValidation` and `validateAttributeValues`: validates product or variant attribute values against definitions, in draft mode (required not enforced) or publish mode. Only file in core that uses `zod`. Must not accept unknown keys silently.
- `src/catalog/store-attributes.ts` - public view of attributes: `isPublicAttribute`, `selectPublicAttributes`, `publicAttributeDefinitions`. The one allowlist deciding what the store API may expose (visible on storefront and not internal). Must not be bypassed; the store serializer feeds it and never filters itself.

## Options and variants

- `src/catalog/variants.ts` - `computeOptionSignature` (sorted `code=value` pairs joined with `;`; internal), `generateVariants` (cartesian product, skips existing combinations, enforces limits), invariant checks (`checkExactlyOneDefault`, `checkOptionCoverage`, `checkUniqueSignatures`, `checkSignatureConsistency`, `checkVariantInvariants`).
- `src/catalog/variant-rules.ts` - `canDeleteVariant` (draft only, not the last, not the default, no stock history: `has_stock_history`, ADR 0013, and no order line: `has_order_lines`, ADR 0020), `canRebuildVariants` (refuses an option change that rebuilds all variants while any variant has stock history, ADR 0014, or an order line, ADR 0020), `canCreateVariantManually` (draft only).
- `src/catalog/sellable.ts` - `isVariantSellable({productStatus, variantIsActive, hasShopPrice})`: the one rule for "can be bought" that the store listing and `ReservationsService.reserve` both follow. Pure; must not know about SQL.
- `src/catalog/product-option-change.ts` - `planProductOptionChange`: what a change of a product's options and chosen values does (works on ids, returns a plan; the service applies it in one transaction).

## Categories

- `src/catalog/category-tree.ts` - `depthOf`, `subtreeHeight`, `wouldCreateCycle`, `validateMove`, `validateNewNode`, `validateTree`: depth 5, no cycles, existence of parent or node. Pure; takes the whole tree as input.
- `src/catalog/category-assignments.ts` - `normalizeCategoryAssignments` (exactly one primary when a product has categories), `promotePrimaryAfterRemoval`.

## Lifecycle, rules and type changes

- `src/catalog/lifecycle.ts` - `canTransition` (draft, active, archived), `canHardDelete` (never published), `publishPreconditions` (every violation at once: title, slug, default variant, active variant, option coverage, SKU, required attributes, allowed options, `price_missing` for every active variant whose snapshot has `hasShopPrice: false`; inactive variants never trigger it).
- `src/catalog/publish-timestamp.ts` - `nextPublishedAt`: set on the first publish, never moved. Takes `now` as a parameter.
- `src/catalog/type-change-rules.ts` - `decide*` functions for ADR 0006 section 5 (code, input type, localization, unit, level, attribute and option removal, product type change, option change on products). Each takes facts the service read from the database and returns `allowed` or a reason code. Must not read anything itself.

## Admin authentication rules (ADR 0009)

Pure decisions only: no hashing, no cookies, no random numbers, no clock (`now` is a parameter). The API does the I/O (scrypt, sessions, database) and calls these.

- `src/auth/index.ts` - barrel of the auth modules below. Add new modules here.
- `src/auth/roles.ts` - `ROLES` (`owner`, `manager`, `viewer`), `PERMISSIONS` (`catalog.read`, `catalog.write`, `catalog.publish`, `users.manage`, `orders.read`, `orders.write`, `customers.read`, `customers.write`, `shipping.manage`, `email.manage`), frozen `ROLE_PERMISSIONS` (owner all; manager all but `users.manage`; viewer `catalog.read` only, because orders and customers hold personal data), `isAdminRole`, `isAdminPermission`, `permissionsOf` (frozen copy), `hasPermission`. Unknown role or permission strings (also `__proto__`, `constructor`) never grant anything. The one place roles are defined.
- `src/auth/password-policy.ts` - `PASSWORD_LIMITS` (12 to 128 code points), `validatePassword`: `too_short`, `too_long`, `equals_email`, `not_a_string`, `contains_nul`. No composition rules. Must not hash.
- `src/auth/email.ts` - `normalizeEmail` (trim, lower-case; the stored form), `validateEmail` (a small format check, not the RFC; returns the normalized email).
- `src/auth/lockout.ts` - `LOCKOUT_DEFAULTS` (5 failures, 15 minutes), `isLocked`, `registerFailedLogin`, `registerSuccessfulLogin`. Returns the new counter and lock; does not write them.
- `src/auth/session.ts` - `SESSION_DEFAULTS` (720 idle minutes, 168 hours), `CUSTOMER_SESSION_DEFAULTS` (43 200 idle minutes = 30 days, 2 160 hours = 90 days; ADR 0016) and `SESSION_BOUNDS` (at most one year for either limit; `@fluxkit/config` repeats the numbers, a test in apps/api asserts they agree; customers reuse `evaluateSession`, `normalizeEmail`, the password policy and the lockout rules unchanged), `evaluateSession` (`idle_timeout`, `max_lifetime`, `invalid_session`; a limit reached exactly is expired), `shouldTouchSession` (at most once a minute), `sessionExpiry`. Must not read the clock.
- `src/auth/user-rules.ts` - `decideUserChange`: the last active owner cannot be demoted or deactivated; unknown roles are rejected. The caller passes the active owner ids read in the same transaction.

## Money (ADR 0011)

Pure and dependency-free: integers and BigInt only, no float arithmetic for anything rounded or multiplied, no clock, no randomness, never `-0`. Data errors are typed results; only misconfiguration throws `RangeError`. The API and later modules must not do their own money arithmetic or rounding.

- `src/pricing/index.ts` - barrel of the pricing modules below. Add new modules here.
- `src/pricing/currency.ts` - `CURRENCIES` (UAH, USD, EUR, PLN, GBP, CZK, CHF, CAD: 2; JPY: 0; KWD: 3), `CURRENCY_CODES`, `SupportedCurrency`, `isSupportedCurrency` (exact, own-property check), `exponentOf`. Must not read configuration; the shop currency is validated elsewhere against this table.
- `src/pricing/limits.ts` - `MAX_AMOUNT` (10^12 minor units), `MAX_QUANTITY` (1 000 000), `BASIS_POINTS_PER_UNIT` (10 000), `MAX_PERCENTAGE_BASIS_POINTS` (1 000 000). Constants only.
- `src/pricing/money.ts` - `Money`, `createMoney`, `addMoney`, `subtractMoney`, `multiplyByQuantity`, `compareMoney`, `negateMoney`, `isZero`, `percentageOf` (modes `half_away_from_zero` default, `half_even`, `floor`, `ceil`), `toDecimalString`, `parseDecimalString`. Must not accept floats, mix currencies, exceed the limit or know about prices (non-negative prices are a price rule, not a money rule).
- `src/pricing/price.ts` - `Price`, `validatePrice` (integer amount 0 to `MAX_AMOUNT`, supported currency, optional compare-at strictly greater than the amount; typed reasons incl. `negative_amount`, `compare_at_not_greater`), `pickSellablePrice` (the price in the shop currency or `no_price_in_shop_currency`; never converts or picks another currency; a duplicate or invalid stored price is a `RangeError`). Must not do arithmetic or know about the database.

## Stock rules (ADR 0011)

Pure decisions over one `inventory_level`; the API calls them under the row lock and writes the result and the journal row in one transaction. Bad caller data (a quantity, a reservation in the wrong state) is a typed refusal; corrupt stored data (negative level, unknown status, bad flags) is a `RangeError`.

- `src/inventory/index.ts` - barrel of the inventory modules below. Add new modules here.
- `src/inventory/limits.ts` - `MAX_ON_HAND` (10^9) and `MAX_RESERVED` (the same bound for the reserved total of a level). Constants only.
- `src/inventory/types.ts` - `StockFlags`, `StockLevel`, `StockReservation`, `ReservationStatus`, `StockMovement`, `StockMovementKind` and the `assertValid*` guards. Must not carry ORM types.
- `src/inventory/availability.ts` - `availabilityOf(flags, levels, lowStockThreshold)`: `in_stock`, `low_stock` or `out_of_stock` from the sum of `max(0, onHand - reserved)`; never exposes a quantity.
- `src/inventory/decisions.ts` - `decideReserve` (refuses `insufficient_stock` unless backorder, `not_tracked`, `reserved_out_of_range` above `MAX_RESERVED`), `decideRelease`, `decideExpire` (lower `reserved` only), `decideCommit` (lowers `onHand` and `reserved`, yields a `sale` movement with a negative delta), `decideAdjustment` (delta or `setOnHand`; refuses a result below 0, a change that lowers on hand below `reserved` (a raise is always allowed, so partial receipts reduce a backorder), a zero change, receipts or returns that remove stock). `decideExtend` (moves the expiry of an `active` reservation later; the same time is accepted, an earlier one is `would_shorten`; `not_active`, `already_committed`, `invalid_expiry`; changes no level). A reservation leaves `active` once: `committed`, `released` or `expired`. Must not read the clock or a database.

## Cart rules (ADR 0015)

Pure and dependency-free like the money module: money only through `src/pricing/money.ts`, no clock, no I/O, inputs never mutated, outputs frozen. Bad caller input (a quantity from a request) is a typed refusal; a stored cart that breaks the rules (duplicate variants, quantity 0, 101 lines) or a corrupt fact is a `RangeError`.

- `src/cart/index.ts` - barrel of the cart modules below. Add new modules here.
- `src/cart/limits.ts` - `MAX_CART_LINES` (100) and `MAX_LINE_QUANTITY` (999). Constants only; not a public contract.
- `src/cart/lines.ts` - `CartLine` (`variantId`, `quantity`, `seen` unit price or `null`), `addLine`, `setLineQuantity`, `removeLine` (`invalid_quantity`, `quantity_limit` (never a silent cap), `too_many_lines`, `line_not_found`), `mergeCarts` (customer lines first, one line per variant, quantities added and capped at 999 with notice `quantity_capped`, guest-only lines beyond 100 dropped with notice `lines_dropped`; `seen` keeps the older customer price). Must not know about the database or the clock.
- `src/cart/pricing.ts` - `priceCart(currency, lines)`: from per-line facts (`sellable`, `currentPrice`, `availability`, `seen`) to unit price, compare-at, line total (`multiplyByQuantity`), notices (`price_changed {previousAmount}`, `unavailable`, `out_of_stock`), subtotal (`addMoney`, unavailable lines left out), `itemCount` and `purchasable`. A price in another currency is never mixed in (the line is `unavailable`). Overflow is the typed refusal `line_total_out_of_range` (with every offending index) or `subtotal_out_of_range`, never a clamp.

## Order rules (ADR 0017)

Same conventions as the cart. Statuses, transitions and totals are decided here; the API reads the facts, writes the result and records the journal.

- `src/orders/index.ts` - barrel of the order modules below. Add new modules here.
- `src/orders/consent.ts` - `decideCheckoutConsent({expectedTotal, total, shippingSelected, linePricesChanged})` (ADR 0029 decision 4): agree when the total equals the expected total (another currency never agrees); otherwise `cart_changed` without a method or when a line price changed since the shopper saw it, else `shipping_changed` (also when the method is not available: `total` null). Must not compute totals.
- `src/orders/totals.ts` - `computeOrderTotals(lines, adjustments)` -> `subtotal`, `shippingTotal`, `discountTotal`, `taxTotal`, `total`. Adjustments (`shipping` and `tax` not negative, `discount` not positive, plugin kinds any sign, kind is a code) that are `includedInPrice` are reported in their kind total but not added. Refusals: `no_lines`, `currency_mismatch`, `invalid_adjustment` (with the position), `subtotal_out_of_range`, `adjustments_out_of_range`, `total_out_of_range`, `negative_total`. Must not round or use floats.
- `src/orders/snapshot.ts` - `buildOrderLine(facts, {defaultLocale, locales})`: validates ids, SKU, option values, copies every real translation of the texts (also in locales that are no longer configured; the default locale is not required, an empty text is refused, ADR 0025; the options only check the configuration), image URL (http or https), price, quantity (1 to 999) and the shipping flag, computes the line total and returns a deep-frozen copy; typed refusals per field, `line_total_out_of_range` for an overflow. Must not read the catalog itself.
- `src/orders/status.ts` - `ORDER_STATUSES`, `ORDER_ACTORS`, the transition table `ORDER_TRANSITIONS` (data, deeply frozen), `decideTransition(from, to, actor)` (`invalid_transition`, `not_allowed_for_actor`; `from` is `null` for creation), `stockEffectOf(from, to)` (`reserve`, `commit`, `release`, `release_unsold`: the cancel of a paid order, ADR 0022), `isTerminalStatus`. Must not touch the database or reservations.
- `src/orders/number.ts` - `formatOrderNumber(bytes)` (exactly 5 random bytes -> `XXXX-XXXX`, Crockford base32 without I, L, O, U), `parseOrderNumber(text)` (lower case, missing dash, O/I/L look-alikes forgiven; everything else `invalid_order_number`), `ORDER_NUMBER_PATTERN`. Must not generate randomness.
- `src/orders/contact.ts` - `normalizePhone` (optional `+`, 7 to 15 digits, never guesses a country), `validatePersonName`, `validateAddress` (generic structured address, every error at once, unknown fields refused, no country-specific rule), `shippingAddressRequired(lines)`, `CONTACT_LIMITS`.
- `src/orders/expiry.ts` - `orderExpiresAt(placedAt, ttlMinutes)`, `reservationExpiresAt(orderExpiry)` (+10 minutes), `backorderHoldUntil(now)` (+`BACKORDER_HOLD_DAYS`, 365), `guestAccessExpiresAt`, `isGuestAccessValid(createdAt, now, days)`, `isGuestAccessCurrent(accessExpiresAt, now)` (the one boundary rule for a stored expiry) and the configured ranges.
- `src/orders/access-token.ts` - `deriveGuestAccessToken({secret, orderId, idempotencyKey}, hmacSha256)`: the pure rule of the guest access token (ADR 0023): secret of at least `GUEST_ACCESS_TOKEN_SECRET_MIN_LENGTH` (32) characters, message layout `fluxkit:order-access-token:v1\n<orderId>\n<key>`, 32-byte result in unpadded base64url; RangeError on a short secret, an empty or multi-line field or a port that does not return 32 bytes. The HMAC is a port (`HmacSha256`) the API supplies; must NOT import node:crypto or hold a secret.
- `src/orders/base64url.ts` - internal `toBase64Url` (unpadded base64url without Buffer or btoa), shared by the guest order token and the customer auth token (`src/email/auth-token.ts`); not re-exported from the barrel.
- `src/orders/events.ts` - types and constants only (ADR 0018): `ORDER_EVENT_TYPES`, `CUSTOMER_EVENT_TYPES`, `orderEventTypeFor(status)`, `buildOrderEventPayload` (order id, number and status, nothing else), `DOMAIN_EVENT_HANDLER_METADATA` with `domainEventHandlerMetadata(types)` (validated value for `SetMetadata`), `DOMAIN_EVENT_TYPE_PATTERN` and the handler types `DomainEventHandler` / `DomainEventEnvelope` (`docs/contracts/events.md`), the `OrderPaymentsPort` interface with `MarkPaidRequest` / `MarkPaidOutcome` and its token `ORDER_PAYMENTS_PORT`. The dispatcher is `apps/api/src/jobs/`. Takes `now` as a parameter; a value outside its range is a `RangeError`.
- `src/orders/read-port.ts` - types and constants only (ADR 0018, plan step 6): `ORDER_READ_PORT` (token), the `OrderReadPort` interface (`getOrder(orderId)`) and the read-only `AdminOrderView` with its parts, the shipments (`AdminOrderShipmentView`, `AdminOrderShipmentHistoryEntry`) included since shipping plan step 8 and the payments (`AdminOrderPaymentView`, `AdminOrderPaymentRefundView`, `AdminOrderPaymentHistoryEntry`) since payments plan step 8 (`docs/contracts/events.md`). Implemented by `apps/api`; must not hold I/O or a builder.

## Transactional email rules (ADR 0031)

Pure rules of mail delivery (email plan step 2, `docs/plans/2026-10-26-email.md`). No I/O and no `node:` import: the API reads and writes `email_message` and `customer_auth_token`, renders templates, supplies the HMAC and calls the provider through `EmailProviderPort`. Token rules, the retry schedule, statuses, address and header checks and escaping were written test first. Core never imports a provider (`core-must-not-import-providers`).

- `src/email/index.ts` - barrel of the email modules below (not `text.ts`). Add new modules here.
- `src/email/limits.ts` - `EMAIL_PROVIDER_CODE_PATTERN` (`CODE_PATTERN`), `EMAIL_TEMPLATE_KEY_PATTERN` (dotted lower-case segments, at least two) and `EMAIL_TEMPLATE_KEY_MAX_LENGTH` (64), `EMAIL_LOCALE_PATTERN` (as `sales_order.locale`), `EMAIL_CODE_PATTERN` (`[A-Za-z0-9_.:-]{1,64}`: provider codes, message ids, error codes; message text never fits), `EMAIL_TAG_VALUE_PATTERN` (Resend's tag rule), `EMAIL_RECIPIENT_KINDS`, `EMAIL_LIMITS` (subject 200, mailbox 200, display name 100 code points, local part 64, label 63, variables 16 KiB, 10 codes, idempotency key 256), `EMAIL_SEND_TIMEOUT_MS` (10 s), `EMAIL_LEASE_SECONDS` (120), `EMAIL_DEADLINE_HOURS` (12), `AUTH_EMAIL_DEADLINE_MINUTES` (60). Must not read configuration.
- `src/email/provider-port.ts` - types and constants only (ADR 0031 decision 3; internal, not yet in `docs/contracts/`): `EmailProviderPort` (`code`, `capabilities {idempotencyKeys, maxRecipients}`, `send(message, {idempotencyKey}, signal)`), `OutgoingEmail` (one recipient, mandatory text part, `tags.category`), `EmailSent`, `EmailProviderResult` with `emailProviderOk` / `emailProviderFailure` (reasons `unavailable`, `rate_limited`, `rejected`, `misconfigured`, `quota_exceeded`, `idempotency_conflict`, `not_sent`; codes by `EMAIL_CODE_PATTERN`, at most 10; optional whole `retryAfterSeconds`; `quotaPeriod` `daily`/`monthly` with `quota_exceeded` only), `EMAIL_PROVIDER_METADATA` = `"fluxkit:email-provider"` with `emailProviderMetadata(code)`, `EMAIL_PROVIDER_PACKAGE_KIND` = `"email"`. Uses the shipping `ProviderAbortSignal`. Must not hold I/O.
- `src/email/provider-contract.ts` - `checkEmailProviderContract(provider, scenario)`: the reusable contract check, pure and framework-free like `checkShippingProviderContract`; the scenario supplies an accepted and a refused message, an observer of the requests that reached the provider's stub service and signals. Checks code and capabilities, a typed success with a code-shaped message id, exactly one request per send with the idempotency key passed through and exactly one recipient, a typed failure with codes for the refused message, `not_sent` and no request for a message that fails `validateOutgoingEmail` and for an already aborted signal. Must not do I/O itself or use a test framework.
- `src/email/outgoing.ts` - `validateOutgoingEmail(message, idempotencyKey)`: every `{path, code}` problem before a send (normalized header-safe mailboxes, header-safe subject, non-blank HTML and text, tag, key of 1 to 256 visible ASCII characters).
- `src/email/address.ts` - `EmailAddress` (`address`, `displayName`), `validateEmailAddress` (refuses any header-unsafe character before trimming, non-ASCII (`non_ascii`: SMTPUTF8 not assumed; IDN domains in punycode), quoted local parts, commas, angle brackets; RFC 5322 dot-atom local part of at most 64, at least two DNS labels of at most 63, non-numeric last label, `EMAIL_MAX_LENGTH`; answers the `normalizeEmail` form), `validateDisplayName` (any script, NFC, trimmed, at most 100 code points, no header-unsafe character and none of `" < > \`), `parseMailbox` (`EMAIL_FROM` / `EMAIL_REPLY_TO`: bare address or `Name <address>`, optionally quoted name, at most 200 code points, one mailbox) and `formatMailbox` (`"Name" <address>`; throws for parts that are not validated and normalized). Stricter than the account rule `validateEmail`; must not repair a header value.
- `src/email/header.ts` - `hasHeaderUnsafeCharacter` (C0 and C1 controls, CR, LF, NUL, tab, DEL, NEL, U+2028, U+2029, bidi controls, lone surrogates), `validateSubject` (not blank, at most 200 code points, trimmed, NFC, no unsafe character) and `sanitizeSubject` (NFC, every unsafe or white-space run to one space, trimmed, cut to 200 code points with `…`, never inside a surrogate pair; a non-string throws).
- `src/email/html.ts` - `escapeHtml` (`&`, `<`, `>`, `"`, `'` in one pass; a non-string throws), the `html` tagged template (escapes every string by default, prints finite numbers, joins arrays, inserts `SafeHtml`; `undefined`, `null`, booleans, NaN, objects and dates throw), `SafeHtml` (unforgeable: a private field and a module-private construction key) with `isSafeHtml`, and `unsafeRawHtml` (the one explicit marker for markup not built by `html`). Prettier formats literals tagged `html` as HTML, so a template's bytes change with formatting (a template version bump).
- `src/email/auth-token.ts` - `AUTH_TOKEN_PURPOSES` (`password_reset`, `email_verification`), `AUTH_TOKEN_LIFETIME_MINUTES` (60, 2 880), `authTokenExpiresAt`, `CUSTOMER_AUTH_TOKEN_LABEL` (`fluxkit:customer-auth-token:v1`), `customerAuthTokenMessage(purpose, tokenId)` (the HMAC input: label, purpose, lower-case UUID token id, separated by `\n`), `deriveCustomerAuthToken({secret, purpose, tokenId}, hmacSha256)` (the ADR 0023 technique: the HMAC is the `HmacSha256` port the API supplies; secret at least 32 characters; 43 base64url characters), `CUSTOMER_AUTH_TOKEN_PATTERN` / `isCustomerAuthTokenFormat` (checked before the hash lookup) and `evaluateAuthToken({token, customer, purpose, now})` (`not_found`, `wrong_purpose`, `expired` at exactly `expiresAt`, `customer_inactive` (also a missing customer), `email_changed` (normalized comparison), `used` last, so `used` means valid in every other way). Must not hash, store or compare tokens itself.
- `src/email/status.ts` - `EMAIL_MESSAGE_STATUSES` (`pending`, `sending`, `sent`, `failed`, `unknown`, `cancelled`), `EMAIL_MESSAGE_ACTORS` (`system`, `admin`), the transition table `EMAIL_MESSAGE_TRANSITIONS` (data, deeply frozen: created `pending`; claim `pending`/`sending` (expired lease) to `sending`; record `sending` to `sent`, `pending`, `failed`, `unknown`; a claim past the deadline `pending` to `failed`; admin cancel `pending` to `cancelled` only), `decideEmailTransition`, `isFinalEmailStatus`, `EMAIL_RETENTION_DAYS` (sent and cancelled 30, failed and unknown 90) and `emailRetentionDays` (`null` for an open status).
- `src/email/retry.ts` - `EMAIL_RETRY_DELAYS_MINUTES` (1, 2, 5, 10, 20, 40), `EMAIL_RETRY_MAX_DELAY_MINUTES` (60), `EMAIL_QUOTA_RESET_UTC` (00:05), `nextEmailAttempt({attempts, failure, now, deadlineAt})` (`rejected` -> `failed`; `idempotency_conflict` -> `unknown`; `unavailable` and `not_sent` the schedule or a longer `retry-after`; `rate_limited` exactly the `retry-after` else the schedule; `misconfigured` hourly; a daily quota the next 00:05 UTC strictly after now, a monthly or unnamed quota hourly; a relative wait at least 1 s; a next attempt at or after the deadline -> `failed` `deadline_passed`; UTC epoch arithmetic), `emailDeadlineAt` (created + 12 h; auth mails `min(expires_at, created + 1 h)`) and `isPastEmailDeadline` (at or after the deadline).

- `src/auth/*.spec.ts`, `src/cart/*.spec.ts`, `src/catalog/*.spec.ts`, `src/email/*.spec.ts`, `src/media/*.spec.ts`, `src/orders/*.spec.ts`, `src/pricing/*.spec.ts`, `src/inventory/*.spec.ts`, `src/search/*.spec.ts`, `src/shipping/*.spec.ts` - Vitest unit tests next to each module (rules and edge cases); `src/pricing/money.property.spec.ts` compares rounding, arithmetic and decimal strings with independent BigInt references on tens of thousands of cases from a seeded generator (no `Math.random`); `src/inventory/decisions.property.spec.ts` runs seeded random sequences of reserve, release, expire, commit and adjustment and checks that on hand and reserved never go negative, reserved stays within on hand without backorder, on hand equals the sum of journal deltas and availability matches an independent reference; `src/orders/totals.property.spec.ts` compares the order totals and every refusal with an independent BigInt reference on 30 000 seeded random orders; `src/orders/status.spec.ts` checks the whole start state x target x actor matrix against a literal copy of the plan table; `src/orders/number.spec.ts` round-trips 20 000 seeded order numbers against a bit-reading reference; `src/index.spec.ts` checks the public entry point.
