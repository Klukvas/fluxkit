# apps/admin (React + Vite SPA under `/admin-ui/`)

Run, headers and conventions: `apps/admin/README.md`. Plan: `docs/plans/2026-10-19-admin-ui.md`; ADR 0027.

## Root
- `index.html` - SPA document (`lang`, `noindex`, `no-referrer`); no inline script (strict CSP).
- `vite.config.ts` - base `/admin-ui/`, build manifest, dev and preview proxy of `/admin` and `/media` to `ADMIN_DEV_API_URL` (dev only). Must not proxy `/admin-ui`.
- `vitest.config.ts` - Vitest in node: `src/**/*.spec.ts(x)` and the root specs.
- `security-headers.ts` - the header set for `/admin-ui/*` (CSP, framing, referrer, cache); plain TS so proxies can import it.
- `security-headers.spec.ts`, `vite-config.spec.ts` - pin the headers, the base path and the proxy rule.
- `build-output.spec.ts` - checks of the built `dist/`: no inline script or external URL, assets under the base path, lazy area chunks, initial JS budget, no zod, storage use. Needs `vite build` first.

## e2e (Playwright, plan step 11; run with `pnpm test:e2e` (root, after the storefront suite) or `pnpm --filter @fluxkit/admin test:e2e` after a build; NOT part of `pnpm test`; details: `e2e/README.md`)
- `playwright.config.ts` - Chromium only, one worker, `*.e2e.ts` under `e2e/tests`; starts the built API (after `prepare-database.ts`) and the proxy as `webServer` entries on ports 3110 and 3112 (never reuses a running server), then `global-setup.ts` (and `global-teardown.ts` after the last test); retries 0 locally and 1 in CI; trace on first retry, screenshot and video on failure.
- `proxy.ts` - the test-only same-origin proxy (node:http, imports only node:* and `security-headers.ts`, erasable TypeScript run by `node --experimental-strip-types`): `/admin-ui` and `/admin-ui/*` from `dist` with the `index.html` fallback (a missing asset is a 404) and `ADMIN_SECURITY_HEADERS` plus `ADMIN_CACHE_CONTROL`; `/admin/*`, `/store/*` and `/media/*` (uploaded images, GET and HEAD) to the API with `X-Forwarded-For` set from the TEST-ONLY `x-e2e-client` header, the API's answer passed back unchanged and no cookie added; everything else 404. Must NOT be used outside the suite.
- `prepare-database.ts` - wipes a `*_e2e_test` database (refuses any other name), runs the API's built migrate, seed and create-admin (the owner). Also wipes and creates the temp upload directory `ADMIN_E2E_MEDIA_DIR`. Must NOT touch any other database or directory. `global-setup.ts` - creates the manager and the viewer through the users API with the owner's session. `global-teardown.ts` - removes the temp upload directory.
- `support/env.ts` - ports, the three throwaway admins, `requireE2eDatabaseUrl`, `apiEnvironment` (every behavioural variable of the API process, the `MEDIA_*` ones included: a temp `MEDIA_DIR`, `MEDIA_PUBLIC_BASE_URL` on the proxy origin), `ADMIN_E2E_MEDIA_DIR`, `clientMarker`. `support/images.ts` - the files the upload scenarios send, made in code (a PNG built from chunks, a tiny JPEG and WebP as base64, an EXIF block spliced into the JPEG, an SVG with a script, text renamed `.jpg`, a buffer of zeros). `support/api.ts` - `AdminApi` (sign-in and plain requests with the CSRF header, users) and `StoreApi` (register, sign-in, cart, a guest order with an `Idempotency-Key`) for setup and checks only. `support/fixtures.ts` - the `test` object (per-test client marker, `signIn`, `openAs`, `owner`, `shopper`, `apiContext`, `unique`) and `Guard` (on every browser context: same-origin `/admin-ui` and `/admin` requests and image loads of `/media` only, CSRF on every write, no CSP violation, no console or page error except the ones a scenario names with `expectConsoleErrors` (only the broken route chunk of `serving`), no problem `detail` in the page's text).
- `tests/*.e2e.ts` - the scenarios: `sign-in`, `roles`, `serving`, `dictionaries`, `product`, `orders`, `customers`, `users`, `session`, `keyboard`, `media-upload` (product Media tab, refused files, the focus staying on the upload control during and after an upload, viewer, brand logo, served headers, `/media` 404s). They assert what an admin sees; they never import code from `src` (the guard reads `src/messages/*` as data).

- `user-detail-page.tsx` - the detail's data and writes: user read (kept on screen while it reloads), the role choice, the dialogs' state, one single flight, `runWrite`, a reload after every answer, the status line (kept above a failed read, so it survives the `401` after the own password reset); `UserNoticeView`. Must not hold the reset password. `user-detail-view.tsx` - the detail's markup (summary, own-account warning, role, activity, reset slot; props in, markup out). `user-dialogs.tsx` - role change, deactivation and reset confirmations with their consequences. `user-reset-form.tsx` - the reset form: the only holder of the typed new password, cleared after every answer; its view and its confirmation.
- `user-actions.ts` - actions offered from the permission list (each with its `ADMIN_OPERATIONS` operation), PATCH bodies of the changed field (`diffForPatch`), confirmations and the own-account tick, what an action does to the own session, last-owner refusals, the stored state after a lost answer. No React, no client.
- `user-form.ts` - the create and reset models: early checks (email required and length, the password policy), the create body, `409` on `email` to the field, `400` paths to fields. `user-lookup.ts` - after a lost create answer, the email among at most 10 pages of 100 users (reads only). `password-policy.ts` - core's password rules copied (compared with core) and the live feedback. `password-generator.ts` - `crypto.getRandomValues`, no modulo bias, never `Math.random`. `user-view.ts` - roles and their permissions (compared with core), labels and tones, `userHref` by id, `isSelf` by id. `user-parts.tsx` - status line, badges, role choices with permissions, the new-password field (policy feedback, show or hide, generate), the confirmation dialog with the own-account tick (an id per dialog), pager.
- Specs: one per pure module, `users-screen.spec.tsx` (static markup of every state, by permission, the dialogs, the notices, real uk and en messages), `user-messages.spec.ts` (keys built from data), `users-source.spec.ts` (one send per write through the single flight, no timer, loop or retry, reload after every answer, confirmations, the password kept in its form and out of URLs, storage and logs, ids only in links, permissions from the list).
- `messages/{uk,en}/users.json` - the area's strings (`user.*`; role names are the eager `role.*`; the route titles are in `navigation.json`).
