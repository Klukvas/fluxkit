# apps/admin (React + Vite SPA under `/admin-ui/`)

Run, headers and conventions: `apps/admin/README.md`. Plan: `docs/plans/2026-10-19-admin-ui.md`; ADR 0027.

## Root
- `index.html` - SPA document (`lang`, `noindex`, `no-referrer`); no inline script (strict CSP).
- `vite.config.ts` - base `/admin-ui/`, build manifest, dev and preview proxy of `/admin` and `/media` to `ADMIN_DEV_API_URL` (dev only). Must not proxy `/admin-ui`.
- `vitest.config.ts` - Vitest in node: `src/**/*.spec.ts(x)` and the root specs.
- `security-headers.ts` - the header set for `/admin-ui/*` (CSP, framing, referrer, cache); plain TS so proxies can import it. The CSP has one inline allowance, `style-src-attr 'unsafe-inline'` (inline style attributes only), for the Email area's mail preview.
- `security-headers.spec.ts`, `vite-config.spec.ts` - pin the headers, the base path and the proxy rule.
- `build-output.spec.ts` - checks of the built `dist/`: no inline script or external URL, assets under the base path, lazy area chunks, initial JS budget, no zod, storage use. Needs `vite build` first.

## e2e (Playwright, plan step 11; run with `pnpm test:e2e` (root, after the storefront suite) or `pnpm --filter @fluxkit/admin test:e2e` after a build; NOT part of `pnpm test`; details: `e2e/README.md`)
- `playwright.config.ts` - Chromium only, one worker, `*.e2e.ts` under `e2e/tests`; starts the built API (after `prepare-database.ts`) and the proxy as `webServer` entries on ports 3110 and 3112 (never reuses a running server), then `global-setup.ts` (and `global-teardown.ts` after the last test); retries 0 locally and 1 in CI; trace on first retry, screenshot and video on failure.
- `proxy.ts` - the test-only same-origin proxy (node:http, imports only node:* and `security-headers.ts`, erasable TypeScript run by `node --experimental-strip-types`): `/admin-ui` and `/admin-ui/*` from `dist` with the `index.html` fallback (a missing asset is a 404) and `ADMIN_SECURITY_HEADERS` plus `ADMIN_CACHE_CONTROL`; `/admin/*`, `/store/*` and `/media/*` (uploaded images, GET and HEAD) to the API with `X-Forwarded-For` set from the TEST-ONLY `x-e2e-client` header, the API's answer passed back unchanged and no cookie added; everything else 404. Must NOT be used outside the suite.
- `prepare-database.ts` - wipes a `*_e2e_test` database (refuses any other name), runs the API's built migrate, seed and create-admin (the owner). Also wipes and creates the temp upload directory `ADMIN_E2E_MEDIA_DIR`. Must NOT touch any other database or directory. `global-setup.ts` - creates the manager and the viewer through the users API with the owner's session. `global-teardown.ts` - removes the temp upload directory.
- `support/env.ts` - ports, the three throwaway admins, `requireE2eDatabaseUrl`, `apiEnvironment` (every behavioural variable of the API process, `SHIPPING_PROVIDERS_ENABLED=fake`, `EMAIL_PROVIDER=fake` with `EMAIL_FROM` and `STOREFRONT_PUBLIC_URL`, and the `MEDIA_*` ones included: a temp `MEDIA_DIR`, `MEDIA_PUBLIC_BASE_URL` on the proxy origin), `ADMIN_E2E_MEDIA_DIR`, `clientMarker`. `support/images.ts` - the files the upload scenarios send, made in code (a PNG built from chunks, a tiny JPEG and WebP as base64, an EXIF block spliced into the JPEG, an SVG with a script, text renamed `.jpg`, a buffer of zeros). `support/payments-db.ts` - inserts a succeeded payment (and its journal row) into the e2e database for the payments scenarios; the only place the suite writes SQL besides `prepare-database.ts`. `support/api.ts` - `AdminApi` (sign-in and plain requests with the CSRF header, users) and `StoreApi` (register, sign-in, cart, a guest order with an `Idempotency-Key`) for setup and checks only. `support/fixtures.ts` - the `test` object (per-test client marker, `signIn`, `openAs`, `owner`, `shopper`, `apiContext`, `unique`) and `Guard` (on every browser context: same-origin `/admin-ui` and `/admin` requests and image loads of `/media` only, CSRF on every write, no CSP violation, no console or page error except the ones a scenario names with `expectConsoleErrors` (only the broken route chunk of `serving`), no problem `detail` in the page's text).
- `tests/*.e2e.ts` - the scenarios: `sign-in`, `roles`, `serving`, `dictionaries`, `product`, `orders`, `customers`, `users`, `session`, `keyboard`, `media-upload` (product Media tab, refused files, the focus staying on the upload control during and after an upload, viewer, brand logo, served headers, `/media` 404s), `payments` (the payment panel, the refund dialog with its confirmation and keys, closing an attention item, the attention list with Load more; payment rows are inserted into the e2e database, no provider is loaded), `email` (status, a test mail, the list with filters, the detail, a resend after a confirmation, the sandboxed preview and its CSP, the test-send limit; the API runs with `EMAIL_PROVIDER=fake`), `privacy` (privacy plan step 12: lookup by email, a JSON export downloaded as a file, the blockers of an open order, the erase dialog and its typed word, the erased order label, the audit log with filters and load more, the manager's missing area and 403), `shipping` (methods, carriers and the waybill flow against the fake carrier; the API runs with `SHIPPING_PROVIDERS_ENABLED=fake` and every scenario ends by switching all methods off). They assert what an admin sees; they never import code from `src` (the guard reads `src/messages/*` as data).
