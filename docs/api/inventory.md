# API: inventory

Admin stock endpoints and the reservation domain service. Model and decisions: `docs/adr/0011-money-and-stock-model.md`, `docs/adr/0012-pricing-inventory-schema.md`, plan `docs/plans/2026-10-16-pricing-and-inventory.md`. Pure stock rules (what a change may do): `packages/core/src/inventory` (`docs/files/core.md`).
Conventions shared with the catalog (session cookie, CSRF header, problem+json, ids, timestamps, pagination): `docs/api/catalog.md`. Source of truth for routes and schemas: `docs/api/openapi.json`. No feature flag: inventory is core.
Prices are in `docs/api/pricing.md`. The public availability status and the store price fields are in the Store section of `docs/api/pricing.md`.

## Model in short

- Per-variant flags `trackInventory` (default `true`; `false` for variants of a product type with `requires_shipping = false`, set when the variant is created) and `allowBackorder` (default `false`). An untracked variant has no stock to count and is never reserved.
- Stock lives in a level per variant and location: `onHand` and `reserved`; `available = max(0, onHand - reserved)`. Reserved never exceeds on hand unless the variant allows backorder, and never exceeds 1 000 000 000 (the same bound as `onHand`; reserving beyond it is refused with `reserved_out_of_range`).
- Every change of `onHand` is a row in the append-only `stock_movement` journal (`kind`: `receipt`, `adjustment`, `sale`, `return`), written in the same transaction as the level change, with `onHandAfter`, the acting admin (`actorId`), `reason` and `reference`. Nothing in the code updates or deletes a journal row.
- Quantities and locations are admin-only. They never appear in a `/store/*` response; the store shows only the status `in_stock`, `low_stock` or `out_of_stock` (`docs/api/pricing.md`, Store).
- Locations: one default location `main` is created by the migration. Locations are read-only in the API for now.

## Endpoints

Permissions: `GET` needs `catalog.read`; `POST` needs `catalog.write` (`owner`, `manager`; `viewer` reads only). State-changing requests need the CSRF header. The acting admin is the signed-in user of the session; it is never read from the body.

| Endpoint | Auth | Purpose | Request | Response | Errors | Flag |
|---|---|---|---|---|---|---|
| `GET /admin/locations` | admin | List the stock locations, ordered by code | none | 200 `{items: [{id, code, name, isDefault}]}`; exactly one is the default | 401, 403 | - |
| `GET /admin/products/{id}/variants/{variantId}/inventory` | admin | Stock flags and levels of a variant per location | path `id`, `variantId` | 200 `{variantId, trackInventory, allowBackorder, levels: [{locationId, locationCode, onHand, reserved, available}], totalAvailable}`; `levels` only holds locations with a level row, so a variant that never had stock shows `[]` and `0`; a read creates nothing; `totalAvailable` is the sum of `available` whatever the flags say | 400 (malformed id), 404 (unknown product, unknown variant, variant of another product) | - |
| `POST /admin/products/{id}/variants/{variantId}/inventory/adjustments` | admin | Receive, count, return or write off stock: change `onHand` by a delta or set it, with a journal row | body (strict) `kind` (`receipt`, `adjustment`, `return`; `sale` is only written by a reservation commit), exactly one of `delta` (signed whole number) and `setOnHand` (counted quantity), optional `locationId` (default: the default location), `reason` (max 500), `reference` (max 255); empty text means none | 201 `{level: {locationId, locationCode, onHand, reserved, available}, movement: {id, variantId, locationId, locationCode, kind, delta, onHandAfter, reason, reference, actorId, createdAt}}`. The level row is created by the first accepted change | 400 `validation_failed`: body shape (`kind` `required` or `invalid_value`, `delta_or_set_on_hand` when both or neither are sent, `unknown_field`, `too_big`, `invalid_type`), `delta` or `setOnHand` `invalid_quantity` (not a whole number) or `on_hand_out_of_range` (result above 1 000 000 000), `locationId` `invalid_reference` (unknown location); 404; 409 `rule_violation` with `rule` = the core reason: `negative_on_hand` (result below 0, also a negative `setOnHand`), `below_reserved` (a change that lowers `onHand` below the reserved units; release the reservations first. A change that raises `onHand` is always accepted, even while the result stays below the reserved units, so a receipt smaller than a backorder is allowed and the backorder shrinks step by step), `no_change` (delta 0 or the same quantity), `kind_requires_increase` (a `receipt` or `return` that lowers stock). A refused change leaves no level row and no journal row | - |
| `GET /admin/products/{id}/variants/{variantId}/inventory/movements` | admin | The stock journal of a variant, newest first | path ids, `limit` (1 to 100, default 50), `offset` | 200 `{items: [movement], total, limit, offset}` (movement as above) | 400 (ids, paging), 404 | - |

Variant flags are written by the variant routes (`docs/api/catalog.md`): `POST` and `PATCH /admin/products/{id}/variants[/{variantId}]` accept `trackInventory` and `allowBackorder`; every admin variant response shows both.

Notes:

- **Locking.** An adjustment is one transaction: product row lock (the lock publishing, variant edits and price writes take), then `SELECT ... FOR UPDATE` of the level row, then the core decision, the level update and the journal row. The order is always product, then level. A first change for a variant and location inserts the level row `ON CONFLICT DO NOTHING` and then locks it, so parallel first receipts create one row and all of them count.
- **Journal order.** `created_at` of a journal row is taken when it is written under the level lock (`clock_timestamp()`), so parallel writers appear in the order they held the lock and `onHandAfter` is a running sum when sorted by time (ties broken by id).
- **Actor.** `actorId` is the admin user of the session. If that user is deleted later the journal row stays and `actorId` becomes `null` (ADR 0012). A change made by the system without an admin user (the demo seed, `InventoryService.adjust(..., null)`) has `actorId` `null` from the start; no HTTP route can do that.
- **Deleting a product** that was never published removes its levels, journal and reservations with its variants (cascade, ADR 0012).
- **Deleting a variant** with any journal or reservation row is refused (`409 rule_violation` `has_stock_history`, ADR 0013): switch it off instead. A variant with only prices or an empty level can still be deleted.

## Reservation domain service (no HTTP route)

`ReservationsService` (`apps/api/src/inventory/reservations/`, exported by `InventoryModule`) holds, releases, sells and expires reservations. There is deliberately no route: the cart and checkout plan will call it (each operation is its own transaction). Every operation takes the level row lock first (`SELECT ... FOR UPDATE`), then the reservation row lock when it works on an existing reservation; it asks the core decision (`decideReserve`, `decideRelease`, `decideExpire`, `decideCommit`) and writes the level, the reservation status and, for a commit only, the `sale` journal row. Refusals are returned as `{ok: false, reason}`, never thrown; a thrown error is a bug or damaged data.

| Operation | Purpose | Result |
|---|---|---|
| `reserve({variantId, locationId?, quantity, expiresAt, reference?})` | Hold `quantity` units (1 to 1 000 000) at a location (default: the default location) until `expiresAt`, a `Date` the caller chooses. Raises `reserved`; writes no journal row | `{ok: true, reservation}` or `{ok: false, reason}` with `invalid_quantity`, `not_tracked` (the variant has no stock to hold: the caller skips the reservation and sells it freely), `insufficient_stock` (also when the variant has no level row), `reserved_out_of_range` (the reserved total would pass 1 000 000 000; only reachable with backorder), `variant_not_found`, `variant_not_sellable`, `location_not_found`. Nothing is written on a refusal. An invalid `expiresAt` throws `RangeError` (a caller bug) |
| `release(reservationId)` | Give the held units back (cancelled cart or order). Lowers `reserved`; status `released`; no journal row | `{ok: true, reservation}` or `reservation_not_found`, `not_active`, `already_committed`, `level_inconsistent`, `invalid_quantity` |
| `commit(reservationId, {actorId?, reference?})` | Sell the held units: lowers `onHand` and `reserved`, status `committed`, appends the `sale` movement (`delta` = minus the quantity, `reference` = the option, else the reservation's own reference, `actorId` = the option or none; it must be an existing admin user id). The expiry time is not checked: an overdue reservation that `expireDue` has not swept yet can still be sold | `{ok: true, reservation}` or the refusals of `release` plus `insufficient_stock` (backordered units that are not on hand yet; the reservation stays active) |
| `expireDue(now, {limit?})` | Expire the active reservations with `expires_at <= now` (`now` is an argument, the service never reads the clock), oldest first, at most `limit` (1 to 10 000, default 500) per call. Each reservation is its own transaction. Lowers `reserved`; status `expired`; no journal row | `{scanned, expired, skipped, failures: [{reservationId, reason}], nextCursor}`. `skipped` counts reservations a commit or release finished first. A reservation it cannot expire (damaged data) is listed in `failures` and the others still run; callers must alert on `failures`. The due list is ordered by `(expires_at, id)`. `nextCursor` is `null` when the call looked at fewer than `limit` reservations (stop), else an opaque `{expiresAt, id}` (the last reservation looked at). Loop: `after = undefined; do { r = expireDue(now, {limit, after}); after = r.nextCursor } while (after !== null)`. Passing `nextCursor` back as `after` moves past damaged reservations, so the loop ends even if `limit` or more of them sit at the head; without `after` they come first on every call. A malformed `after` throws `RangeError` |

`variant_not_sellable` (decided here): the variant cannot be bought by the one core rule `isVariantSellable` that the store lists by: its product is `active`, the variant is active and it has a price in `SHOP_CURRENCY`. So an active variant of a live product without a shop price (the store hides it) is refused too. It is checked before any stock rule, so checkout can use it as "this line is no longer for sale". The variant row is read `FOR SHARE` in the reservation transaction, so a flag or activity change (a `PATCH` of the variant) or a variant delete waits for a reservation in progress. A product unpublished a moment after the read can still get that reservation; checkout validates again before payment.

Concurrency rules the tests prove: parallel reservations of the last unit give exactly one winner; `reserved` always equals the sum of the active reservations of the level and never exceeds `onHand` without backorder; `onHand` never goes below 0; commit, release and expire of one reservation are mutually exclusive (one wins, the others get `already_committed` or `not_active`); with backorder allowed reserving beyond `onHand` works but commit refuses (`insufficient_stock`) until the stock arrives; receipts may arrive in parts, and as soon as `onHand` covers one reservation that reservation can be committed, one by one. One reservation holds one location; spreading an order over several locations is for the checkout plan.
