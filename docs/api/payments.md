# Payments

Online payments (ADR 0032, `docs/plans/2026-10-26-payments-monobank.md`). Core, no feature flag: providers are selected by `PAYMENT_PROVIDERS_ENABLED` (`docs/contracts/config.md`); with none enabled the webhook route answers `404`, a store create is `409 rule_violation payment_not_available`, the admin reads still work and job 11 does nothing. Built: the payment service, the webhook route and job 11 (plan step 5), the Monobank plugin (step 7), the store and admin routes (step 8). The storefront pay step and return page (step 9, `apps/storefront/README.md`, "Online payment") and the admin payment panel, refund dialogs and attention list (step 10, `apps/admin/README.md`, "Payments") are built. Source of truth for the shapes: `docs/api/openapi.json`.

## Endpoints

| Endpoint | Auth | Purpose | Request | Response | Errors | Flag |
|---|---|---|---|---|---|---|
| `POST /store/orders/payments` | public (guest number + access token in the body), store CSRF header | Start the online payment of a guest order | header `Idempotency-Key` (UUID, required); strict body `{number, accessToken, provider?, locale?}` (no amount: the server uses the order total) | `201 {paymentId, status, redirectUrl, expiresAt}`; `200` same body for a replay of the key | `400` (body, key, locale), `404` (unknown or malformed number, wrong or expired token, a customer's order: one identical answer), `409 rule_violation` (`order_not_payable`, `payment_in_progress`, `payment_window_too_short`, `payment_not_available`), `409 idempotency_key_reused` (same key, another provider), `429` (`paymentCreate`), `503 payment_provider_unavailable` + `Retry-After` + `payment {paymentId, status, canRetry}` | `PAYMENT_PROVIDERS_ENABLED` |
| `POST /store/orders/payments/status` | public (guest number + access token), store CSRF header | One attempt's state for the return page | `{number, accessToken, paymentId}` | `200 {paymentId, status, failureCategory, expiresAt, orderStatus, canRetry}` | `400`, `404` (as the lookup; also an attempt of another order), `429` (`paymentStatus`) | - |
| `POST /store/account/orders/{number}/payments` | customer session, store CSRF header | As the guest create, for an own order | `Idempotency-Key`; optional strict body `{provider?, locale?}` | as the guest create | `400`, `401`, `404` (another customer's order, a guest order, unknown number), `409`, `429` (`paymentCreate`), `503` as above | `PAYMENT_PROVIDERS_ENABLED` |
| `GET /store/account/orders/{number}/payments/{paymentId}` | customer session | As the guest status | - | as the guest status | `400`, `401`, `404`, `429` (`paymentStatus`) | - |
| `GET /admin/orders/{id}/payments` | admin `orders.read` | The payment attempts of an order | - | `200 {items: AdminPayment[]}` (oldest first; the same view as `payments` of `GET /admin/orders/{id}`) | `400`, `401`, `403`, `404` | - |
| `POST /admin/orders/{id}/payments/{paymentId}/refunds` | admin `payments.refund` (owner, manager), CSRF | Full or partial refund | header `Idempotency-Key` (UUID, required); strict `{amount: {amount, currency}, note}` (note trimmed, 1 to 500) | `202 {refund, payment}` (refund `succeeded`, `processing`, `failed`, `requested` or `unknown`); `200` same for a replay of key and body | `400` (body, key, `currency_mismatch`), `401`, `403`, `404` (unknown payment or another order's), `409 rule_violation` (`refund_not_allowed`, `refund_exceeds_remaining`, `partial_refund_not_supported`), `409 idempotency_key_reused`, `429` (`paymentRefund`, per admin) | - |
| `POST /admin/orders/{id}/payments/{paymentId}/resync` | admin `orders.write`, CSRF | Read the provider's status now | - | `200 AdminPayment` | `400`, `401`, `403`, `404`, `409 rule_violation payment_not_available` (its provider is not enabled), `429` (`paymentResync`, per admin), `503 payment_provider_unavailable` + `Retry-After` | - |
| `GET /admin/payments?needsAttention=&limit=&cursor=` | admin `orders.read` | Payment attempts newest first; `needsAttention=true` is the attention list | strict query (`needsAttention` `true`/`false`, `limit` 1 to 100, default 20, `cursor` = `nextCursor`) | `200 {items: [{orderId, orderNumber, payment}], limit, nextCursor}` | `400` (misspelt filter, damaged cursor), `401`, `403` | - |
| `POST /admin/payments/{paymentId}/attention/clear` | admin `payments.refund`, CSRF | Close an attention item (journaled with the admin) | no body | `200 AdminPayment` (`needsAttention` false, `attentionCode` kept; unchanged when nothing was open) | `400`, `401`, `403`, `404` | - |
| `POST /webhooks/payments/{provider}` | the provider's signature (no session, no CSRF) | A payment provider's status notification | the provider's own JSON (`Content-Type: application/json`), at most 64 KiB, its signature header (Monobank `X-Sign`; the test-only `fake` provider `x-fake-signature`) | `200` empty body once recorded, also for a duplicate and for a payment we do not know | `400` (signed but unreadable), `401` (missing or invalid signature; no detail, nothing stored), `404` (provider not enabled), `413`, `415` (not JSON), `429` (limit `paymentWebhook`, 300 per minute per address), `503` (not recorded; the provider retries) | `PAYMENT_PROVIDERS_ENABLED` |

The webhook route is in `openapi.json` (it is part of the public surface, ADR 0032 decision 18) with a free-form object body: the body is the provider's format, never ours. Every store payment answer, errors included, is `Cache-Control: no-store` (as the order routes); every admin answer too.

## Store routes (ADR 0032 decisions 6 and 14)

- **Ownership** exactly as the order lookup and cancel (ADR 0023): a guest opens the order with the number and the access token in the POST body (never in a URL); a customer through the session, the owner filter in SQL. Every miss is the same `404`; nothing is created and no provider is called.
- **Never trusts the client:** the amount and currency of an attempt are the order total read under the order lock; the bodies are strict (`amount`, `currency`, `returnUrl` or any other member is a `400`); the return and webhook URLs come from `STOREFRONT_PUBLIC_URL` only (forged `Host`, `X-Forwarded-Host` and `Forwarded` are ignored).
- **Shopper statuses** (core `shopperPaymentStatus`): `waiting` (`awaiting_customer`: the provider page is open; `redirectUrl` is given only then), `processing` (`creating`, `processing`, `create_unknown`), `paid` (`succeeded` and the order took it), `failed` with `failureCategory` `declined` (the provider reported a failed payment), `technical` (no invoice was made, or a lost create was closed) or `not_accepted` (a success the order could not take: late, duplicate or amount mismatch; refunded or settled by the shop), `expired` (`expired`, `invalidated`; category `expired`). Never a provider status, code, id, card or text.
- **`503 payment_provider_unavailable`:** `payment.canRetry` true (the provider refused, throttled us or nothing was sent: the attempt is `failed`; `Retry-After` is the provider's or 30 s) or false (the answer was lost: `create_unknown`, never retried; a new attempt is refused `payment_in_progress` until job 11 closes it at its invoice end, so `Retry-After` is the time until then, at least 30 s; meanwhile a webhook may still pay the order: read the status instead).
- **Status reads** (`PaymentReadsService`): while the attempt is live and has a provider id, the route reads the provider when this process did not read it in the last 10 s (`PAYMENT_LIMITS.statusReadMinAgeSeconds`); concurrent calls share one read; the read is applied like a webhook (`source` `poll`, so a success pays the order) and does not move job 11's schedule; a failed read answers what the shop knows (`200`). A final attempt is never read.
- **Order views:** `POST /store/orders/lookup|cancel` and `GET /store/account/orders/{number}` carry `payment: {canPay, providers, latest}` (`docs/api/orders.md`).

## Admin routes (ADR 0032 decisions 11, 13 and 18)

- **Permissions:** reads `orders.read`, resync `orders.write` (decision 18), refunds and the attention clear `payments.refund` (owner and manager, never the viewer). `x-fluxkit-permission` in `openapi.json` names each.
- **Admin payment view:** id, provider code and id, status, amount, final amount, refunded and refundable amount (the amount less every refund that is not `failed`, for a `succeeded` attempt), provider status and time, failure code, order outcome, attention flag and code, card (`{system, last4}` only), creator, invoice end, times, next reconcile check, refunds (amount, status, reason, note, admin, failure code) and the journal (status changes, provider facts with `applied`, admin actions with `action` `attention_cleared`; the refund send claims are left out). Never the page URL, an idempotency or dedupe key, the reconcile counter or provider text.
- **Refund:** the payment must belong to the order in the path (else `404`); `requestAdminRefund` under the payment row lock (the cumulative limit holds for concurrent admins), then `sendRefund` once after commit with no transaction open; the answer shows the refund as the provider left it. A lost answer is `unknown` (it keeps its amount reserved and is settled from the provider's refund list by job 11, never resent); `rate_limited` leaves it `requested` for job 11; a refused refund is `failed` with its code and attention, and frees its amount. A replay of the same key and body (any admin) answers the same refund with `200` and sends nothing; the same key with another payment, amount, currency or note is `idempotency_key_reused`. A refund never changes the order status.
- **Resync:** one `getPayment` (10 s), applied like a webhook without moving job 11's schedule; an attempt without a provider id has nothing to read (`200` as stored).
- **Attention clear:** `needs_attention` false, the code kept, an `admin` journal row with the admin id (dedupe key `admin:attention-cleared:<code>:<uuid>`). ADR 0032 named a `note`; the journal has no note column, so the route takes no body (no schema change in step 8).

## Webhook route (ADR 0032 decision 12)

- **Raw body.** The app factory mounts a reader on `/webhooks/payments` only, BEFORE Nest's JSON parser: it keeps the exact bytes (at most 64 KiB, `413` by `Content-Length` or as they arrive), so no other route keeps its raw body and the JSON parser skips the request. Nothing parses the body before the provider port verified the signature over those bytes (`verifyWebhook({headers, rawBody})`, 10 s limit); a body re-serialized after parsing never verifies.
- **Steps.** Provider not enabled: `404`. Not JSON: `415`. Invalid or missing signature: `401` and a warning naming the provider only. Verified: the fact goes through the fact application below in ONE transaction with the dedupe key `webhook:<sha256 of the raw body>`; `200` with an empty body (also a duplicate, and a fact about an attempt we do not know: logged, a retry would not help). A failure to record answers `503` with `Retry-After` so the provider sends it again (Monobank retries up to 3 times, M9).
- **No CSRF, no session, no CORS change.** The route is outside `/store` and `/admin`, whose guards do not apply; the caller is the provider's server, so no browser origin is involved. The edge proxy needs a `/webhooks` route next to `/store`, `/admin`, `/media` that passes the body unchanged (decision 17; plan step 11 adds it to the e2e proxies and the README).
- **No outbound call** on this path except what the plugin needs to verify (Monobank: a public key refetch, at most once per 60 s). Automatic refunds are sent by job 11, never here.
- **Logs** carry the provider code, the payment ids and codes; never the body, a header, a signature, a token or card data.

## Service behaviour (`apps/api/src/payments/`)

- **Only a verified fact pays** (decision 7): a webhook whose signature verified, or a status read job 11 made with the shop's credentials. Never a redirect, a query parameter or a client-sent amount.
- **Fact application** (`PaymentFactsService.applyProviderFact`): finds the attempt by the provider's id, else by our reference (the attempt id; this binds a `create_unknown` attempt); locks the order row, then the attempt (ADR 0015 order); a dedupe key already journaled is a duplicate and changes nothing; core `bindFact` (provider id, reference, amount, currency, final amount): a fact that does not bind is journaled `applied = false`, raises attention (`amount_mismatch`, `fact_not_bound`) and never pays; core `normalizeProviderFact` orders facts by the provider's `modifiedAt` (an older one is journaled unapplied; `succeeded` never moves back). Entering `succeeded` calls `OrdersService.markPaidIn` in the same transaction with the reference `<provider>:<providerPaymentId>`, and core `decideOrderOutcome` stores `order_outcome`:

| `markPaidIn` answer | Result |
|---|---|
| ok | `applied`; `order.paid` written by the order |
| ok, already paid with this reference | `already_paid` |
| `order_not_payable` (expired, cancelled, stock no longer held) | attention `late_payment`; a full refund queued `requested` (reason `late_payment`) |
| `payment_reference_conflict` (paid by another attempt or by hand) | attention `duplicate_payment`; a full refund queued (reason `duplicate_payment`) |
| `amount_mismatch` | attention `amount_mismatch`; no automatic refund (an admin decides) |

- When a success pays the order (`applied`), every other `awaiting_customer` attempt of the order is closed `invalidated` in the same transaction (job 11 invalidates its invoice), so an open page cannot take a second payment.
- Our refunds listed in a fact are settled by our refund id (core `decideRefundFromFact`); `reversed` after a success not explained by our own refunds raises `external_reversal`; a status the plugin does not know raises `unknown_provider_status`. Attention keeps the first open code (the journal keeps every fact).
- **Create flow** (`PaymentCreateService.createPaymentForOrder({orderId, idempotencyKey, createdBy, locale?, providerCode?})`, called by the store routes after their ownership check): one transaction with the order row lock (replay by `Idempotency-Key` answers the same attempt; core `decideNewPaymentAttempt`: `order_not_payable`, `payment_in_progress`, `payment_window_too_short`, `payment_not_available` (no provider for the currency, or no `STOREFRONT_PUBLIC_URL`); every `awaiting_customer` attempt closed `invalidated`; the new attempt inserted `creating` with the order total as its amount and `expires_at` = the order deadline less 3 minutes); the provider's `createPayment` with NO transaction open and a 10 s limit (return URL `STOREFRONT_PUBLIC_URL/{locale}/payment/return?payment=<id>`, webhook URL `STOREFRONT_PUBLIC_URL/webhooks/payments/<provider>`, never from a request's `Host`; the localized description "Order <number>"; the order lines plus the shipping line when they add up to the amount, else none); then core `paymentStatusAfterCreate`: `awaiting_customer` (the page URL must be `https`, else the answer is malformed), `failed` (`rejected`, `misconfigured`, `not_sent`, `rate_limited`: the shopper may try again at once) or `create_unknown` (`unavailable`, a timeout, an error, a malformed answer: never created again; it blocks a new attempt until job 11 closes it at its invoice end). Answers `created` (`replay`), `refused` (the rule), `not_found`, or `provider_unavailable` (the attempt, `retryAfterSeconds`) for the route to map to `201`/`200`, `409 rule_violation`, `404` and `503 payment_provider_unavailable`.
- **Refunds** (`PaymentRefundsService`): `requestAdminRefund({orderId, paymentId, adminId, amount, note, idempotencyKey, now})` (the admin refund route, permission `payments.refund`): under the payment row lock, a payment of another order is `not_found`, replay by `Idempotency-Key` (another payment, amount, currency or note: `idempotency_key_reused`), core `decideRefund` with every refund of the payment (`refund_not_allowed`, `refund_exceeds_remaining`, `partial_refund_not_supported`, also under concurrency), inserted `requested`. `sendRefund(refundId, now)` sends one `requested` refund exactly once per claim (`docs/api/jobs.md`, job 11); a lost answer is `unknown` and is settled by a status read, never resent. A refund never changes the order status.
- **Writers.** `PaymentChanges` is the only writer of `payment.status` and `payment_refund.status` (core transition tables), each change with its `payment_event` journal row and its `payment.status_changed` / `payment.refund_status_changed` outbox event in the same transaction (`docs/contracts/events.md`). `OrdersService` stays the only writer of the order status.
- **Order side** (`docs/api/orders.md`): the `payment_in_progress` guards of the cancels and of the manual mark paid, and the expiry deferral of job 1 (`docs/api/jobs.md`).
- **Job 11** `reconcile-payments`: `docs/api/jobs.md`.
