# API: email

The admin side of transactional email (ADR 0031 decision 15, plan step 9 of `docs/plans/2026-10-26-email.md`): delivery status, the test send, the outbox with detail, resend and cancel, and the template list with preview. The customer routes that cause mail (password reset, email verification) are in `customers.md`; the jobs that send are in `jobs.md`; the template extension point is `docs/contracts/email-templates.md`.

Every route needs the permission `email.manage` (owner and manager; the viewer gets `403`), reads included: the outbox shows recipient addresses, which are personal data. State-changing requests need `X-Fluxkit-CSRF: 1` and, with a body, `Content-Type: application/json` (otherwise `403`, before authentication). Every response carries `Cache-Control: no-store`. Problem bodies are the common `application/problem+json` of `catalog.md`. Rule codes of `rule_violation` are in the `rule` member. Nothing here returns or logs the provider key; addresses, variables, subjects and links are never logged.

With `EMAIL_PROVIDER=none` the status, the list, the detail, the cancel, the template list and the preview still work; the test send and the resend answer `409 rule_violation` `email_not_configured` (the same code the storefront never sees: its mail routes are `404`).

## A message

`{id, templateKey, templateVersion, locale, to, recipientKind, customerId, orderId, adminUserId, status, attempts, nextAttemptAt, leaseUntil, deadlineAt, providerCode, providerMessageId, pinnedProviderCode, lastErrorCode, resendOf, createdByAdminId, createdAt, sentAt, updatedAt, canCancel, canResend}`.

- `to` is the recipient address (personal data). `recipientKind` is `customer`, `guest` or `admin` (a test send).
- `status` is `pending`, `sending`, `sent` (accepted by the provider, not delivered), `failed`, `unknown` (the provider may or may not have sent it; never retried automatically. It also covers a mail whose attempt failed after the claim but before any provider call, for example a guest order that could not be read until the deadline: the lease ran out, so the sender cannot tell; see email review F6) or `cancelled`. Codes (`lastErrorCode`, `providerCode`) are short codes, never provider text.
- `canCancel` is true while pending. `canResend` is true for a final mail that is not a `customer.*` account mail; it does not look at the provider or the template, the resend itself does.
- `variables` (detail only) is the stored template input: only the top-level keys the template declares in `displayVariables` (`docs/contracts/email-templates.md`) keep their value; every other value, every value of a `customer.*` mail and every value of a template that is not registered any more is `[redacted]` (an allowlist since email review F3; it was a key-name denylist); texts are cut to 200 characters.

## Decisions of step 9

- The test mail goes to the caller's own address only and takes the language of the request (`locale`, default `DEFAULT_LOCALE`): admins have no locale column.
- A resend of `admin.test` is allowed and goes to the resending admin's own address.
- The list pages by `limit` and `offset` like every admin list (the ADR sketched a cursor).
- The preview is a `GET` with `?locale` (the ADR sketched a `POST`): it reads nothing and writes nothing.

- `pinnedProviderCode` (nullable, additive on list/detail/cancel responses): the provider of an earlier possibly accepted attempt. Its pin survives retries/cancel. Missing pinned configuration holds the row with `pinned_provider_unavailable` and rechecks every minute up to its deadline. Restoration retries only the same provider/UUID before the original safe cutoff; at expiry it is `unknown`. A pinned terminal failure is also `unknown`; only an authoritative accepting result becomes `sent`.
- Cancelling pinned pending mail stops local retries only: an earlier attempt may still arrive and manual resend can duplicate it. The uk/en admin confirmation warns accordingly. `providerMessageId` preserves the bounded legacy or single bracketed reference verbatim (maximum 255 characters); it is separate from short error codes.

## Shared local suppressions (ADR 0056 step 1b)

- `POST /webhooks/email/{provider}` — public, provider-authenticated raw JSON (64 KiB), no session/CSRF; only selected `resend`/`brevo` with configured verifier/secret; `204` after commit (also duplicate/ignored), `401` authentication, `400` malformed/stale event (code-only operator warning), `404` unknown/inactive/no secret, `413` too large, transient local failure `429` with `Retry-After: 5` (controller/guard exceptions and raw-body middleware failures included); intentional rate limits retain their own `Retry-After`. Ingestion sets transaction-local `lock_timeout=2000` ms and `statement_timeout=5000` ms before advisory locks; failed transactions roll back for a later retry. Existing erasure wait/transaction semantics are unchanged. Both edge proxies map email-only upstream 502/503/504 to `429` with `Retry-After: 5`.
- `GET /admin/email/suppressions?limit&offset` — `email.manage`, bounded pagination, newest last-seen first; `{items:[{id,toAddress,toAddressMasked,reason,sourceProvider,firstSeenAt,lastSeenAt}],total,limit,offset}`. `toAddress` is the full normalized recipient, matching message list/detail exposure under `email.manage`. No separate reveal endpoint exists in the admin; suppressions follow the messages exposure, masked by default in the UI with a per-row show/hide button. Removal confirmation always shows the full address. No address in path/query/logs/errors/audit.
- `DELETE /admin/email/suppressions/{id}` — `email.manage`, CSRF, UUID; `204`, `400` invalid UUID/query, `401/403`, `404` missing; removal and IDs-only `email_suppression.removed` audit commit together. Receipts remain; replay cannot recreate the block. No automatic resend or remote-blocklist change.

Facts store only a normalized address, allowlisted reason/provider and event times. No soft bounce, raw body, vendor text or delivery tracking. Resend permanent `email.bounced` → `hard_bounce`, `email.complained` → `complaint`, `email.suppressed`/`suppression.added` → `blocked`; `suppression.removed` is ignored. Brevo `hard_bounce`/`spam`/`unsubscribed`/`blocked` map to `hard_bounce`/`complaint`/`unsubscribe`/`blocked`. Seven-day event age and five-minute future tolerance are separate from Resend's five-minute signed-delivery window; receipts expire after eight days via job 10. A fresh valid event can suppress again after removal.

All sends check the shared list before pacing: unpinned blocked mail becomes `failed` with `lastErrorCode=suppressed`, pinned blocked mail `unknown/suppressed`. Lookup failures defer without sending. Feedback arriving after pacing admission cannot recall that admitted/in-flight send. Public auth answers/token rules remain unchanged; auth mail has no exemption.
