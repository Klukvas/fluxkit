# Contract: configuration and feature flags

Status: draft (first version, introduced in plan step 5). Covered by SemVer (AGENTS.md section 17).

## Environment variables read by `apps/api` (validated by `@fluxkit/config` `loadEnv`)
| Variable | Required | Default | Meaning |
|---|---|---|---|
| `DATABASE_URL` | yes | - | Postgres connection string |
| `REDIS_URL` | no | - | Redis connection string (queues, cache) |
| `PORT` | no | 3000 | HTTP port |
| `FEATURES_ENABLED` | no | empty | Comma-separated optional feature names; unset means none |
| `FEATURES_DIR` | no | `<repo>/packages/features` | Where feature packages are discovered |
| `SHIPPING_PROVIDERS_ENABLED` | no | empty | Comma-separated shipping provider codes (lowercase letters, digits, underscores, starting with a letter, at most 64 characters); entries are trimmed, lowercased and de-duplicated; unset or blank means none. A malformed code, or an enabled code with no provider package or a broken one, stops the startup. The only provider in the template is the test-only `fake`; never enable it in a real shop: with `NODE_ENV=production` the startup (and every command that calls `loadEnv`) refuses `fake` (`TEST_ONLY_SHIPPING_PROVIDERS`, step 13 review fixes) |
| `PAYMENT_PROVIDERS_ENABLED` | no | empty | Comma-separated online payment provider codes (ADR 0032 decision 3 and 16, payments plan step 4); `loadEnv` returns them as `enabledPaymentProviders`. Unset or blank means none: no provider package is read, `onlinePayment` is `false` and the shop works as before (orders are paid by hand). Strict, unlike the shipping list: entries are trimmed, but each must be a code written exactly (`^[a-z][a-z0-9_]{0,63}$`, upper case is NOT folded), an empty entry (`a,,b`, a trailing comma) or a code listed twice stops the startup, naming the variable and the rule, never the entry. `monobank` is the Monobank acquiring plugin (`packages/providers/monobank`, plan step 7; needs `MONOBANK_TOKEN`, see "Variables of the payment provider packages"). `fake` is test-only (`packages/providers/_fake-payment`, it charges nothing): with `NODE_ENV=production` the startup (and every command that calls `loadEnv`) refuses it (`TEST_ONLY_PAYMENT_PROVIDERS`). With at least one provider: `ORDER_PAYMENT_TTL_MINUTES` must be at least 8 (the invoice ends 3 minutes before the order and needs 5 minutes to pay, core `PAYMENT_INVOICE_WINDOW`; a shorter time means no order could be paid online, so the startup refuses instead of running a shop whose pay button never works), in production `STOREFRONT_PUBLIC_URL` is required and must be `https`, and a provider that does not list `SHOP_CURRENCY` in its `capabilities.currencies` stops the startup (`monobank` declares `UAH`). An enabled code with no provider package or a broken one stops the startup |
| `EMAIL_PROVIDER` | no | `none` | The one email provider the API loads (ADR 0031, email plan step 4): exactly `none`, `resend` or `fake`; trimmed, lower case, blank counts as unset, anything else stops the startup naming the variable. `none` loads no provider package and no mail is sent (`emailDelivery` is `false`). `fake` is test-only (it delivers nothing): with `NODE_ENV=production` the startup (and every command that calls `loadEnv`) refuses it (`TEST_ONLY_EMAIL_PROVIDERS`). `resend` is the Resend plugin (`packages/providers/resend`, plan step 6; needs `RESEND_API_KEY`). With `none` the password reset and email verification routes answer `404`, and a start with `NODE_ENV=production` logs one warning (customers cannot reset passwords) |
| `EMAIL_FROM` | when `EMAIL_PROVIDER` is not `none` | none | The sender: `Display Name <local@domain>` (the name may be in double quotes) or a bare address; the display name is the shop name in mail. At most 200 characters, ASCII dot-atom address with a domain of two or more labels, no CR, LF, NUL or other control or bidi character, no `"`, `<`, `>` or `\` inside the name, one mailbox only. Checked whenever it is set, so a typo is found at boot; the same rules as core `parseMailbox` (a spec compares them). Errors name the variable, never the value |
| `EMAIL_REPLY_TO` | no | none | One mailbox, same rules as `EMAIL_FROM` |
| `STOREFRONT_PUBLIC_URL` | when `EMAIL_PROVIDER` is not `none` or `PAYMENT_PROVIDERS_ENABLED` names a provider, and `NODE_ENV` is `production` | `http://localhost:3001` when `NODE_ENV` is not `production` | Also read by the API (the storefront reads it too, same variable and origin format, `loadStorefrontEnv`): the ONLY base of every link in a mail, never a request's `Host` or `X-Forwarded-Host`. An `http(s)` origin without path, query, fragment or credentials (a trailing slash is dropped). With an email provider configured in production it must be `https`; likewise with a payment provider in production (the base of the return address `/{locale}/payment/return` and the webhook address `/webhooks/payments/<provider>`, payments plan step 5; the check exists since step 4); with neither the API only checks the format |
| `DEFAULT_LOCALE` | no | `uk` | Locale every translated text must contain; must be in `LOCALES` |
| `LOCALES` | no | `uk,en` | Comma-separated locales accepted in translated texts; lowercase codes (2 to 8 letters, optional `-` segments), no duplicates |
| `ADMIN_COOKIE_SECURE` | no | `true` | `Secure` flag of the admin session cookie. Exactly `true` or `false` (anything else, including an empty value, fails startup); `false` only for local plain-HTTP development |
| `ADMIN_SESSION_IDLE_MINUTES` | no | `720` | Admin session ends after this many idle minutes. Positive whole number, at most 525 600 (one year) |
| `ADMIN_SESSION_MAX_HOURS` | no | `168` | Absolute admin session lifetime in hours, even when used continuously. Positive whole number, at most 8 760 (one year) |
| `STORE_COOKIE_SECURE` | no | `true` | `Secure` flag of the customer session cookie (`fluxkit_customer_session`). Exactly `true` or `false` (anything else, including an empty value, fails startup); `false` only for local plain-HTTP development. Independent of `ADMIN_COOKIE_SECURE` |
| `CUSTOMER_SESSION_IDLE_MINUTES` | no | `43200` | Customer session ends after this many idle minutes (30 days). Positive whole number, digits only, at most 525 600 (one year) |
| `CUSTOMER_SESSION_MAX_HOURS` | no | `2160` | Absolute customer session lifetime in hours (90 days), even when used continuously. Positive whole number, digits only, at most 8 760 (one year) |
| `CART_TTL_DAYS` | no | `30` | A cart expires this many days after its last change (a customer cart too), and the guest cart cookie `fluxkit_cart` has the same `Max-Age`. Positive whole number, digits only, from 1 to 365. Its `Secure` flag follows `STORE_COOKIE_SECURE` |
| `ORDER_PAYMENT_TTL_MINUTES` | no | `30` | An order waits this many minutes for payment before it expires and gives its reserved stock back; the reservations outlive the order by a fixed 10 minutes. Whole number from 5 to 1440, digits only. At least 8 when `PAYMENT_PROVIDERS_ENABLED` names a provider (the startup refuses 5 to 7 then, naming both variables) |
| `ORDER_GUEST_ACCESS_DAYS` | no | `90` | A guest can open their order with its access token for this many days after the token was issued (a replay of the checkout renews the window). Whole number from 1 to 3650, digits only |
| `ORDER_CONTACT_RETENTION_DAYS` | no | none (off) | Days after an order closed (its fulfilment, cancellation or expiry, or its newest refund when later) before job 12 `anonymise-orders` anonymises the order's contact fields (ADR 0033 decision 8; `docs/api/jobs.md`). Unset: job 12 does nothing and a production API logs a startup warning that order contact data is kept without a retention period. With it, job 12 also deletes closed privacy requests 3 years after completion and admin audit events after 1 year (proposals for the lawyer). Whole number from 1 to 36 500, digits only. Irreversible: shortening it anonymises older orders at the next tick. TODO(fluxkit): legal review of the value per market (plan task O5) |
| `ORDER_TOKEN_SECRET` | yes (API start; `loadEnv` also in production) | none | Secret the guest order access tokens are derived from (HMAC-SHA256 over the order id and the checkout `Idempotency-Key`, ADR 0023), so a repeated checkout request gets the same token. At least 32 characters, no default, used exactly as given (no trimming); a shorter value, including an empty one, fails startup. Required whenever `NODE_ENV` is `production` (for every command that reads the environment) and by the API process in every environment. Generate with `openssl rand -base64 48`; never commit or log it. Changing it does not break tokens already handed out; the next replay of an old checkout derives a token under the new secret and the earlier one stops working (ADR 0023, operational note). Also the key of the customer password reset and email verification tokens, under its own label (ADR 0031 decision 9, email plan step 7): changing it invalidates reset and verification links not yet clicked (at most 60 minutes and 48 hours old) |
| `MAX_OPEN_ORDERS` | no | `3` | Unpaid (`awaiting_payment`) orders one customer, or one guest email (normalized, orders without a customer), may hold at once (ADR 0024). The checkout of one more is refused with `409 too_many_open_orders`; a paid, cancelled, expired or fulfilled order no longer counts; a replay of an existing checkout is answered even at the limit. Whole number from 1 to 50, digits only. It limits an email and a customer, not an IP address |
| `TRUST_PROXY` | no | `0` | Number of reverse-proxy hops in front of the API, the value of Express `trust proxy` (ADR 0024). `0` trusts none: the client is the connecting address and `X-Forwarded-For` is ignored. `n` trusts the last `n` addresses of the chain, so `request.ip` is the client the outermost trusted proxy saw. The store rate limits and the admin login limit count per `request.ip`. Whole number from 0 to 10, digits only. Set the EXACT number of hops: too high lets a client choose its own address with `X-Forwarded-For` and dodge the limits, too low keeps every shopper in the proxy's window |
| `SCHEDULER_ENABLED` | no | `true` | Whether this API process runs the scheduler (order expiry, reservation sweep, domain event delivery, cart and customer session cleanup). Exactly `true` or `false` (anything else, including an empty value, fails startup). With `false` nothing expires unless `pnpm jobs:run-once` runs (a cron): unpaid orders keep their stock reserved. `docs/api/jobs.md` |
| `SCHEDULER_INTERVAL_SECONDS` | no | `60` | Seconds between scheduler ticks. Whole number from 10 to 3600, digits only. Only one API instance works per tick (a Postgres advisory lock), so several instances do not multiply the work |
| `SHOP_CURRENCY` | no | `UAH` | The one currency the shop sells in. Exactly one of `UAH`, `USD`, `EUR`, `PLN`, `GBP`, `CZK`, `CHF`, `CAD`, `JPY`, `KWD` (upper case, the table of `@fluxkit/core`); anything else, including a lower-case code or an empty value, fails startup. An active variant needs a price in this currency to be published or switched on; prices in other currencies may be stored but are never sold or converted. **Changing it after data exists** hides every live product that has no price in the new currency: the store lists nothing for it (a list without it, a detail answering 404) while the product stays `active` in the admin. Price the variants in the new currency first (`PUT /admin/products/{id}/prices`, up to 500 prices per call), then change the setting. `pnpm seed` does not help: it never prices or stocks products that already exist |
| `PRICES_INCLUDE_TAX` | no | `true` | Whether stored prices already include tax. Exactly `true` or `false`. Only a flag for the storefront: no tax is calculated |
| `LOW_STOCK_THRESHOLD` | no | `5` | Available quantity at or below which (and above 0) a tracked variant is `low_stock`. Whole number from 0 to 1 000 000 000, digits only. Read by the API and used by the store API (`availability`: `low_stock` from 1 up to and including this threshold) |
| `MEDIA_STORAGE_DRIVER` | in production | `local` outside production | Where uploaded images are stored (ADR 0028). Exactly `local` (a directory on disk) or `none` (uploads off: URL entry only); anything else, including an empty value, a different case or an unknown driver such as `s3`, fails startup. In production the variable must be set: there is no silent fallback to local disk, and the name is checked even for commands that only read the environment (`pnpm db:migrate` and the others). **`none` is not a temporary switch once uploads exist**: with `none` the read route answers `404` for EVERY uploaded file (product images, brand logos and the `order_item.image_url` snapshots that use them) and the cleanup job does nothing; switching back to `local` serves the files again, but the cleanup job then deletes every never-attached upload older than 24 hours. Attach marking keeps working under `none` for `MEDIA_PUBLIC_BASE_URL` (its default outside production, the given value in production), so a save made meanwhile still marks the uploads it uses. Keep `local` while uploads exist (for a full disk, free space instead) |
| `MEDIA_DIR` | with `local` in production | `<repo>/var/media` outside production (git-ignored) | Absolute directory of the stored images. The value is normalized (`/srv/a/../m/` becomes `/srv/m`); a relative path, a path with a NUL byte and the file system root fail startup. With `none` it is validated when given and otherwise unset. The parser never touches the file system: the API checks at start that the directory exists and is writable (probe file) and refuses to start otherwise. Only when `MEDIA_DIR` is unset outside production do the API and `pnpm jobs:run-once` create the default directory (mode 0750) first |
| `MEDIA_PUBLIC_BASE_URL` | with `local` in production | `http://127.0.0.1:<PORT>/media` outside production with either driver (follows `PORT`); in production with `none` unset unless given | URL prefix of every stored image: the URL of an upload is `<prefix>/<key>`, and the prefix attach marking looks for (also with `none`, so set it to the old value when a production shop with uploads runs `none`; unset there, nothing is checked). An absolute `http` or `https` URL without a trailing slash, query, fragment or credentials, written in normalized form (lower-case scheme and host, no default port, no dot segments), so it can be compared with stored URLs as a text prefix; `https` is required in production. A host-only value such as `https://media.shop.example.com` is valid. **Changing it later does not rewrite stored URLs** (`media.url`, `brand.logo_url`, `order_item.image_url`): old URLs keep the old prefix, and URLs under it are no longer checked by attach marking (ADR 0028 decision 5). Error messages never repeat the value |
| `MEDIA_MAX_BYTES` | no | `10485760` | Largest accepted upload in bytes. Whole number from 1 024 to 52 428 800 (50 MiB), digits only |
| `MEDIA_MAX_PIXELS` | no | `50000000` | Largest accepted input image, width times height. Whole number from 1 to 100 000 000, digits only. The side limit (12 000 px) and the stored size (fits 4 096 px) are constants of `@fluxkit/core` `MEDIA_LIMITS`, not variables |
| `SEARCH_ENABLED` | no | `false` (`true` in `.env.example`) | Catalog search (ADR 0034, search plan step 5): exactly `true` or `false`. `false` reads no `MEILI_*` variable (not even to check it), creates no engine client, mounts no search route (every `/store/search*` and `/admin/search/*` answers `404`), writes nothing to the search tables and makes the search jobs do nothing; `search` is `false` in both config routes. `true` needs `MEILI_URL` and `MEILI_API_KEY`; the API makes no engine call at startup (the engine may start later) and logs `Search: enabled (<prefix>)` (`Search: disabled` otherwise) |
| `MEILI_URL` | when `SEARCH_ENABLED=true` | none | The engine's base URL: an absolute `http` or `https` URL without credentials, query or fragment (a trailing slash is dropped; a path prefix is kept). With `NODE_ENV=production` it must be `https` or a private address (loopback, RFC 1918, IPv6 loopback or unique local, `localhost`, or a single-label host such as the Compose service name `meilisearch`). Never sent to a browser. Also read by the integration tests (with `MEILI_MASTER_KEY`). Errors never repeat the value |
| `MEILI_API_KEY` | when `SEARCH_ENABLED=true` | none | The engine key the API uses: 16 to 256 visible ASCII characters. Create a key scoped to `<MEILI_INDEX_PREFIX>*` with the actions `search`, `documents.add`, `documents.delete`, `indexes.create`, `indexes.delete`, `indexes.swap`, `settings.update`, `settings.get`, `tasks.get`, `tasks.delete`, `stats.get` (README "Catalog search"); never the master key. A leaked key can rewrite the shop's indexes but no other index or key. Never logged, never in an error or a response |
| `MEILI_INDEX_PREFIX` | no | `fluxkit_` | Prefix of every index uid the API creates, swaps or deletes (`<prefix>catalog_<locale>` and its builds); `^[a-z][a-z0-9_]{0,31}_$` (equals core `SEARCH_INDEX_PREFIX_PATTERN`, a spec compares them). Lets several environments or tests share one engine. Blank counts as unset |
| `MEILI_MASTER_KEY` | - | - | Not read by the API: only the engine (Compose) and the integration tests use it (tests create a scoped key with it) |

Invalid values fail startup with a readable `Invalid environment: ...` error. The media variables were added by media upload plan step 3 (additive for the schema; requiring `MEDIA_STORAGE_DRIVER` in production is the one new production requirement, recorded in `CHANGELOG.md`).

`pnpm db:migrate` reads only `DATABASE_URL` (through `loadEnv`, like the other commands; no default, a missing value fails with exit code 1) and takes no arguments. It applies the migrations of `apps/api/drizzle/` forward only and never rolls back (rollbacks are the manual `drizzle/NNNN_name.down.sql` scripts). Details: `README.md` (Database migrations).

`pnpm jobs:run-once` reads the same file and variables through `loadEnv` (a malformed value fails it with exit code 1, like the API), takes no arguments, builds the application WITHOUT the timer (it ignores `SCHEDULER_ENABLED`) and runs every scheduler job once under the same advisory lock. Exit codes `0` (ran), `1` (a job failed or bad input), `2` (the lock is held by a running scheduler: nothing was run). Details: `docs/api/jobs.md`.

`pnpm admin:create` reads the same file and `DATABASE_URL` (and the locale variables) through `loadEnv`, plus one variable that only that command reads: `ADMIN_PASSWORD`, the password of the user to create (12 to 128 characters). It is not a setting of the API and is deliberately absent from `.env.example`: pass it for one command (`ADMIN_PASSWORD=... pnpm admin:create --email ...`) or type the password at the prompt instead; do not store it in `.env`. Details: `README.md` (Admin sign-in).

## Environment variables read by `apps/storefront` (validated by `@fluxkit/config` `loadStorefrontEnv`)
The storefront reads only these (and `NODE_ENV`); it never needs the API's variables or secrets. `next dev` and `next start` also read the repository's root `.env` (the same file as the API; variables set in the shell win), `next build` reads only `STOREFRONT_IMAGE_HOSTS` (for the `Content-Security-Policy` headers) and never calls the API. Invalid values fail startup with a readable `Invalid storefront environment: ...` error that names the variable and never shows its value. Added by storefront plan step 3 (additive: new optional contract surface).

| Variable | Required | Default | Meaning |
|---|---|---|---|
| `API_INTERNAL_URL` | yes, for `next dev` and `next start` | - | Where the Next server reaches the API: server-side catalog fetches and, in `next dev` only, the `/store/*` rewrite. An `http` or `https` origin without path, query, fragment or credentials (a trailing slash is dropped), for example `http://127.0.0.1:3000`. Not used by the browser, which calls `/store/*` on its own origin |
| `STOREFRONT_PUBLIC_URL` | in production | `http://localhost:3001` when `NODE_ENV` is not `production` | The public origin of the storefront, for canonical URLs, hreflang, the sitemap and JSON-LD. Same format as `API_INTERNAL_URL`. A blank value counts as unset, so it is required (and rejected when missing) when `NODE_ENV` is `production` |
| `STOREFRONT_IMAGE_HOSTS` | no | empty | Comma-separated host names allowed for image optimisation and `img-src` (for example `cdn.example.com,images.example.org`); trimmed, lower-cased, de-duplicated. Host names only: a scheme, port, path, wildcard, empty entry or invalid label fails startup. Read twice: by `next build` (the `Content-Security-Policy` headers are stored in the build output, so changing the CSP list needs a rebuild) and again by `next start` (the image optimizer's allow-list and the pages' own check); set it identically for both |
| `STOREFRONT_REQUIRE_LEGAL_TEXT` | no | unset | Read by `next build` only. `true` makes a production build REFUSE while a `legal.*` message of any language still carries the placeholder marker `TODO(fluxkit): replace with the shop's own legal text`, naming each file and key; any other value or unset: no check (master ships placeholders). For a client fork's release build; the check fails closed when it is asked for and the messages cannot be read. Privacy plan step 10 (additive: a new optional build variable; the legal identity and the cookie table are code configuration in `apps/storefront/src/config/legal.ts`, not variables) |
| `STOREFRONT_FORWARD_CLIENT_ADDRESS` | no | `false` | Read by `next start` (and `next dev`), per request. Exactly `true` or `false` (blank is unset; any other value fails startup, naming the variable). `true`: the search results page passes the page request's `X-Forwarded-For` on to `GET /store/search`, after the check of `forwardableAddresses` (a well-formed chain of at most 10 IP addresses, else nothing), so the API's per-address `search` window counts shoppers. Only for a storefront reachable through the edge proxy alone, which sets or replaces that header on page requests: a client reaching `next start` directly would otherwise choose its own rate-limit key. `false` or unset: no request header is read and every results page counts as the Next server's address (one shared window). `infra/production.env.example` sets `true`. Search UI review F1, ADR 0038 (additive: a new optional variable; the forwarding was unconditional before) |

The `/store/*` rewrite in `apps/storefront/next.config.ts` exists for `next dev` only (the Next phase, not `NODE_ENV`); production builds and servers never emit it. A deployed environment routes `/store/*` to the API with an edge reverse proxy that sets `X-Forwarded-For` itself and runs the API with the exact `TRUST_PROXY` hop count (ADR 0026; runtime evidence in `docs/plans/2026-10-18-storefront.md`, "Runtime test of the dev rewrite").

## Shipping provider package contract
- A shipping provider is a package under `packages/providers` whose `package.json` has `"fluxkit": { "provider": "<code>", "kind": "shipping" }` (`provider` without `kind` is an error; other kinds are ignored by the shipping loader). The folder name is irrelevant; the code matches `SHIPPING_PROVIDER_CODE_PATTERN` (`@fluxkit/core`).
- `main` (default `dist/index.js`) must export `providerModule`, a Nest module. It is imported dynamically and mounted only if `<code>` is in `SHIPPING_PROVIDERS_ENABLED`; with nothing enabled the folder is not even read.
- Inside the module, a provider class carries `@SetMetadata(SHIPPING_PROVIDER_METADATA, shippingProviderMetadata("<code>"))` and implements `ShippingProviderPort` (`@fluxkit/core`). The API finds it with `DiscoveryService` (`ShippingProviderRegistry`). Startup fails when the class is not a static provider with every port method and capability, when its `code` differs from the metadata, when two classes share a code, when an enabled provider has no marked class, or when a marked class is not enabled.
- Neither core nor `apps/api` imports a provider (dependency-cruiser `core-must-not-import-providers`, `apps-must-not-import-providers`). A provider imports `@fluxkit/core` for the port and helpers, never `apps/api`. Enabled but missing or broken provider: startup fails loudly. Disabled or deleted provider: no effect.
- At startup the registry logs one line, `Shipping providers loaded: <codes or none>`, which the CI provider matrix reads. It is a log line, not a contract of the API.
- Provider variables (an API key and so on) are read by the provider package itself with its own small parser (when its module is created, so a missing or malformed value stops the startup, naming the variable and never the value), are secrets in the environment only, and are listed below. They are not part of `loadEnv`. The test-only `fake` provider has none.
- The provider class also implements `validateSettings` (the port, plan step 7b): the admin settings route applies it after its bounded check.

### Variables of the shipping provider packages
| Variable | Package (code) | Required | Default | Meaning |
|---|---|---|---|---|
| `NOVA_POST_API_KEY` | `packages/providers/nova-post` (`nova_post`) | yes, when `nova_post` is enabled | none | The Nova Post API key (business cabinet `new.novaposhta.ua`, "Settings - Security"). 16 to 512 visible ASCII characters without spaces; missing or malformed stops the startup (`NovaPostConfigError`, the variable named, the value never shown). A secret: never logged, stored or returned; it travels only in the query of `GET /clients/authorization` (whose URL is never logged). Rotating it needs a restart |
| `NOVA_POST_ENVIRONMENT` | `packages/providers/nova-post` (`nova_post`) | no | `sandbox` | `sandbox` (`https://api-stage.novapost.com/v.1.0`) or `production` (`https://api.novapost.com/v.1.0`); unset or empty is `sandbox`, anything else stops the startup. Production must be written explicitly. No URL variable exists (no SSRF) |

## Email provider package contract
Added by email plan step 4 (ADR 0031 decision 4); `EmailProviderPort` stays internal until the first external plugin.
- An email provider is a package under `packages/providers` whose `package.json` has `"fluxkit": { "provider": "<code>", "kind": "email" }` (`provider` without `kind` is an error; other kinds are ignored by the email loader and the email kind by the shipping loader, so `fake` exists once for each kind). The folder name is irrelevant; the code matches `EMAIL_PROVIDER_CODE_PATTERN` (`@fluxkit/core`). Both loaders are the same internal scan, `loadProviderPackages({kind, ...})` in `apps/api/src/common/provider-package-loader.ts`.
- Exactly ONE provider is active, the one `EMAIL_PROVIDER` names; it is not a list and there is no failover. With `none` no package is read or imported.
- `main` (default `dist/index.js`) must export `providerModule`, a Nest module, imported dynamically and only for the selected code.
- Inside the module, a provider class carries `@SetMetadata(EMAIL_PROVIDER_METADATA, emailProviderMetadata("<code>"))` (`fluxkit:email-provider`) and implements `EmailProviderPort` (`@fluxkit/core`: `code`, `capabilities`, `send`). The API finds it with `DiscoveryService` (`EmailProviderRegistry`). Startup fails when the class is not a static provider with `send` and the capabilities, when its `code` differs from the metadata, when two classes share a code, when the selected provider has no marked class, or when a marked class is not the selected one.
- Neither core nor `apps/api` imports a provider (`core-must-not-import-providers`, `apps-must-not-import-providers`); deleting a provider folder never breaks a build, and a selected but missing provider stops the startup (`scripts/feature-matrix.sh providers-deleted`).
- At startup the registry logs one line, `Email provider loaded: <code or none>`, which the CI matrix (`providers-email-fake`, `providers-email-none`, `providers-email-resend`) reads. It is a log line, not a contract of the API. `GET /store/config` and `GET /admin/config` carry `emailDelivery: boolean` (additive; `false` for `none`).

### Variables of the email provider packages
| Variable | Package (code) | Required | Default | Meaning |
|---|---|---|---|---|

## Payment provider package contract
Added by payments plan step 4 (ADR 0032 decision 3); `PaymentProviderPort` stays internal until the first external plugin.
- A payment provider is a package under `packages/providers` whose `package.json` has `"fluxkit": { "provider": "<code>", "kind": "payment" }` (`provider` without `kind` is an error; other kinds are ignored by the payment loader and the payment kind by the shipping and email loaders, so `fake` exists once for each kind). The folder name is irrelevant; the code matches `PAYMENT_PROVIDER_CODE_PATTERN` (`@fluxkit/core`). The scan is the same internal `loadProviderPackages({kind: "payment", ...})`.
- ANY NUMBER of providers may be active (a list, like shipping, not the email "one provider" rule): the codes `PAYMENT_PROVIDERS_ENABLED` names. With none no package is read or imported.
- `main` (default `dist/index.js`) must export `providerModule`, a Nest module, imported dynamically and only for the enabled codes.
- Inside the module, a provider class carries `@SetMetadata(PAYMENT_PROVIDER_METADATA, paymentProviderMetadata("<code>"))` (`fluxkit:payment-provider`) and implements `PaymentProviderPort` (`@fluxkit/core`: `code`, `capabilities`, `createPayment`, `getPayment`, `invalidatePayment`, `refund`, `verifyWebhook`). The API finds it with `DiscoveryService` (`PaymentProviderRegistry`: `get(code)`, `list()`, `onlineEnabled()`). Startup fails when the class is not a static provider with every port method and the capabilities (a non-empty `currencies` list and the four flags), when its `code` differs from the metadata, when two classes share a code, when an enabled provider has no marked class, when a marked class is not enabled, or when an enabled provider does not take `SHOP_CURRENCY`.
- Neither core nor `apps/api` imports a provider (`core-must-not-import-providers`, `apps-must-not-import-providers`); deleting a provider folder never breaks a build, and an enabled but missing provider stops the startup (`scripts/feature-matrix.sh providers-deleted`).
- Provider variables (`MONOBANK_TOKEN`) are read by the provider package itself with its own parser (when its module is created, so a missing or malformed value stops the startup, naming the variable and never the value), are secrets in the environment only, and are not part of `loadEnv`. The test-only `fake` provider reads none (its e2e hooks arrive with the e2e step).
- At startup the registry logs one line, `Payment providers loaded: <codes or none>`, which the CI matrix (`providers-payment-fake`, `providers-payment-none`, `providers-payment-monobank`) reads. It is a log line, not a contract of the API. `GET /store/config` and `GET /admin/config` carry `onlinePayment: boolean` (additive; `false` when the list is empty; a plain flag, never a provider code).

## Feature package contract
- A feature is a package under the features directory whose `package.json` has `"fluxkit": { "feature": "<name>" }`. The folder name is irrelevant.
- `main` (default `dist/index.js`) must export `featureModule`, a Nest module. It is imported dynamically and mounted only if `<name>` is in `FEATURES_ENABLED`.
- Core never imports features statically. Enabled but missing or broken feature: startup fails loudly. Disabled or deleted feature: no effect.
- Admin routes of a feature: features cannot import from `apps/api` (module boundary rule), so they use a plain `@Controller("admin/<name>")`. The API's global default-deny guard
  (`AdminPathGuard`) protects every path under `/admin` (see `docs/contracts/api.md`), so such a route answers `401` when nobody is signed in, without the feature importing anything. A plain `@Controller` has no permission metadata, so it answers `403 forbidden` to every signed-in admin: a feature route must declare its permission with `@RequirePermission` (`apps/api/src/auth/route-access.ts`) or is unusable until the extension point for features exists.
  Routes of a feature outside `/admin` are NOT guarded by the core: a feature that exposes a privileged route elsewhere owns its authorization.
