# @fluxkit/provider-nova-post

Purpose: the Nova Post shipping provider (code `nova_post`) on the new Nova Post REST API `v.1.0` (JWT), ADR 0030. It implements `ShippingProviderPort` for Ukraine: city and branch/parcel-locker lookups for the storefront picker, an informational estimate, waybill creation, find-back after a lost answer (`reconcile`), cancellation, tracking by polling and the marking label. Plan: `docs/plans/2026-10-25-nova-post-plugin.md` (every carrier fact used is cited there: spike 7a on production and its rerun, the official documentation).

- Env selection: `SHIPPING_PROVIDERS_ENABLED=nova_post`. Presence (including blank = off) selects the unchanged env Nest module. Absence delegates to explicitly activated encrypted admin credentials.
- Manifest: `"fluxkit": { "provider": "nova_post", "kind": "shipping" }` in `package.json`.
- Entry: `src/index.ts` exports `providerModule`, loaded dynamically by `apps/api` only when the code is enabled.
- Dependencies: `@fluxkit/core`, `zod` 4.6.7 (the version the workspace pins); Node 22 `fetch`. No HTTP library.
- Routes, DB tables, migrations: none (settings live in the core table `shipping_provider_setting`).
- Extension points used: the provider loader and registry (`apps/api/src/shipping/registry`), the admin settings route (`validateSettings`).

## Variables (read by this package, never by `loadEnv`)
| Variable | Rule |
|---|---|
| `NOVA_POST_API_KEY` | Required when `nova_post` is enabled; 16 to 512 visible ASCII characters without spaces. Missing or malformed: the API refuses to start, naming the variable, never the value. Never logged, stored or returned; it travels only in the query of `GET /clients/authorization`, whose URL is never logged. Create it in the business cabinet `new.novaposhta.ua`, "Settings - Security" (issued to a natural person). Rotating it needs a restart. |
| `NOVA_POST_ENVIRONMENT` | `sandbox` (default when unset or empty, `https://api-stage.novapost.com/v.1.0`) or `production` (`https://api.novapost.com/v.1.0`); anything else stops the startup. Production must be written explicitly. There is no URL variable. The provider logs its environment once at startup. Note: Nova Post says sandbox keys for Ukrainian accounts are "currently not supported". |

## Settings (the sender profile, `PUT /admin/shipping/providers/nova_post/settings`)
Validated by `validateSettings` (unknown keys refused): `senderName` (1 to 100 characters, at least two words), `senderPhone` (`380` + 9 digits), optional `senderEmail`, optional `senderCompanyTin` (8 to 20 digits) with `senderCompanyName` (both or neither; a legal entity), `senderDivisionId` (the integer division id where parcels are handed in, from `GET /divisions`, never `externalId`), `payerDefault` (`Sender` or `Recipient`, used by the estimate), optional `payerContractNumber` (2 to 20 characters, non-cash payment by the sender), `defaultParcel` (`weightGrams`, `lengthMm`, `widthMm`, `heightMm`, positive integers; used by the estimate). Example: `{"senderName": "Іван Петренко", "senderPhone": "380501234567", "senderDivisionId": 12345, "payerDefault": "Recipient", "defaultParcel": {"weightGrams": 1000, "lengthMm": 300, "widthMm": 200, "heightMm": 100}}` (placeholder values).

## What each operation does
| Port | Nova Post | Notes |
|---|---|---|
| `searchCities` | `GET /settlements?countryCodes[]=UA&textSearch=&limit=` | `Accept-language` `uk` or `en` (without it names are Latin); region = "district, oblast" |
| `listPickupPoints` | `GET /divisions?settlementIds[]=&divisionCategories[]=&limit=100&page=` | `branch` = `PostBranch` + `CargoBranch`, `locker` = `Postomat`; `PUDO` not offered; points that do not issue skipped; the first branch and locker pages together, then branches first, at most 15 pages per call, 4 in flight, and a time budget: no page is started after 3.5 s from the call's start (a JWT included) and a page still in flight at 4.5 s is abandoned, both below the API's 5 s lookup limit; a cut list answers the points read and is logged (see Limits) |
| `findPickupPoint` | `GET /divisions?ids[]=<id>` | undocumented filter (observed); anything but exactly that division throws (never another point) |
| `estimate` | `POST /shipments/calculations` | pickup points only, UAH shops only (the answer names no currency); sum of `services[].cost` in hryvnias; never answered `200` in the spike: unverified |
| `createWaybill` | `POST /shipments` | inline sender (settings) and recipient (order; a name of fewer than two words is refused without a call), `clientOrder` = order number, one parcel, declared value in whole hryvnias rounded up; pickup points only (an address is `not_supported`); **never repeated** (no idempotency); a `422` naming a field of the request is `rejected`, a `422` naming none (how production dressed a server error on the print route) is `unavailable` (the API's `unknown` + reconcile); when the JWT authorization fails before the `POST`, the failure carries `not_sent` and the API settles the shipment `failed` (nothing left) |
| `findWaybill` | `GET /shipments?limit=100&page=` | newest first; `clientOrder` + `createdAt` inside the window; at most 10 pages, then a failure (never `null`); a list that changes while it is read (another `total` or `last_page`, another page than asked for, a row seen twice) is `unavailable` `list_changed` (offset paging over a live list can hide a row); two matches: `rejected` |
| `cancelWaybill` | `DELETE /shipments/<uuid>` | a repeat (`422 shipment_was_deleted`) counts as done |
| `track` | `GET /shipments/tracking?numbers[]=` | `phones` ignored; codes mapped by `src/status-map.ts` (only `1` and `2` observed) |
| `fetchLabel` | `GET /shipments/print?numbers[]=<number>&type=marking` | best effort: production answered `422 "Internal Server Error"` (2026-10-25); a `422` naming no field is `unavailable`, one naming a field of the request (`type`) is `rejected`; never a made-up PDF |
| `checkConnection` | a fresh JWT, then `GET /divisions?countryCodes[]=UA&limit=1` | |

Timeouts: the API's signal plus a per-request ceiling from `SHIPPING_PROVIDER_TIMEOUTS_MS` (5 s lookups and estimates, 15 s waybill calls). The JWT is kept in memory until 5 minutes before its `exp` (50 minutes without one), fetched by one call at a time, and a `401` refreshes it and repeats a read or a delete once (never a create). Failures carry carrier codes only (the HTTP status, error keys that look like field paths: lower camelCase or snake_case names and indexes of up to 3 digits joined by dots, at most 32 characters, no run of 4 or more digits, `items[1]` kept as `items.1`; snake_case values such as `shipment_was_deleted`), never a carrier text and never a key that could echo a value (a phone, a fragment of the key or the JWT). Logs: operation, status or kind, codes, duration; never the key, the JWT, a URL with a query, a body, a name or a phone.

## Limits and known gaps
- In the largest cities the picker lists all branches but only part of the lockers (Kyiv: about 8 000 points, 7 400 of them lockers; at most 15 pages of 100, fewer when the carrier is slow: the time budget keeps the answer inside the 5 s lookup limit); the cut is logged. A locker not listed still works when its id reaches the checkout.
- Not built: delivery to an address, cash on delivery, webhooks, international shipments, several parcels, courier pickups.
- Unverified: domestic prices and their unit, every status code but `1` and `2`, the label answer, rate-limit numbers, the tracking batch limit, the `ids[]` filter staying available, `totalCost` on list rows (absent: a reconciled waybill has no carrier cost), whether `GET /shipments` stays sorted by `createdAt` across pages.
- Tracking of a MIXED batch (known and unknown numbers) is unverified: production answered `404 "Shipments not found"` for batches of unknown numbers only. If it answered `404` for a whole mixed batch, every shipment of that batch would go without updates (job 8 sends up to 100 numbers per call); the stub answers the known part, an assumption.
- A `422` without field keys on a create is read as a server error (`unavailable`, then reconcile settles `failed` after 5 minutes when nothing exists): a carrier refusal worded only in `errorMessage` therefore takes that longer way.

## Tests
`pnpm --filter @fluxkit/provider-nova-post test`: a local stub carrier on `127.0.0.1` (`src/test-support/stub-carrier.ts`, invented data only) and a no-network guard (`src/test-support/no-network.ts`) that fails a spec file on any request to another host. The stub refuses what production refused (a create body without a required field or with a one-word contact name, a print without `type=marking`, settlements without upper-case `countryCodes[]`; `src/stub-carrier.spec.ts`), and a spec that does not import the guard checks it is wired for every file (`src/no-network-wired.spec.ts`). Specs cover the verified request shapes, the JWT cache, error and size mapping, `findWaybill` paging, the status table, secrets in logs, the module's startup refusal and the core provider contract check.

How to remove: delete `packages/providers/nova-post`, remove `nova_post` from `SHIPPING_PROVIDERS_ENABLED` and the two variables from the environment. Nothing in core or `apps/api` references it (CI: `scripts/feature-matrix.sh providers-deleted`). Orders and shipments already made keep their snapshot; env-bound shipment actions answer `409 provider_not_enabled`; managed bindings answer `409 credential_unavailable` because the bound provider package is missing.

## Managed credentials (PR 3)

- Manifest environments: `sandbox`, `production`, default `sandbox`, env lock `NOVA_POST_ENVIRONMENT`. Keys are issued per environment; Ukrainian sandbox key availability remains unverified. Environment changes require saving a new immutable version; a JWT never crosses versions/environments.
- Entry exports `createOutboundClient(secrets, context)` and `checkCredentials(secrets, context, signal)`. The factory reads only `secrets.api_key` and `context.environment`; it does no I/O and reads no process env. The existing env Nest module is unchanged.
- Each client's `NovaPostHttp` owns its JWT cache/single-flight. Every actual request passes `context.transport.start`, including fresh JWT exchange, retries and each directory/list page; the gate thunk starts fetch synchronously. Refusal makes no fetch and returns code-only failure. Authorization URLs/query values, JWTs and carrier text are never logged.
- Check reuses `checkConnection`: fresh JWT, then one division read; no waybill is created. Tracking remains polling; no webhook setup is needed.
- Activation/rotation selects keys only for new work. Bound shipments keep their old active/draining key for reconcile, tracking, cancellation and labels after disable; revoke stops later calls. Directory caches belong to the exact version/environment. A sender profile and shipping methods are still required, with no profile relocation.
- Managed contract tests run against the HTTP stub; denial tests assert zero fetch, including authorization. This does not establish live sandbox/account behavior. See [deployment cutover](../../../docs/deployment.md#switching-shipping-from-env-keys-to-admin-keys).
