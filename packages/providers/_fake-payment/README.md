# @fluxkit/provider-fake-payment

Purpose: a TEST-ONLY payment provider with code `fake` (ADR 0032, payments plan step 4). It implements the whole `PaymentProviderPort` in memory, with no network, no wall clock and no randomness, keeps every invoice a test can read, and is driven by the test: an invoice only changes state when the test says so. It is the fixture for the payment matrix modes (`providers-payment-fake`, `providers-payment-none`, `providers-deleted`) and for the tests and e2e suites of the payment module. It charges NOTHING: never enable it in a real shop. `loadEnv` refuses `PAYMENT_PROVIDERS_ENABLED=fake` when `NODE_ENV=production` (the API does not start).

- Flag: `PAYMENT_PROVIDERS_ENABLED=fake` (with a provider enabled `ORDER_PAYMENT_TTL_MINUTES` must be at least 8).
- Manifest: `"fluxkit": { "provider": "fake", "kind": "payment" }` in `package.json`. Codes are unique per kind, so this does not clash with the shipping `fake` (`packages/providers/_fake`) or the email `fake` (`packages/providers/_fake-email`).
- Entry: `src/index.ts` exports `providerModule`, loaded dynamically by `apps/api` only when `PAYMENT_PROVIDERS_ENABLED` names `fake`.
- Variable: `FAKE_PAYMENT_ADOPT_WEBHOOKS` (optional, `true` or `false`, default off; `docs/contracts/config.md`). The hooks below act inside one process; a separate API process (the e2e suites) is driven through signed webhooks instead, see "Driving it from another process". No hosted payment page exists: the page host is reserved and the e2e suites answer it with a browser stub.
- Routes, DB tables, migrations: none.
- Extension points used: the payment provider loader and registry (`apps/api/src/payments/registry`).

## Behaviour
- Money, statuses and facts follow the core port. The capabilities list every currency core knows (so the startup check passes for any `SHOP_CURRENCY`), partial and several refunds, invalidation of an unpaid invoice and webhooks.
- `createPayment` answers `fake-pay-000001`, `fake-pay-000002`, ... (counted per instance) and a page `https://pay.fake.invalid/pay/<id>` (a reserved host: nothing resolves it). It is NOT idempotent, like Monobank (M5): a second create with the same payment id makes a second invoice, so a payment module that repeats a create is caught. A create that fails local validation (an aborted signal, a non-positive amount, a currency the fake does not take, a description over 280 characters) answers `not_sent` and records no request.
- `getPayment` answers the invoice as a `ProviderPaymentFact`: the reference is the payment id sent, the raw status is Monobank's word (`created`, `processing`, `hold`, `success`, `failure`, `reversed`, `expired`), `modifiedAt` comes from a logical clock that moves one second per state change (so the greater `modifiedAt` is current, M10), refunds are listed under their refund id (a lost refund answer can be settled, decision 13). An unknown id is `not_found`.
- `invalidatePayment`: an unpaid invoice becomes `expired` (`{invalidated: true}`, repeatable); a paid one is `not_cancellable` (`already_paid`); a processing one `not_cancellable` (`in_progress`).
- `refund` is deduplicated by our refund id (`extRef`, assumed for Monobank, M13): the same id and amount replays its answer, the same id with another amount is `rejected` (`extref_reused`). Several partial refunds are taken up to the amount (`not_cancellable`, `refund_exceeds_remaining`); a full refund after a partial one is refused; an unpaid payment is `not_cancellable` (`not_paid`). The final amount of the fact is the amount less the succeeded refunds.
- `verifyWebhook` checks the signature over the exact raw bytes first. Scheme (NOT Monobank's ECDSA): the header `x-fake-signature` is the lower-case hex HMAC-SHA256 of the raw body with the fixed public test key `fluxkit-fake-payment-webhook-test-key`; a missing, malformed or wrong signature, or a body changed by one byte, is `invalid_signature`. A correctly signed body that is not the fake's shape is `rejected` (`malformed_body`); over 64 KiB `rejected` (`body_too_large`); an unknown raw status word gives a fact with `status: null` and the word kept.
- Its spec runs the core contract check `checkPaymentProviderContract`.

## Test hooks
`FakePaymentProvider` has methods beyond the port. A test reaches the instance with `app.get(FakePaymentProvider)` (from this package) or by casting the registry's answer.
- `failNext({ operation?, reason?, providerCodes?, retryAfterSeconds?, times?, afterEffect?, hang?, throws? })`: the next `times` (default 1) matching calls fail. `operation` is one of `createPayment`, `getPayment`, `invalidatePayment`, `refund`, `verifyWebhook`; without it the next call of the first four. `reason` is any `PaymentProviderFailureReason` (`unavailable` by default, `rate_limited`, `rejected`, `misconfigured`, `not_found`, `not_cancellable`, `invalid_signature`, `not_sent`). `afterEffect: true` does the work (the invoice is created, the refund recorded, the invoice invalidated) and then loses the answer: the "unknown outcome" case. `hang: true` never answers until the abort signal fires, then rejects with its reason (a timeout). `throws: true` rejects with a plain error. A bad description throws at once (`RangeError`).
- Status transitions, each moving `modifiedAt` forward and refusing (`RangeError`) what the real service would not do from the current status: `process(id)`, `complete(id, card?)`, `fail(id, code?)`, `expire(id)` (the real service sends no webhook for `expired`, M8; `webhookFor` still builds one), `reverse(id)`, `addExternalRefund(id, amount)` (a refund made outside the shop, `refundId` null), `setRefundMode("succeeded" | "processing")`, `settleRefund(id, refundId, "succeeded" | "failed")`.
- `webhookFor(id)`: the signed `PaymentWebhookInput` of the invoice's current state; `fakeWebhookInput(body)`, `signFakeWebhook(bytes)` and `FAKE_PAYMENT_SIGNATURE_HEADER` build or check others.
- `invoices()`, `invoice(id)` (copies), `requests()` (every call that passed local validation), `reset()` (forgets everything; numbering, the logical clock and the refund mode restart).

## Driving it from another process (the e2e suites)
The hooks above need the test and the API in one process. The e2e suites run the BUILT API in its own process, and the production API gets no test-only route, so the suites speak to it the way a real provider does: through the public routes and the signed webhook.
- The shopper creates a payment through the store API; the answer's `redirectUrl` is `https://pay.fake.invalid/pay/<providerPaymentId>`, which is how the test learns the invoice id (ids are `fake-pay-000001`, ... per process).
- The test POSTs the provider's webhook to the real `POST /webhooks/payments/fake` (through the suite's proxy) with the exact body bytes and the header `x-fake-signature` = hex HMAC-SHA256 of those bytes with the public test key above. The body is the fake's JSON shape (`invoiceId`, `reference`, `status`, `amount`, `currency`, `finalAmount`, `modifiedDate`, `failureCode`, `cancelList`, `card`); `reference` is the attempt id (`paymentId`) the store create answered. The API verifies the signature over the raw bytes exactly as for any provider, so a forged, unsigned or altered body is `401`.
- With `FAKE_PAYMENT_ADOPT_WEBHOOKS=true` a verified webhook also moves the fake's own invoice to the state it announces, so a later admin refund (which the API sends to the fake) finds a paid invoice. Only a webhook about an invoice the fake holds, with that invoice's reference and amount and a `modifiedDate` not older than the invoice's, is adopted; a mismatching amount, an unknown invoice or an older time changes nothing (the API still sees the fact and decides). The logical clock is moved past an adopted time, so refunds made afterwards stay newer.
- Not possible this way: `failNext`, `process`, `expire`, `setRefundMode` and the other hooks (no bridge), and the real service sends no `expired` webhook anyway.

## How to remove it
Delete `packages/providers/_fake-payment` and take `fake` out of `PAYMENT_PROVIDERS_ENABLED`. Nothing in core or `apps/api` references it (CI: `scripts/feature-matrix.sh providers-deleted` removes it and checks that `PAYMENT_PROVIDERS_ENABLED=fake` then refuses to start while lint, types, boundaries and tests stay green).
