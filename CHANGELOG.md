- Add the scheduler (cart plan step 5c, ADR 0021, `docs/api/jobs.md`; no route, no schema change, no dependency): an in-process timer (`SCHEDULER_ENABLED` default `true`, `SCHEDULER_INTERVAL_SECONDS` default 60, 10 to 3600) takes a Postgres advisory lock (key 7426003, own connection, never waits) and runs the jobs in order: expire due orders through `OrdersService.expireOne`, the `ReservationsService.expireDue` loop (failures logged as errors), delivery of the `domain_event` outbox to handlers, deletion of events dispatched more than 7 days ago, expired carts and expired customer sessions (absolute expiry). Unpaid orders now expire by themselves and give their stock back.
- Add domain event delivery (ADR 0018, 0021, `docs/contracts/events.md`, new public contract): handlers are providers marked with `SetMetadata(DOMAIN_EVENT_HANDLER_METADATA, domainEventHandlerMetadata([...]))` and found at startup; at-least-once, an event is dispatched when every handler succeeded, retried at `created_at + (2^n - 1) minutes`, given up after 10 failures (error log, stays for an operator); only an error code is stored. `@fluxkit/core` exports `domainEventHandlerMetadata`, `DOMAIN_EVENT_TYPE_PATTERN`, `DomainEventHandler` and `DomainEventEnvelope` (additive).
- Add `pnpm jobs:run-once`: runs every scheduler job once under the same lock (exit 0 ran, 1 a job failed or bad input, 2 lock held by a running scheduler).
- Add the admin order routes (cart plan step 6, `docs/api/orders.md`; no schema, config or dependency change): `GET /admin/orders` (filters `status`, `placedFrom`, `placedTo`, `q` = exact order number or exact email, `limit`, `offset`; newest first with an id tiebreaker), `GET /admin/orders/{id}` (contact, addresses, snapshot with every locale, totals, status journal with the acting admin, reservation status and quantity), `POST /admin/orders/{id}/cancel` `{reason}` (an admin may also cancel a paid order: nothing is restocked or refunded by the system), `POST /admin/orders/{id}/mark-paid` `{reference, amount}` (the same `OrdersService.markPaid` entry as a payment plugin; repeating the reference answers 200 unchanged) and `POST /admin/orders/{id}/mark-fulfilled`. Permissions `orders.read` for `GET` and `orders.write` for every `POST` (owner and manager; not the viewer). New `rule_violation` rules `order_not_payable`, `amount_mismatch`, `payment_reference_conflict`, `awaiting_stock` on these routes.
- Add the `OrderReadPort` (ADR 0018, `docs/contracts/events.md`, public contract): `@fluxkit/core` exports `ORDER_READ_PORT`, the `OrderReadPort` interface and the read-only `AdminOrderView` types (additive); `apps/api` implements the port with the same builder as `GET /admin/orders/{id}`.
- Fix: cancelling a paid order now releases its still-`active` reservations (the held remainder of a backordered line); sold units stay sold, no restock. Core `StockEffect` gains `release_unsold` and loses the unused `none` (ADR 0022; no schema change).
- Document the checkout flow (cart plan step 7, docs only): the README "Checkout walkthrough" (curl from the seeded catalog to a fulfilled and a cancelled order), the seed documented to create no customers, carts or orders, and corrected notes in the cart, customer, order, inventory and contract pages; no code, schema, config or dependency change.
- Fix the dead guest access token after a double submit (review High 1, ADR 0023): the token is now derived (HMAC-SHA256 over the order id and the `Idempotency-Key` under the new required variable `ORDER_TOKEN_SECRET`, at least 32 characters, required when `NODE_ENV=production` and by the API process always), so a replay of a checkout returns the SAME `accessToken` instead of rotating it; core gains `deriveGuestAccessToken` (the HMAC is a port supplied by the API). Behavior change: the `200` of a replay carries the first answer's token. Setting `ORDER_TOKEN_SECRET` is needed to start the API (`.env.example`, `docs/contracts/config.md`). No schema change.
- Limit unpaid orders per guest email and per customer (review Medium 4, ADR 0024): new optional `MAX_OPEN_ORDERS` (1 to 50, default 3); a checkout that would exceed it answers `409 too_many_open_orders` (new problem code in `docs/contracts/api.md`, `docs/api/orders.md` and `docs/api/openapi.json`); a replay of an existing checkout is still answered; paid, cancelled, expired and fulfilled orders do not count. Race-safe with an advisory lock per guest email, taken after the cart row and before the catalog rows (lock order updated). No schema change. Per-IP counting is not done (accepted gap).
- Add `TRUST_PROXY` (review High 2, ADR 0024): new optional variable, number of trusted proxy hops 0 to 10, default 0 (unchanged behaviour), applied as Express `trust proxy` in `createApp`, so the store rate limits and the admin login limit count per client address behind a proxy instead of one shop-wide window. Set the exact hop count (README, Deployment notes).
- Fix the outbox dispatcher (review Medium 1, ADR 0025): a per-event lease, the attempt is committed before any handler runs, handlers run with no transaction open and the result is recorded in a second short transaction, so a dying transaction can no longer redeliver an event for ever; `attempts` now counts started attempts, `previousFailures` the earlier attempts, `occurredAt` is documented as the insert time. No schema change.
