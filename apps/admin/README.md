# @fluxkit/admin

The admin SPA: React 19 on Vite, served as static files under `/admin-ui/` on the storefront origin (ADR 0027). It calls the admin API `/admin/*` on the same origin with the `HttpOnly` session cookie; authorization stays on the API. Plan: `docs/plans/2026-10-19-admin-ui.md`. File map: `docs/files/admin.md`.

Status (step 10): the shell is built (sign-in, re-sign-in dialog, role-aware navigation, own account with password change, language switch, error, not-found and not-allowed views), the catalog dictionaries are built (attributes, options, product types, brands, category tree; see "Catalog dictionaries" below), the products (list, create, the editor with General, Attributes, Categories, Media, Options, Variants, Prices and Stock and the lifecycle; see "Products" below), the orders (list, detail, mark paid, mark fulfilled, cancel; see "Orders" below), the customers (list, detail, deactivate, activate, unlock; see "Customers" below) and the admin users (owner only: list, create, role, activity, password reset; see "Admin users" below). Every area of the plan is built; browser e2e is step 11.

## Run

```bash
pnpm build                                     # once: workspace packages
pnpm --filter @fluxkit/api start               # the API, with ADMIN_COOKIE_SECURE=false and TRUST_PROXY=0 for plain HTTP
pnpm --filter @fluxkit/admin dev               # http://localhost:5173/admin-ui/
```

- The dev server proxies `/admin`, `/admin/*` and `/admin?…` to `ADMIN_DEV_API_URL` (default `http://127.0.0.1:3000`; read from the shell or the root `.env`, development only, a malformed value stops the dev server). `/admin-ui` is never proxied.
- Sign in with an owner from `pnpm admin:create`. The cookie is host-only, so open the dev server by the host name you configured (not a mix of `localhost` and `127.0.0.1`).
- `pnpm --filter @fluxkit/admin preview` serves the build with the security headers below and the same proxy (a local CSP check).
- Tests: `pnpm --filter @fluxkit/admin test` (Vitest, node, `renderToStaticMarkup`; no DOM library, owner answer 9). `build-output.spec.ts` checks `dist/`, so run `pnpm --filter @fluxkit/admin build` first (the root `pnpm test` builds). Browser e2e is step 11.

## Serving and security headers

The edge proxy serves `apps/admin/dist` for `/admin-ui` and `/admin-ui/*` with an `index.html` fallback (deep links and reloads), keeps routing `/admin/*` and `/store/*` to the API and everything else to the storefront. Every response under `/admin-ui` carries these headers; the single copy is `security-headers.ts` (`ADMIN_SECURITY_HEADERS`, `adminSecurityHeaders({ imageHosts })`, `ADMIN_CACHE_CONTROL`), for the e2e proxy and the deployment docs to reuse:

| Header | Value |
|---|---|
| `Content-Security-Policy` | `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data: [https://<image host> ...]; connect-src 'self'; font-src 'self'; object-src 'none'; base-uri 'none'; form-action 'self'; frame-ancestors 'none'` |
| `X-Frame-Options` | `DENY` |
| `X-Content-Type-Options` | `nosniff` |
| `Referrer-Policy` | `no-referrer` (ADR 0027; also a `<meta name="referrer">` in `index.html`) |
| `Permissions-Policy` | `camera=(), microphone=(), geolocation=()` |
| `Cross-Origin-Opener-Policy` | `same-origin` |
| `Cache-Control` | `index.html` (and the fallback): `no-cache`; `/admin-ui/assets/*` (hashed): `public, max-age=31536000, immutable` |
| `Strict-Transport-Security` | set by the TLS proxy, as for the storefront |

Image hosts: the same list as `STOREFRONT_IMAGE_HOSTS` (a static SPA has no runtime configuration). The CSP protects the SPA from injected script; it does NOT protect the admin API from an XSS in the storefront, which shares the origin (risk accepted in ADR 0027). The router writes the start page as `/admin-ui` (no slash), so the proxy must serve both `/admin-ui` and `/admin-ui/*`.

Checked after every build (`build-output.spec.ts`): `index.html` has no inline script, style or handler and no external URL, every asset is under `/admin-ui/assets/`, each area is its own lazy chunk, each lazy message file is its own chunk per language and none of its texts is in the initial JavaScript, the initial JavaScript stays within its budget (440 000 bytes raw, 135 000 gzip; measured 392 050 and 120 027 on 2026-10-19 for the shell; 439 481 and 129 557 on 2026-10-20 with the catalog dictionaries when their messages were merged into the entry; 398 093 and 121 328 after the area messages became lazy, and 398 881 and 121 484 with the products area of step 6a; unchanged by steps 6b and 7, whose code and messages are in the products chunks: 398 881 raw and 121 481 gzip after step 7; 399 489 raw and 121 606 gzip after step 8, whose code and messages are in the orders chunks (the entry gained one route row, one path and two message loaders): 399 489 raw and 121 606 gzip is the step 8 figure; 400 159 raw and 121 952 gzip after step 9, whose code and messages are in the customers chunks (the entry gained one route row, one path and two message loaders and one route title): the budget is about 10 % above that; 400 678 raw and 120 320 gzip after step 10, measured the same way on 2026-10-20, whose code and messages are in the users chunks (the entry gained two route rows, two paths, two message loaders and two route titles)), no zod, `localStorage` once (the UI language).

## Structure and conventions

- `src/routes.ts` is the route table: path (relative to `/admin-ui`), the API operation whose permission guards it (from `ADMIN_OPERATIONS`, tested against `x-fluxkit-permission` in `docs/api/openapi.json`), title key, page (eager or lazy). Only `/login` is public; no route may start with `/admin`. A new screen adds one row and, for the navigation, one entry in `src/layout/navigation.ts`.
- `can(permission)` reads only the permission list of `GET /admin/auth/me`. A 403 reloads `me`; a 401 anywhere except sign-in opens the re-sign-in dialog over the page (input survives, the failed request is not replayed; another user signing in drops all state and goes to the start page).
- Data: `adminClient` (`src/lib/api.ts`; CSRF header on writes, 15 s reads, 30 s writes, never retries) and `useResource(loader, deps)` (abort on unmount and on new deps, states `loading | ready | error | forbidden | notFound`, `reload()`), with `ResourceFallback` for the non-ready states. No cache library, no optimistic updates. A timed-out write's result is unknown: reload and show what the server has.
- Errors: `src/lib/problem-messages.ts` maps every problem `code` (`errors.code.*`) and every documented rule and `errors[].code` (`errors.reason.*`) to uk/en text; an unknown code shows a generic message plus the code in small print; the API's English `detail` is never shown. `fieldErrorsFromProblem` puts `errors[].path` on form fields.
- i18n: `src/messages/{uk,en}/<file>.json`, one file per area, listed in `src/messages/index.ts` (a key in two files throws). EAGER files (shell, common, errors with the problem map, auth, account, navigation with every route title, status) are in the entry chunk; LAZY files (`catalog-dictionaries`, `products`, `orders`, `customers`, `users`) are one chunk per file and language. An area module exports `MESSAGE_FILES` (the type of the route table requires it); the route renders the area only after those files are loaded for the UI language (`i18n/area-messages.tsx`, the shell's loading view meanwhile; a file that cannot be loaded goes to the route's error boundary), so the translator, which throws on a missing key, never meets one. The language switch first loads, for the new language, every file the current one shows, then switches (the open screen keeps its state; if a file cannot be loaded the language stays and a line says so). `messages.spec.ts` checks both locales, and that every key a file uses is in the eager files or in the files of its area. UI language: stored choice, else the browser language, else `uk`; the switch is remembered in `localStorage` (the only storage use; nothing personal, no credential).
- Forms: `method="post"` and no `action`, native constraints for early feedback, server errors on the fields and in a focused summary, `useUnsavedChangesGuard` plus `UnsavedChangesDialog` for dirty forms.
- Money and dates: `src/lib/format.ts` (integer minor units to a decimal string, `Intl` with the exponent from `GET /admin/config`; never `amount / 100`); `src/lib/money-input.ts` (typed decimal text to integer minor units by the currency's exponent, BigInt only: a copy of core's `parseDecimalString` grammar plus the input rules of a price field, compared with core over every currency and generated texts). The source guard refuses `parseFloat`, `toFixed`, `* 100`, `/ 100` and scaling by `10 **` anywhere. `safeHttpUrl` for URLs from data.
- Tokens only (design guard and contrast scan read `src/`); no hardcoded text (`source-guards.spec.ts` walks the JSX); no `dangerouslySetInnerHTML`.
- No `@fluxkit/core` in the bundle: core has a single entry and no `"sideEffects": false`, so importing `parseDecimalString` and `toDecimalString` pulled zod and the whole core (measured 88.6 KB minified; with `"sideEffects": false` in core it would be 1.5 KB, a change outside this app that needs the orchestrator's approval). Constants and rules the admin needs are copied and compared with core in tests (`PASSWORD_LIMITS`, `MAX_AMOUNT` and `parseDecimalString`/`toDecimalString`, `MAX_ON_HAND`, `decideAdjustment`'s order of refusals, `availabilityOf`, `validatePrice`'s compare-at rule).
- react-router 8.4.0 is used in data-router mode only (`createBrowserRouter`, `RouterProvider`, lazy route objects, `useBlocker`); no framework mode, no server features, no `ScrollRestoration` (the shell scrolls to the top on a path change). It reads one `sessionStorage` key of its own (view transitions, unused here) and writes none.

## Catalog dictionaries (`src/areas/catalog-dictionaries/`)

One lazy chunk for five screens, each with a list (or the category tree), a create form and an editor. Routes (`src/routes.ts`; the navigation already listed the five lists): `/catalog/{attributes,options,product-types,brands,categories}`, `.../new` (permission of the create operation, `catalog.write`) and `.../:id` (`catalog.read`). A sub-navigation links the five dictionaries on every screen.

- **Roles**: reads need `catalog.read`; every write control (create link, save, add, change, delete, assign, move) is rendered only if the session may run all the dictionary write operations (`dictionary-permissions.ts`, names `ADMIN_OPERATIONS` entries, so the table follows the API). The viewer sees read-only forms (inputs `readOnly`, checkboxes disabled, no actions) and `.../new` shows "not allowed"; a 403 still shows its message and reloads `me`.
- **Content locales** come from `GET /admin/config` (`ConfigGate`, nothing renders before they are known): one labelled field per locale, the default locale required, an empty optional locale omitted from the request map (`locale-text.ts`). A PATCH sends the whole map when one locale changed.
- **Forms are pure models first** (`attribute-form.ts`, `dictionary-forms.ts`, tested before the screens): early checks (code, slug and URL patterns copied from core and compared with core in tests, position 0 to 1 000 000, unit length, typed `validation`), request bodies, and PATCH bodies through `diffForPatch` (`src/lib/diff-for-patch.ts`, generic: changed fields only, maps and arrays replace whole, `null` clears, nothing for an unchanged field). The server stays the authority: its `400` paths (`name.uk`, `validation.min_length`, ...) land on the fields, a `409 conflict` that names a column (`code`, `slug`) on that field, anything else in the focused error summary.
- **Attributes**: all six flags by their API names; the input type and `isLocalized` are chosen once (read-only on edit); the `validation` fields follow the input type (text `min_length`/`max_length`, number `min`/`max`/`integer`/`max_decimals`, multiselect `min_items`/`max_items`, date `min`/`max`; none for boolean and select); the flags a type cannot have are disabled, and an internal attribute cannot be public (the form switches the public flags off). Options (select and multiselect) are added, changed (label, position) and deleted in a dialog.
- **Options** have values with the same dialog. **Product types** have `requiresShipping` and two assignment sections: attributes (picker, level `product`/`variant`, required, position; `PUT`/`DELETE`) and options (picker, position). Pickers are paged server lists: 100 per request, "load more", an item that cannot be chosen (already assigned) stays in the list, marked; nothing filters a loaded page (`picker-model.ts`).
- **Brands** take the logo as an http(s) URL (`safeHttpUrl`); the preview is a lazy `img` without referrer whose `alt` comes from the form's name. The page's CSP allows only the configured image hosts, so a logo from another host is reported in text instead of shown (no upload in this step).
- **Category tree**: nested list with an expand button per category (`aria-expanded`, Tab and Enter or Space), levels loaded when expanded (`GET /admin/categories?parentId=`), "load more" for a level over 100, no expand button at depth 5 (`category-tree.ts` is the tested model). **Known workaround:** the API cannot list the root level alone (no `parentId=null`), so the roots are found by paging the flat list (100 rows per request, at most 10 requests) and keeping the rows without a parent; if the cap is hit the screen says the list is truncated. An additive `parentId=null` filter would remove this (HANDOFF, known gaps). The expansion is not kept across a visit to an editor. Create takes its parent from the tree ("Add subcategory", `?parentId=`); move (`POST .../move`) is its own section with a parent picker and a confirmation.
- **Writes**: never optimistic, one request per click (`run-write.ts`; no retry), the button disabled while it runs. After a write the page reloads what the server has (`useRefreshingResource` keeps the old data on screen meanwhile, so a form being edited elsewhere on the page keeps its input), the status line (a live region the focus moves to) says "Saved". A create shows a confirmation panel (focused) with links to the new item; a delete replaces the editor with a panel (focused) and a link back. A lost answer (network, timeout, unreadable) is "the result is unknown": the page reloads and says so, a failed create points to the list; the screen never repeats the write. A refused delete (`409 in_use` or a rule) is explained in the dialog.
- **Unsaved changes**: every form uses `useUnsavedChangesGuard`; a dialog form (row or assignment) is discarded by Escape or Cancel on purpose.
- Messages: `src/messages/{uk,en}/catalog-dictionaries.json` (namespace `dict.*`; lazy, loaded with the area; the route titles are in the eager `navigation.json`); `dictionary-messages.spec.ts` checks the keys that are built from data.

## Products (`src/areas/products/`, steps 6a, 6b and 7)

One lazy chunk (with the catalog dictionaries' form parts, pickers and category tree, whose messages it loads too). Routes: `/products` (`catalog.read`), `/products/new` (`createProduct`: `catalog.write`), `/products/:id` (`catalog.read`).

- **List**: server-driven table (title in the UI language with fallback to the default locale and then the slug, slug, status as text plus tone, brand, updated). Filters status, brand (paged picker), category (paged flat list; direct assignments only, as the API filters) and `q`: the start of a slug or an exact SKU, letters, digits, `.`, `_`, `-`, at most 160 (the API's rule; anything else is explained under the field and not sent). Typed text is applied 300 ms after the last keystroke (`lib/debounce.ts`, replacing the history entry); filters and paging are in the URL (`product-list-query.ts`). Brand names: one read per distinct brand on the page, at most six at a time (`lib/load-by-ids.ts`). Loading rows, empty ("no products yet", create only when allowed), no match (clear the filters), error with retry, not allowed.
- **Create**: product type (paged picker, required, cannot change later), title per content locale (default locale required), description, slug (empty: generated from the title), brand. The API creates the draft with its default variant; attributes and categories are set in the editor. A focused panel links to the editor (no redirect from a form, as in step 5).
- **Editor**: summary (the title is the `h1`, status as text, type, slug, last update, first publish) with the lifecycle actions the session may run (`lifecycle.ts`: publish, unpublish, archive, restore with `catalog.publish`; delete of a never-published product with `catalog.write`, a danger confirmation; unpublish and archive are confirmed); the tabs of `src/layout/product-editor.ts` in order (General, Attributes, Categories, Media, Options, Variants, Prices, Stock), WAI-ARIA tabs, the tab in `?tab=`, each tab shown when the session may run its main read. Switching tabs changes the query string, so a tab with unsaved input asks first (`useUnsavedChangesGuard`); while a tab is dirty the lifecycle actions are locked (they reload the product). After a write the editor reloads the product and remounts the tab when the stored content changed (the tab's key is `productRevision`: the product's `updatedAt` plus the ids and timestamps of its variants and media, its option values and categories, because a variant, media or option write does not change the product's own `updatedAt`; a reload after a lost answer that finds nothing changed keeps the input); the status line (a focused live region) says what happened; a lost answer is "result unknown".
- **General**: title, description (a textarea, never HTML), slug, brand; PATCH of the changed fields only (`diffForPatch`; a locale map whole, an emptied description or brand `null`). The API has no SEO fields.
- **Attributes**: generated from the product type's PRODUCT-level assignments and their embedded definitions (`attribute-values-form.ts`): text (localized: one field per content locale), number (with its unit, a decimal string checked like core: integer, decimals, range), yes/no/not set, one choice, several choices (checkboxes, the stored order kept), date; hints from `validation` with core's defaults; an "Internal" badge for internal attributes; a stored choice that is no longer an option is kept and shown. Variant-level attributes are not here (step 6b). An active product needs its required attributes on every save (native `required`); a draft may stay incomplete ("required to publish"). The API replaces all product-level values on a PATCH with `attributes` (no partial update), so the body is the whole map; an attribute the admin did not touch is sent exactly as stored, a value for a code the type no longer assigns is kept, an emptied field is left out. `400` errors at `attributes.<code>[.<locale>]` land on the field with the attribute reason's message (`products.attributeReason.*`).
- **Categories**: the assigned categories in order with the primary one (a radio group), remove, and the lazy category tree in "pick" mode to add (the roots through the same `collectRoots` workaround as the category screen; at most 100); `PUT /admin/products/{id}/categories` with the whole set and the primary.
- **Media** (`media-list.ts`, `tabs/media-tab.tsx`): the product's images as http(s) addresses (no upload yet, step 2b), at most 100, in their order (the position); each row has a preview (a lazy `img` with explicit size, `referrerPolicy="no-referrer"`, `alt` from the row's alt text, only for an address that passes `safeHttpUrl`), the address (checked like the preview: absolute http(s), no credentials, at most 2048), the alt text per content locale (at most 255; once any locale has text the default locale is needed too, core's rule for optional texts), and the option value it shows (one of the values the product chose: a select of "option: value"). Move up and move down are buttons (keyboard, no dragging), remove takes the row out; the whole list is saved with one `PUT .../media` (positions 0, 1, 2, ...), and a save that removes stored images asks first. The admin's CSP shows only images of the configured hosts; a blocked or broken image is a translated text, and the tab says why.
- **Options** (`option-selection.ts`, `tabs/options-tab.tsx`): the product's options and chosen values (names from `GET /admin/options/{id}`, one read per option of the type, at most six at a time; codes until they arrive or if they fail, with a retry), each a focus target of its publish problem (`options.<code>`, for example an option the type no longer allows). A DRAFT gets a form with every option the type allows and a checkbox per value (at most 3 options, 1 to 30 values each, at most 250 variants: core's limits); the line under it says what a save does, mirroring the API: only new values of used options keep the variants and add the new combinations; an added or removed option or a removed value deletes every variant and generates them again (SKUs, barcodes, attribute values, flags and prices are lost; the API refuses with `has_stock_history` or `has_order_lines` if a variant has stock history or order lines), which is confirmed; a removed value that an image still links is refused before sending (the API's `in_use`). A PUBLISHED or ARCHIVED product's options are frozen (`options_frozen`, explained): each option offers "add a value" (a value of the option the product has not chosen), confirmed because it cannot be removed again and its variants may start switched off (ADR 0008).
- **Variants** (`variant-form.ts`, `tabs/variants-tab.tsx`): the variants of the product detail (at most 250, one read, in the order the API's `variants.N` counts in) in a table: row, SKU (the row header and the focus target of the row's problems), option values, barcode, status and default as text, stock flags, the variant-level attributes (a missing required one is marked) and the row's publish problems. "Generate missing variants" (`POST .../variants/generate`, idempotent; says how many were created and skipped); "Add a variant by hand" on a draft (one value of every option, a free combination, an optional SKU the API otherwise proposes, the flags; attributes afterwards). Per row: edit (an inline form under the table: SKU normalized like core, trimmed and ASCII upper case, with a "saved as" hint and core's pattern; barcode; active, count stock, sell beyond stock; the variant attributes generated from the type's `level=variant` assignments by the same model as the product's, with the variant prefix `variant-attribute-*`; a PATCH of the changed fields only, the attribute map whole when it changed; a duplicate SKU, `409 conflict` on `sku`, on the SKU field), make default, switch on or off, delete (danger confirmation). What the API would refuse is said instead of offering the button: a published or archived product's variants are not deleted (`product_not_draft`), never the default or the last variant, a live product's default stays on and one variant stays active, only an active variant becomes a live product's default; `has_stock_history` and `has_order_lines` come from the API and are explained in the dialog. Prices and stock are their own tabs (below).
- **Prices** (`prices/price-grid.ts`, `prices/prices-tab.tsx`, step 7): one read of every variant's prices (`GET /admin/products/{id}/prices`), a table of variants (SKU, option values, active or switched off) by currencies: the shop currency (from `GET /admin/config`) first, then every other currency that has a stored price, in the config's order; "show another currency" adds an empty column of a supported currency (hidden again while it holds nothing). A writer gets per cell the stored price formatted with `Intl` from its integer minor units, an amount input and an optional compare-at input (decimal text: a dot, at most the currency's decimals, 0 for JPY and 3 for KWD; outer whitespace is trimmed; a comma or a space inside the number is refused with its own message and never guessed, because `1,234` is ambiguous between languages; negative values and minus zero are refused) and, when the typed value differs, "will be stored as" the formatted value. Save checks every cell first (an amount next to a compare-at price, compare-at strictly higher than the price as the API demands, `MAX_AMOUNT`), then sends ONE bulk `PUT /admin/products/{id}/prices` with only the new and changed cells (compared as integers: `12` and `12.00` are the same price), each with an explicit `compareAtAmount` (`null` clears it); more than 500 changes are refused before sending (the API's limit, all or nothing). A stored price is removed with its own button and a danger confirmation (`DELETE .../prices/{currency}`), never by emptying the field; the shop-currency price of an active variant of a published product gets the `last_shop_price` explanation instead of the button (the API refuses it), and removing is locked while the grid has unsaved changes. Server errors `items.N.<field>` land on the cell of the N-th item sent. A refused publish's `variants.N` `price_missing` is listed on this tab and focuses that variant's shop-currency amount (the editor waits for the tab's read). After a save or a delete the tab reads the prices again and the grid is rebuilt from the stored values (keyed by `pricesRevision`); a lost answer is "result unknown" and the reload shows what the server has. Viewer: the stored prices only.
- **Stock** (`stock/stock-adjustment.ts`, `stock/stock-view.ts`, `stock/stock-access.ts`, `stock/stock-tab.tsx`, step 7): `GET /admin/locations` and `GET /admin/products/{id}/inventory` (two requests whatever the number of variants); a summary table of every variant with its state as text and tone (in stock, low stock at `lowStockThreshold` or fewer available units, out of stock, "stock not counted" for an untracked variant, "sold beyond stock" for backorder; core's `availabilityOf`, compared in the spec) and the on hand, reserved and available totals; one variant at a time is opened (its reads are bounded: the newest movement, one journal page of 20, one reservations page of 20). The open variant shows its levels per location, the adjustment form for `catalog.write` (kind exactly as the API: receipt, correction (`adjustment`), return; a receipt or a return takes the added quantity, a correction a signed change or the counted quantity (`setOnHand`); a location picker only when there is more than one location, otherwise the API's default; reason up to 500 and reference up to 255 characters; the current level at the chosen location next to the quantity), checked first like core's `decideAdjustment` against the last read (`no_change`, `kind_requires_increase`, `negative_on_hand`, `on_hand_out_of_range`, `below_reserved`), and confirmed when it lowers stock or sets a counted quantity (the dialog states before, after and the change). It is sent once: a second click while it runs sends nothing (`lib/single-flight.ts`), it is never retried and nothing is shown before the answer (owner answer 12). After every answer, accepted, refused or lost, the levels, the newest movement and the journal's first page are read again; an accepted change shows the server's movement; a refusal its reason on the field (`below_reserved`: release or wait for the reservations); a lost answer "result unknown" plus one read of the newest movement that says whether a new movement by you, by someone else, or none appeared since the one seen before sending. The journal (newest first, paged) names the actor "you" for the signed-in admin, the email for owners (the users list is read only with `users.manage`, at most 10 pages of 100, `src/lib/use-admin-emails.ts`; nobody else makes that request), otherwise "another admin" with the first eight characters of the id, and "the system" for a sale or a deleted admin (owner answer 11). Reservations (`GET .../inventory/reservations`, status filter, paged) are shown and requested only with `orders.read`; each links to the orders list searched by its order number (`/orders?q=<number>`, the id when there is no number; step 8's list reads `q` from the URL). A dirty form asks before leaving, locks the lifecycle actions and the switch to another variant. Viewer: levels, states and journal; no form, no reservations.
- **Publish refusals**: a `400` lists every `errors[]` entry (`publish-problems.ts`) with a button that opens the owning tab and focuses the field: `title`, `description`, `slug`, `brandId` to General, `attributes.<code>[.<locale>]` to Attributes, `categories`/`primaryCategoryId` to Categories, `media.N.<field>` to that image's field, `options.<code>` to that option, `variants.N` `price_missing` to the variant's shop-currency cell on Prices, every other `variants.N[.attributes.<code>[.<locale>]]` to the variant's row (N is the index in the product detail's variant order; the problem keeps the variant's id and SKU, so it stays on its row when the table changes; an attribute problem also marks that field in the variant's form); a problem of no row (or of a variant that no longer exists) is listed at the top of its tab. A tab's problems also show on its fields until that tab is saved (a saved variant clears only its own). Other refusals (`409 invalid_transition`, rules such as `product_was_published`) are explained through the problem map.
- **Writes**: every write of the three tabs is sent once through `runWrite` (no retry), never optimistic; the editor reloads the product afterwards and the status line says what happened ("saved", "variants generated: N new, M existed", "variant created", "variant deleted", "value added"); a lost answer is "result unknown" and the reload shows what the server has. A tab with unsaved input (the media list, the option form, a variant's form) asks before it is left and locks the lifecycle actions.
- **Viewer**: the list without the create link, every tab read-only (inputs read-only, choices disabled), no save, add, move, remove, generate, edit, default, switch, delete or lifecycle button, no price input and no stock form or reservations, `/products/new` not allowed.
- Messages: `src/messages/{uk,en}/products.json` (lazy); `product-messages.spec.ts` checks the keys built from data.

## Orders (`src/areas/orders/`, step 8)

One lazy chunk with its own messages only (`orders`; it imports nothing from the other areas). Routes: `/orders` (`listOrders`: `orders.read`) and `/orders/:id` (`getOrder`: `orders.read`). The viewer has no `orders.read`: both routes show "not allowed" and no order request is made.

- **List**: server-driven table, 20 a page (the API's default): number (link to the detail, the row header), placed (date and time with `Intl` in the browser's time zone), status as text plus tone for all five statuses, the email with "no customer account" when the order has none, the item count (units), the total formatted from its integer minor units with the exponent of `GET /admin/config`. Filters, all in the URL (`order-list-query.ts`): status; placed from and placed until as calendar days (`<input type="date">`), both days included: the page turns them into `placedFrom` = the first instant of the from day and `placedTo` = the first instant of the day after the until day (exclusive), each written as `YYYY-MM-DDTHH:mm:ss±HH:MM` with the offset in force at that instant in the browser's zone (`date-range.ts`: across a daylight-saving change the two ends get different offsets; a day whose midnight does not exist starts at its first instant; a day outside the API's window, 2000-01-01 to 2200-01-01, or an until day before the from day is explained on its field and nothing is requested); `q`, an exact order number (the API forgives case, a missing dash and the look-alike letters) or an exact email, at most 254 characters, applied 300 ms after the last keystroke (replacing the history entry); `customerId` (from step 9's customer screen) as a chip with a "show all customers" link. The Stock tab's reservation links (`/orders?q=<order number>`) land on the list searched by that number; a `q` that is an order id (a reservation without a number) offers "open the order with this id" when nothing matches. Loading rows, empty ("no orders yet"), no match (clear the filters), past the end, error with retry, not allowed.
- **Detail**: one read (`GET /admin/orders/{id}`, lines included, plus the config once): the number as the `h1` with the status, a status line (live region, focused after an action), the actions (below), the summary (status, placed, "expires unless paid" while unpaid, paid, fulfilled, cancelled, expired, the payment reference, the cancellation reason, the order's language, the customer: the email as text, a link to the customer's detail by the account id (since step 9 registered `customerDetail`: `customerDetailHref` reads the path table; a guest order or a deleted account has no link), "guest order", "account deleted since" or "customer account", and a link to the customer's orders through `customerId`), the contact, the shipping and billing addresses, the lines (image only for an http(s) address, lazy, no referrer; the snapshot title, variant title and option values in the UI language, else the order's language, else any text; SKU; unit price and compare-at; quantity; the line total; the reservations as "quantity status"), the totals (subtotal, shipping, discount, tax, total and any adjustment, exactly as the API sends them; nothing is computed or multiplied in the browser) and the status history (when, from and to, by whom, reason). Every text of the order (names, addresses, reasons, titles) is rendered as text.
- **Actors** (owner answer 11): "you" for the signed-in admin, the email for owners (the users list is read only with `users.manage`, at most 10 pages of 100, `src/lib/use-admin-emails.ts`, shared with the Stock tab), otherwise "another admin" with the first eight characters of the id; "the customer", "the guest shopper", "the system", and "an admin whose account was deleted" for an admin row without an id.
- **Actions**: offered per status as hints (`order-actions.ts`, compared with core's transition table: mark paid and cancel while awaiting payment, mark fulfilled and cancel when paid, nothing for fulfilled, cancelled or expired), each only when the session may run its own operation (`markOrderPaid`, `markOrderFulfilled`, `cancelOrder`: `orders.write`). The server decides; its refusal is shown in the dialog and the order is read again. Every write goes through `runWrite` (once, never retried) inside one single flight per page (a second submit while one runs sends nothing); the buttons are disabled while it runs and while the order reloads; after every answer the order is read again (never optimistic) and the status line says what happened ("The history below shows the change").
  - **Mark paid** (owner answer 8, `mark-paid-form.ts`): the amount is the order total, shown read-only (formatted plus the currency code); there is no amount field, the body takes `order.total` as stored. A payment reference (trimmed, 1 to 255 characters, no control characters, the API's rule) and the "I received this amount" checkbox are required before anything is sent. Refusals: `amount_mismatch`, `order_not_payable`, `payment_reference_conflict`, `invalid_transition` have their own explanations. A lost answer (network, timeout) is "the result is unknown": the dialog closes, the order is read once to say whether the payment with that reference was recorded, paid with another reference, not recorded, or the order is now cancelled or expired, and the screen reloads. Nothing is resent by the screen. When it was not recorded the next mark-paid dialog keeps the SAME reference (and asks for the confirmation again): `docs/api/orders.md` says the same reference on an order that is already paid (or fulfilled) answers `200` with the order unchanged and another reference is `payment_reference_conflict`, so a retry with the same reference cannot record a second payment.
  - **Mark fulfilled**: a confirmation; `awaiting_stock` (a backordered line not on hand yet; nothing changes) is explained with what to do (receive the stock on the product's Stock tab).
  - **Cancel** (`cancel-form.ts`): a required reason (trimmed, 1 to 500 characters, kept on the order and in the history), a danger button; for an unpaid order "the reserved stock is released"; for a paid order a warning that cancelling does not restock and does not refund anything (sold units stay sold; record the stock return and the refund by hand; only units still reserved for a backordered line are released), as `docs/api/orders.md` and ADR 0022 state.
  - A dialog with typed input (reference, reason) asks before the page is left (`useUnsavedChangesGuard`); Escape and Close are off while a write runs.
- Messages: `src/messages/{uk,en}/orders.json` (namespace `order.*`, not `orders.*`, because the messages spec treats every `"<namespace>.<...>"` literal as a key and `"orders.read"` / `"orders.write"` are permission names); `order-messages.spec.ts` checks the keys built from data.

## Customers (`src/areas/customers/`, step 9)

One lazy chunk with its own messages only (`customers`; it imports nothing from the other areas). Routes: `/customers` (`listCustomers`: `customers.read`) and `/customers/:id` (`getCustomer`: `customers.read`, route id `customerDetail`). The viewer has no `customers.read`: the navigation item is hidden, both routes show "not allowed" and no customer request is made.

- **List** (`customer-list-page.tsx`, `customer-list-view.tsx`, `customer-list-query.ts`): server-driven table, 50 a page (the API's default): email (link to the detail by id, the row header), name (first and last name as text, "no name given" when both are empty), status as text plus tone (active, deactivated), last sign-in and registration date (`Intl`, the browser's time zone). The API's list answers `{id, email, firstName, lastName, isActive, lastLoginAt, createdAt}` only: it has no lock state, no order count and no status filter, so the list shows none of them and makes no per-row request (no N+1; those are on the detail). The only filter is `q`, the start of the email: trimmed (the API ignores surrounding spaces and case), at most 254 characters (longer text is explained and never sent), debounced 300 ms, replacing the history entry while typing; `q` and the paging are in the URL, which holds nothing else (never a name, a phone or an email except what the admin typed into the search). States: loading rows, empty ("no customers yet"), no match (with "clear the search"), past the end of the list, failure with a retry, forbidden.
- **Detail** (`customer-detail-page.tsx`, `customer-detail-view.tsx`): one read (`GET /admin/customers/{id}`). Profile: email, name and phone as text (a name like `<b>x</b>` is shown as written), "no phone given" for `null`. Account: status, the sign-in lock as text plus tone (`isLocked`; the API gives only that flag, never a time, so a locked account shows an alert that says what the docs say: five failed sign-ins lock an account for 15 minutes, sign-in is refused meanwhile, the lock ends by itself or an admin with `customers.write` can clear it, and the API does not tell when), `orderCount`, last sign-in, registered, last changed (`updatedAt`). "Orders of this customer" links `/orders?customerId=<id>` (the id only), shown when the session may read orders (`listOrders`). A deleted id shows "does not exist", a malformed one the API's `400` as a translated failure.
- **Actions** (`customer-actions.ts`: offered as hints; the server decides): **Deactivate** for an active customer and **Activate** for a deactivated one (both `PATCH /admin/customers/{id}` `{isActive}`, `customers.write`), and **Unlock** (`POST /admin/customers/{id}/unlock`, `customers.write`) only while `isLocked`. A viewer, or a session with only `customers.read`, is offered none and no button is rendered. Deactivate asks first (`ConfirmDialog`, danger, focus on the safe choice, Escape cancels) and says what the docs say: all the customer's sessions end at once, their sign-in is refused while the account is deactivated, the account and its orders are kept, and it can be activated again. Activate and Unlock need no confirmation; the text beside each says what it does (activate lets the customer sign in again; unlock clears the failed sign-in counter and the lock and leaves sessions alone). Every write goes through `runWrite` (once, never retried) inside one single flight per page (a second submit while one runs sends nothing); nothing is optimistic: after every answer (done, refused or lost) the customer is read again and the focused status line says what happened. A refusal is explained by the shell's problem map (the customer routes document `400` and `404` only; the API's English `detail` is never shown). A lost answer ("result unknown") says so, reads the customer again and tells what is stored (now deactivated, still active, now active, still deactivated, not locked, still locked) without claiming the write landed; the admin presses the button again if it did not.
- Messages: `src/messages/{uk,en}/customers.json` (namespace `customer.*`, not `customers.*`, because the messages spec treats every `"<namespace>.<...>"` literal as a key and `"customers.read"` / `"customers.write"` are permission names); `customer-messages.spec.ts` checks the keys built from data, `customers-source.spec.ts` pins the rules a markup test cannot see (one send per write through the single flight, no timer or loop, a reload after every answer, a confirmation only for deactivate, ids only in links, the debounce).

## Admin users (`src/areas/users/`, step 10)

One lazy chunk with its own messages only (`users`; it imports nothing from the other areas except the account area's `PASSWORD_LIMITS`, whose messages are eager). Routes: `/users` (`listUsers`), `/users/new` (`createUser`) and `/users/:id` (`getUser`), all `users.manage` (owner only). Without `users.manage` in the session's permission list (never the role name) the navigation item is hidden, all three routes show "not allowed" and no users request is made.

- **List** (`user-list-page.tsx`, `user-list-view.tsx`, `user-list-query.ts`): server-driven table, 50 a page (the API's default; `limit` and `offset` in the URL, nothing else): email (link to the detail by id, the row header) with "you" on the signed-in admin's row (by id from `me`), role and activity as text plus tone, last sign-in ("never signed in"), created. The API's list has no filter and is ordered by email, so the screen has none. Loading rows, past the end, error with retry, not allowed; the create link only when the session may run `createUser`.
- **Roles** (`user-view.ts`): the three fixed roles of ADR 0009, each explained by exactly its permissions (a copy of core's `ROLE_PERMISSIONS`, compared in `user-view.spec.ts`), one sentence per permission and nothing more.
- **Password policy** (`password-policy.ts`): core's `validatePassword` copied (12 to 128 characters counted as code points, not the account's email trimmed and in any case, no NUL, no composition rules), with the limits from `areas/account/password-form.ts`; compared with core over about 580 inputs. The field (`NewPasswordField` in `user-parts.tsx`) is `type="password"` with `autocomplete="new-password"`, shows under it "met / not met" for the length (with the count) and "not the email", has a show or hide button (`aria-pressed`) and a "generate a password" button (`password-generator.ts`: 20 characters from 57 without look-alikes, `crypto.getRandomValues`, bytes above the last full round of the alphabet thrown away; the generated password is put into the field and shown there once). A password that breaks the policy is refused before sending with core's reason (`errors.reason.*`, the messages the account form shows); the server still decides and its `400` lands on the field.
- **Create** (`user-create-page.tsx`, `user-create-view.tsx`, `user-form.ts`): email (`type="email"`, `autocomplete="off"`, at most 254), role (radio group, the viewer preselected), initial password. Sent once (single flight, `runWrite`, never retried); after every answer the password is cleared and hidden. Success replaces the form by a focused panel with the stored email and role, a link to the user and to the list: the password is not shown again, no email exists, so the owner hands it over out of band and the user changes it under Your account. A duplicate email (`409 conflict` with `field: "email"`, any case) is shown on the email field. A lost answer reads the list (at most 10 pages of 100, reads only, `user-lookup.ts`) and says whether a user with that email is stored now (without claiming this request created it), that none is, that the list is too long to check here, or that it could not be read; nothing is resent.
- **Detail** (`user-detail-page.tsx`, `user-detail-view.tsx`, `user-dialogs.tsx`, `user-actions.ts`): email, role, activity, last sign-in, created, last changed, and on the own account a warning that changing the own role or activity can lock the owner out (the server keeps at least one active owner). Actions (hints; each needs its operation's permission from `ADMIN_OPERATIONS`): **change role** (radio group; `PATCH {role}` only, through `diffForPatch`; disabled while the stored role is chosen) confirmed with "applies from the user's next request; sessions stay"; **deactivate** (`PATCH {isActive: false}`) as a danger confirmation that says all sessions end at once and sign-in is refused until activated; **activate** (`PATCH {isActive: true}`) without a confirmation; **reset password** (`user-reset-form.ts`: `{newPassword}` with the same field and policy checked against the target's email) as a danger confirmation that says ALL sessions of that user end and the sign-in lock is cleared. On the own account the role and deactivation dialogs need an extra tick ("I understand that this changes my own account") before the confirm button works and say what happens: another role removes the users area from the next request (the `403` then reloads `me` and the page shows "not allowed"); deactivation ends this session and sign-in stays refused; the reset dialog says this session ends too: after the `204` the next read is a `401`, the shell's re-sign-in dialog asks for the new password and the status line stays. The refusals `last_owner_cannot_be_demoted` and `last_owner_cannot_be_deactivated` are explained inside the open dialog (and in the status line): make another user an owner first. Every write is sent once through one single flight per page and `runWrite`, never retried and never optimistic; after every answer (done, refused, lost) the user is read again and the focused status line says what happened; a lost answer says what the stored user is now (role, activity) without claiming the request landed, and for a reset that the stored user cannot show it. The typed reset password lives only in the reset form's own state and is cleared after every answer; the unsaved-changes guard covers a chosen role and a typed password.
- Messages: `src/messages/{uk,en}/users.json` (namespace `user.*`, because `users.manage` is a permission name and the messages spec reads every `"<namespace>.<...>"` literal as a key); role names are the eager `role.*` of the account area. `user-messages.spec.ts` checks the keys built from data, `users-screen.spec.tsx` the markup of every state with sentinel and real uk/en messages, `users-source.spec.ts` the rules a markup test cannot see (each write called from one page, once, through the single flight; no timer, loop or retry; a reload after every answer; confirmations exactly where required; the password kept in its form, cleared after every answer, never in a URL, storage or log; crypto random only; ids only in links; offers from the permission list; no other area).

## Known limits

- Concurrent edits are last-write-wins per field (no version on the API, owner answer 13); there is no audit log for catalog, price, user or customer changes.
- No proactive "session ends soon" warning (the API does not expose the expiry).
- The focus moves to the heading only when the path changes, not on a query-only change.
- Media and option changes replace whole sets (the API has no partial update): two admins editing one product's images or options at the same time overwrite each other (last write wins for the set).
- A click on a tab's button while the product reloads after a write may be lost when the tab remounts with the new data (the tab is marked busy meanwhile).
- Prices: a comma is never taken as the decimal separator (refused with a message), so an admin on a keyboard that offers only a comma for `inputmode="decimal"` types a dot by hand. Prices in other currencies than the shop's are kept but never sold or converted (API rule). Two admins editing prices of one product at the same time: the last bulk save wins per cell (no version on the API).
- Stock: the form's checks use the last read; the server decides under its row lock (another admin's change in between can still refuse it, and the refusal is shown). The adjustment API has no idempotency key (owner answer 12): after a lost answer the journal check tells whether a new movement by you appeared, but it cannot prove that this movement is the one sent (an admin working in two tabs could mistake one for the other). Locations are read-only in the API, so the tab shows no location management. The reservation links open the orders list searched by the order number (step 8).
- Variants cannot be reordered in this step (the API's `position` exists; the table shows the stored order), and the read-only `variant.title` is not shown.
- Orders: the date filter uses the browser's time zone (no shop time zone setting, plan gap 18), so two admins in different zones get different lists for the same days in the URL. The search finds an exact number or an exact email only (no prefix or name search in the API). The list has no sort option (newest first). Mark-paid records full payments of the total only (owner answer 8). Mark fulfilled and cancel have no idempotency key (none needed: a repeated mark fulfilled or cancel is refused as `invalid_transition`), but after a lost answer the admin reads the reloaded status before acting again.
- Admin users: the list has no search or filter and no lock state (the API offers none; a locked admin is unlocked by a password reset or `pnpm admin:unlock`); there is no delete (deactivate instead), no email change and no audit log of user changes; the last-owner rule is the server's (the screen does not count owners, it explains the refusal); a lost answer to a password reset cannot be told from the stored user (set it again if the new password does not work); after resetting the own password the page shows the `401` failure under its status line until the admin signs in again and presses retry; after a lost create answer only the first 1 000 users are checked for the email.
- Customers: the list has no lock state, order count or status filter (the API's list does not offer them) and the search finds the start of an email only, not a name. The lock shows as a flag; the API gives no time for it. An admin cannot create or delete a customer, change an email or set a password (no such route); deactivating does not restore sessions when the account is activated again (they were deleted). A lost answer is shown with the stored state and never retried by the screen.
