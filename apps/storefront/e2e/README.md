# Storefront end-to-end tests (Playwright)

Browser tests of the purchase flow against the real stack: Postgres, Redis, Meilisearch, the built API, the built storefront and a same-origin proxy. Plan: `docs/plans/2026-10-18-storefront.md`, step 8. Chromium only. They are NOT part of `pnpm test` (they are slow and need a browser); run them with `pnpm test:e2e`.

## Run it locally

1. Services up (README quick start: Compose, or native Postgres, Redis and Meilisearch). Node 22, `pnpm install`.
2. Create a database for the suite. Its name MUST end in `_e2e_test`; the suite DROPS everything in it at the start of every run, so do not reuse `fluxkit_test` (`pnpm test`) or a development database:
   ```bash
   createdb -h 127.0.0.1 -U <user> fluxkit_e2e_test          # or: psql ... -c 'create database fluxkit_e2e_test'
   ```
3. Install the browser once: `pnpm --filter @fluxkit/storefront exec playwright install chromium` (add `--with-deps` on a fresh Linux machine). If `PLAYWRIGHT_BROWSERS_PATH` already points at a Chromium of the right revision (1248 for the pinned `@playwright/test` 1.64.1, see `browsers.json` of `playwright-core`) nothing is downloaded.
4. Run, from the repository root:
   ```bash
   ( export E2E_DATABASE_URL=postgres://<user>:<password>@127.0.0.1:5432/fluxkit_e2e_test \
            REDIS_URL=redis://127.0.0.1:6379 MEILI_URL=http://127.0.0.1:7700 MEILI_MASTER_KEY=<key>
     pnpm test:e2e )
   ```
   `pnpm test:e2e` runs `pnpm build` first, then Playwright. A single scenario: `pnpm --filter @fluxkit/storefront test:e2e guest-purchase` (after a build). Headed/debug: `pnpm --filter @fluxkit/storefront exec playwright test -c e2e/playwright.config.ts --headed --debug`.

Redis and Meilisearch are required (the same variables as the integration tests). Redis is used for nothing else; Meilisearch holds the suite's search index since the search plan's step 10a (below). The root `.env` is never read.

## What a run does

`e2e/playwright.config.ts` starts three web servers (it never reuses a running one) and waits until they answer:

| Server                                                 | Port | Command                                                          |
| ------------------------------------------------------ | ---- | ---------------------------------------------------------------- |
| API (built, `apps/api/dist/main.js`)                   | 3100 | `e2e/prepare-database.ts` first, then the API                    |
| Storefront (built, `next start`)                       | 3101 | `.next/cache/fetch-cache` is deleted first (see Troubleshooting); `STOREFRONT_FORWARD_CLIENT_ADDRESS=true` |
| Proxy (`e2e/proxy.ts`, the only origin a browser sees) | 3102 | `node --experimental-strip-types e2e/proxy.ts`                   |
| Storefront again, search on only                       | 3103 | the same build with `STOREFRONT_FORWARD_CLIENT_ADDRESS=false`, reached directly by one search test (ADR 0038) |

Ports can be changed with `E2E_PORT`, `E2E_API_PORT`, `E2E_STOREFRONT_PORT`, `E2E_STOREFRONT_UNFORWARDED_PORT`.

- **Database.** `e2e/prepare-database.ts` refuses a name that does not end in `_e2e_test` (and checks `select current_database()`), drops the `drizzle` and `public` schemas, then runs the API's own built commands: `database/migrate.js`, `seed/seed.js --dataset test` (the TEST FIXTURE catalog of `pnpm seed:test`, not the coffee demo of `pnpm seed`) and `auth/create-admin.js` (one owner, `e2e-owner@example.com`, a throwaway password in `support/env.ts`). It is part of the API's `webServer` command and not a `globalSetup` because Playwright starts web servers BEFORE `globalSetup`. `pg` is resolved from `apps/api` (no dependency of its own).
- **API environment.** `apiEnvironment()` in `support/env.ts` SETS every variable that decides behaviour (`TRUST_PROXY=1`, `STORE_COOKIE_SECURE=false`, `ADMIN_COOKIE_SECURE=false`, `ORDER_TOKEN_SECRET`, `SCHEDULER_ENABLED=false`, `FEATURES_ENABLED=`, `SHIPPING_PROVIDERS_ENABLED=fake`, `MAX_OPEN_ORDERS=3`, ...), so a variable exported in your shell cannot change a run. The processes are started with plain `node`, not with the package scripts that need a root `.env`.
- **Same origin (ADR 0026).** The cookies have `Path=/store`, writes need `X-Fluxkit-CSRF` and the API sends no CORS headers, so the browser must reach `/store/*` and the pages on one origin. `proxy.ts` routes `/store/*`, `/admin/*` and `/media/*` (uploaded images, ADR 0028) to the API and everything else to the storefront, and SETS `X-Forwarded-For` itself, like the production edge proxy (the API trusts exactly this one hop). The API's answers come back unchanged: the proxy adds no cookie and no header.
- **Uploads.** The API runs with `MEDIA_STORAGE_DRIVER=local`, `MEDIA_DIR` = `<system temp>/fluxkit-storefront-e2e-media-<proxy port>` (`E2E_MEDIA_DIR`; wiped and created by `prepare-database.ts`, removed by `global-teardown.ts`; never the repository's `var/media`) and `MEDIA_PUBLIC_BASE_URL` = the proxy origin + `/media`. This suite checks only the routing: `media-route` uploads a 1x1 PNG through the admin API, reads it through the proxy (the API's headers, a `404` for a missing key and a traversal that is not the storefront's HTML) and opens a product page whose image is that upload. It does NOT show the uploaded image in the storefront: the storefront accepts only absolute `https` URLs of `STOREFRONT_IMAGE_HOSTS` and the Next image optimizer refuses a loopback address, so on this stack the page shows the placeholder (and the test asserts that, and that no `/media` or `/_next/image` request is made). The browser e2e of the upload controls is `apps/admin/e2e`.
- **Email (email plan step 10).** The API process runs with `EMAIL_PROVIDER=fake`, `EMAIL_FROM`, `STOREFRONT_PUBLIC_URL` (the proxy origin: the ONLY base of links in mail) and `FAKE_EMAIL_CAPTURE_FILE` = `<system temp>/fluxkit-storefront-e2e-mail-<proxy port>.jsonl` (`E2E_MAIL_FILE`; removed by `prepare-database.ts` at the start and by `global-teardown.ts` at the end). The test-only `fake` provider (`packages/providers/_fake-email`) delivers nothing: it appends every accepted mail as one JSON line, and `support/mailbox.ts` reads that file (`newestLink(email, "reset-password" | "verify-email")` polls until the mail is there and returns the newest link; links are read from the plain-text part). The mail goes out right after the API's answer (the immediate attempt), so no scheduler is needed. With a provider, the storefront shows "Forgot password?" and the verification notice, and registration sends one verification mail; no other scenario depends on mail, so the rest of the suite runs as before (every test uses its own addresses; the capture file only grows). Verification mails are written in `DEFAULT_LOCALE` (`uk`): a test that checks English wording opens `inLocale(link, "en")`. The `emailDelivery=false` behaviour cannot be switched in this stack (the shells read the flag on the server) and is covered by unit tests.
- **Payments (payments plan steps 9 and 11).** The API process runs with `PAYMENT_PROVIDERS_ENABLED=fake` (the test-only provider of `packages/providers/_fake-payment`; `ORDER_PAYMENT_TTL_MINUTES=30`, `STOREFRONT_PUBLIC_URL` is the proxy origin), so `GET /store/config` says `onlinePayment: true` and every order page shows the pay step. A payment is CREATED through the real routes (an invoice with the page `https://pay.fake.invalid/pay/<id>`, which is how a test learns the invoice id) and SETTLED by the test playing the provider: `support/fake-provider.ts` POSTs the fake's webhook to the real `POST /webhooks/payments/fake` through the proxy, signed (`x-fake-signature`, HMAC-SHA256 over the exact body bytes with the fake's PUBLIC test key, `packages/providers/_fake-payment/README.md`, "Driving it from another process"). The API therefore runs its real raw-body reader, signature check, fact binding and order integration, and the production API has no test-only route. The proxy routes `/webhooks/payments` to the API and forwards the bytes unchanged, like the production edge proxy (`infra/proxy/nginx`). The fake's in-process hooks (`failNext`, `process`, `expire`, ...) still cannot cross the process boundary, so the scenarios of `payment.e2e.ts` use browser-level stubs for the states a webhook cannot produce. The scheduler is off, so job 11 never runs (the `jobs:run-once` command would run in a process that does not hold the fake's invoices): the automatic refund of a late payment is asserted as QUEUED, not sent. The page host `pay.fake.invalid` is answered by a Playwright stub; nothing leaves the machine. `FAKE_PAYMENT_ADOPT_WEBHOOKS` is not set here (this suite never refunds); the admin suite sets it.
- **Shipping.** The API process runs with the test-only `fake` shipping provider (`packages/providers/_fake`: cities Kyiv, Lviv, Odesa, a branch and a locker in each, numbered waybills; no network). Enabling a provider changes nothing for the shop until a method is ACTIVE, so the other scenarios run as before shipping existed. `shipping-checkout` creates its methods through the admin API (the owner holds `shipping.manage`) with codes that carry the retry number, and an `afterEach` hook deactivates every method (methods stay, orders may link them). A scenario that adds a method must do the same, or the later files would need a delivery choice.
- **Rate limits.** The `checkout` limit is 10 per 10 minutes per client address, in memory. Every test sends a header `x-e2e-client: <number>` (Playwright `extraHTTPHeaders`, see `support/fixtures.ts`); only the proxy reads it, turns it into `10.a.b.c`, uses that as `X-Forwarded-For` and removes it. So each test, retry and "other shopper" has its own address and window. No production code knows about the header. `MAX_OPEN_ORDERS` (3 unpaid orders per email) is avoided with a unique email per test (`uniqueEmail`).
- **Search (search plan step 10a).** By default the API runs with `SEARCH_ENABLED=true` against the REAL Meilisearch of `MEILI_URL`, with its own index prefix `e2e<proxy port>_` (`MEILI_INDEX_PREFIX`, so the engine can be shared with other runs). Setup order in `prepare-database.ts`: remove leftovers of an earlier run (the suite's indexes and keys, found by prefix and by the key description `fluxkit storefront e2e <port>`), create a KEY SCOPED to `e2e<port>_*` with the actions the API needs and nothing else (`support/meili.ts`, exactly the operator's recipe in the root README, made with `MEILI_MASTER_KEY`, which only this setup and the teardown hold; the key goes to `<system temp>/fluxkit-storefront-e2e-meili-key-<port>.json`, mode 0600), wipe, migrate, seed (the catalog writes mark the products for the index), create the owner, then run the built `search/reindex.js` (`pnpm search:reindex`: builds the index of both locales and swaps it in; the scheduler is off, so nothing else would). The API process reads the key from that file in its start command, so it is in no process list and no config. `global-teardown.ts` deletes the key, the indexes and the file. `apiEnvironment()` never takes `MEILI_API_KEY` from the shell. **`E2E_SEARCH=off`** starts the same stack with `SEARCH_ENABLED=false` (no key, no reindex): `search.e2e.ts` and `catalog-facets.e2e.ts` then skip themselves and `search-off.e2e.ts` runs; every other file runs in both modes, so the catalog without search stays covered. CI runs the default (search on) mode; run `E2E_SEARCH=off pnpm test:e2e` for the other. The 429 test uses the proxy's per-test client address: it proves that the Next server passes the shopper's `X-Forwarded-For` on to the API when `STOREFRONT_FORWARD_CLIENT_ADDRESS=true`; the test after it reaches the second storefront (forwarding off) directly with a new invented address per page and is still limited, so an off storefront passes nothing on.
- **Workers.** One worker, tests in file order. The scenarios change shared catalog data (a price, the last unit of a product) and each test uses a product no other test changes, so they are deterministic; they do not depend on each other's orders.
- **Retries and artifacts.** No retry locally; one in CI (`CI` set). Trace on the first retry, screenshot and video only on failure, in `apps/storefront/test-results/`; CI also writes the HTML report to `apps/storefront/playwright-report/` and uploads both when the job fails (both are git-ignored). **The artifacts contain session material**: the `fluxkit_cart` and `fluxkit_customer_session` cookies, guest order tokens in request bodies and URLs, and the e2e owner's admin session. All of it belongs to a throwaway database that is wiped at every run and to an ephemeral API, so this is acceptable; keep it that way (never put a real secret or real data into the e2e environment). Retention is 7 days. Open a trace: `pnpm --filter @fluxkit/storefront exec playwright show-trace test-results/<test>/trace.zip`.
- **No sleeps.** Tests wait with Playwright's auto-waiting and web-first assertions. The one synchronisation helper, `waitForHydration` (`support/flows.ts`), waits for the cart badge to show a count, which only happens after the page's islands run in the browser.

## Troubleshooting

- `E2E_DATABASE_URL must be set` / `Refusing to wipe database ...`: see step 2; the name rule is deliberate.
- `Executable doesn't exist ...`: the browser for this Playwright version is not installed (step 3). Playwright 1.64.1 needs Chromium revision 1248.
- A web server "timed out": run the three commands of the table by hand to see the error. The API needs `pnpm build` (the suite uses `dist/`), Redis and Meilisearch.
- Product pages answer "Nothing was found" on add to cart: the storefront rendered ids of a previous seed from its on-disk data cache (`.next/cache/fetch-cache`, 60 s). The suite deletes that directory before it starts the storefront; if you start the storefront yourself against a re-seeded database, delete it too.
- Port in use: another run or server holds 3100 to 3102 (`reuseExistingServer` is off on purpose): stop it or set the `E2E_*` ports.
- A test hangs in `request.allHeaders()` until its timeout: that promise settles only for a request that got its response (Chromium reports the raw headers then). Read it in `requestfinished`, never in `request` (`token-hygiene.e2e.ts` shows how; it showed up under load, several workers).
- One Playwright run at a time per database (the schema is wiped at the start).

For every entry of the fixed selector list (`support/visual/selectors.ts`, versioned; roles, `data-*`, element selectors and text, never classes) the first visible match's `getComputedStyle`: four corner radii, font family, size, weight, line height, letter spacing, text transform, text decoration line, colour, background, four border colours, widths and styles, box shadow, outline (colour, style, width, offset), four paddings, aspect ratio. An element missing on one side is a `presence` difference. Positive coverage: each page must stay on its address and find its `REQUIRED_SELECTORS` (`support/visual/pages.ts`: body, header, h1, footer everywhere; cards and prices on home and catalog; the secondary button in the cart; field and submit button on login, register and checkout; summary and badge on the product page), or the recording fails; the report warns about selectors absent on every page and side. |
| Screenshots (`tests/screenshots.visual.ts`) | secondary | full-page frames of `/uk`, catalog, product, cart, checkout, `/uk/search?q=футболка`, login, register, privacy, `/uk/nonexistent` at 390 x 844 and 1280 x 800 in light and dark, plus `system` with a dark colour scheme on home and product; `/en` and `/en/catalog` at 1280; element shots (header, footer, first card, hero) on home; `/uk` and `/en` register without JavaScript. `toHaveScreenshot` with `animations: "disabled"`, `caret: "hide"`, `scale: "css"`, `maxDiffPixels: 0`. |

Both freeze what they can: `reducedMotion: "reduce"`, `page.clock.install({ time: "2026-11-08T12:00:00Z" })` before the visit (scripts on), the seeded fixture, `STOREFRONT_IMAGE_HOSTS` empty (placeholder pictures), then wait for the load, the network to go quiet, hydration (React attached to `<main>`), no pending streamed boundary, no `[aria-busy="true"]`, fonts ready; the focus is dropped before reading.

Run it (the suite's variables of "Run it locally" exported, Chromium installed, the base branch fetched with history):

```bash
bash scripts/visual-compare.sh origin/main                     # both checks; exit 0 identical, 1 computed styles differ, 3 screenshots only, 2 harness failed
bash scripts/visual-compare.sh origin/main --skip-screenshots  # computed styles only (about half the time)
```

Options: `--keep-base-tree` keeps `.visual/base-tree` (the base's worktree, otherwise removed), `--skip-current-build` when this tree is already built, `--strict` (used by CI) also fails the computed styles when a declared exception matched nothing. Each run wipes the e2e database. Nothing under `.visual/` is committed except a PR's own `exceptions.json`.

Read the report (`.visual/report/`; in CI the `visual-report` artifact, and `visual-snapshots` with `baseline/` and `current/`, 7 days):
- `summary.txt` and `computed-styles.status` / `screenshots.status` (`pass`, `fail`, `error`, `skipped`),
- `computed-styles.txt`: one row per difference, `page | theme | selector | property | before | after` (`before` is the base), then the declared ones with their reasons, the exceptions that matched nothing and the selectors absent everywhere; `computed-styles.json` the same as data,
- `screenshots-html/index.html`: Playwright's report with expected, actual and diff side by side; `screenshots-results/` the raw diff images.

Declared exceptions (plan principle 2: any undeclared difference is a defect): commit `.visual/exceptions.json` in the PR that means to change something, a JSON array of
`{ "page": "<page id>" | "*", "theme"?: "light" | "dark" | "system", "selector": "<selector name>", "property": "<recorded property>" | "presence" | "*" | "screenshot", "reason": "<why>" }`.
`"*"` covers every property and the presence; `"screenshot"` masks the element in that page's screenshots (both sides). Page ids are in `support/visual/pages.ts` (`home`, `catalog`, `product`, `cart`, `checkout`, `login`, `register`, `legal-privacy`, `search`, `not-found`, `en-home`, `en-catalog`, `en-register`, and the phone pass `home-390`, `catalog-390`). A reason is required; an unknown field, page, selector or property or a duplicate is an error (exit 2, also checked before the runs: `node --experimental-strip-types apps/storefront/e2e/support/visual/compare-cli.ts --check-exceptions .visual/exceptions.json`). Only the entries this tree ADDED count: an entry already in the merge-base's file (same page, theme, selector and property, whatever its reason) belongs to an earlier PR and declares nothing, so exceptions never outlive their PR. Old entries may stay or be removed by any PR. In CI (`--strict`) an added entry that matches no difference fails the job. Example (B4, neutral demo pictures):

```json
[{ "page": "home", "selector": "home.hero", "property": "screenshot", "reason": "B4: neutral hero picture, before/after shown to the owner" }]
```

Tolerance: the default is exact (`maxDiffPixels: 0`). Only when a frame differs by anti-aliasing and the PR attaches that frame's diff image from an exact run, `VISUAL_TOLERANCE=ratio bash scripts/visual-compare.sh ...` uses `maxDiffPixelRatio: 0.005` with `threshold: 0.2`. The computed styles never have a tolerance.

The selector list and frames are a contract of this harness only: a PR that changes what an entry finds bumps `SELECTOR_LIST_VERSION`; both sides always run this tree's harness (the script copies `visual.config.ts`, `tests/*.visual.ts` and `support/visual/` into the base tree), so they never mix versions. The harness imports only `support/env.ts` of the other e2e files for that reason. Unit tests of its pure parts (selector rules, frames, snapshot merge, exceptions, diff, report, CLI exit codes): `pnpm --filter @fluxkit/storefront exec vitest run -c e2e/support/visual/vitest.config.ts` (not part of `pnpm test`; the `visual` CI job runs them).

CI: job `visual` (`.github/workflows/ci.yml`), after the cheap `visual-gate`, on a PR labelled `visual-check` (the label counts from the next push), on a PR that changes `packages/theme/**`, `packages/ui/**`, `apps/storefront/src/**`, `apps/storefront/public/**`, the storefront's `next.config.ts` or `postcss.config.mjs`, `e2e/support/env.ts`, `.visual/exceptions.json` or the harness, and on a manual run of the CI workflow (Actions, "Run workflow", base branch; it runs every job of the workflow and cancels an in-progress run on the same ref). The visual project runs without retries. Its "Computed styles" step fails on any undeclared difference, its "Screenshots" step on any frame over the tolerance.
