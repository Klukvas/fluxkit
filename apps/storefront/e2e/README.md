# Storefront end-to-end tests (Playwright)

Browser tests of the purchase flow against the real stack: Postgres, Redis, Meilisearch, the built API, the built storefront and a same-origin proxy. Plan: `docs/plans/2026-10-18-storefront.md`, step 8. Chromium only. They are NOT part of `pnpm test` (they are slow and need a browser); run them with `pnpm test:e2e`.

## Run it locally

1. Services up (README quick start: Compose, or native Postgres, Redis and Meilisearch). Node 22, `pnpm install`.
2. Create a database for the suite. Its name MUST end in `_e2e_test`; the suite DROPS everything in it at the start of every run, so do not reuse `fluxkit_test` (`pnpm test`) or a development database:
   ```bash
   createdb -h 127.0.0.1 -U <user> fluxkit_e2e_test          # or: psql ... -c 'create database fluxkit_e2e_test'
   ```
3. Install the browser once: `pnpm --filter @fluxkit/storefront exec playwright install chromium` (add `--with-deps` on a fresh Linux machine). If `PLAYWRIGHT_BROWSERS_PATH` already points at a Chromium of the right revision (1194 for the pinned `@playwright/test` 1.56.1) nothing is downloaded.
4. Run, from the repository root:
   ```bash
   ( export E2E_DATABASE_URL=postgres://<user>:<password>@127.0.0.1:5432/fluxkit_e2e_test \
            REDIS_URL=redis://127.0.0.1:6379 MEILI_URL=http://127.0.0.1:7700 MEILI_MASTER_KEY=<key>
     pnpm test:e2e )
   ```
   `pnpm test:e2e` runs `pnpm build` first, then Playwright. A single scenario: `pnpm --filter @fluxkit/storefront test:e2e guest-purchase` (after a build). Headed/debug: `pnpm --filter @fluxkit/storefront exec playwright test -c e2e/playwright.config.ts --headed --debug`.

Redis and Meilisearch are required by the API at start-up (the same variables as the integration tests; the suite does not use Redis for anything else and needs no Meilisearch index). The root `.env` is never read.

## What a run does

`e2e/playwright.config.ts` starts three web servers (it never reuses a running one) and waits until they answer:

| Server                                                 | Port | Command                                                          |
| ------------------------------------------------------ | ---- | ---------------------------------------------------------------- |
| API (built, `apps/api/dist/main.js`)                   | 3100 | `e2e/prepare-database.ts` first, then the API                    |
| Storefront (built, `next start`)                       | 3101 | `.next/cache/fetch-cache` is deleted first (see Troubleshooting) |
| Proxy (`e2e/proxy.ts`, the only origin a browser sees) | 3102 | `node --experimental-strip-types e2e/proxy.ts`                   |

Ports can be changed with `E2E_PORT`, `E2E_API_PORT`, `E2E_STOREFRONT_PORT`.

- **Database.** `e2e/prepare-database.ts` refuses a name that does not end in `_e2e_test` (and checks `select current_database()`), drops the `drizzle` and `public` schemas, then runs the API's own built commands: `database/migrate.js`, `seed/seed.js` (the demo catalog) and `auth/create-admin.js` (one owner, `e2e-owner@example.com`, a throwaway password in `support/env.ts`). It is part of the API's `webServer` command and not a `globalSetup` because Playwright starts web servers BEFORE `globalSetup`. `pg` is resolved from `apps/api` (no dependency of its own).
- **API environment.** `apiEnvironment()` in `support/env.ts` SETS every variable that decides behaviour (`TRUST_PROXY=1`, `STORE_COOKIE_SECURE=false`, `ADMIN_COOKIE_SECURE=false`, `ORDER_TOKEN_SECRET`, `SCHEDULER_ENABLED=false`, `FEATURES_ENABLED=`, `SHIPPING_PROVIDERS_ENABLED=fake`, `MAX_OPEN_ORDERS=3`, ...), so a variable exported in your shell cannot change a run. The processes are started with plain `node`, not with the package scripts that need a root `.env`.
- **Same origin (ADR 0026).** The cookies have `Path=/store`, writes need `X-Fluxkit-CSRF` and the API sends no CORS headers, so the browser must reach `/store/*` and the pages on one origin. `proxy.ts` routes `/store/*`, `/admin/*` and `/media/*` (uploaded images, ADR 0028) to the API and everything else to the storefront, and SETS `X-Forwarded-For` itself, like the production edge proxy (the API trusts exactly this one hop). The API's answers come back unchanged: the proxy adds no cookie and no header.
- **Uploads.** The API runs with `MEDIA_STORAGE_DRIVER=local`, `MEDIA_DIR` = `<system temp>/fluxkit-storefront-e2e-media-<proxy port>` (`E2E_MEDIA_DIR`; wiped and created by `prepare-database.ts`, removed by `global-teardown.ts`; never the repository's `var/media`) and `MEDIA_PUBLIC_BASE_URL` = the proxy origin + `/media`. This suite checks only the routing: `media-route` uploads a 1x1 PNG through the admin API, reads it through the proxy (the API's headers, a `404` for a missing key and a traversal that is not the storefront's HTML) and opens a product page whose image is that upload. It does NOT show the uploaded image in the storefront: the storefront accepts only absolute `https` URLs of `STOREFRONT_IMAGE_HOSTS` and the Next image optimizer refuses a loopback address, so on this stack the page shows the placeholder (and the test asserts that, and that no `/media` or `/_next/image` request is made). The browser e2e of the upload controls is `apps/admin/e2e`.
- **Email (email plan step 10).** The API process runs with `EMAIL_PROVIDER=fake`, `EMAIL_FROM`, `STOREFRONT_PUBLIC_URL` (the proxy origin: the ONLY base of links in mail) and `FAKE_EMAIL_CAPTURE_FILE` = `<system temp>/fluxkit-storefront-e2e-mail-<proxy port>.jsonl` (`E2E_MAIL_FILE`; removed by `prepare-database.ts` at the start and by `global-teardown.ts` at the end). The test-only `fake` provider (`packages/providers/_fake-email`) delivers nothing: it appends every accepted mail as one JSON line, and `support/mailbox.ts` reads that file (`newestLink(email, "reset-password" | "verify-email")` polls until the mail is there and returns the newest link; links are read from the plain-text part). The mail goes out right after the API's answer (the immediate attempt), so no scheduler is needed. With a provider, the storefront shows "Forgot password?" and the verification notice, and registration sends one verification mail; no other scenario depends on mail, so the rest of the suite runs as before (every test uses its own addresses; the capture file only grows). Verification mails are written in `DEFAULT_LOCALE` (`uk`): a test that checks English wording opens `inLocale(link, "en")`. The `emailDelivery=false` behaviour cannot be switched in this stack (the shells read the flag on the server) and is covered by unit tests.
- **Payments (payments plan step 9).** The API process runs with `PAYMENT_PROVIDERS_ENABLED=fake` (the test-only provider of `packages/providers/_fake-payment`; `ORDER_PAYMENT_TTL_MINUTES=30`, `STOREFRONT_PUBLIC_URL` is the proxy origin), so `GET /store/config` says `onlinePayment: true` and every order page shows the pay step. A payment can be CREATED (an invoice with the page `https://pay.fake.invalid/pay/...`) and read, but not settled: the fake's `complete`/`fail`/`expire` hooks exist only inside the API process and there is no bridge. The scenarios therefore answer that reserved host with a Playwright stub and use browser-level stubs for the states they cannot produce. The proxy still has no `/webhooks` route (plan step 11), so no webhook reaches the API in this suite.
- **Shipping.** The API process runs with the test-only `fake` shipping provider (`packages/providers/_fake`: cities Kyiv, Lviv, Odesa, a branch and a locker in each, numbered waybills; no network). Enabling a provider changes nothing for the shop until a method is ACTIVE, so the other scenarios run as before shipping existed. `shipping-checkout` creates its methods through the admin API (the owner holds `shipping.manage`) with codes that carry the retry number, and an `afterEach` hook deactivates every method (methods stay, orders may link them). A scenario that adds a method must do the same, or the later files would need a delivery choice.
- **Rate limits.** The `checkout` limit is 10 per 10 minutes per client address, in memory. Every test sends a header `x-e2e-client: <number>` (Playwright `extraHTTPHeaders`, see `support/fixtures.ts`); only the proxy reads it, turns it into `10.a.b.c`, uses that as `X-Forwarded-For` and removes it. So each test, retry and "other shopper" has its own address and window. No production code knows about the header. `MAX_OPEN_ORDERS` (3 unpaid orders per email) is avoided with a unique email per test (`uniqueEmail`).
- **Workers.** One worker, tests in file order. The scenarios change shared catalog data (a price, the last unit of a product) and each test uses a product no other test changes, so they are deterministic; they do not depend on each other's orders.
- **Retries and artifacts.** No retry locally; one in CI (`CI` set). Trace on the first retry, screenshot and video only on failure, in `apps/storefront/test-results/`; CI also writes the HTML report to `apps/storefront/playwright-report/` and uploads both when the job fails (both are git-ignored). **The artifacts contain session material**: the `fluxkit_cart` and `fluxkit_customer_session` cookies, guest order tokens in request bodies and URLs, and the e2e owner's admin session. All of it belongs to a throwaway database that is wiped at every run and to an ephemeral API, so this is acceptable; keep it that way (never put a real secret or real data into the e2e environment). Retention is 7 days. Open a trace: `pnpm --filter @fluxkit/storefront exec playwright show-trace test-results/<test>/trace.zip`.
- **No sleeps.** Tests wait with Playwright's auto-waiting and web-first assertions. The one synchronisation helper, `waitForHydration` (`support/flows.ts`), waits for the cart badge to show a count, which only happens after the page's islands run in the browser.

## Troubleshooting

- `E2E_DATABASE_URL must be set` / `Refusing to wipe database ...`: see step 2; the name rule is deliberate.
- `Executable doesn't exist ...`: the browser for this Playwright version is not installed (step 3). Playwright 1.56.1 needs Chromium revision 1194.
- A web server "timed out": run the three commands of the table by hand to see the error. The API needs `pnpm build` (the suite uses `dist/`), Redis and Meilisearch.
- Product pages answer "Nothing was found" on add to cart: the storefront rendered ids of a previous seed from its on-disk data cache (`.next/cache/fetch-cache`, 60 s). The suite deletes that directory before it starts the storefront; if you start the storefront yourself against a re-seeded database, delete it too.
- Port in use: another run or server holds 3100 to 3102 (`reuseExistingServer` is off on purpose): stop it or set the `E2E_*` ports.
- A test hangs in `request.allHeaders()` until its timeout: that promise settles only for a request that got its response (Chromium reports the raw headers then). Read it in `requestfinished`, never in `request` (`token-hygiene.e2e.ts` shows how; it showed up under load, several workers).
- One Playwright run at a time per database (the schema is wiped at the start).
