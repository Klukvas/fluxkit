# @fluxkit/storefront

Next.js 16 (App Router, Turbopack) customer storefront. Plan: `docs/plans/2026-10-18-storefront.md`, decisions: ADR 0026, rules: `AGENTS.md` section 2.2 (theming, i18n, layout composition) and `apps/storefront/AGENTS.md` (read the Next docs in `node_modules/next/dist/docs/` before writing Next code: this version differs from older knowledge).

Status: steps 1 to 10 of the plan are merged (PRs #66 to #79; #78 is the step 9 docs sweep, #79 the step 10 review fixes). The browser tests are in `e2e/`, see "End-to-end tests (step 8)". Scope so far: checkout and orders, and since the shipping plan's step 10 (#125) the delivery step and the delivery and tracking of the order pages (see "Delivery and shipping"). On top of the catalog (home sections, catalog, category and product pages, SEO metadata, JSON-LD, `sitemap.xml`, `robots.txt`) and the cart and accounts (step 6), the checkout page, the guest order page (private link with the token in the URL fragment) and the customer's order history and order page exist, all rendered in the browser (see "Checkout and orders (step 7)"). **v1 takes no payment** (owner answer 9): an order stays `awaiting_payment` until an admin marks it paid or it expires (`ORDER_PAYMENT_TTL_MINUTES`, 30 minutes by default), so the template is not for live sales until the payment plan.

## Routes

| Route | Rendering | Data (all through the 60 s data cache) | Indexing |
|---|---|---|---|
| `/{locale}` | server, per request | `GET /store/products?limit=8`, `GET /store/categories`, `GET /store/config` | index, canonical, hreflang |
| `/{locale}/catalog` (`?page`, `?brand`) | server, per request | `GET /store/products?limit=24&offset=` (+ `brand`), `GET /store/config` | page 1 index; `noindex, follow` on a brand filter and on page 2 and later; canonical never has `brand` |
| `/{locale}/c/{slug}` (`?page`, `?brand`) | server, per request | categories tree (breadcrumbs, children), products with `category=` (descendants included by the API) | same rules as the catalog |
| `/{locale}/p/{slug}` | server, per request; `ProductPurchase` is a client island | `GET /store/products/{slug}`, config, categories | index, Product and BreadcrumbList JSON-LD |
| `/{locale}/cart` | shell on the server (the shop's currency digits and the image host list); the cart itself is read in the browser | `GET /store/cart` and the cart writes, `no-store`, same origin | `noindex, nofollow`, no canonical |
| `/{locale}/account/login`, `/register` (`?next`) | shell + client form | `POST /store/account/login`, `register` | `noindex, nofollow` |
| `/{locale}/account`, `/account/profile` | shell + client, behind the account gate | `GET`, `PATCH /store/account/me`, `change-password`, `logout` | `noindex, nofollow` |
| `/{locale}/checkout` | shell (the shop's currency digits) + client | the shared cart, `me` (prefill), `GET /store/shipping/options` and the carrier lookups (`GET /store/shipping/providers/{code}/cities`, `.../pickup-points`), `POST /store/checkout` with `Idempotency-Key`, `POST /store/cart/acknowledge` | `noindex, nofollow` |
| `/{locale}/order/{number}` (token in `#t=`) | shell (shop currency and digits) + client | `POST /store/orders/lookup`, `POST /store/orders/cancel` (token in the body) | `noindex, nofollow`, `Referrer-Policy: no-referrer`, fixed title |
| `/{locale}/account/forgot-password` | shell (`emailDelivery`) + client form | `POST /store/account/password-reset` | `noindex, nofollow`, `Referrer-Policy: no-referrer` |
| `/{locale}/account/reset-password` (token in `#t=`) | shell (`emailDelivery`) + client | `POST /store/account/password-reset/confirm` (token in the body) | `noindex, nofollow`, `Referrer-Policy: no-referrer` and `<meta name="referrer">`, fixed title |
| `/{locale}/account/verify-email` (token in `#t=`) | shell (`emailDelivery`) + client | `POST /store/account/verify-email` (token in the body), `POST /store/account/verify-email/resend` | same as reset-password |
| `/{locale}/account/orders` (`?page`), `/account/orders/{number}` | shell + client, behind the account gate | `GET /store/account/orders` (24 per page), `GET /store/account/orders/{number}`, `POST .../cancel` | `noindex, nofollow` |
| `/sitemap.xml`, `/robots.txt` | server, per request | products in pages of 100 (1 hour cache), categories | - |

- **Real 404s.** The catalog, category and product routes live in the `(catalog)` route group, which has NO `loading.tsx` (see the finding in "Rendering and caching"): `notFound()` before the first byte answers HTTP 404. `route-structure.spec.ts` fails if a `loading.tsx` ever appears above them. The cost: these pages show no loading skeleton; the whole page waits for its data (cached 60 s, so usually fast).
- **Not found, decided:** an unknown or inactive category, an unknown, unpublished or unsellable product slug (the API's 404, or its 400 for a slug over 160 characters), a malformed `page` (`0`, `-1`, `1.5`, `abc`, `01`), a `page` beyond the last page, a `page` above the API's offset cap (418 at 24 per page; the API is not even asked) and a `brand` that is not a slug are all `404`. Never silently page 1 or the last page. An empty first page (no products, an empty category, a brand with no products) is `200` with an empty state.
- **Paging.** 24 per page, `offset = (page - 1) * 24`; the API refuses `offset` above 10 000, so the last reachable page is 417 and the pager never offers more (API gap 8: a larger catalog is listed only up to there).
- **Brand filter** exists only as links (`?brand=<slug>`): the brand name on a product card or page links to the catalog (or the current category) filtered by it, and the active filter shows a "clear" link. There is no brand list and no sort control (owner answers 10 and 11). The brand name shown in the filter chip comes from a listed product.
- **Data requests.** One request per need: list items already carry price and availability (no N+1). A page and its `generateMetadata` share one load through React `cache` (`lib/catalog-pages.server.ts`). A product page reads the product, the config (`currencyExponent`) and the category tree (breadcrumbs); the last two are the same cached reads the layout makes.

## Run

```
pnpm build                                       # once, so the workspace packages exist (the storefront build needs NO running API)
pnpm --filter @fluxkit/storefront dev -p 3001    # development; needs API_INTERNAL_URL (root .env or shell) and the API on :3000
pnpm --filter @fluxkit/storefront start -p 3001  # after `pnpm build`
pnpm --filter @fluxkit/storefront test           # Vitest (unit and renderToStaticMarkup component tests)
pnpm test:e2e                                    # (repository root) Playwright browser tests: builds, starts API + storefront + proxy on a *_e2e_test database; e2e/README.md
```

`next.config.ts` loads the root `.env` for `dev` and `start` (shell variables win). `next start` sets `NODE_ENV=production` when it is unset (`next/dist/bin/next`), so `STOREFRONT_PUBLIC_URL` is required there as well as `API_INTERNAL_URL`; `loadStorefrontEnv` runs per request, so a missing value shows on the first request that needs it, not at start-up. Variables (`docs/contracts/config.md`):

| Variable | Read when | Used for |
|---|---|---|
| `API_INTERNAL_URL` | per request, by the server data layer (and by `next dev` for the `/store/*` rewrite) | catalog reads from the Next server. Missing or malformed: the request fails loudly, the build is unaffected |
| `STOREFRONT_PUBLIC_URL` | per request (required when `NODE_ENV=production`; validated together with the others by `loadStorefrontEnv`) | canonical URLs, hreflang, Open Graph URLs, JSON-LD, the sitemap and robots.txt |
| `STOREFRONT_IMAGE_HOSTS` | **at `next build` and again at `next start`** (see "Images") | the CSP `img-src` (build), the image optimizer's allow-list and the pages' image check (start) |

## Rendering and caching (verified against Next 16.4.1)

- **Every page under `[locale]` renders per request** (`ƒ` in the `next build` table), because the shell reads the API (categories, config). `generateStaticParams` returns the locales but prerenders nothing. HTML is sent with `Cache-Control: private, no-cache, no-store`.
- **How it is made dynamic:** `lib/store-data.server.ts` awaits `connection()` (`next/server`) before any API read, so a catalog read can never run while Next prerenders. `next build` therefore never calls the API and passes without `API_INTERNAL_URL` (checked: `env -u API_INTERNAL_URL pnpm build`). Nothing in a layout or page needs `export const dynamic`.
- **API responses are cached, not pages:** `fetch(..., { next: { revalidate: 60, tags } })` (`CATALOG_REVALIDATE_SECONDS`, an internal constant in `lib/store-data.ts`). Measured: five page requests produce one `GET /store/config` and one `GET /store/categories`.
  - The Next 16 docs say `dynamic = "force-dynamic"` is equivalent to `fetchCache = 'force-no-store'`. Measured on 16.4.1: with `force-dynamic` on the layout the explicit `revalidate` was still honored (one call each for five requests). `connection()` is used anyway because it is structural (it sits in the data layer, not in each file) and leaves routes that never read the API free to be static.
  - **Only bounded keys are cached** (review M2). `next start` writes every cached answer to `.next/cache/fetch-cache` and never deletes one, so a free value in the URL would grow the disk without limit. `isCacheableProductQuery` (`lib/store-data.ts`) decides: a product list with a `brand` filter (a free slug; there is no brand list to check it against) is read with `cache: "no-store"`; everything else in a cached URL is bounded (the locale, a category that exists, the page size, an offset below the API's cap of 10,000, the slugs of real products; a `404` is never cached). Real run: 300 distinct `?brand=` values leave the number of files in `.next/cache/fetch-cache` unchanged (3 before and after); with the rule removed they create 300 files. A brand page therefore costs one API call per view; the API's catalog reads are not rate limited (a known launch blocker, recorded in `docs/HANDOFF.md`).
  - The data cache is on disk (`.next/cache/fetch-cache`) and survives a restart: a restarted server can serve an entry from before the restart until it is revalidated. Delete the folder to reset it.
  - When the API fails after an entry expired, Next serves the stale entry and revalidates in the background (measured with a stub API that began answering `503`: pages kept the old categories). On top of that `store-data.ts` keeps the last good response per request in memory (200 entries per process) and serves it when the API cannot be reached or answers 5xx, with a logged warning. With neither, it logs the error and throws `StoreUnavailableError`: the route's `error.tsx` renders. A `4xx` problem (a missing product) is an answer, not an outage, and is returned to the page. There is no silent fallback data.
- **Locale check** (`lib/locale-check.ts`, `app/[locale]/(site)/layout.tsx`): on every request each locale of `@fluxkit/ui` must be in the cached `GET /store/config` `locales`; otherwise a logged `LocaleMismatchError` and `error.tsx` (HTTP 500). It lives in `(site)/layout.tsx`, below the locale layout, so the header and footer still render around the error.
- **Finding (Next 16.4.1, reproduced with a minimal app, not specific to this code):** a `notFound()` or an error thrown before the first byte is streamed answers the right status (404, 500) with an HTML document whose `<body>` is empty (`<html id="__next_error__">`); the browser completes the page from the embedded RSC payload (which contains the shell and the translated content: checked in the payload, NOT in a browser, none is available in this environment). With a `loading.tsx` above the page the shell streams first: full server-rendered HTML, but the status is `200` (plus `<meta name="robots" content="noindex">`). Consequences: `[locale]/[...rest]/page.tsx` (unknown paths under a locale) lives outside `(site)` on purpose, so it keeps a real 404. **Step 5 therefore keeps the catalog, category and product routes in the `(catalog)` route group, which has no `loading.tsx`** (checked with a real run: an unknown slug answers 404; `route-structure.spec.ts` guards it). An unknown first segment (`/foo`) gets Next's built-in untranslated 404 (a root layout under a dynamic segment cannot render one; `global-not-found` is experimental and not enabled).
- `next/link` is used for navigation inside a locale; the locale switcher uses plain `<a>` on purpose (a language change is a full page load: `<html lang>`, messages and the islands start from the new locale). It keeps the path, the query and the fragment (step 7: the guest order page's token is in the fragment). The fragment is read from `location.hash` in an effect after each commit of a new path or query and on `hashchange`, so the server render and the first client render have none (no hydration mismatch, never in server HTML); a browser never sends a fragment with a request.

## Images

Product images go through `next/image` (owner answer 7) and only for hosts in `STOREFRONT_IMAGE_HOSTS`; everything else gets the token-styled placeholder of `@fluxkit/ui` (never a broken image, never a request to an unknown host).

- **Where it is decided:** `lib/image-source.ts` `allowedImageUrl`: `https` only, no credentials, no port, hostname exactly in the list (look-alike hosts such as `cdn.example.com.evil.example` or `cdn.example.com@evil.example` fail). The server components check every URL and pass only a checked `src` or `null` to the `StoreImage` client component, which also falls back to the placeholder when the image fails to load (including a failure before hydration).
- **`STOREFRONT_IMAGE_HOSTS` is read twice (verified on Next 16.4.1, `next start` with a different value than the build):**
  1. `next build` reads it for the CSP `headers()` (stored in the build output) and for `images.remotePatterns`.
  2. `next start` evaluates `next.config.ts` AGAIN: the image optimizer allows the hosts of the variable as the server STARTS, not as it was built (build without hosts, start with `example.com`: the optimizer fetched `example.com`; build with `example.com`, start without: the optimizer answered 400 for it). The pages read the same live variable (`lib/image-hosts.server.ts`), so a page never offers an image the optimizer refuses. The CSP list keeps the build value; it is not needed for optimized images, which load from `/_next/image` (`'self'`).
  - Operate it as: set the same value for `next build` and `next start`; changing the list needs a restart, changing the CSP part also a rebuild.
- **Sizes and loading:** explicit `width` and `height` (square boxes, `object-cover`, so the space is reserved and nothing shifts), a `sizes` attribute per use, `loading="lazy"` except the first four list images and the main product image (`eager`, the main one with `fetchPriority="high"`).
- **Alt text:** the media `alt` from the API, else the product title; never empty for an informative image. The thumbnails of the gallery are decorative inside a labelled button.
- **Seed images** (`https://example.com/placeholder/...`) do not resolve, and `example.com` is not in the default list, so a fresh clone shows placeholders everywhere. With `STOREFRONT_IMAGE_HOSTS=example.com` the page emits `<img src="/_next/image?url=...">` and the optimizer answers 404 for the missing upstream file; in a browser `onError` then shows the placeholder (NOT verified here: no browser).
- **Uploaded images** (admin upload, ADR 0028; `/media/<key>` on the shop host or on a media host): the storefront code is unchanged. The URL passes `allowedImageUrl` only if it is an absolute `https` URL whose host is in `STOREFRONT_IMAGE_HOSTS`, and the Next optimizer then fetches it over the network from the storefront server, which must resolve that host to a PUBLIC address (Next 16.4.1 refuses loopback and private addresses; split-horizon DNS breaks it, the page shows the placeholder). Over `http` (development, the e2e stack) every uploaded image is a placeholder here. The deployment notes are in the root `README.md`, "Uploaded images"; the e2e proof that a product with an uploaded image still renders is `e2e/tests/media-route.e2e.ts`.
- Open Graph and JSON-LD use the media URL as the API gives it (a crawler fetches it directly) when it is an `http(s)` URL, whether or not its host is in the list.

## Variant picker (`lib/variant-matcher.ts`)

Pure and niche-neutral: option and value codes are data from the API; nothing knows what "size" or "color" is (`source-guards.spec.ts` fails on a quoted `size`, `color`, `material`, ... in the source).

- A product with no options has one default variant and no picker (`hasOptionPicker`). `findVariant` needs a complete selection that equals a variant exactly; otherwise `null` (the page then says the combination does not exist and disables the button).
- `initialSelection`: the first variant that is not `out_of_stock`, else the first.
- A value of option N is **available** only when some sellable variant has it together with the current values of options 1 to N-1. So the first option never has a disabled value, and `selectValue` repairs the later options when an earlier choice makes them impossible (it picks the first value that exists). The picker therefore cannot dead-end, whatever holes the variant grid has (tested exhaustively on two sparse fixtures).
- Media belonging to a selected option value is shown first (`galleryFor`), then general media, then the rest.

## Add to cart and the cart event

- `ProductPurchase` adds through the shared cart store (`cart.add`, `lib/cart-store.ts`): the cart cookie has `Path=/store`, so only the browser can send it; the api-client adds `X-Fluxkit-CSRF`. Quantity 1 to 999 is checked before the request. The button is disabled while the request runs and for an `out_of_stock` variant (decision: the cart would accept such a line but the checkout refuses it; a backorder or untracked variant reports `in_stock`, so the shop's own rule decides).
- **Messages:** failures show the translated message of the problem (`errors.rule.variant_not_sellable`, `errors.rule.quantity_limit`, `errors.too_many_requests` for 429, `errors.network`, `errors.invalidResponse`, `errors.generic` for anything unknown), never the API's text. The result is announced through a `role="status"` region that is always in the page (a live region only announces changes to a region that already exists); an error is an `Alert` with `role="alert"`. An add failure is returned to the product page and NOT kept in the shared state (the cart page would otherwise show a stale "too many requests" later).
- **Cart event (`lib/cart-events.ts`, step 5, unchanged):** `fluxkit:cart-changed` on `window` with `{ itemCount }`. It is still the one signal, but the cart store now publishes it for EVERY applied answer (add, quantity, remove, clear, acknowledge, a sign-in's cart reload, the first read) and also follows it: an event from another publisher whose count differs from the store's re-reads the cart (once; the store's own events are ignored, so there is no loop).

## SEO

- `generateMetadata` per page (`lib/page-metadata.ts`): title `"<page> — <site>"` (`seo.pageTitle`, with "(Page N)" on later pages), description (product and category descriptions are trimmed plain text, 160 characters, cut at a word), canonical and `alternates.languages` for every locale plus `x-default` (the default locale) from `STOREFRONT_PUBLIC_URL`, Open Graph title, description, URL, site name and the first media image.
- **Robots:** `noindex, follow` on a brand filter and on page 2 and later; everything else indexable. The canonical of a filtered view is the UNFILTERED list (same `page`), and a later page canonicalizes to itself, not to page 1.
- **JSON-LD** (`components/json-ld.tsx`, the only `dangerouslySetInnerHTML` in the app): `Product` with `offers` and `BreadcrumbList`. One price is an `Offer`; a range is an `AggregateOffer` (`lowPrice`, `highPrice`, `offerCount` = variants). Prices are decimal STRINGS from the integer minor units (`minorUnitsToDecimalString`, BigInt), availability maps to `InStock`, `LimitedAvailability` and `OutOfStock`. `serializeJsonLd` escapes `<`, `>`, `&` and U+2028/2029 as unicode escapes, so product text cannot close the script element (tested with a malicious title).
- **`/sitemap.xml`:** home, catalog, every category and every product, once per locale, each with hreflang alternates; `lastmod` is `publishedAt` (API gap 7). Products come 100 per request (first page, then batches of 8 in parallel) up to the API's offset cap, so at most 10 100 products are listed (about 20 200 product URLs, under the 50 000 a file may hold); a refused page fails the sitemap loudly. API reads are cached for 1 hour. **`/robots.txt`:** allows everything, disallows `/{locale}/cart|checkout|account|order` and `/store/`, and names the sitemap.
- Both files read `STOREFRONT_PUBLIC_URL` per request (after `connection()`), so `next build` needs no environment.

## Content-Security-Policy and headers (`next.config.ts`, `headers()`)

Applied to every path: `Content-Security-Policy` (`default-src 'self'`; `script-src 'self' 'unsafe-inline'`; `style-src 'self' 'unsafe-inline'`; `img-src 'self' data:` plus `https://<host>` for each `STOREFRONT_IMAGE_HOSTS` entry; `connect-src 'self'`; `frame-ancestors 'none'`; `base-uri 'self'`; `form-action 'self'`), `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin` (the guest order page `/{locale}/order/...` overrides it with `no-referrer`: a second rule after the site-wide one, the last matching rule wins; tested with Next's own path matcher), `Permissions-Policy: camera=(), microphone=(), geolocation=()`, and `Strict-Transport-Security: max-age=31536000` outside `next dev`. No nonces (owner answer 13): acceptable only because no third-party script is loaded and no HTML from the API is rendered. `next dev` adds `'unsafe-eval'` and `ws:`/`wss:`.

- **The CSP part of `STOREFRONT_IMAGE_HOSTS` is read at build time:** Next evaluates `headers()` during `next build` and stores the result in `.next/routes-manifest.json`. Verified: a build without the variable and a `next start` with it kept `img-src 'self' data:`; a build with it contains the host. Change the variable, rebuild. (The image optimizer and the pages read it again at start, see "Images".)
- The header code lives in `next.config.ts` itself: Next compiles only that one file for its config, and a relative import of another TypeScript file fails with `MODULE_NOT_FOUND`.

## Structure

See `docs/files/storefront.md` for one line per file. In short:

- `src/app/[locale]/` routes only compose. `layout.tsx` is the root layout (`<html lang>`, `SiteShell`); `(site)/` holds the pages that need the locale check and the loading state; `error.tsx`, `not-found.tsx` and `[...rest]` are the error states.
- `src/components/`: storefront components; dumb token-styled parts come from `@fluxkit/ui`. Client islands (`'use client'`): `session-provider` (the cart and account stores), `cart-badge`, `account-link`, `session-notices`, `cart-page`, `login-form`, `register-form`, `account-gate`, `account-overview`, `profile-forms`, `account-forgot-password`, `account-reset-password`, `account-verify-email`, `account-verify-notice` (with `account-email-parts` and the `use-fragment-token` hook), `checkout-page`, `delivery-section` (also the city and pickup point pickers), `lookup-combobox`, `guest-order-page`, `account-orders`, `product-purchase`, `store-image`, `locale-switcher`, `i18n-provider` and the three tiny route files for loading, error and not-found. The pure `*View` components next to them are what the tests render.
- `src/lib/`: logic without markup (`money`, `date`, `problem-messages`, `failure`, `store-data` and `store-data.server`, `locale-check`, `locale-path`, `safe-next`, `cart-store`, `account-store`, `session-stores`, `cart-model`, `cart-handlers`, `checkout-attempt`, `checkout-form`, `checkout-store`, `shipping-model`, `shipping-store`, `shipping-text`, `lookup-source`, `combobox-model`, `order-links`, `order-model`, `order-store`, `fragment-token`, `account-email-flows`, `reset-password-form`, `email-links`, `client-messages`, `navigation-categories`).
- `src/layout/` and `src/config/`: configuration (below). `src/messages/`: `uk.json`, `en.json`.

### Layout composition is configuration

- Home page: `src/layout/home.ts` lists the sections in order with props (message keys, a `limit`); `components/home-sections.tsx` has the registry (one renderer per section type). `categoryTiles` and `newProducts` get their data from `loadHomeData` (`lib/catalog-data.ts`, called by the page) and render an empty state when there is none. The registry renderers are synchronous and receive the loaded data in their context, so they stay testable with `renderToStaticMarkup`.
- Header and footer links: `src/layout/navigation.ts` (message keys and locale-less paths; `localizedHref` adds the locale and refuses anything that is not a plain path).
- Checkout settings (the country list of the checkout WITHOUT shipping methods, default country `UA`, which address fields are shown): `src/config/checkout.ts`, consumed by step 7. With shipping methods the country list comes from the methods (see "Delivery and shipping").

**Add a home section:** add a member to the `HomeSection` union and an entry to `homeSections` in `layout/home.ts`, and a renderer in `homeSectionRegistry` (TypeScript fails until both exist). **Add a header or footer link:** add `{ labelKey, href }` to `navigation.ts` and the message key to both JSON files.

### i18n

- Every user-facing string is a message key in `src/messages/{uk,en}.json`; components receive a translator (`createTranslator(messages, locale)` from `@fluxkit/ui`), a missing key or placeholder value throws. Server components build it from `messagesByLocale`; client components use `useI18n()`.
- **Client subset:** only keys with a prefix in `lib/client-messages.ts` (`nav.`, `locale.`, `error.`, `errors.`, `notFound.`, `loading.`, `product.`, `availability.`, `cart.`, `account.`, `checkout.`, `order.`) are serialized into the page for the browser. A client component that needs a new namespace must add its prefix there.
- **Add a message:** add the key to BOTH files. Plural forms are separate keys (`nav.cart.items.one|few|many|other` for `uk`, `one|other` for `en`, each with `{count}`), used with `t.plural(key, count)`. `messages/messages.spec.ts` fails on: a key in one file only, different `{placeholders}`, an incomplete plural group, and a string literal in the source that looks like a key but is not in the files.
- **Problems from the API** (`lib/problem-messages.ts`): only translated messages are shown, never the API's `detail` or `message`. `errors.<code>` for a problem `code` (every value of `ProblemDetailsDoc.code`; a test compares the list with `docs/api/openapi.json`), `errors.rule.<rule>` for a `rule_violation` rule, `errors.field.<code>` for an `errors[].code`, `errors.network` and `errors.invalidResponse` for the client's thrown errors, `errors.generic` for anything unknown (the unknown code is logged with `console.warn` in development only). A new API code fails the test until it gets a decision and a message.
- Money and dates: `lib/money.ts` (`formatMoney({amount, currency}, exponent, locale)`: the amount becomes a decimal string with BigInt arithmetic and `Intl.NumberFormat` formats the string; the exponent is the shop's `currencyExponent` from `GET /store/config`, falling back to Intl's digits for the currency; the storefront never adds or multiplies money) and `lib/date.ts` (`Intl.DateTimeFormat`; an invalid date throws).

## Cart and accounts (step 6)

All personalized pages follow ADR 0026: a server-rendered shell plus client components that call `/store/*` from the browser (`baseUrl ""`, same origin, `cache: "no-store"`; the cookies have `Path=/store` and never reach the Next server). They live in the `(site)` route group (locale check and loading skeleton; they never answer a 404 themselves, so the `(catalog)` rule about real status codes does not apply) and never call `notFound()` (`lib/route-locale.ts` narrows the locale type instead).

### One store, one read (how the cart context and the header badge share the fetch)

`components/session-provider.tsx` sits in `SiteShell`, inside the locale layout, and creates two plain stores (no library; `useSyncExternalStore` hooks `useCart()` and `useAccount()`): `lib/cart-store.ts` and `lib/account-store.ts`, wired by `lib/session-stores.ts`. **Decision:** the header badge and the account link no longer fetch by themselves; they read the stores. So one page load makes ONE `GET /store/cart` and ONE `GET /store/account/me`, whichever islands exist, and the cart page, the badge and the add-to-cart button always show the same cart. `start()` is idempotent (React strict mode mounts twice and still reads once). When the cart page is opened by client-side navigation (the state is already known and may be old) it reads again once; on a direct load the first read is still in flight and no second one is made. Guards: `client-boundary.spec.ts` (the only client file that creates a store client is the provider; the header islands call nothing) and the store tests (`start` twice is one request).

### Cart store rules (each has a test; `lib/cart-store.spec.ts`)

- Server values only. No optimistic update of a quantity or an amount: the cart changes when an answer arrives (mutation checked: an optimistic quantity fails three tests). Busy lines are disabled instead.
- Every answer that holds a cart replaces the state and publishes `fluxkit:cart-changed`: a `200`, and the `cart` inside a `409 cart_changed` (the reason is still shown, in `failure`).
- Requests are numbered when they START; an answer replaces the state only when its number is higher than the last applied one. A slow older answer (a write whose reply arrives after a newer write's, or a read that started before a write) is dropped and not published; the failure of an older request is not shown either. Tested both with out-of-order and in-order answers.
- A failed write (`429` with its `Retry-After` wait, network, `5xx`, a refused rule) keeps the previous cart and shows a translated message (`failureText`: the message, plus "Try again in N seconds" for a 429). A failed FIRST read leaves `status: "error"` with a retry. An unexpected exception (a bug) releases the busy mark and is rethrown.
- `clear()` is `DELETE /store/cart` and then a read: the empty cart (with its currency) is the server's, the storefront never builds money. There is no "empty the cart" button yet (decision: an accidental click would drop up to 100 lines, and a confirmation step is more UI than step 6 needs); the store method exists and is tested.
- Quantities 1 to 999 are checked before a request (`errors.field.invalid_quantity`).

### Cart page (`/{locale}/cart`, `components/cart-page.tsx`)

- Lines: image (`StoreImage`, the host allow-list comes from the server shell as a prop; any other host shows the placeholder), title linked to the product, option text from the API's `optionValues`, SKU, unit price, line total, quantity form, remove. The quantity is a draft until the shopper presses "Update" (one request per submit, not one per keystroke); a new server quantity resets the draft.
- Notices exactly as the plan says: `price_changed` "was X, now Y" (a price seen in ANOTHER currency is formatted with that currency's own digits, not the shop's), `unavailable` (no price, no quantity box, remove), `out_of_stock` (badge plus a hint that the order may be refused), `line_total_out_of_range` ("lower the quantity"; the quantity box stays because lowering it is the repair).
- Cart-level banner "prices changed" with OK = `POST /store/cart/acknowledge` (disabled while a whole-cart write runs).
- Summary: item count, subtotal and total through `formatMoney` from the API values; nothing is added or multiplied (mutation checked: a subtotal summed from lines fails two tests). `lineTotal` is shown as the API gives it.
- Checkout: a link to `/{locale}/checkout` while `purchasable`; otherwise a disabled button with a visible reason (`aria-describedby`).
- States: skeleton with `aria-busy` (loading), an alert with retry (first read failed), an `EmptyState` with a link to the catalog, an alert with dismiss for a failed write. An always-mounted `role="status" aria-live="polite"` region says what the last action did ("Cart updated. Items: 2. Total: ...").

### Session handling (`lib/account-store.ts`)

- The header link shows "Sign in" for a guest (`401` from `me` is the normal answer and logs nothing), the customer's FIRST NAME for a signed-in shopper (`nav.account.named`, rendered as text: a test renders a hostile name and finds no markup; the link truncates a long name), and the neutral account link when the session could not be read.
- A sign-in or registration sets the session, keeps `cartNotices` and asks the cart to reload (`onSessionChanged`), so the badge shows the merged cart. A sign-out does the same (the account's cart is no longer visible) and drops the notices; a `401` from logout means the session was already gone and counts as signed out. A late session read never overwrites a sign-in that finished after it started (numbered like the cart).
- **Identical failure.** A `401` on login is ONE message (`account.login.invalid`) with no field marked, whatever the API body says (the API answers the same for an unknown email, a wrong password, a locked and an inactive account; the message only says that repeated failures pause sign-in "for a while", no number). A `429` shows `errors.too_many_requests` plus the wait from `Retry-After` (whole seconds only, capped at a day; anything else shows no wait). A taken email on registration is a field error worded "sign in instead" (the API accepts that trade-off, ADR 0016).
- **Double submit:** the button is disabled while pending, a ref drops a second submit that arrives before React rendered the disabled button, and the store joins a second call of the same action to the request in flight (one request; tested).
- **No secrets anywhere:** a password lives in the request body only: never in a URL, the stores' state, a log, `localStorage` or `sessionStorage` (`source-guards.spec.ts` fails on browser storage or `document.cookie` in the cart and account files and on a `console.*` that mentions a password, values or a body; a store test serializes the state after a failed login and looks for the password). A password field is emptied after a refused sign-in; both password fields are emptied after a password change.
- **Account gate** (`components/account-gate.tsx`): `/account` and `/account/profile` show a skeleton while the session is read, the page for a signed-in customer, and for a guest a link to sign in plus a `router.replace` to the login page with the page as `next`. Any protected call that answers `401` (the session ended while the page was open) makes the store a guest, which triggers the same redirect. Every state has one `h1`, also in the server HTML. When the session cannot be read there is a retry.
- **Sign-out** goes to the home page.

### The safe `next` rule (`lib/safe-next.ts`)

`/account/login?next=` and `/account/register?next=` say where to go after signing in. It comes from the URL, so `safeNextPath(value, locale)` accepts only a path inside the CURRENT locale's storefront: it must start with `/{locale}/`, contain no backslash, no `//`, no `#`, no control character or space, no `..` segment, in the text AND in any percent-decoded form of it (up to three decodings; a malformed escape is refused), must parse as a same-origin path, and must not be the login or register page itself (a loop): the pathname is resolved by the URL parser (dot segments), percent-decoded and stripped of trailing slashes before it is compared, so `/uk/account/login/`, `/uk/account/%6Cogin` and `/uk/account/./login` are refused too (review L6). There is no separate final "URL parser says same origin" check any more: after the string rules it can never fire (review L5, mutation m4 was equivalent), and `safe-next.spec.ts` instead parses the answer for 20,000 generated values and fails when it is off-site, off-locale or an auth page (removing any string rule fails it). Anything else (including a missing value or a repeated parameter) falls back to `/{locale}/account`. Tested with `//evil.com`, `/\evil.com`, `https://evil.com`, `javascript:...` in mixed case, `data:`, encoded and double-encoded slashes and backslashes, encoded tabs, dot segments (plain and encoded), NUL, a fragment, another locale, a prefix that only looks like the locale, and a 2000 character value. `authHref`/`loginHref` build the links and keep `next` only when it passes. The account gate builds its `next` from the path AND the query string of the page (`currentPath(pathname, location.search)`, read in the browser after hydration; the same safe rules apply), so `/account/orders?page=3` comes back to page 3. The forms navigate with `router.replace(safeNextPath(...))`; `source-guards.spec.ts` fails on any `router.push/replace` argument that is not built by `safeNextPath`, `localizedHref` `loginHref` or the gate's own login link, and on `window.location` assignments.

### `cartNotices` (merge notices) once

A sign-in or registration returns `cartNotices` (`quantity_capped`, `lines_dropped`). The account store keeps them in memory; `SessionNotices` (the only place that renders them, at the top of `<main>`, guarded by a source test) shows them as a dismissible polite message on whatever page the shopper lands on; dismissing clears them, the next sign-in replaces them, a reload loses them. Verified at the API with a real merge: 600 + 600 gives `quantity_capped` and a line of 999.

### Forms and accessibility

**Every `<form>` is `method="post"` with no `action`** (review H1). The pages are server-rendered, and until React hydrates the browser submits a form natively; a form without a method uses GET, which would put the password and the personal data into the address bar, history, access logs and the `Referer` of every later request. With `method="post"` a native submit POSTs to the page itself: Next answers `200` and renders the same page (measured with the API up: the POST to `/en/account/login` returns the login page, the body is not echoed, nothing crashes; the e2e tests below check it with JavaScript off and with the scripts held back). `source-guards.spec.ts` fails for any `<form` in `src` or `packages/ui` without `method="post"` or with an `action` (there is no allow-list: every form holds personal data or a quantity). `Referer` cannot carry a secret: no secret is in a URL at any time (the order token is in the fragment, which is never sent; the guards above keep passwords and personal data out of URLs).

Labelled inputs (`Field`), `aria-invalid`, hint and error linked with `aria-describedby`, `required`, `autocomplete` tokens (`email`, `current-password`, `new-password`, `given-name`, `family-name`, `tel`; tested per input, a mutation removing one fails a test), `noValidate` forms with the server as the judge (blank required fields are reported at once, without a request). After a failed submit focus goes to the first invalid field in PAGE order, else to the error summary (`lib/failure.ts` `focusAfterFailure`, tested with a fake document); the summary is one `role="alert"` box that lists each field error as a link to its field. The password rules (12 to 128 characters, not the email) are a hint; the API's answer shows through `errors.field.*`.

## Checkout and orders (step 7)

Same model as step 6 (ADR 0026): server shells, client islands that call `/store/*` from the browser through the shared store client (`useStoreClient()`, created once in `SessionProvider`). The logic is pure TypeScript in `src/lib` with injected client, storage and crypto; the islands only wire it to React.

### The checkout attempt (`lib/checkout-attempt.ts`)

One attempt `{key, salt, requestHash}` in `sessionStorage` under `fluxkit.checkoutAttempt`: the `Idempotency-Key`, a random salt (`crypto.randomUUID()`, new for every attempt) and the SHA-256 (`crypto.subtle`) of the salt and the canonical JSON of the request body and the expected total (keys sorted at every depth, `undefined` dropped). No personal data is stored: a key, a salt and a hash (tested by reading the stored value). The salt means the hash cannot be compared with the plain hash of a guessed email, phone or address, and cannot be precomputed (review L7); it sits next to the hash, so someone who can read the entry can still test one guess per hash. On submit the body is hashed with the KEPT attempt's salt; the same hash reuses the key, a different one gets a new key and a new salt that replace the attempt. An entry without a salt (written by an earlier version) is not trusted: it is replaced. So a double submit, a retry after a network error and a reload of the tab are one attempt (the API answers a repeat with `200` and the same order and token, ADR 0023); a changed email, address or total is a new one.

- **Secure context.** `crypto.randomUUID` and `crypto.subtle` exist only on HTTPS and `localhost`. Without them `webAttemptCrypto` throws `InsecureContextError`: the page shows `checkout.error.insecureContext`, logs the reason once (no personal data) and disables the submit. There is NO fallback to `Math.random` or an unhashed body (a weak key could collide with someone else's and replay their order). For testing from another device on the local network use HTTPS (or a tunnel); `http://192.168.x.x` is not a secure context.
- **Storage unavailable** (blocked site data, private modes that refuse writes): `sessionAttemptStorage` probes `window.sessionStorage` once and returns `null`; a later write that throws switches to memory too. The attempt then lives in memory for the life of the page (a double submit and a retry still reuse the key) and the page shows `checkout.warning.storage` ("do not reload while the order is being placed"). Decision: loud but not blocking, because refusing private browsing would lose real orders while the only loss is replay protection across a reload.
- A stored value the manager did not write (malformed JSON, another shape) is ignored and replaced.

**Outcome table** (`checkoutOutcome`, one pure function, a test per row; `checkout-store.ts` applies the side effects):

| Answer | Key | What the page does |
|---|---|---|
| `201`, `200` (replay) | clear | read the cart again (the badge empties), `router.replace` to `/{locale}/order/{number}#t={accessToken}` for a guest (an answer with a token) or `/{locale}/account/orders/{number}` for a customer; the form stays disabled |
| network failure, unreadable answer (a proxy's HTML page), `5xx`, `503` | keep | "try again" (with the `Retry-After` wait of a 503); the next submit of the same body replays safely, a lost `201` comes back as `200` with the same token |
| `429` | keep | the wait from `Retry-After`, no automatic retry |
| `409 cart_changed` | keep (the key changes by itself when the total does) | the fresh cart from the problem body replaces the shared cart (`applyCart`, also the badge), its notices show, the submit is blocked until the shopper presses OK on a price change (`POST /store/cart/acknowledge`) or "Confirm the new total" |
| `409 checkout_refused` | keep | the lines named by `errors[].path` (`lines.N` = position in the cart) are marked with the translated code (`errors.field.<code>`, also `product_title_missing`), only while the cart is the one that was refused; a link to edit the cart |
| `409 cart_empty` | clear | read the cart again and go to the cart page (a parallel tab already ordered) |
| `409 too_many_open_orders` | keep | the translated explanation; a customer also gets a link to the order history |
| `409 idempotency_key_reused` | clear | "submit again" (a lost cart cookie or a changed session); the next submit gets a new key |
| `400` | keep | `errors[]` mapped to the form fields by path (`email`, `shippingAddress.city`, `shippingAddress` for `shipping_address_required` focuses the country select); focus to the first invalid field or the error summary |
| any other problem (`403`, a `rule_violation` such as `subtotal_out_of_range`) | keep | its translated message |
| an abort or a bug (`InvalidRequestError`, a `TypeError`) | - | rethrown: never shown as a friendly message; the form is freed |

### The checkout page (`components/checkout-page.tsx`)

- Needs a non-empty cart: loading skeleton (`aria-busy`), retry when the cart could not be read, an empty state with a link to the catalog. A cart that is not `purchasable` shows the reason and a link to the cart; the submit is disabled with the reason linked by `aria-describedby`.
- Contact (`email`, `tel`, `given-name`, `family-name`) and, ONLY when the cart's `requiresShipping` is true, the address: a country select (`country`; `allowedShippingCountries` named with `Intl.DisplayNames`, default `UA`) and the fields of `config/checkout.ts` in order (`address-level1`, `address-level2`, `postal-code`, `address-line1`, `address-line2`), optional ones labelled "(optional)". A blank optional field is not sent (the API refuses a sent blank as `empty`). A digital-only cart sends no address at all.
- **Billing address (decision, plan silent):** not asked and not sent: nothing uses it while there is no payment or invoice, and asking would collect personal data for no purpose. **Recipient fields:** not sent; the order's contact is the recipient.
- Signed-in customers: email, names and phone are prefilled once from `me` (only empty fields; editable); the email may be left blank (the account email is used) and is then not sent. Guests get a "Sign in" link with `next=/{locale}/checkout`.
- Client checks are UX only (blank required fields, no request); the API judges every value and its `errors[]` are shown through `errors.field.*`.
- Summary from the cart answer: lines with options, quantity, line total and notices, item count, subtotal and total through `formatMoney`; nothing is added or multiplied (a test uses lines that do not sum to the total). `expectedTotal` is the total of the cart in the shared store AT SUBMIT TIME, so always the most recent cart the shopper sees (tested with a cart replaced between page load and submit).
- Payment (owner answer 9): `checkout.payment.note` says that no payment is taken on the site and that the shop will contact the shopper to arrange it; the order page shows the expiry. Never a claim that paying online is possible (a test scans both message files). A client replaces these message keys with its own wording.
- Submit: disabled while in flight with `aria-busy` and "Placing the order"; a second submit before the disabled state renders is dropped (`useForm` ref) and the store returns the request in flight (one request; tested). The form values live in component state only: not in a URL, browser storage or a log.

### The guest order page (`components/guest-order-page.tsx`)

- `/{locale}/order/{number}#t={token}`: the server shell knows the number only. After hydration the island reads `location.hash` (`tokenFromFragment`: exactly one `t`, base64url, 16 to 128 characters) and calls `POST /store/orders/lookup {number, accessToken}`; the cancel is `POST /store/orders/cancel` with the same body, after a confirmation step ("Cancel this order? ... Yes / Keep the order"). A `409` on cancel (paid or expired meanwhile) reads the order again and shows the reason.
- One not-found state for everything that is not an order: an unknown or malformed number, a missing, malformed, wrong or expired token, someone else's order (the API's identical `404`, and its `400` for a malformed body). No request is made without a well-formed number and token.
- "Save this link": the full link in a labelled read-only field (select and copy by hand always works) and a "Copy the link" button using the Clipboard API (`copyLink`; a missing API, as on plain HTTP, or a refusal shows `order.saveLink.copyFailed` next to the field). It is rendered only in the browser.
- Status texts for `awaiting_payment`, `paid`, `fulfilled`, `cancelled`, `expired` (and a neutral fallback), always as text in a badge; while `awaiting_payment` the payment wording with the expiry time (`formatDateTime` of `expiresAt` in the shopper's zone). Items, the API's totals (zero shipping, discount and tax lines are hidden), contact, the shipping address (country named by Intl) and the history.
- **The fragment stays in the address bar (decision):** removing it would break the reload and the bookmark that the "save this link" text asks for, and a fragment never leaves the browser (not in requests, not in `Referer`). The route also sends `Referrer-Policy: no-referrer` and loads nothing from another origin.

### The customer's orders (`components/account-orders.tsx`)

Behind the account gate. `/{locale}/account/orders?page=N`: 24 per page (the API default; `offset` capped at 10 000 like the catalog), newest first, each with its number (link), date, item count (plural), status and total; a malformed or empty later page shows "no orders on this page" with a link to page 1; an empty history an empty state. `/{locale}/account/orders/{number}`: the order with cancel while `awaiting_payment`; someone else's order is the same not-found state. A `401` on any of these (the session ended) makes the account store a guest (`sessionEnded`), and the gate sends the shopper to sign in. The account overview links to the history.

### Threat model of the guest token

- Protected: server and proxy logs and `Referer` (the token is only in the fragment and the POST bodies; the real run's proxy log of every request line contains no token and no `#t=`), other shoppers (one identical `404`, the API's constant-time comparison and `orderLookup` / `guestCancel` limits), the Next server (it never receives the fragment; the order route shell reads no query, header or cookie: a source test).
- Kept out by tests: the token in a request URL (the api-client calls of the lookup, the cancel and the checkout are inspected), in a `console` call (runtime spies and a source guard), in the stores' state, in the document title (no `document.title` anywhere; the order page title is fixed metadata), in server HTML (the island renders the loading shell on the server), in browser storage (no `localStorage`; `sessionStorage` holds the checkout attempt only).
- Not protected (accepted, plan "Guest order token"): anyone with the link (history, sync, a screenshot, a shared computer) can read and cancel the unpaid order until `ORDER_GUEST_ACCESS_DAYS`; a script on the storefront origin (XSS) can read the fragment, which is why no HTML from the API is rendered, the CSP has no third-party source, and no third-party script is loaded. Next's client router may hold the full URL (with the fragment) in its in-memory state after `router.replace`; it strips client-only state from the router-state header it sends (read in `next/dist/client/flight-data-helpers.js`) and a browser never sends a fragment in a request.

## End-to-end tests (step 8)

`e2e/` holds the Playwright suite (Chromium; run `pnpm test:e2e` from the repository root; how it works, the database rule and troubleshooting: `e2e/README.md`). Fifteen files, 34 tests, about 55 seconds after a build (the shipping plan's step 10 added `shipping-checkout`, four tests: see "Delivery and shipping"). The storefront plan's step 10 added `pre-hydration-forms` (no password or personal data in a URL or `Referer` before hydration: JavaScript off, and scripts held back), `account-gate` (a guest on `/account/orders?page=3` lands on the login page with that path and query as `next`; an auth page as `next` is dropped), `navigation-focus` (the focus is on the new page's heading after a client-side navigation) and a title check in `not-found`; `double-submit` now holds the first answer 1.5 s so a second request that the client's guards fail to stop would leave the browser (it fails when all three guards are removed).

**Now verified in a real browser** (it was "not verified" in the steps 6 and 7 reports): typing into every checkout, login and register field; the redirects after sign-in, registration and checkout (`router.replace`); focus after a failed submit (the sign-in summary receives it; password cleared, email kept); `location.hash` read after hydration (reload of the order link) AND after the client-side navigation from the checkout to the order page; the locale switcher carrying the query string and the fragment in both directions (after hydration); the Clipboard copy and its fallback message when `navigator.clipboard` is missing; the `sessionStorage` attempt across a reload (a refused checkout keeps `{key, salt, requestHash}` only, the same request reuses the key, a changed one gets a new key, a placed order removes it); a double click on the submit; the cart merge notice shown once and dismissed for good; the price-change flow with a real admin price change; `checkout_refused` on the line after another session bought the last unit; the whole purchase and the order cancel by keyboard alone (focus order of the form); the order token absent from every URL, header, body (except the two POST bodies that must carry it), server HTML, title, cookie, storage and console line; HTTP 404 with the not-found page in the browser.

**Still NOT verified in a browser:** screen readers (the live regions and the focus moves are asserted as DOM state, not heard); private browsing and blocked storage (the in-memory attempt and its warning); the insecure-context refusal (all runs are on `127.0.0.1`, a secure context); the +/- and Update buttons of a cart line and removing a line; the account gate's redirect to sign-in with `next` (a guest opening an account page), sign-out, profile and password forms, order-history paging; other browsers and viewports; `next dev`; strict-mode double effects (the suite runs the production build).

**Findings of step 8** (details in the step 8 report):
- Fixed (separate commit): after "Cancel the order" and after confirming, the focused button disappeared and the focus fell to the start of the page. `lib/cancel-focus.ts` now decides where it goes (the safe answer, the ask button, the success message) and `use-cancel-focus.ts` applies it; the keyboard scenario fails without it.
- `Referrer-Policy` is a property of a DOCUMENT. After the client-side navigation from the checkout to the order page the document is still the checkout's, so the lookup request carries the default policy's `Referer` (the order page URL without its fragment; a `Referer` never contains a fragment, so the token is not exposed). After a hard load (the bookmark case, a reload) the header applies and the e2e test asserts no `Referer`. A `<meta name="referrer">` on the order route would close the gap; not done (no leak found).
- Before hydration the locale switcher's links have neither the query string nor the fragment (the server cannot know the fragment); a click in that first moment switches the language and loses them. The e2e test waits for the finished link.
- After a failed sign-in the password field is cleared (the email stays); a second submit without typing the password again reports "Fill in this field".
- The 60 s data cache of `next start` is kept on disk (`.next/cache/fetch-cache`): a storefront restarted within a minute of a re-seed shows variant ids of the old seed (add to cart answers "Nothing was found"). The suite deletes the directory before it starts the server.
- The "confirm the new total" step after `409 cart_changed` is not part of the price-change flow: the price notice's OK is the consent and unblocks the submit (as designed in step 7); the confirmation appears for a changed total without a price notice.

## Emailed links: forgot password, reset password, verify email (email plan step 10)

Three pages for the mails of ADR 0031 (`docs/plans/2026-10-26-email.md`, step 10). Storefront only: no API, api-client, schema, dependency or variable change. The API routes and their rules are in `docs/api/customers.md`.

States: confirming, confirmed (heading takes the focus; the account store is read again so the notice goes), "does not work" (a signed-in customer gets "Send the link again" there, a guest a sign-in link), a retryable error with "Try again". |

- **`emailDelivery`.** The three routes and the entry points depend on `emailDelivery` of `GET /store/config` (`getEmailDelivery()` in `catalog-pages.server.ts`, the same 60 s data cache as the rest of the config): the server shells pass it down. With `false` the sign-in page has no "Forgot password?" link (`forgotPasswordHref`), the account page shows no verification notice and no "confirmed" line, and the three pages show a friendly "Not available" state with a link to sign in (also when the cached flag is stale and the API answers `404`: `unavailable` outcome). The e2e stack always runs a provider, so this half is covered by unit tests (`account-email.spec.tsx`, `email-links.spec.ts`).
- **Account page.** `VerifyEmailNotice` (a warning with the customer's address and "Send the link again", 3 an hour at the API: a `429` shows the wait; `409 already_verified` reads the customer again so the notice goes) appears only with `emailDelivery` and an unverified customer; a confirmed address shows "Email address confirmed" next to it.
- **Tokens (ADR 0031, plan section 11).** The token is in the fragment, so no server, log or `Referer` sees it. It lives in a React state of the page, goes into the body of ONE call (`confirmPasswordReset`, `confirmEmailVerification`; `lib/account-email-flows.ts`) and nowhere else: not a URL, a link (`switchLocalePath` drops the fragment on the two token pages, so the language switcher cannot keep a copy), the title (fixed metadata), storage, the console or an error text (`Failure` holds message keys only; nothing from the API's `detail` is shown). A second link pasted into the same tab (`hashchange`) is read the same way. Decision: switching the language on a token page needs the emailed link again (the mail has the right language in its path).
- **Headers.** `next.config.ts` sends `Referrer-Policy: no-referrer` for the three pages (`ACCOUNT_EMAIL_PAGE_SOURCE`, after the site-wide rule) and `privateMetadata(..., { noReferrer: true })` adds `<meta name="referrer" content="no-referrer">` and `noindex, nofollow`. The pages are dynamic (the config is read per request), so Next answers them with its own `no-store` style cache headers; they load nothing from another origin (the CSP stays `'self'`).
- **A11y.** Every state has one `h1` (also in the server HTML; the fragment is unknown to the server, so the first render of the token pages is a heading with a spinner "Checking the link"), labelled inputs with `autocomplete` (`email`, `new-password`), the field error linked with `aria-describedby`, the error summary as on the other forms, `method="post"` with no `action`, and the heading (`tabIndex -1`) takes the focus when an outcome appears (`useHeadingFocus`), never on the first render.
- **Tests.** `fragment-token.spec.ts`, `account-email-flows.spec.ts` (neutral answer for any body, one state for every token problem, one confirm request, no token in a failure), `reset-password-form.spec.ts`, `email-links.spec.ts`, `account-email.spec.tsx` (markup, ARIA, focus targets, `emailDelivery` hides, sentinel check for hardcoded text, message keys in uk and en), source guards (the fragment is read in one place, the confirm calls live in one module, no token in a template literal URL, no `fetch`, storage or `console` in the emailed-link code), `locale-path.spec.ts`, `security-headers.spec.ts`, `next.config.spec.ts`, `route-structure.spec.ts`. Browser: `e2e/tests/account-email.e2e.ts` (see `e2e/README.md`).

## Step 10 review fixes

The independent review of the storefront (`docs/plans/2026-10-18-storefront.md`, "Step 10 review outcome") led to these changes; each has a test, and the mutation that removes it fails a test.

- **Time limits (M1, `lib/request-timeout.ts`).** Server catalog reads end after 8 s (`SERVER_READ_TIMEOUT_MS`, an `AbortSignal.timeout` on every read), so the last good copy or `error.tsx` takes over instead of waiting for undici's 300 s. Measured against a TCP server that accepts and never answers: `GET /en/catalog` answers `500` after 16 s (the layout reads the config and the categories one after the other, 8 s each) instead of not answering for minutes. The browser's store client wraps `fetch` in `withTimeout` (`session-provider.tsx`): reads 15 s, writes (including the checkout) 30 s. A timeout is a retryable failure with its own message (`errors.timeout`, `failureFromThrown`: a `TimeoutError` cause, also when the client marked the request aborted), so a hung checkout frees the form and shows "try again"; its idempotency key is kept and the retry sends the same key. A caller's own abort (`AbortError`) is still not shown as a message: it is rethrown, loud, as before (nothing in the storefront aborts on purpose today).
- **Logs keep the root cause (L3).** A failed catalog read logs the client's message plus the NAME and CODE of every cause (`[cause: TimeoutError]`, `[cause: TypeError <- Error ECONNREFUSED]`), never a cause's message, a URL or a body.
- **`border-input` token (M3).** Inputs, textareas, selects, checkboxes and the quantity field use `border-border-input` (`--fk-color-border-input`, at least 3:1 on `background` and `muted` in both themes). The decorative `border` token is unchanged. `packages/theme/src/contrast.spec.ts` lists every pair the components use, reads the class strings of `packages/ui` and this app, and fails when a pair is neither listed nor declared decorative. The invalid border (`aria-invalid:border-danger`) and the focus outline still win (checked in the built CSS: the variant rule comes later and is more specific).
- **Own properties only (L2).** Attribute and option codes are data and may be `constructor`, `__proto__` or `toString`: `attributeRows` and the variant matcher read them with `Object.hasOwn` and build selections with `Object.fromEntries`.
- **Focus and titles (L9).** After a client-side navigation to another path `RouteFocus` (`lib/navigation-focus.ts`) moves the focus to the new page's `h1` (`tabindex=-1`, no scroll), or to `main` while the page is a loading state; not on the first load. The not-found view renders its own `<title>` (React hoists it to the head), so the 404 page no longer has the generic site title (`site.` and `seo.` messages are now sent to the browser).
- **Known gaps recorded, not fixed:**
  - L1: the checkout cart fingerprint covers the cart id, not the lines. A lost `201` followed by refilling the cart with the same total and sending the same body returns `200` with the OLD order (the new lines are not ordered). Small impact (the old order holds the same products); the owner decided to record it, not to change the API or the storefront.
  - Focus after navigation is by path: a change of the query string only (paging, a brand link) keeps the focus where it is. The route announcer still announces the new title.
  - L4: every 404 and error page is an empty shell without JavaScript (above).
  - The API's catalog reads are not rate limited (launch blocker in `docs/HANDOFF.md`); brand-filtered lists are uncached, so each view is one API call.

## Delivery and shipping (shipping plan step 10)

The delivery step of `docs/plans/2026-10-24-shipping.md` (section 5) and the delivery and tracking of the order pages. API: `docs/api/shipping.md` (Store), decisions: `docs/adr/0029-shipping.md`. Everything is the same model as the checkout: pure TypeScript in `src/lib` with injected client and timers, thin client islands, no new dependency.

**The rule that matters: the browser never adds money.** `deliveryPlan` (`lib/shipping-model.ts`) decides what an order is delivered with, and the checkout sends `expectedTotal` = the `total` the server computed for the chosen option (`GET /store/shipping/options`: cart subtotal plus the method's price). The summary shows the subtotal of that answer, the method's price (a price, "Free", or "paid to the carrier on delivery, about X" with the carrier's informational estimate) and that same total. Display only goes through `formatMoney`.

| Situation | `deliveryPlan` | Checkout |
|---|---|---|
| The cart ships nothing (`requiresShipping` false) | `none` | no delivery section, no `shipping` member (the API refuses one), `expectedTotal` = the cart's total |
| The shop offers NO method (`options: []`: none active, or only ones the API does not offer, such as another currency or a pickup point of a provider that is not loaded) | `none` | **exactly the checkout without shipping**: address as before, no `shipping` member, `expectedTotal` = the cart's total (regression tests in `checkout-store.spec.ts`, `checkout.spec.tsx`, `shipping-model.spec.ts`) |
| First answer not there yet, a read is running for a shop with methods, or the read failed | `blocked` (`loading` / `error`) | skeleton or retry, the submit is disabled with the reason; nothing is sent on an old price |
| Methods exist, none chosen, or the chosen one is unavailable | `blocked` (`choose` / `unavailable`) | the submit is disabled with the reason; a method that becomes unavailable is never swapped for another silently |
| A method is chosen and orderable | `ship` | `shipping: {methodCode}` (+ `pickupPointRef` for a pickup point), the address only for an `address` method, `expectedTotal` = the option's `total` |

- **Delivery section** (`components/delivery-section.tsx`, before the address): a radio group (a `fieldset` with an `h2` legend that takes the focus on an error, native radios with the price or the reason a method is unavailable linked by `aria-describedby`). The first available method is chosen when none is. `address` shows today's address fields, with a country list made from the countries the `address` methods serve (`servedCountries`; the config list is only for the no-method checkout); `pickup_point` shows the two pickers; `store_pickup` shows the method's description as the pickup text and needs no address. A read that failed shows the error with a retry; no available method says so.
- **Pickers** (`components/lookup-combobox.tsx`, `lib/combobox-model.ts`, `lib/lookup-source.ts`): city, then branch or locker of that city, through `listShippingCities` and `listShippingPickupPoints` of the typed client (the CSP `connect-src 'self'` and a source guard keep the browser away from carriers). WAI-ARIA combobox with a listbox popup: `role="combobox"`, `aria-expanded`, `aria-controls`, `aria-autocomplete="list"`, `aria-activedescendant` (focus stays in the text box); keys: ArrowDown/ArrowUp open and move (wrapping), Enter accepts (and does not submit the form while the list is open), Escape closes, Tab leaves (no trap), Home/End stay with the caret. Search is debounced 300 ms; the city needs 2 characters (the API's minimum); the points of a chosen city are listed at once (first 50, "Showing 50 of N" note) and any typed text narrows them (decision: the API has no minimum for points and branch numbers are short). Old results are cleared as soon as the text changes; only the newest query's answer is applied. A polite live region (rendered from the start) announces "N results", "Nothing found", "Searching" and failures; below the box: searching, nothing found, a failed lookup with a retry and a hint to choose another method, the "carrier not answering, list may be out of date" note when the API says `stale`, and the cut-list note. Option text is the carrier's own (`№` number, kind and address), shown as text. Editing the text of a chosen city or point clears the choice.
- **`409 shipping_changed`** (`checkout-store.ts`): the options are read again, the store remembers the method and the total and price the shopper had seen (`shippingConsent`), and the submit stays blocked while the new price loads and until the shopper presses "I agree to the new price" (the alert shows the new price, the new total and the old total). Never resubmitted by itself. If the method is not offered any more there is nothing to confirm (a message and the choice of another method); choosing another method drops the consent. `409 cart_changed` keeps today's handling and also re-reads the options (the shipping store follows the cart store and re-reads in the same notification, so a new cart is never shown with the old delivery price).
- **Other answers:** `503 shipping_provider_unavailable` is its own outcome (key kept: send the same body again, or choose another method; the `Retry-After` wait is shown); `400 shipping_method_required` and `shipping_not_applicable` re-read the options; `400` `unknown_pickup_point` lands on its field through `errors.field.*` messages (`not_applicable` too, although the API now answers a request shaped for another kind with `409 shipping_changed`, step 13 review fixes).
- **Idempotency:** the attempt key hashes the whole body (`checkout-attempt.ts`), so a changed method, pickup point or server total is a new attempt with a new key, and the same body (a retry, a double submit, a reload) keeps its key. Tested at the manager and at the store level, including "only the price of the same method changed".
- **Order pages** (`components/order-details.tsx`, guest and account): a Delivery section with the method title, the price the shop charged (Free, or paid to the carrier on delivery with the estimate) and, for a pickup point, its kind, number, city and the carrier's text once (the duplicate address block is left out); the totals keep a delivery row (also for Free) when the order has a snapshot. When the shop created a waybill, a Tracking section lists each shipment's tracking number (a code, never translated) and its normalized status as a badge with a uk/en label for every status (`order.shipment.status.*`, plus a neutral fallback for a status the storefront does not know yet).
- **Messages:** `checkout.shipping.*`, `checkout.summary.shipping*`, `checkout.blocked.shipping*`, `checkout.shippingChanged.*`, `order.shipping.*`, `order.shipment*`, `errors.field.unknown_pickup_point`, `errors.field.not_applicable`; all inside the serialized `checkout.` and `order.` namespaces. Carrier texts (city, branch, address, titles) are shown as sent; the carrier answers in the language the lookup asked for, and for a language it does not have (Nova Poshta: no English, as far as known) the text is what the carrier sends.
- **Tests:** unit (`shipping-model`, `shipping-store`, `shipping-text`, `lookup-source`, `combobox-model`, `checkout-store`, `checkout-attempt`, `checkout-form`), views (`delivery.spec.tsx`, `checkout.spec.tsx`, `orders.spec.tsx`: markup, ARIA attributes, handlers, no hardcoded text) and e2e (`e2e/tests/shipping-checkout.e2e.ts`: flat courier with the page's total equal to the stored order total, a pickup point of the fake provider chosen with the keyboard and its tracking after the shop created a waybill, a free store pickup, a price changed behind the shopper's back). Mutations shown to fail a test: the expected total taken from the cart instead of the option, the no-method path treated as "must choose", the consent not recorded or not blocking (also in the browser).
- **Not verified:** a screen reader (the live region and `aria-activedescendant` are asserted as DOM state, not heard), the Nova Post plugin (`nova_post`; the browser suites use the fake provider, whose cities are `Kyiv`, `Lviv`, `Odesa`; real Nova Post lists are large: in the biggest cities the plugin lists all branches but only part of the lockers, `packages/providers/nova-post/README.md`), hover and touch behaviour of the pickers, other browsers and small screens.
- **Release coupling (resolved here):** `docs/api/shipping.md` said the storefront v1 sends neither a method nor the option's total. This step is the storefront side: once a shop activates a method, this storefront sends both. The coupling remains for older clients.
